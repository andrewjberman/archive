## 2. Should `firm_registry.json` be a BUILDER OUTPUT from `infra/logic/registry/` (Rule 30) rather than a tracked file?

**It already partly is, and the served copies are the exception, not the rule.** `data/firm_registry.json`
(the repo-root canonical copy) is GENERATED by `lib/opal_naming.py generate` from
`infra/logic/registry/scopes.json` (its own header, quoted in section 1). The TWO Lambda functions
(`irpt-intake-poller`, `irpt-ycharts-generate`) serve a DIFFERENT, older, non-generated vintage that
was deployed once and never captured by that generator OR by any commit. So the live question is not
"builder output vs. tracked file" in the abstract -- Rule 30 already answers that for NEW
resources -- it is "does the DEPLOYED firm_registry.json for these two functions get re-derived from
`lib/opal_naming.py generate` (making the Lambda's `staged_from` point at a builder invocation's
OUTPUT the same way `holdings/stage.py` and this order's own `_ids/` entries point at a TRACKED
FILE), or does someone re-author the missing firm set directly into `scopes.json` first". Either path
converges on the SAME mechanism this order already generalised (a `staged_from` entry with a
verified blob) -- the open work is producing the CONTENT (a registry decision, Rule-30-owned), not
the declaration mechanism (already built, this order).

## 3. What W4-S35's `_meta.artifact` claim means for the family's provenance stamps

Every member this family's `_authz`/`_ids`/`ycharts` code stamps with a `_meta.artifact` /
`_meta.authority` self-declaration is a CLAIM the file makes about its OWN origin, not a verified
fact -- and this order measured that claim can go stale INDEPENDENTLY of the file it describes:
`settings.json`'s header still names `intake/settings.json` as its source two cells after that path's
tracked content diverged from what got deployed (row `W4-S35`). The family has no MECHANISM that
re-checks a `_meta.artifact` pointer against the tracked path it names at build or deploy time --
`build-and-upload.sh`'s own `staged_from` verification checks a DECLARED pin's blob against a
DECLARED sha256, which is a different, gate-enforced claim; the free-text `_meta.artifact` header
inside a served file's own bytes is decorative documentation with no consumer that can reject a
stale one. **Recommendation for the CTO's read, not a verdict:** either drop the in-file
`_meta.artifact` self-claim in favor of `lambda-source-map.json`'s own `staged_from` record (now the
single verified source of truth for every member this order and `IB-rte-4` touched), or add a
build-time check that a file carrying `_meta.artifact` actually resolves at the path it names.

## 4. Should `_authz/` be a shared package? (IB-rte-4's carried question)

Restated, not re-litigated: `IB-rte-4`'s own `R54-AC2_judgment.md` (@`5a5d50a047b501ff692d636c04483df7107febb9`)
already answered this with the SAME framing this order's own findings reinforce twice over. This
order adds one data point: the 18 STALE-PIN members (row `W4-S40`) are a DIRECT CONSEQUENCE of the
current "staged, flat copy, per-function pin" shape -- `_authz/served.py`/`_authz/loaders.py`/
`_ids/ids.py` were each edited ONCE (by `IB-rte-6`'s projection-seam wiring) and the edit had to be
manually propagated to SEVEN separate `staged_from` pins across `lambda-source-map.json`, and it
was NOT (until this order). A Lambda LAYER (already precedented for `irpt-common` per `IB-rte-4`'s
own citation) has exactly one version to bump per shared-file edit, not `N` pins to hunt down; a
staged-flat-copy has `N` independent pins that can each silently go stale one at a time, exactly as
measured here. This does not decide the layer-vs-staged-flat question (a shape decision for L4) but
it is a second, independently-measured cost on the staged-flat side of that ledger.
