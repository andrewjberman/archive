## R26.3 FROZEN CONTRACTS

**Z1 UNCATALOGUED ROWS** `uncatalogued_rows.json`, schema `gateway_uncatalogued_rows/1`: `{"schema","items":[{"table","bucket","prefix","disposition":"row"|"reason","row":null|{"entity","bucket","prefix","vendor","firm","table"},"reason":str,"evidence":[str,...]}]}`. One item for each of the 15 entries of `4.0.0_SA_CRO~Y/census.json` whose `src` is `live-extra`, exactly those, once each, keyed by (`bucket`,`prefix`); `table` equals the census `table`. The item for `opal-data-inf` prefix `silver/transactions/` is FIRST in the list; the rest are sorted by (bucket, prefix). `row`: a catalog row the table reads as, with `entity` a lower-case word-and-underscore id not already an entity of the catalog and not repeated, `bucket` and `prefix` equal to the item's, `vendor` one of the catalog's vendors plus opal, ycharts, microsoft, bloomberg, other (the vendor that produces the table: orion, eclipse, blackdiamond etc. as the catalog names them), `firm` a string. `reason`: for a `row` item, one ASCII sentence of at least eight words on what the table holds; for a `reason` item, at least eight ASCII words saying why no row is written (an empty table, a meta folder, a copy that duplicates a catalogued table). `evidence` has at least one entry: `<path>:<line>` of a file that exists, or `census.json#<bucket>/<prefix>` that resolves in the census file. A `reason` item may not be chosen for `opal-data-inf/silver/transactions/`, `opal-data-inf/silver/orion-rest/transactions/` or `opal-data-bd/silver/realized/` (live advisor or realized data).

**Z2 ECLIPSE COPIER** `eclipse_copier.json`, schema `gateway_eclipse_copier/1`: `{"schema","producer":{"bucket","prefix","owner_project"},"copy":{"bucket","prefix"},"copier":{"kind":"lambda"|"script"|"glue"|"ecs-task"|"terraform-only"|"other","name":str,"cite":"<path>:<line>"},"schedule":{"expression":str,"cite":"<path>:<line>"},"lag":{"trading_days":int,"cause":str},"owner":str,"evidence":[str,...]}`. `producer` is `opal-data-inf` `silver/eclipse/`; `copy` is the catalogued copy named by the catalog (the Eclipse silver prefix under `opal-data-assets`, read from the catalog rows of the Eclipse entities and the CRO brief section 4.2). Find, in the repository, the code or infrastructure that copies producer output into the copy (a Lambda, script, Glue job or scheduled task) and its schedule. `copier.cite`, `schedule.cite` and every `evidence` entry must resolve (the file and line exist); at least two evidence entries; `lag.trading_days` is 1 (the brief); `lag.cause` is at least eight ASCII words explaining the lag from the schedule against the producer's cadence; `owner` is the project code that owns the copier (a code that exists in `org/projects/`). When no copier is found in the repository, `copier.kind` is `terraform-only` or `other` with `name` `none-found`, `cite` the path of the closest candidate searched, and `evidence` at least three entries naming what was searched.

**Z3 PROBE PLAN** `probe_plan.json`, schema `gateway_probe_plan/1`: `{"schema","items":[{"tool","class":"graph"|"integration"|"store","route":"direct-graph"|"vendor-api"|"direct-dynamodb"|"none","call":str,"fact":str,"answer_field":str,"feasible":bool,"reason":str,"cite":"<path>:<line>"}]}`. One item for each tool of `SOURCE_COMPARE_20261020c.json` whose `agrees` is null and whose source `kind` is graph, integration or store (46 tools), exactly those, sorted by tool; `class` equals the source kind. The plan states the SECOND-CLIENT read that would check the answer against its own source: `route` direct-graph (the tester's own Microsoft Graph call outside the gateway), vendor-api (the vendor's own API outside the gateway), direct-dynamodb (a direct DynamoDB read); `call` names the exact request (method and path or table and key) in at least eight ASCII words; `fact` is the one fact compared (a count, a latest date, an id) and `answer_field` is the field of the gateway answer (from `results_all_r25.json` for the tool's ok result, or the tool's definition when it has no ok result) that carries the same fact. `feasible` is true only when the route needs nothing beyond the owner's own delegated sign-in or an AWS read the repository already uses (cite the path:line of the same call in the gateway source); otherwise `feasible` is false, `route` may stay the intended route or `none`, and `reason` (at least eight ASCII words) says what is missing (a vendor key, a write, no read-only call exists). Every `cite` resolves. Tools whose answer is a write-gated or sender tool, or which have no ok result and no read-only definition, are `feasible` false with that reason.

**Z4 COVERAGE TWO** `coverage_two.json`, schema `gateway_coverage_two/1`: `{"schema","items":[{"tool","disposition":"row"|"c","row":null|{"entity","bucket","prefix","vendor","firm"},"reason":str,"cite":"<path>:<line>"}]}`. One item for each of the two refusals of `COVERAGE_r25_candidate_c.json` (`opal_describe`, `opal_discover`), exactly those. `row`: a catalog row the tool reads, `entity` unique and not already in the catalog, `bucket`/`prefix` overlapping an `s3` source of the tool's source set (`source_sets_integrations.json`), `vendor` in the allowed vocabulary; `c`: the tool reads no data a row can describe, `reason` of at least eight ASCII words and an existing `cite`. Read the two tools' code (`app/integrations/opal_discover/integration.py`) and the catalog rows `DATA_CATALOG.yaml` already holds for the portal datasets they describe before choosing.
