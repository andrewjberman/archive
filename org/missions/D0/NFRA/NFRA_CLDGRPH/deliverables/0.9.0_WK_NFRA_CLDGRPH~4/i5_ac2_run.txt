STEP 1 -- WHICH ROUTE IS REAL, and the question has TWO answers
==============================================================================
  BY OUTCOME the hand route is the only real one. It is the only route that
  has ever placed a CORRECT source zip in S3 -- 5 of 5 served zips, and the
  committed route's own 8 successes packed ZERO portal/src files, so its
  correct-publish count over its whole life is 0 of 855.

  BY TRIGGER the committed route is the only real one, and this is the half
  that decides a HOME. Its trigger fired 855 times on exactly the right paths
  with the right branch pin, the right OIDC role, a concurrency group and a
  PR exclusion. NONE of that is broken. What is broken is one repo secret,
  three steps in.

  THE HAND ROUTE HAS NO TRIGGER AT ALL. It ran five times because a task
  order told a worker to run it five times. That is not a cadence, it is five
  instructions. And it cannot acquire one: the only mechanism in this estate
  that could fire a repo-subset packer on a repo change IS a GitHub Action,
  because the nightly Fargate derive-runner is repo-less -- which is the
  stated reason LEG-1 exists at all (.github/workflows/stitch-source-push.yml, header).

  So the two answers do not conflict; they are answers to different
  questions. 'Which route produced the artifact' is the hand route. 'Which
  route can OWN the artifact' is the workflow, and a home is an ownership
  question, not a history one.

STEP 2 -- WHAT WOULD HAVE TO BE TRUE FOR THE HAND ROUTE TO BE THE HOME
==============================================================================
  Three things, and the third is disqualifying:
   1. a production location chosen for the script. Out of this worker's
      <paths>, and already assigned: CG-s-38 item 1 names 1.0.0_SA_CTO to
      decide which plane owns a repo-subset packer.
   2. an owner to run it. CG-s-38 item 1 names 0.7.0_AE_CloudOps.
   3. A TRIGGER. There is none, and building one means building a
      push-triggered CI job that zips the repo subset and puts it on the same
      S3 key -- which is the workflow, rebuilt beside the workflow. That is a
      SHADOW PIPELINE and a DUPLICATE OUTPUT PATH under CLAUDE.md s.5, on
      which Andrew holds a complete veto. Absent that, the hand route stays
      human-triggered forever, and 'a production input refreshed only when
      somebody remembers' is the finding this cell exists to close, not a
      resolution of it.

  AND THE STANDING COST OF CHOOSING IT: two live producers of one served key,
  with no ordering between them. The moment the secret is provisioned the
  workflow starts publishing too, and a hand push and a pushed-triggered run
  can interleave on the same object with no lock and no versioning on the
  bucket to reconstruct which won.
