## The commands a Dell runs, in order (Python 3.14; the standard library only is needed for the first two)

Replace `<kit>` with the folder the kit was delivered to.

1. `python org/devices/kit_python_repack.py verify --from <kit>`  -- every wheel against `MANIFEST.json` (sha256, size), nothing stray.
2. `python org/devices/kit_python_repack.py install-check --from <kit> --scratch <a NEW empty folder>`  -- runs
   `python -m pip install --no-index --no-deps --find-links <kit> -r <kit>/requirements-kit.txt --target <scratch>` (a failure
   changes nothing in the Dell's real environment), then one `import` per top-level module in its own subprocess (60 s bound), the
   scratch folder first on the path. Last line: `PY-KIT-INSTALL python=<v> wheels=49 installed=<i> imported=<m> import_missing_dep=<d> failed=<f> ok=<True|False>`.
   `import_missing_dep` is the EXPECTED finding for a package whose dependency is not in the kit (the 73 unlisted dependencies are not
   carried; `--no-deps` is deliberate); it names the missing module. A package whose import fails for any other reason, or whose wheel
   will not install, joins the list for the CTO.
3. On the Dell's own decision, the real install: `python -m pip install --no-index --no-deps --find-links <kit> -r <kit>/requirements-kit.txt --user`

## What stays unproven

- Nothing was installed on a Python 3.14 interpreter; this machine has none (row NFRA_CTLPLN-W13-S15). Whether pip on 3.14 accepts each
  wheel, and which of the 49 import there, is the Dell's `install-check`.
- The wheels were rebuilt from INSTALLED files, not downloaded: a `py3-none-any` wheel carries the installed copy's bytes; for the 8
  compiled packages the files are the 3.12 box's build of a stable-ABI or ABI-free wheel (bcrypt, curl_cffi, psutil, PyMuPDF,
  cryptography, safetensors, tokenizers, ruff). Each is marked cp3X-abi3 or py3-none-win_amd64 by its own WHEEL file; that these run on
  3.14 is the build's claim, unread here.
- Dependencies of the 49 that are not among the 49: the 73 undeclared dependencies and the 18
  NEEDS-FETCH requirements are not carried (the CTO's ruling, msg 106317).
- No file was packed without a hash comparison (0 unverified); but the RECORD hash is the installed copy's own claim,
  not a comparison with an index's published wheel (none was fetched).
- The `.data/scripts` handling was exercised on a synthetic distribution and read for awscli, pdfminer.six and ruff; pip's install of
  those on a Dell is unread.
