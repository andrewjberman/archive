## 1. Where the truth lives

**(a) A new registry file, read by the generator, with the Lambda module and the portal carrier both generated from it.** The matrix becomes rows of one file (infra/logic/registry/firm_pages.json). Each generated view is a carrier of that file, and a hand edit to any carrier is refused by the naming gate (Lambda module, now) or by a portal-side drift test (portal carrier, later). The cost is a builder edit: load_registry reads only the names in REGISTRY_FILES (opal_naming.py line 277), so the new name joins that tuple, and the renderer, its VIEWS and BLOCKS entries and its validate() rows are written. Nothing existing re-marks, because only the new targets read the new file.

**(b) firmAccess.ts stays the source and a generated carrier reads it.** The generator would parse TypeScript in Python to recover the matrix. The Lambda would then depend on a file in the portal repository at a pin, and the census records that the checkout (2ed4373d) is ahead of the gitlink pin (c96efe1714) (census header, line 20). A fragile parser on a moving checkout is the wrong single source, and it reverses the registry's role. Rejected.

**(c) The existing firm registry gains a pages column (scopes.json tenant rows).** Every view whose TARGET_REGISTRY_KEYS names scopes.json moves its mark when any scopes.json byte moves (opal_naming.py lines 155-196; _view_mark, line 205, reads the per-target file list). The list includes the lambda-edge firm-config.mjs (line 159-160), a deployed CloudFront edge artifact. A one-field change to scopes.json would therefore re-stamp deployed edge bytes. The scope rows also yield 5 tenant ids against the 4 the portal admits (section 0), so a pages column still needs an explicit admit default for the test tenant. Rejected.

**RECOMMENDATION: (a).** The registry is the single source. Its generated views are the Lambda module (in ajb_workspace, one writer) and, in a later order, the portal carrier.

**One-writer consequence for the portal.** The portal is a separate repository and a gitlink in this one. The generator already writes two portal files (firmDisplayNames.generated.ts and vendorDisplayNames.generated.ts, opal_naming.py lines 107-108, shipped by portal CI per `targets`), so the pattern is live. A generated firmAccess block would make the registry the only writer of the matrix, and three things follow. (i) The portal commit carrying a regenerated block must land before the workspace gitlink moves. (ii) A hand edit inside the portal checkout is not caught by the workspace naming gate, since portal commits do not pass naming-gate.py; a drift test must live in the portal repository and run in its CI. (iii) A content change to the matrix changes which pages partner firms see, which is a client-facing PROD change under the push law (CLAUDE.md, Agent Autonomy). The regeneration of an unchanged matrix is DELTA=0. The portal carrier is therefore a later order, after the Lambda carrier lands. The Lambda carrier has a single writer.

## 6. Does this need an R20 register entry or a gate edit

**NO R20 entry.** Doctrine R20 (infra/logic/02_DOCTRINE.md lines 573-587) governs a departure from a rule on the five axes A1 to A5 (bucket, naming, compute, format, ingestion). This change departs from none: the registry row and its generated view hold no storage plane, no S3 key and no resource name. R1 (lines 149-176) grades keys and names, and the new rows are neither. R16 and R21 (lines 536-553 and 588-597) reach storage paths, which this change does not touch. The CTO's ruling that the route is a registry row, not a departure, stands.

**NO gate edit.** .tools/naming-gate.py takes its generated-target list from mod.VIEWS (line 748) and its firm spellings from scopes.json (lines 749-760), so the new VIEWS entry is covered without editing the gate. The new registry rows fall under the gate's context rule as registry files (naming-gate.py lines 1-40). The builder edit (REGISTRY_FILES, VIEWS, BLOCKS, the renderer) is a change to lib/opal_naming.py, which is the generator and not a gate.
