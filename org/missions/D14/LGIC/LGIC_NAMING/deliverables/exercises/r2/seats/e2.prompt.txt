# 05 — THE IDENTITY SPINE (seed) — v0.1

**Author:** 4.0.0_SA_CRO~D · **Date:** 2026-09-12 · **Row:** `ORDER_OF_OPERATIONS.md` #10 (outcome O4)
**What this is:** the SEED of one registry of firms, products, vendors and masters with stable keys,
so that a route, a bucket name, an IAM condition, a key prefix or a Terraform module **references a
key** instead of choosing a spelling. **What this is not:** the registry's runtime (a DynamoDB table,
a YAML the gates read, a Terraform data source) — that is an L7 build decision the PRD makes; this
seed is the CONTRACT and the MEASURED CONTENT it must hold on day one.
⛔ **Nothing here renames a bucket, rewrites a key, or edits IAM.** It records what exists and names
the one key each thing should resolve to.

## §4. WHAT A CONSUMER DOES WITH THIS

- **A route** (`shared-advisor-router`, `/api/scoped/*`) resolves `X-Firm-Id` → FIRM key → the
  firm's bucket **from the registry**, not from a hardcoded `opal-data-{firmId}` string — which is
  how `bd` and `49financial` stop being two answers.
- **A bucket or prefix** is named from a key: `opal-data-{FIRM}`, `{VENDOR}/{FIRM|MASTER}/{tier}/`.
- **An IAM condition** (`NFRA_IAMROLES202609`, the cross-firm key-prefix Deny) enumerates prefixes
  from the FIRM keys and their recorded aliases, so a new spelling is a registry edit, not a gate
  edit found later.
- **`FirmDestinationPolicy`** (IRPT_BCKEND FWD-10) enumerates per-firm locations by FIRM key.
- **Onboarding firm N+1** (O5) begins by minting a FIRM key here; every later step references it.
