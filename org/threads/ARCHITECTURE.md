# Thread System — Technical Architecture

End-to-end reference for how threads are created, executed, and how
outputs land in the org file system. Covers every file, every script,
and every data transformation.

---

## 1. System Overview

```
CEO-CTO Interview
    |
    v
CTO writes PRD (docs/architecture/{feature}.md)
    |
    v
COO reads PRD, registers project (org/projects/{CODE}.json)
    |
    v
COO writes staging script (org/threads/staging/run-{CODE}-{NNN}-{slug}.sh)
    |  - embeds CONTEXT.json (what files to inject)
    |  - embeds opening message (COO's agenda for the thread)
    |  - passes --project {CODE} to create-thread.sh
    v
create-thread.sh
    |  - scaffolds thread folder (org/threads/{CODE}-{NNN}-{slug}/)
    |  - auto-injects participant context (README, logs, task orders, commits)
    |  - resolves explicit CONTEXT.json entries (code, docs, commits, inline)
    |  - generates CONTEXT_COMPILED.md (single briefing document)
    |  - writes THREAD.json, TURN.json, messages/000.md
    |  - updates org/projects/{CODE}.json (increments counter, appends thread entry)
    v
orchestrator.py (turn loop)
    |  - reads THREAD.json + TURN.json
    |  - for each turn: builds system prompt + user prompt -> calls OpenAI API
    |  - writes agent response as messages/{NNN}.md
    |  - parses signal (continue / converge / escalate)
    |  - updates TURN.json
    |  - loops until termination condition
    v
Thread completes
    |  - writes receipt to each participant's threads/ folder
    |  - format: {thread_id}_{other_serials}.md
    v
COO reads receipts -> writes precise task orders referencing receipt paths
    |
    v
DS / DE / RD / DT implement against the agreed contracts
```

## 2. File Structure

```
org/
  projects/
    REGISTRY.md                   Human-readable project index
    {CODE}.json                   One file per project (e.g., ADVI.json, MKOV.json)

  threads/
    README.md                     Quick start and pattern reference
    ARCHITECTURE.md               This file
    CONFIG.md                     All tunable settings
    THREAD_KNOWLEDGE.md           Mandatory rules (M1-M9) and observations
    orchestrator.py               Python turn loop (OpenAI API)
    orchestrator.sh               Legacy shell wrapper (deprecated)
    create-thread.sh              Thread scaffolding + context materialization
    run-exploratory.sh            Convenience wrapper for 2-party sync threads
    test-model.py                 Model compatibility checker
    templates/
      THREAD.json                 Schema template
      TURN.json                   Schema template
      CONTEXT.json                Schema template
      message.md                  Message format template
    staging/
      BESPOKE_TEMPLATE.sh         Template for generated staging scripts
      run-{CODE}-{NNN}-{slug}.sh  Per-thread run scripts (generated by COO)

    {thread_id}/                  One folder per completed or active thread
      THREAD.json                 Thread metadata (id, participants, status, project, serial)
      CONTEXT.json                Original context manifest (preserved)
      TURN.json                   Mutable turn state (updated each turn)
      CONTEXT_COMPILED.md         All context merged into one briefing document
      context/
        agents/
          {serial}_README.md      Agent identity (auto-injected)
          {serial}_logs/          Agent session logs (auto-injected, 3 most recent dates)
          {serial}_task_orders/   Pending task orders (auto-injected)
          {serial}_commits.txt    Recent commits by this agent (auto-injected)
          {serial}_deployment_tags.txt  Recent pipeline tags (AE/DT only, auto-injected)
        refs/
          {label_slug}.md         Copied documents from CONTEXT.json
          {label_slug}.{ext}      Copied code files from CONTEXT.json
        commits/
          {label_slug}.txt        Git log + diff stats from CONTEXT.json ranges
        inline_notes.md           COO's briefing paragraph from CONTEXT.json inline field
      messages/
        000.md                    Opening message (written by thread creator / COO)
        001.md                    First agent response (turn 1)
        002.md                    Second agent response (turn 2)
        ...

{agent_folder}/
  threads/
    {thread_id}_{other_serials}.md   Receipt deposited on thread completion
    ADVI-001-*.md                    Project ADVI threads (filterable by code prefix)
    MKOV-003-*.md                    Project MKOV threads
```

## 3. Project File Schema (org/projects/{CODE}.json)

```json
{
  "code": "ADVI",
  "name": "AdvisorIntelligence",
  "description": "Complete the AdvisorIntelligence UI page",
  "prd": "docs/architecture/ADVISOR_INTELLIGENCE_COMPLETION.md",
  "status": "active",
  "created": "2026-03-03",
  "pods": ["0.4"],
  "pipeline": "bd-pipeline",
  "thread_counter": 3,
  "threads": [
    {
      "serial": "ADVI-001",
      "thread_id": "2026-03-03-continuous-nna-cla-alignment",
      "topic": "Pattern 0 alignment: adv_drill + cla_timeseries",
      "participants": ["0.4.0_DS_ClientPlatform", "0.4.0_DE_ClientPlatform", "0.4.2_RD_AdvisorIntelligence"],
      "pattern": "Pattern 0",
      "status": "complete",
      "date": "2026-03-03"
    }
  ]
}
```

`thread_counter` is the source of truth for the next serial number.
`create-thread.sh` increments it and appends to `threads[]` atomically.

## 4. THREAD.json Schema

```json
{
  "id": "ADVI-004-books-publisher-gap",
  "project": "ADVI",
  "serial": "ADVI-004",
  "created_by": "2.0.0_SA_COO",

  "status": "active"
```

`project` and `serial` are only present when `--project` was passed to `create-thread.sh`.
`status` values: `active` | `complete` | `blocked` | `needs_human`

## 5. Context Materialization Pipeline

`create-thread.sh` builds `CONTEXT_COMPILED.md` from four sources, in this order:

### 5A. Auto-injected per participant (no CONTEXT.json entry needed)

For every serial in `participants`:

| What | Source path | Destination |
|------|-------------|-------------|
| Identity (README.md) | `{agent_folder}/README.md` | `context/agents/{serial}_README.md` |
| Session logs (3 most recent dates) | `{agent_folder}/logs/{date}/*.md` | `context/agents/{serial}_logs/` |
| Pending task orders | `{agent_folder}/task_orders/*.md` (status=pending only) | `context/agents/{serial}_task_orders/` |
| Recent commits | `git log --grep="{serial}" -20` | `context/agents/{serial}_commits.txt` |
| Deployment tags (AE/DT only) | `git tag --sort=-creatordate` | `context/agents/{serial}_deployment_tags.txt` |

### 5B. Explicit CONTEXT.json entries

| Type | How materialized |
|------|-----------------|
| `documents[]` | File copied to `context/refs/{label_slug}.md` |
| `code[]` | File copied to `context/refs/{label_slug}.{ext}` (optional line range extraction) |
| `commits[]` | `git log --oneline {range}` + `git diff --stat` -> `context/commits/{label_slug}.txt` |
| `logs[]` by agent+date | Log folder copied to `context/refs/{label_slug}/` |
| `logs[]` by path | File copied to `context/refs/{label_slug}.md` |
| `inline` | Written to `context/inline_notes.md` |

### 5C. CONTEXT_COMPILED.md assembly order

```
1. Header (thread ID, created_by, created_at)
2. Participants section -- each agent's README.md
3. Reference Material section:
     - Briefing Notes (inline_notes.md)
     - All refs/ files (documents + code, in filesystem order)
     - All commits/ files
4. Participant Background section (per agent):
     - Recent session logs
     - Pending task orders
     - Recent commits
     - Recent deployment tags (AE/DT only)
```

Everything is pre-loaded at thread creation time. Source files are copied,
not symlinked -- the thread is a self-contained snapshot of state at creation time.

## 6. Prompt Construction (orchestrator.py, per turn)

### System Prompt

Concatenation of two files read from disk at invocation time:

```
org/ref/prompts/{role}.md          # Role-generic base persona (e.g., data_scientist.md)
+
{agent_folder}/prompt.md           # Agent-specific grounded prompt
```

This is why prompt enrichment (PROMPT_CONSTRUCTION_PROCESS.md) directly improves
thread quality -- a thin 20-line prompt produces shallow answers; an enriched
150-line prompt with Lambda specs and S3 keys produces grounded answers.

### User Prompt

Assembled in this order by `build_user_prompt()`:

```
## YOUR TURN -- Thread Protocol
[Turn identity, topic, turn number, remaining turns]

### Instructions
[Signal format, constraints, source priority rules]

---
## CONTEXT
[Full contents of CONTEXT_COMPILED.md]

---
## PREVIOUS MESSAGES
[All messages/NNN.md files in order, separated by headers]
```

On the agent's **last turn**, the instructions append:
`"THIS IS YOUR LAST TURN. Your signal MUST be converge."`

### API Call Parameters

```python
client.chat.completions.create(
    model=args.model,          # e.g., gpt-5.2
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user",   "content": user_prompt},
    ],
    temperature=0.3,
    tools=TOOLS,               # read_file, glob_files, grep_content (if not --no-tools)
    tool_choice="auto",
)
```

## 7. Orchestrator Turn Loop

```
while True:
    Read TURN.json
    Check termination:
        - All agents exhausted max_turns_per_agent -> complete, write receipts
        - Last 2 messages both signal "converge" -> complete, write receipts
        - Any message signals "escalate" -> needs_human, halt
    current = TURN.json.next_agent
    Build system prompt (base persona + agent prompt.md)
    Build user prompt (CONTEXT_COMPILED.md + messages + turn instructions)
    Call OpenAI API (with tool loop if tools enabled)
    Write response to messages/{NNN:03d}.md
    Parse signal from YAML frontmatter
    If "escalate": set status=needs_human, halt
    Advance TURN.json: increment turn_number, set next_agent (round-robin)
```

### Tool Loop (bespoke threads only)

```
while model returns tool_calls:
    if tool_calls_used >= MAX_TOOL_CALLS_PER_TURN (5):
        force final answer without tools
    for each tool_call:
        execute read_file / glob_files / grep_content
        append result as role="tool" message
    call API again with updated messages
```

## 8. Receipt Deposit (ops for agent folders)

When a thread reaches `complete` status, `write_receipts()` runs:

```
For each participant in thread.participants:
    others = all other participant serials joined with "+"
    receipt_path = {agent_folder}/threads/{thread_id}_{others}.md
    receipt_content = header + all messages concatenated
    write receipt_path
```

**Receipt content includes:**
- Thread ID, project serial (if set), created_by, created_at, status, participants
- All message files (000.md through NNN.md) in order with separators

**Naming convention:**
```
ADVI-004-books-publisher-gap_0.4.0_DT_ClientPlatform.md
  ^^^^^^^^^^^^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^
  thread_id                 other participants joined with +
```

**Where to find receipts:**
- Any agent: `ls {agent_folder}/threads/`
- Filter by project: `ls {agent_folder}/threads/ADVI-*.md`
- All receipts for a project: search across all agent threads/ folders

Receipts are NOT generated for threads that end as `needs_human`.

## 9. Project File Lifecycle

```
1. COO creates project file: org/projects/{CODE}.json
   - thread_counter: 0
   - threads: []

2. For each thread created with --project {CODE}:
   create-thread.sh:
     - reads thread_counter (e.g., 3)
     - increments to 4
     - assigns serial = "{CODE}-004"
     - builds thread_id = "{CODE}-004-{topic_slug}"
     - creates thread folder
     - AFTER thread folder created successfully:
         writes project_file.thread_counter = 4
         appends thread entry to project_file.threads[]

3. After thread completes:
   COO manually updates status in project_file.threads[N].status = "complete"
   (orchestrator does not write back to project file -- receipt is the completion signal)

4. COO reads org/projects/{CODE}.json on every session start:
   - sees all threads, their serials, status, and participants
   - knows which receipts to read (by serial -> thread_id -> receipt filename)
```

## 10. Staging Script Convention

Staging scripts live in `org/threads/staging/` and are self-contained:
- CONTEXT.json is embedded as a heredoc (no external file dependency)
- Opening message is embedded as a heredoc
- Script creates the thread AND runs the orchestrator in one invocation
- SA/DE agents run these directly via Bash tool -- no Andrew handoff required

**Naming:**
- Project thread: `run-{CODE}-{NNN}-{slug}.sh` (e.g., `run-ADVI-004-books-publisher-gap.sh`)
- Non-project: `run-YYYY-MM-DD-{slug}.sh`

**Generation:**
COO describes the thread to Claude Code in natural language, Claude Code generates
the staging script from `staging/BESPOKE_TEMPLATE.sh`. COO reviews, then runs it.

## 11. Troubleshooting

| Symptom | Check |
|---------|-------|
| Thread stuck, no agent responding | `TURN.json next_agent` -- does that serial resolve to a valid folder? |
| Signal not parsed | Message must start with `---` YAML frontmatter. Check `signal:` field exists. |
| Context materialization failed | All paths in CONTEXT.json must exist relative to repo root. |
| Receipts not generated | Only generated on `complete` status. `needs_human` threads do not get receipts. |
| Model API error | Run `python org/threads/test-model.py --model <name>` to verify compatibility. |
| Wrong tier folder (agent not found) | Check serial format -- `0.Y.Z` where Z>0 = tier3_junior; `0.Y.0` where Y>0 = tier2_senior. |
| Project file not updated | Check create-thread.sh stderr. JQ must be available at `.tools/jq.exe`. |
