Per Andrew direct ask: design the bucket structure for `opal-data-imo` (FIND_INSURE project), benchmarked against existing Opal patterns (opal-data-bd, opal-data-inf, opal-data-demo, opal-data-mdpf). ## TL;DR for CTO (one-paragraph decision frame)

PRD v0.2 §3.2 specifies the **per-IMO grouped layout** (`corp/{slug}/{medallion}/{channel}/{date}/` + `serving/` at root). This brief CORROBORATES that PRD layout for the data-class prefixes and recommends ADDING **5 sibling root prefixes** (`code/`, `config/`, `telemetry/`, `qa/`, `archives/`) to match the inf-pipeline pattern and support fabric discipline (comp-pipescript deployed MATCH check; runtime config separation; Lambda execution telemetry; ad-hoc verification artifacts; long-tail archive). It pins date-partition format YYYY-MM-DD UTC (matches inf/orion). It specifies a 6-prefix lifecycle policy for cost discipline on bronze. It locks SSE-S3 (AES256) + versioning Enabled + public-access-block all-true per inf precedent. It DEFERS CORS until Phase 3b portal surface lands. It surfaces 4 ratification-needed open questions to CTO for explicit ruling at v0.3 amendment OR pre-FIND_INSURE.001 implementation. **None of the recommendations BLOCK FIND_INSURE.001 ship** — AE 0.7 can ship a bucket meeting these recommendations OR ship the minimal PRD §3.2 layout and add via amendment.

## §2. Bucket prefix layout

### §2.1 PRD v0.2 §3.2 layout (CVO CORROBORATE as-shipped)

PRD §3.2 specifies:

```
opal-data-imo/
  corp/{company-slug}/
    bronze/{web-scrape,linkedin-scrape,job-posting-scrape}/{date}/
    silver/{web-scrape,linkedin-scrape,job-posting-scrape}/{date}/
    gold/{web-scrape,linkedin-scrape,job-posting-scrape}/{date}/
  serving/
    companies.{json,parquet}
    employees.{json,parquet}
    scoring.{json,parquet}
    _meta/
```

**CVO assessment:** the per-IMO grouping (`corp/{slug}/`) is the correct primary organizing dimension for this workload because (a) per-IMO listings are the common access pattern (`aws s3 ls s3://opal-data-imo/corp/wlth-rx/` for one-IMO diagnostic), (b) per-IMO deletion (e.g., IMO drops out of source list) is a single subtree delete, (c) the cross-IMO operation (Phase 3 serving consolidation) is RARE relative to per-IMO operations and is the consolidation Lambda's specific job to scan-all-corp-fanout once per run. Diverges from inf-pipeline (which puts `bronze/` at root + per-tenant subdir under each medallion); but this divergence is **justified by the workload shape** — inf is small-tenant-count with high-per-tenant-volume; FIND_INSURE is ~100-tenant with low-per-tenant-volume + per-tenant-isolation more important.

PRD §3.2 medallion-channel ordering (medallion THEN channel: `bronze/web-scrape/` not `web-scrape/bronze/`) is also CORROBORATE — re-processing a pipeline stage ("re-parse all silver/web-scrape/* into gold/web-scrape/* with v2 term taxonomy") is the more common cross-IMO operation than re-processing-by-channel (which is rare; channels are independent pipelines).

### §2.2 Additional root-prefix recommendations (sibling to corp/ + serving/)

**RECOMMEND ADDING 5 sibling root prefixes**, each justified by an inf-pipeline precedent + a FIND_INSURE-specific use case:

| Prefix | Inf-pattern parallel | FIND_INSURE-specific use | Priority |
|---|---|---|---|
| **`code/`** | inf has `code/` (deployed Lambda source mirror; supports `comp-pipescript deployed` MATCH check per CLAUDE.md `comp-pipescript deployed [script]`) | Mirror of `data/find/imo/scripts/**/*.py` deployed-state. AE 0.7's deploy pipeline `aws s3 cp` syncs into this prefix; runner-vs-CLOUD MATCH check uses it. | **HIGH — adopt at Phase 0** |
| **`config/`** | inf has `config/` (runtime config like term taxonomies, scoring weights, normalization tables) | (a) `config/term-taxonomy-{version}.json` — Phase 1 score-web term list (PRD §4 Phase 1 explicit deliverable); (b) `config/scoring-weights-{version}.json` — Phase 3 relevance scoring weights (PRD §4 Phase 3 deliverable 2 + Q2); (c) `config/board-endpoint-manifest-{date}.json` — Stage Bα output (PRD §4 Phase 2 Part B); (d) `config/lookalike-seed-{date}.json` — Phase 3 Lusha Lookalikes input | **HIGH — adopt at Phase 0** |
| **`telemetry/`** | inf has `telemetry/` (structured ndjson logs per Lambda invocation, CloudWatch-Logs-mirror) | Per-Lambda-run ndjson records: `{lambda, run_id, imo_slug, started_at, ended_at, status, rows_in, rows_out, credits_burned, error_class}`. Enables cost-discipline retro (Lusha credit-burn-per-run + Bright Data API-call-per-run per Q4/Q7 PRD §9). | **MEDIUM — adopt at Phase 1** when Lambdas land |
| **`qa/`** | inf has `qa/` (ad-hoc verification artifacts during RAVC2 cycles) | Phase 1 RAVC2 sample-manual-review-of-10-IMOs artifact storage (PRD §4 Phase 1 deliverable 4). Phase 2/3 RAVC2 artifact storage. CVO /verify-channel comprehensive cycle artifact storage. | **MEDIUM — adopt at Phase 1** |
| **`archives/`** | bd has `GOOD_RUN_2026-01-21_1015AM/`-style ad-hoc archives; inf does NOT | Optional. Reserved for IR-team "freeze this snapshot of serving/* for the Q2 outreach campaign" use case. Phase 3b candidate. | **LOW — defer to Phase 3b need-emerges** |

**NOT recommended:**
- `diagnostic/` separate from `qa/` — bd has both; conflation here would dilute the qa/ semantic. One is enough.
- `lambda-{deploy,layers,packages}/` — bd has these as legacy pre-Terraform-only-deploy doctrine; CLAUDE.md Rule 1 mandates Terraform-only Lambda deploy; these prefixes would be artifacts of the wrong workflow.
- `backfill_v2/` / `forwardfill_v2/` — bd-specific BACKFILL/FORWARDFILL operational patterns; FIND_INSURE has no analogous backfill class at v0.1 (date-partitioned + idempotent extractors).

## §3. Date partitioning convention

### §3.1 Format — pin YYYY-MM-DD UTC

PRD §3.2 + §4 use the literal `{run-date}` placeholder without format pin. RECOMMEND pinning **`YYYY-MM-DD` UTC** per:

- **Empirical inf precedent** — `aws s3 ls s3://opal-data-inf/bronze/orion/` returns `2026-04-21/` and `2026-04-29/` (dashed YYYY-MM-DD).
- **Consistency with fabric** — orion + smartx + black-diamond all use dashed YYYY-MM-DD; YYYYMMDD-without-dashes would create scan-time confusion for ad-hoc operators.
- **Lexicographic-sort = chronological-sort** — both formats satisfy, but dashed is more human-readable.
- **UTC discipline** — cron + SSM are UTC per [[feedback_commit_age_use_iso_utc_not_local]] + ws CVO /spot-check timestamp-discipline (AE~C catch 2026-05-23); local-tz date partitioning creates DST + cross-region drift.

**Recommend codifying** in PRD v0.3 §3.2 with one line: "Date partitions use `YYYY-MM-DD` UTC format (e.g., `bronze/web-scrape/wlth-rx/2026-05-30/`)."

### §3.2 Re-run semantics

PRD doesn't pin the re-run semantic. Two patterns observed in fabric:

| Pattern | Used by | Mechanic |
|---|---|---|
| **Append-by-date** | Inf bronze/silver/gold | Each run writes to a NEW date partition; prior dates persist immutable (subject to lifecycle); re-run within same day creates an in-day re-write but Phase-N+1 reads the date-partition path |
| **Overwrite-in-place** | Inf platinum (some keys) | Single canonical path; latest write wins; versioning catches accidental destructive overwrites |

**Recommend:**
- `corp/{slug}/{medallion}/{channel}/{date}/` — **append-by-date**. Each pipeline run writes a fresh date partition; re-runs within day overwrite same-date paths; prior dates persist for lineage (and re-processing into newer scoring versions). Matches inf bronze/silver/gold.
- `serving/{companies,employees,scoring}.{json,parquet}` — **overwrite-in-place** (canonical-live-served). Versioning Enabled catches accidental deletes; OPTIONALLY also write archive copy at `serving/_history/{date}/` for time-travel auditability (recommend YES for serving/scoring.json specifically — when IR-team feedback drives a re-weighting, the prior scoring methodology should be cite-able).
- `serving/_meta/{file}-{date}.json` — **append-by-date** (already PRD-implicit since PRD says `source-list-{date}.json`).

### §3.3 Slug normalization (Phase 0 unit-of-discipline)

PRD §3.2 specifies "deterministic slugifier (lowercase, ASCII, `-`-separated, no diacritics) — same pattern as existing `data/demo/scripts/transform/fake_identities.py` slugging. Slug stability is load-bearing across phases (path persistence on re-runs)."

**RECOMMEND ADDING Phase 0 sub-deliverable** under FIND_INSURE.002 or a new .002b: extract slug logic into a shared util at `data/find/imo/scripts/_util/slugify.py` that ALL FIND_INSURE Lambdas (Phase 0 extract-source-list + Phase 1 crawl-web + Phase 2 crawl-linkedin + Phase 2 crawl-job-posting + Phase 3 serving-build) import and use identically. Otherwise drift risk is HIGH: extract-source-list slugs "Wlth Rx Insurance" → `wlth-rx-insurance`, crawl-web slugs it → `wlth-rx-ins` (different diacritic stripper), path mismatch → silver/gold parsing fails to find bronze.

This is the most common silent-defect class in slug-keyed pipelines (caught in fabric history at Inf positions migration). Single-source-slug-util at Phase 0 prevents it structurally.

## §4. Lifecycle policy recommendations

PRD doesn't specify lifecycle policies. Recommend 6-prefix rule set per cost-discipline rationale:

| Prefix pattern | Transition rule | Expiration rule | Rationale |
|---|---|---|---|
| `corp/*/bronze/*/*` | Standard-IA at 90d; Glacier Flexible Retrieval at 365d; Deep Archive at 730d | NEVER (preserve for forensic / re-processing) | Bronze = raw HTML / JSON dumps; quarter-old data is cold; year-old is glacier-cold; two-year is deep-archive. Re-fetch is expensive (Bright Data credits + LushaAI credits), so cold storage > delete. |
| `corp/*/silver/*/*` | NEVER | NEVER | Silver = parsed/structured; small enough; re-parse from bronze is also possible but cold-tier latency is undesirable. |
| `corp/*/gold/*/*` | NEVER | NEVER | Gold = scored output; small + frequently re-read for analytics. |
| `serving/*` | NEVER | NEVER | Live-served. Versioning catches deletes. |
| `serving/_meta/*` | NEVER | NEVER | Small + lineage-critical. |
| `serving/_history/*` (if adopted §3.2) | Standard-IA at 90d; Glacier Flexible Retrieval at 365d | NEVER | Historical snapshots of serving/* for time-travel. |
| `code/*` | NEVER | NEVER | Versioning catches deletes; deployed-state must be readable. |
| `config/*` | NEVER | NEVER | Live runtime config; versioning catches deletes. |
| `telemetry/*` | Standard-IA at 30d | 365d | Per-run logs; query freshness window is short; year-old logs rarely useful. |
| `qa/*` | NEVER | 90d | Ad-hoc verification artifacts; auto-clear after a quarter to prevent accumulation. |
| `archives/*` | Standard-IA at 30d; Glacier Flexible Retrieval at 365d | NEVER (manual delete only) | Long-tail snapshot freezes; explicitly archival semantic = cold storage acceptable. |

Implementation: single `aws_s3_bucket_lifecycle_configuration` resource with multiple `rule { }` blocks, one per pattern above (8-9 rules total). Pattern reference: `infra/aws/terraform/inf-pipeline/s3.tf:54-69` is the single-rule shape; multi-rule per AWS docs.

**Cost-discipline meta-note:** Bright Data per-call costs + Lusha per-credit costs (PRD §9 Q4/Q7) dominate the FIND_INSURE budget. The lifecycle rules above are S3-storage-cost-only and are minor relative to fetch costs. Lifecycle is the right discipline anyway (raw payloads stale fast for re-read purposes), but the primary cost lever is the cost-budget gates inside the Lambdas themselves (config/cost-budgets-{version}.json + Lambda-side enforcement) — covered §5 below.

## §6. Encryption + versioning + public-access

### §6.1 Encryption — SSE-S3 (AES256) at v0.1 with KMS upgrade-path documented

PRD doesn't specify. **Recommend SSE-S3 (AES256)** matching inf-pipeline + bd + mdpf + demo precedent. Justifications:
- IR-team-internal-only consumer at v0.1 (no external API surface, no cross-tenant boundary)
- LushaAI contact data IS PII (employee names + emails + LinkedIn URLs) but Opal is the data controller at this stage — internal-storage PII protection via SSE-S3 + bucket-level public-access-block + role-based access discipline = compliant baseline
- SSE-KMS adds operational complexity (key rotation, KMS Decrypt permission on every reader) without proportional security benefit for internal-bucket-internal-consumer

**Document KMS upgrade-path** in module README: "If FIND_INSURE expands to cross-tenant or external-API serving in v0.2+, upgrade to SSE-KMS with shared-infra KMS key. Pattern reference: existing portal-auth pipeline KMS integration." Phase 3b portal surface decision-point would trigger this re-evaluation.

### §6.2 Versioning — Enabled

Matches inf-pipeline. Catches accidental delete of `serving/companies.json` during Phase 3 iteration (which would otherwise silently break the IR-team feed). Cost: marginal (small files, low write frequency on serving/*).

### §6.3 Public-access — all-blocked

`block_public_acls + ignore_public_acls + block_public_policy + restrict_public_buckets` all true. Matches inf precedent. Mandatory; no exception case at v0.1.

## §7. CORS — defer to Phase 3b

PRD §3.4 + §4 are CLI-readable raw S3 artifacts at v0.1. No browser-side fetch surface. **DO NOT** add `aws_s3_bucket_cors_configuration` at v0.1 — it would widen the attack surface unnecessarily.

Add CORS only when Phase 3b portal page is authored. Pattern at that time: copy inf-pipeline cors block; replace `allowed_origins=["*"]` with explicit Opal portal origin allow-list.

## §8. CloudWatch monitoring — staged

Phase 0 — Bucket-level metrics standard (CloudWatch S3 metrics enabled by default).

Phase 1 onward — Add CloudWatch alarms via Terraform:
- `find-insure-lambda-error-alarm` per Lambda: fires on >1 error in 5min window
- `find-insure-bucket-cost-alarm`: monthly cost threshold (initial: $50/mo; tune at Phase 1 ship)
- `find-insure-bright-data-credit-burn-alarm`: pulled from telemetry/ ndjson via metric filter (initial: 80% of Q7 budget)
- `find-insure-lusha-credit-burn-alarm`: same pattern via metric filter on telemetry (initial: 80% of Q4 budget)

Phase 3 — CloudWatch dashboard `find-insure-overview`: bucket size + per-prefix object count + Lambda invocation rate + credit-burn-trend (per inf-pipeline `cloudwatch-dashboards.tf` precedent).

NOT v0.1 deliverable; flag for Phase 1 RAVC2 follow-on TO.

## §9. Cost-discipline gates (Lambda-side, NOT bucket-side)

Per PRD §9 Q4 (Lusha credit ceiling) + Q7 (Bright Data per-call ceiling): these are LAMBDA-side controls, not bucket controls. Recommend:

`config/cost-budgets-{version}.json`:

  "version": "v1",
  "per_imo_ceilings": {
    "lusha_credits_phase_2a": 50,
    "bright_data_calls_phase_1": 10,
    "bright_data_calls_phase_2b_per_board": 5
  },
  "global_daily_ceiling": {
    "lusha_credits": 500,
    "bright_data_calls": 1000

  "abort_behavior_note": "Lambda completes current IMO, writes telemetry record with cost_ceiling_hit=true, then exits cleanly. Next-run resumes from next IMO."
