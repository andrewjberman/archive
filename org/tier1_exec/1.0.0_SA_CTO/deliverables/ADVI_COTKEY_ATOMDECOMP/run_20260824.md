## What the run establishes (for the PRD; the decomp sizes it)

1. **Hypothesis: CONFIRMED, in the strong form.** Not "a derivation of portfolio group" -- the Portfolio Group VALUE is the
   advisor's name, for 861 of 942 accounts (91.4%); 81 accounts (8.6%, 3.84% of AUA) sit in an explicit `No Advisor` book.
2. **The served advisor layer is a bridge, and its planned successor was built on the wrong key.** K1/K3 = one synthetic
   advisor; K9 = rep codes span advisors. The bridge's self-disabling guard ("when real matching lands") is the correct
   hand-off point; the "real matching" is `portfolio_group`, not rep/team.
3. **The remedy is small at the producer and consequential at the consumers.** A_01 keyed from `account_attributes.portfolio_group`
   (advisor = group; `No Advisor` = an explicit unassigned class, never dropped) flips C_08 / D_00c / D_02 / D_04 from one
   book to four; every per-advisor figure the Cottonwood tenant serves changes. That is the decomp's operative surface.
4. **Two state gaps ride with it:** (a) `account_attributes` has ONE partition (08-19) -- point-in-time advisor history
   starts the day the daily pull lands, and an SCD before that date is unmeasurable; (b) template 270648 lacks dim 436,
   so the one two-book account needs a vendor-side answer or a declared keep-first.
5. **Tie-out oracle exists in pattern:** a qt6 group-grain read on the cot BD session is the pre-registered "does it add
   up to the advisor's own dashboard" check, before any per-advisor figure is served.
6. **What this run did NOT measure (decomp cells, not gaps in the claim):** the BD-side Portfolio Group TREE for Cottonwood
   (parent/child groups; whether `No Advisor` is a real group or an absence rendering); whether Cottonwood staff assign
   groups by hand or BD derives them; the D_00b timeseries + C_07 attribution consequences of a four-book history that
   begins 2026-08-19; the Inflection helper's reuse boundary (re-instantiate the slug rule, never import across trees).
