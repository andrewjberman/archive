# CAN WE DEFINE A "SYSTEM" WITHOUT DECLARING ANYTHING?

**A brief on replacing the C3.i definition with a structural one**

## 1. WHAT WE ARE TRYING TO DO

The estate's semantic ladder has five rungs. C0 is facts (nodes), C1 is interactions (edges),
C2 is motifs (recurring shapes), **C3 is systems**, and C4 is segments.

C3 is split in two halves that are supposed to work differently, and the split is deliberate:

| rung | what it is | how membership is decided |
|---|---|---|
| **C3.i** — deterministic structures | what the estate *structurally is* | **DISCOVERED**, never declared |
| **C3.ii** — semantic verticals | what the business *calls things* | **DECLARED**, never discovered |

C3.i is the half that is supposed to be found rather than legislated. **The question in this brief
is whether it actually is** — and if not, what a genuinely discovered definition would look like.

**The requirement that makes this urgent: it has to generalise beyond AWS.** Any definition that
leans on AWS vocabulary cannot describe the portal, the knowledge layer, or a future non-AWS system.

### 2.3 What we found when we looked at the actual definition

Reading the source, the entire C3.i layer — **1,257 structures over a 20,800-node graph** — is
generated by **seven hand-listed AWS node types**:

```python
ANCHOR_CATALOG = {
    "object-data":           {"S3_BUCKET", "S3Key"},
    "compute-orchestration": {"EVENT_RULE", "STATE_MACHINE"},
    "pipeline":              {"PipelineScript", "PipelineFunction"},
    "table-data":            {"DYNAMODB_TABLE"},
    "identity":              {"IAM_ROLE"},
}
HUB_TYPES = {"LAMBDA", "EC2_INSTANCE", "actor"}   # may never anchor a system
```

The algorithm: each C2 motif instance joins a group keyed on `(domain, anchor node)` for every member
matching a catalog type; hubs are skipped; a group becomes a system at 2+ members.

**Four observations followed:**

1. **C3.i is billed "DISCOVERED, never declared" — but its discovery is entirely parameterised by a
   declaration.** Nobody hand-inserts a *system*, true. But someone hand-listed the seven types that
   can *produce* one, and that list does all the work.

2. **The 1,107 unanchored instances (17.8%) are the shadow of that list, not estate noise.** They
   contain no catalog anchor, so no domain claims them.

3. **The catalog is AWS-parochial, which is why two of three substrate sides yield nothing.**
   FRONTEND produces **zero** C3.i structures; the knowledge layer produces **zero**. No portal node
   could ever match an anchor even in principle. *The generalisation problem is not in the future —
   it is already failing.*

4. **System identity is a hash of a mutable anchor** (`sysi:{domain}:{sha1(anchor_node_id)}`).
   Rename or recreate that bucket and the system gets a new identity while the old one silently
   vanishes. A system cannot carry history or accumulate rulings.

### 2.4 A related finding: C3.i is three different id spaces

| surface | identity form | count |

Nothing declares the mapping between them. The business-named surface — the one C3.ii reconciles

## 3. THE OPTIONS CONSIDERED

The brief asked for definitions with as little opinion baked in as possible.

**An honest framing first: zero opinion is not achievable.** Every method embeds a view of what a
system is. What *can* change is where the opinion lives. A hand-list of seven type names cannot be
tested, watched, or shown to be wrong. An objective function can be run, scored, and falsified. That
is the real axis.

| tier | option | parameters |
|---|---|---|
| **A** | Block-cut tree / biconnected components — cut structure; "hubs" become *measured* articulation points rather than a list | none |
| **A** | Connected components — the honest baseline, already rejected for collapsing into one supersystem | none |
| **B** | **Stochastic block model with MDL** — group nodes by connection *pattern*; the data chooses the grouping | none in principle |
| **B** | Link communities — partition edges, so overlap falls out naturally | one, derived |
| **C** | Co-change coupling — what changes together, from git history | none |

**Option B was selected for testing** because it is the most vocabulary-free: it groups nodes by
their *pattern of connection to other groups*, and never asks what a node is. That property is what
ports to the portal, the knowledge layer, and non-AWS estates.

## 4. THE EXPERIMENT, IN PLAIN TERMS

We have a graph: **19,482 things** and **36,513 connections**. The method sorts those things into
groups, allowed to look only at **who connects to whom**. It never sees types or names.

**The scoring idea.** Imagine transmitting the entire wiring diagram using as few bits as possible.
Send the group assignments first; if the groups are good, the wiring becomes predictable ("group 7
mostly connects to group 12") and little else is needed. If the groups are meaningless, they don't
help.

That total is **description length**, measured in *nats* (an information unit like bits).
**Lower = the grouping explains more of how the estate is actually wired.** Every comparison below
uses that one number.

*The layer produced by the old anchor method was excluded from the input — inferring structure from
the previous method's own output would be circular.*

## 5. RESULTS, ONE BY ONE

### Result 1 — the structure is real · **PASS**

**Asked:** is it finding anything, or carving the estate into arbitrary piles?
**Method:** score our grouping, then score random groupings of the same size.

```
random groupings   897,250
our grouping       719,792     ->  177,474 nats better (~20%)
```

**Means:** there are genuine regularities in how the estate is wired, and the method found them.

**Note:** the number 719,792 means nothing alone — there is no scale without the comparison. I had
privately concluded the result was junk because the group sizes looked too even; the random
comparison proved me wrong.

### Result 2 — it did **not** rediscover the AWS vocabulary · **PASS**

**The worry:** the obvious failure mode is grouping all buckets together, all roles together —
handing back the type list we already have, dressed as a discovery. Circular and worthless.

**Method:** a score called **AMI**: 0 = "the groups tell you nothing about type", 1 = "the groups
*are* the types."

```
our grouping vs node_type        0.109      (essentially unrelated)
deliberately grouped BY type     1.000      <- proves the measure works
```

**Means:** the structure found is independent of what things are — the property that lets it work on
non-AWS systems.

**Note:** the second line is the important one. Without it, a low score might just mean a broken
measuring stick.

### Result 3 — the structure beats the vocabulary at explaining the estate · **PASS (conditional)**

```
grouped by AWS type      737,677
discovered structure     719,792     (and 701,618 at finer granularity)
```

**Means:** lower is better, so **the discovered structure describes how the estate actually works
better than the estate's own vocabulary does.** Type names are the weaker signal.

This is the core argument against `ANCHOR_CATALOG`: defining systems by node type is not just
inflexible, it is defining them on the worse of two available signals.

**Limit:** holds at 32 groups or more. At coarse settings (8 or 16) the type vocabulary wins.

### Result 4 — it separated the two firms without being told they exist · **PASS**

The most important result, because it is checkable against something already known to be true.
49 Financial (`bd`) and Inflection (`inf`) are separate firms with separate pipelines, and the
previous anchor-TYPE approach was rejected **precisely because it merged them.**

265 nodes whose names identify them as `bd` or `inf` were tagged *after* the fact, then located:

```
AMI(group, firm)   0.518        ARI 0.618
block purity       0.981        (98.1% sit in a group dominated by their own firm)

   group 26:  bd=132   inf=  0     purity 1.00
   group  4:  bd=  2   inf= 79     purity 0.98
   group 34:  bd=  6   inf=  0     purity 1.00
   group 39:  bd=  0   inf=  6     purity 1.00

NEGATIVE CONTROL (firm labels shuffled):   0.000
```

**Means:** the method recovered the firm boundary **from wiring patterns alone**, having never seen a
firm label. The shuffled-label control confirms this is real and not an artifact of having many
groups.

**RE-RUN AT THE MDL-SELECTED GRANULARITY (B=256, see Result 5) — the criterion should be judged where
the method itself says the answer is:**

```
block purity wrt firm   0.989        (up from 0.981)
AMI(block, firm)        0.311        ARI 0.185
NEGATIVE CONTROL       -0.002

   block 247:  bd=  0  inf= 69   purity 1.00
   block 141:  bd= 37  inf=  0   purity 1.00
   block 228:  bd= 24  inf=  0   purity 1.00
   block  81:  bd= 11  inf=  0   purity 1.00
```

**Purity improved and every substantial block is 100% single-firm.**

⚠ **The AMI fell (0.518 -> 0.311) and that is NOT a regression** — it needs reading correctly or it
looks like one. AMI penalises *fragmentation*: at 48 groups all 132 `bd` nodes sat in one block; at
256 they are spread over seven blocks (37, 24, 11, 11, 9, 8, 7) — **none of which is contaminated.**
The method is resolving *below* firm level, finding sub-systems inside each firm. For a system
decomposition that is the desired behaviour. **Purity, not AMI, is the right measure once granularity
goes finer than the label being tested against.**

### Result 5 — it chooses its own granularity: **256 systems** · **PASS**

**The promise that made this approach attractive** was that it decides *how many* systems exist by
itself: too few groups explain little, too many are just memorisation, and a built-in complexity
penalty punishes the second. Plotted against group count, the score should dip and then rise — and
**the bottom of that curve is the answer.**

It does exactly that:

```
     B            DL   AMI_vs_type  singletons
    64       726,815        0.088           0
   128       701,778        0.131           1
   256       694,007        0.144           1   <-- MINIMUM
   512       698,874        0.175          15   turned up
  1024       715,656        0.197          37   turned up
  2048       740,156        0.204         125   turned up
```

**MDL selects B = 256 systems with no human input.**

Three signs the minimum is real rather than an artifact:

- **Singletons appear exactly where overfitting should start** — 0 at the optimum, then 15 → 37 → 125.
  That is the model beginning to memorise individual nodes, and the penalty punishes it.
- **At B=2048 the fit is WORSE than the crude type baseline** (740,156 vs 737,677). A well-behaved
  penalty should eventually lose to a simple model when it overfits, and it does.
- **AMI never becomes circular at any granularity** (0.088 - 0.204); at the optimum it is 0.144.

> **CORRECTION TO AN EARLIER VERSION OF THIS BRIEF.** This result was first recorded as a FAIL, with
> the note that the complexity penalty was *"quite possibly a defect in the code."* **That was wrong,
> and the error was mine, not the method's.** The first sweep only tested up to 128 groups — entirely
> on the falling side of a U-shaped curve — so the curve looked monotonic. The penalty was working
> correctly the whole time; the tested range was too narrow. Recorded because the same error shape
> occurred twice in this session (see the method note in §7): **both times the method was sound and
> the measurement of it was not.**

⛔ **AND THE FAILURE THIS RUN PRODUCED FIRST, which is the most useful thing in it.** The initial

### Result 7 — the PARTITION is unstable; the FINDINGS are not · **PASS with a hard limit**

*(Run 2026-08-26 on Andrew's question: "would C3.i shift every time we ran it?" It had never been
measured -- every run in this exercise used the same random seed.)*

Exact minimisation is NP-hard, so the fit uses randomised greedy search: random start, random visit
order. Different seed, potentially different answer. Measured, same graph, same B=256:

```
  seed          DL   AMI_vs_type   firm_purity   firm_blocks
     7     694,007         0.144         0.989            48
    23     694,874         0.149         0.996            44
    91     695,063         0.151         0.992            46

  agreement BETWEEN those runs:   AMI ~0.505    ARI ~0.21
  DL spread:                      1,056 nats (0.15% of the best)
```

**Read the two halves separately, because they say opposite things:**

- **The PARTITION is unstable.** Three runs of essentially identical quality (0.15% apart) disagree
  about roughly half of who belongs with whom. **Yes -- C3.i would shift materially every run.**
  This is a *degenerate optimum landscape*: many very different partitions score nearly the same, so
  "the best partition" is not a well-defined object at this granularity.
- **The FINDINGS are stable.** Firm purity 0.989 / 0.996 / 0.992. Non-circularity 0.144 / 0.149 /
  0.151. Every conclusion in Results 1-6 reproduces across independent runs.

> Three people asked to shelve a library onto 256 shelves produce very different shelvings -- and all
> three keep fiction away from non-fiction. The shelving is arbitrary; the boundary is real.

**THE CONCLUSION THIS FORCES, and it is the most useful sentence in this brief:**

> **The method DESCRIBES reliably. It CANNOT MINT IDENTITY.**

Results 1-6 are properties of the estate, not artifacts of one seed -- that was a live risk and it is
now closed by measurement. But **§8 decision 3 (identity) is no longer advisory: it is mandatory.**
A system id derived from any single run would appear and vanish nightly for no reason in the world.

⚠ **WHAT THIS MEASUREMENT CANNOT SEPARATE.** A 0.15% spread across wildly different partitions is
equally consistent with (a) the landscape is genuinely flat -- the wiring does not determine a unique
partition and no optimiser would resolve it -- or (b) the optimiser is weak (greedy, 2 rounds, no
restarts) and all three runs sit in mediocre local optima that happen to score alike. **These have
opposite implications** -- (a) says stop looking for one answer, (b) says run it properly and the
answer sharpens. Distinguishing them needs a stronger optimiser than was built here.

**THE KNOWN REMEDY, if a stable partition is wanted:** **consensus clustering** -- run the fit many
times, record how often each PAIR of nodes lands together, then cluster that co-assignment matrix.
Pairs that always co-occur survive; chance pairings wash out. This is standard practice precisely
because SBM inference on real networks is usually degenerate like this, and it -- not a single seeded
run -- would be the production design.

## 7. WHAT IS NOT PROVEN — read before building on this

1. **Vintage.** Run on the pre-nightly 19,482-node graph, not the current 27,061-node one. Re-derive
   before ratifying.
2. **One greedy run per setting**, no restarts. Proper practice takes the best of many starts. These
   description lengths are a **floor**, not the optimum.
3. **Partition, not cover.** C3.i is currently ruled as a *cover* — overlap by design. A standard
   block model returns a partition. That conflict is unresolved (see decisions below).
4. **The firm test used a name heuristic** to tag `bd`/`inf` nodes. It matched 265 nodes; it is not a
   census of either firm.
5. ~~**The MDL penalty may contain a defect.**~~ **RESOLVED** — the optimum was simply larger than
   the range first tested. The penalty is sound; see Result 5.

*A note on method: two of the checks in this brief initially produced wrong answers because the
measuring instrument was crude, not because the method failed. The first firm-separation test
returned "DISQUALIFIED" on a bad threshold — a 79-inf/2-bd group is 98% pure and was being scored as
"mixed." A badly specified acceptance test kills good work silently, because "it didn't pass" reads as
settled and nobody investigates. Every result above therefore carries its control.*

   than a property of the estate.

3. **Identity — NO LONGER ADVISORY, MANDATORY (Result 7).** Independent of which method wins:
   system identity should stop being `sha1(anchor_node_id)`. Membership can be recomputed nightly; **identity needs minting once and
   tracking through succession.** Without this, any C3.i ↔ C3.ii mapping decays the first time an
   anchor resource is replaced — which is why the three id spaces in §2.4 cannot currently be joined.
