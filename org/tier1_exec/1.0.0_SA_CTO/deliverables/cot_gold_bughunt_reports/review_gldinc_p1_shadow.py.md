## Finding 1 -- [medium/merge-dedup/full]
- **Location:** `gldinc_p1_shadow.py:_normalize (L91-99) + compute_scorecard key-set/merge (L116-140)`
- **Mechanism:** _normalize canonicalizes the join key by strftime('%Y-%m-%d') on the date (L94) and astype(str) on account_id (L95). The upstream producer (_transform_events_to_daily) groups on the FULL datetime64 trade_date and the raw account_id dtype, so two distinct upstream group rows can COLLAPSE to one normalized (date,account_id) string key. The scorecard then compares keys two inconsistent ways: key_set_symmetric_diff/exact_match_rate use Python sets (L116-125) which SILENTLY DEDUP the collapsed key, while inc.merge(ora, how='inner', ...) (L129) produces a CARTESIAN product for that key. This inflates total_cells / within / oracle_rows / incremental_rows, and — critically — cross-pairs the duplicate rows in the max_abs_diff computation (L133-140).
- **Failure scenario:** A silver/transactions partition carries an intraday trade_date timestamp (the lib comment at nna_flows.py:161-171 documents partitions are heterogeneous in trade_date storage), OR account_id appears as int in one partition and float/str in another (e.g. 123 vs 123.0). Upstream groupby then emits two rows for the same account+calendar-day, say daily_inflow=100 and =200, present identically in BOTH inc and ora. After _normalize both collapse to key ('2026-01-01','123'). The inner merge yields 4 rows including the cross pairs (100 vs 200) and (200 vs 100) -> max_abs_diff=100 >> FROZEN_EPSILON_USD(1e-6) -> targets_met=False -> divergence_investigate=True prints a spurious 'P1 DIVERGENCE / STOP' AND the cache is HELD (not advanced), so clean_night_counter can never reach 5 and cutover is permanently blocked by a phantom divergence — even though the two paths are byte-identical. key_set_symmetric_diff stays 0, masking the true cause. (Note: non-fatal to the chain and never touches a served key; blast radius is a false STOP + a stuck cutover-readiness signal + misreported scorecard metrics.)
- **Proposed fix:** After _normalize, collapse to unique keys before comparing: groupby(_KEY_COLS, as_index=False)[_VALUE_COLS].sum() (or assert (date,account_id) uniqueness and fail loudly if not). This makes the set-based symdiff and the merge agree and removes the Cartesian cross-pairing. Alternatively key on the full datetime (don't strftime away sub-day precision) and pin account_id dtype identically on both sides before the merge.

## Finding 2 -- [low/other/full]
- **Location:** `gldinc_p1_shadow.py:main (counter write L291-297 vs cache advance L324-331)`
- **Mechanism:** main() persists the clean_night_counter/consecutive_fallback_nights state to _COUNTER_KEY FIRST (L291-297), then advances the incremental cache+watermark via write_load_flows_state(pending) SECOND (L324-325). The two writes are not atomic and are ordered counter-before-cache.
- **Failure scenario:** On a clean (or fallback) night, _put_json(_COUNTER_KEY,...) succeeds and advances clean_night_counter, but write_load_flows_state then raises (e.g. the parquet PutObject at nna_flows.py:543 fails on a transient S3 error). The exception propagates out of main -> non-zero exit (caught as a non-fatal WARN by the dispatcher). Next night read_load_flows_watermark returns the OLD (un-advanced) watermark so the windowed path re-derives from a stale/absent cache, yet the persisted clean_night_counter has already incremented and can even cross the >=5 cutover_ready threshold while the incremental cache it is supposed to certify was never successfully written — a false GREEN on the cutover-readiness signal. Shadow-only, never a served key.
- **Proposed fix:** Write the cache+watermark (write_load_flows_state) FIRST and persist the counter state only after it returns successfully; or wrap both in a try/except that reconciles (do not advance the counter if the cache write fails).
