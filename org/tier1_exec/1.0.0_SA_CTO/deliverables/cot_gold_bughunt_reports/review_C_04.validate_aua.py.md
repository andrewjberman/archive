## Finding 1 -- [critical/unguarded-read/full]
- **Location:** `C_04.validate_aua.py:234-236 (main), read_parquet_from_s3 at :60-63`
- **Mechanism:** main() reads the gold client_performance parquet via a HARDCODED legacy key `gold/client_performance.parquet` (line 234) with an UNGUARDED get_object (line 236) -- unlike the silver read (:108) and accounts read (:250) which are s3_object_exists-gated. Per lib/s3_layout.py the pipeline migrated: CLIENT_PERFORMANCE is now `gold/timeseries/client_performance.parquet` and `gold/client_performance.parquet` is only the LEGACY dual-write key (s3_layout LEGACY line 276). Every OTHER consumer (C_01, C_06, D_03, E_20, E_21, D_01) reads the NEW key via the CLIENT_PERFORMANCE constant; C_04 is the lone holdout on the legacy string. If the client_performance writer (C_02, absent from the local tree -- deploy drift) does not dual-write the legacy key, get_object raises NoSuchKey -> uncaught in main() -> the __main__ wrapper (:283-290) sys.exit(1). C_04 runs in gold_dispatch PHASE_C4 (C_04 || C_07, line 434) and wait_phase does `exit 1` on any non-zero child (:359), aborting the chain BEFORE PHASE_D1-D4, so the served portal publishers D_00/D_02/D_04 never run.
- **Failure scenario:** cot's cloned C_02 emits only the migrated `gold/timeseries/client_performance.parquet` (the key every other reader now uses) and drops the migration-era legacy dual-write. Nightly `--chain full` reaches PHASE_C4; C_04 get_object on `gold/client_performance.parquet` -> NoSuchKey -> traceback -> sys.exit(1) -> wait_phase FATAL exit 1 -> chain aborts -> served AUA/portal artifacts (D_00 header, D_02 client detail, D_04 platinum) are NOT refreshed. A validator documented 'non-blocking, exits 0' silently takes down the entire served publish. (Even if the legacy key IS still dual-written, C_04 then validates a possibly-stale legacy file instead of the fresh timeseries one -> wrong gap.)
- **Proposed fix:** Import and read CLIENT_PERFORMANCE from lib.s3_layout (the migrated key), with a LEGACY fallback, and GUARD it with s3_object_exists like the other two reads; on absence log ERROR and return/exit 0. A validator must never sys.exit(1) -- wrap main() so every failure path exits 0 (honor the docstring contract).

## Finding 2 -- [high/schema-column/full]
- **Location:** `C_04.validate_aua.py:238-240 (explicit sys.exit(1)) + :283-290 (__main__ except -> sys.exit(1))`
- **Mechanism:** The docstring (:22-23) states 'Non-blocking: any error logs at ERROR and exits 0.' The implementation violates this: line 240 does an explicit sys.exit(1) when client_performance lacks a `date` or `total_aua` column, and the __main__ handler converts ANY exception (e.g. float(cp_today['total_aua'].sum()) raising if total_aua is object/string dtype, or a merge/type error) into sys.exit(1). Because C_04 runs in PHASE_C4 ahead of the D-chain and wait_phase aborts on non-zero, a mere VALIDATION-time schema/type mismatch aborts the served publish rather than logging a WARN.
- **Failure scenario:** The cot C_02 (cloned from bd) writes its AUA column under a cot-specific name (e.g. `aua` or `total_market_value`) rather than `total_aua`, or stores `date` differently. Every nightly, C_04 line 238 sees the missing column -> sys.exit(1) -> PHASE_C4 FATAL -> D publishers skipped. The AUA cross-check never runs AND it blocks the served refresh -- the worst of both.
- **Proposed fix:** Make the validator truly non-blocking: on missing columns / any exception, log ERROR and `return` (exit 0), never sys.exit(1). Confirm the actual cot client_performance schema and reference the real AUA column name. Optionally give C_04 an empty CATALOG-flag wrapper that always exits 0 so a validator can never fail a chain phase.

## Finding 3 -- [medium/incremental-full-break/full]
- **Location:** `C_04.validate_aua.py:264-265 (default date = datetime.date.today()) + validate_date :107-110 (SKIP when today's silver absent)`
- **Mechanism:** In the daily chain C_04 receives no --date (CATALOG entry `C_04|C_04.validate_aua.py|` has empty flags) and does not read GOLD_RUN_DATE, so run_date = datetime.date.today(). But the chain runs against the LATEST SILVER DATA date (the freshness gate in gold_dispatch compares silver/allocations/{date} listing vs gold data_as_of), which is the market/business date -- typically the prior day, and the nightly frequently executes after 00:00 UTC. validate_date then checks silver/allocations/{today}.parquet, finds nothing (s3_object_exists False), logs SKIP and writes no validation. The daily gold-vs-silver AUA cross-check silently validates a date that has no data instead of the date the chain just built.
- **Failure scenario:** Nightly full chain runs ~02:00 UTC processing data_as_of=2026-07-06 (silver/allocations/2026-07-06.parquet is the latest). C_04 uses today()=2026-07-07 -> silver/allocations/2026-07-07.parquet absent -> SKIP, summary SKIP=1, no aua_validation_2026-07-06.json produced. A genuine gold-vs-silver AUA divergence on 07-06 goes completely undetected because the safety-net validator never evaluates the built date.
- **Proposed fix:** Default run_date to the latest silver allocation date (reuse list_silver_dates()[-1]) or read the dispatcher's RUN_DATE / GOLD_RUN_DATE env, not today(). This aligns the validator with the date the chain actually produced.

## Finding 4 -- [low/merge-dedup/full]
- **Location:** `C_04.validate_aua.py:159-174 (account_id set-difference decomposition) + :248 (legacy accounts_dimension key)`
- **Mechanism:** accounts_missing_from_gold = len(set(silver account_id) - set(gold account_id)) drives determine_status (missing>50 -> FAIL). This is a Python set difference over raw values, so a dtype mismatch between silver.account_id and the gold accounts_dimension.account_id (e.g. object 'z00123' vs int64), or a stale gold dimension, makes many/all silver accounts appear 'missing' -> spurious FAIL. Separately, C_04 reads the LEGACY accounts key `gold/accounts_dimension_latest.parquet` (:248) rather than ACCOUNTS_DIMENSION=`gold/dimensions/accounts_dimension_latest.parquet`; the read is guarded, so if A_00 ever stops dual-writing the legacy key the decomposition is SILENTLY disabled (accounts_missing_from_gold stays 0 -> always looks clean). Impact is limited to the advisory validation JSON (not a served number).
- **Failure scenario:** A future A_00 change drops the legacy accounts_dimension dual-write (A_00 currently dual-writes it at :639, so this is latent). C_04's s3_object_exists on the legacy key returns False -> accounts_dim_df stays None -> missing-account decomposition is skipped every run, so accounts_missing_from_gold is always 0 and the missing-account arm of PASS/WARN/FAIL is dead -- a real account-coverage gap can no longer trip the validator. Alternatively, an account_id dtype skew between silver and gold flips every clean day to FAIL.
- **Proposed fix:** Read accounts via the ACCOUNTS_DIMENSION constant from lib.s3_layout (current key) with a legacy fallback; and normalize both account_id columns to a common dtype (astype(str)) before the set difference so a dtype skew can't misclassify all accounts as missing.
