## Finding 1 -- [medium/empty-null-handling/both]
- **Location:** `_build_flow_attribution L120-137 -> _update_one_date L195-198 -> main L352-353`
- **Mechanism:** 49F-inherited script that is a structural no-op for cot. nna_atomic (produced by C_01's CN-P1 shadow writer) ALWAYS creates the 5 role columns architect/implementor/consultant/local_ops/additional_advisor, but for cot they are created as pd.NA (C_01 L598-601: NULL-OK; cot's A_00 acct_dim carries no role attribution because cot silver produces no role columns). So the L120 `if not role_cols` guard does NOT fire (columns exist), and instead every row is dropped by `work['_n_roles']=work[role_cols].notna().sum(axis=1)` -> `work[work['_n_roles']>0]` -> work.empty -> returns an empty flow_attr. Each date then sets result['error']='flow_attribution empty', so ok=[] and err=all-dates, and main ends at `if err and not ok: sys.exit(1)`.
- **Failure scenario:** Operator runs `python C_01c.role_aua_flow_join.py --upload` against opal-data-cot expecting to populate nna_txn/daily_inflow/daily_outflow in role_aua. Every nna_atomic partition has all-NA role columns, so flow_attr is empty for every date, no role_aua partition is ever updated (flow cols stay 0.0), and the process exits 1 while printing 'flow_attribution empty' for each date. The script silently accomplishes nothing and reports failure. It is not in any chain today (no CATALOG/CHAIN membership), but its sibling C_01b IS run manually and if C_01c were ever added to CHAIN_CANONICAL/DOWNSTREAM the same nonzero exit would HARD-FAIL the nightly chain (all gold compute steps abort the chain on non-zero exit).
- **Proposed fix:** Retire C_01c from the cot tree (cot has no role model, so role-attributed flow is meaningless) OR distinguish the structural 'firm has no role attribution' case from a real error: detect all-NA role columns up front and exit 0 (clean skip) instead of erroring per-date and hitting `sys.exit(1)`. Do not wire this into any cot chain.

## Finding 2 -- [low/numeric-sign-units/both]
- **Location:** `_build_flow_attribution L118, L140, L164 (nna_txn=('_cum_nna_share','sum')) and docstring L21`
- **Mechanism:** role_aua.nna_txn is populated from nna_atomic.cum_nna (cumulative net flow through the date), but the column named nna_txn is defined everywhere else in the pipeline (C_01.canonical_nna L395: nna_txn = daily_inflow - daily_outflow) as a single-day figure, and role_aua.daily_inflow/daily_outflow written here ARE daily. So within a served role_aua row the identity nna_txn == daily_inflow - daily_outflow no longer holds; nna_txn is cumulative while the inflow/outflow beside it are daily. This is documented-by-design in the docstring but the name collides with the canonical daily meaning.
- **Failure scenario:** If cot ever gains role attribution (or the script is ported to a firm like bd that has roles), a downstream consumer of role_aua.nna_txn (D_02.advisor_client_detail / D_00c.portal_leaderboard, both read role_aua) that treats nna_txn as a daily NNA the way it is treated for the canonical nna feed would render a cumulative-since-inception magnitude as if it were one day's net flow -- a materially inflated served advisor NNA number. Moot on cot today because the merge never fires (all-NA roles), so nothing is written.
- **Proposed fix:** If retaining the script, either rename the target to an unambiguous column (e.g. cum_nna_txn) or add an explicit contract/comment enforced at the consumer that role_aua.nna_txn is CUMULATIVE, so no consumer treats it as the canonical daily nna_txn.

## Finding 3 -- [low/other/both]
- **Location:** `_update_one_date L227-229 (source_filter_stack append)`
- **Mechanism:** The provenance update `rua_updated.loc[mask,'source_filter_stack'] = rua_updated.loc[mask,'source_filter_stack'].fillna('') + '_' + _FLOW_SOURCE_TAG` appends the tag unconditionally, without checking whether _FLOW_SOURCE_TAG ('p1c_flow_join_nna_atomic') is already present. The flow-column update itself is idempotent (it SETS from freshly recomputed flow_attr, not +=), but the provenance string is not.
- **Failure scenario:** On a firm/date where roles ARE populated, running --upload twice (or re-running after a C_01b re-backfill re-seeds source_filter_stack) yields source_filter_stack values like 'ra_p1b_backfill_p1c_flow_join_nna_atomic_p1c_flow_join_nna_atomic' -- the tag stacks once per run, bloating the provenance field and breaking any downstream exact-match/contains-count logic on source_filter_stack. Numbers are unaffected; provenance is corrupted. Does not fire on cot (no writes).
- **Proposed fix:** Make the append idempotent: only concatenate _FLOW_SOURCE_TAG when it is not already a substring of the existing source_filter_stack value (e.g. mask further on ~source_filter_stack.str.contains(_FLOW_SOURCE_TAG, na=False)).
