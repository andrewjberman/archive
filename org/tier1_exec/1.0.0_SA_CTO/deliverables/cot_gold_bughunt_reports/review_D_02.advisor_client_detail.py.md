## Finding 1 -- [high/schema-column/both]
- **Location:** `load_sources() fut_acct load L434-446 via private _load_parquet L97-105 (unwrapped future .result() at L468)`
- **Mechanism:** D_02 defines its OWN _load_parquet (L97-105) that passes columns= straight into pd.read_parquet(BytesIO(...)). This is NOT the COT-hardened lib.gold_utils._load_parquet, whose docstring explicitly states it schema-filters 'so a column filter never ArrowInvalids on a firm without advisor attribution' and names COT's missing implementor/architect. The fut_acct future (submitted L434, .result() L468 with NO try/except, unlike the wrapped _load_rel_lookup/_load_account_team/_load_fee_rates/_load_assignments_scd loaders) hard-requests 'implementor' from account_performance.parquet. A_00.accounts_dimension force-creates ONLY 'architect' (L495 accts.get('architect',...).fillna('Unassigned')); implementor/consultant/local_ops/additional_advisor survive only if cot silver transactions carry them, and C_03.account_performance column-guards its output (result[[c for c in final_cols if c in result.columns]] L354). Per the pipeline note, cot's cot_silver_merge.py produces NONE of these role columns. All OTHER unwrapped-load columns are safe: C_05 emits every requested tax field incl. short_term_gain/long_term_gain/total_accrued_gain/num_open_lots, A_04 guarantees primary_architect/primary_implementor, and C_03's cot-snapshot branch emits growth+aua_residual (L343-344). So 'implementor' is the single at-risk column.
- **Failure scenario:** If account_performance.parquet lacks the 'implementor' column (cot silver 'produces NONE of these role columns'), pd.read_parquet(BytesIO(body), columns=[...,'implementor',...]) raises pyarrow ArrowInvalid; fut_acct.result() re-raises inside load_sources() (unguarded) -> D_02 exits non-zero -> gold_dispatch.sh wait_phase PHASE_D3 prints 'FATAL' and exit 1 -> the no-timeout downstream chain ABORTS and D_04 (PHASE_D4) never runs, so NO D-layer served refresh completes. Currently likely MASKED: the context's own described mechanism (roles resolve to all-'Unassigned' then get excluded, yielding empty advisor books) requires the implementor column to EXIST populated with 'Unassigned', which means the read succeeds today. This is therefore a latent chain-abort that fires the moment the implementor column drops from account_performance (e.g. a silver schema change, or a first/rebuilt run of A_00 whose source lacked it).
- **Proposed fix:** Route the three currently-unwrapped core loads (ACCOUNT_PERFORMANCE, CLIENT_TAX_LIABILITY, CLIENT_DIMENSION) through the already-imported package's hardened lib.gold_utils._load_parquet (which reads pyarrow schema, requests only present columns, and adds missing requested columns as null), or replicate that present-column filter in the local _load_parquet; never hand a raw columns= list containing optionally-present role columns to pd.read_parquet. Ground against the live account_performance.parquet schema (head-object + pyarrow.read_schema) to confirm whether implementor is currently present (latent -> high) or already absent (currently-firing chain abort -> critical).

## Finding 2 -- [low/numeric-sign-units/full]
- **Location:** `build_advisor_books: ttm_pct L1350 vs ytd_growth_pct/qtd_growth_pct L1337-1340; emitted together in book['growth'] L1516-1522`
- **Mechanism:** ttm_pct = (ttm_nna / ttm_aua_start) is a raw FRACTION with no *100, whereas the sibling ytd_growth_pct and qtd_growth_pct both multiply by 100 ((total_aua - start)/start*100). All three are emitted in the same 'growth' object as ttm_pct / ytd_pct / qtd_pct with inconsistent units (fraction vs percent). The inline comment L1519 even labels it 'TTM growth %' while the code computes a fraction.
- **Failure scenario:** For an advisor with ttm_nna=+$1,000,000 on period-start AUA=$20,000,000, ytd_pct renders 5.0 (percent) but ttm_pct renders 0.05 (fraction); a consumer that renders ttm_pct as a percentage understates TTM growth by 100x (shows 0.05% instead of 5%). Dead-for-cot today (advisor books are empty because every role resolves to 'Unassigned' and is excluded), so not served on cot; it is a live served-number units bug on any firm with resolved advisors (the 49F origin this runner was cloned from).
- **Proposed fix:** Multiply ttm_pct by 100 to match ytd_pct/qtd_pct, or rename it to a fraction-typed field the frontend contract expects; keep all three growth ratios in one unit.
