## Finding 1 -- [high/unguarded-read/full]
- **Location:** `C_03.account_performance.py:156-157 (load_account_flows) -> lib/nna_flows.py:112-113 (load_flows_from_transactions)`
- **Mechanism:** load_account_flows() guards with `if flows is None or flows.empty`, but load_flows_from_transactions() NEVER returns None/empty on the no-input case -- it RAISES `RuntimeError("No transaction data found in silver layer.")` when the silver/transactions/ listing yields zero .parquet keys. The RuntimeError is not caught anywhere in C_03; it propagates out of load_account_flows() -> main() -> uncaught, so C_03 exits non-zero. The dispatcher runs every gold/silver compute step with NO timeout and HARD-FAILs the chain on any non-zero exit (wait_phase PHASE_C3 -> 'FATAL: aborting chain' -> exit 1). The local guard is dead code that gives false assurance the empty-input case is handled.
- **Failure scenario:** cot's silver/transactions/ prefix is empty or absent (new/ramping firm before transactions are ingested, a wiped/renamed prefix, or an isolated `--chain downstream`/`--single C_03` run where C_03 is the first caller). load_flows_from_transactions raises RuntimeError -> C_03 aborts with a non-zero exit -> gold_dispatch treats PHASE_C3 as FATAL and aborts the entire remaining chain, so no served account_performance.parquet and no downstream D_* portal artifacts are produced for the night.
- **Proposed fix:** Make C_03 degrade instead of abort: wrap the call as `try: flows = load_flows_from_transactions() except RuntimeError: flows = None` (then fall through to the existing empty-flows path), OR change nna_flows.load_flows_from_transactions to return an empty [date,account_id,daily_inflow,daily_outflow] DataFrame on empty keys instead of raising (matching the contract the C_03 guard already assumes).

## Finding 2 -- [medium/other/full]
- **Location:** `C_03.account_performance.py:231-232 (aua_prior/aua_change) + 239-258 (trailing-only completeness guard) in load_account_performance_from_snapshot`
- **Mechanism:** aua_prior = per-account shift(1) and aua_change = aua_current - aua_prior are computed over the FULL sorted snapshot series (lines 231-232). The completeness guard (239-258) scans dates from the newest backward and stops at the first date whose non-zero-MV fraction >= COMPLETENESS_NONZERO_FLOOR (0.5), dropping only the TRAILING incomplete dates. A mid-series all-$0 (unpopulated-price) snapshot day is therefore NOT excluded (the code comment at 236-238 explicitly acknowledges 'never drops a mid-series partial date'). That $0 day yields aua_change ~= 0 - prior_full (large negative) and the following day yields full - ~0 (large positive); growth = aua_change - nna inherits the same phantom swing.
- **Failure scenario:** A canonical_holdings/{D}.parquet older than B_00's `--force-recent-days 14` re-pull window was written during a BD same-day pull with prices unpopulated (all market_value=$0, the exact 06-23 class) and never re-pulled/corrected. In served account_performance, every account's growth/aua_change shows a firm-wide crash to ~$0 on day D and a full recovery on D+1, which D_04 client_portal_summary / D_00b timeseries surface as a phantom drawdown-and-rebound in the served portal charts.
- **Proposed fix:** Exclude ANY date below the non-zero-fraction floor (not just trailing ones) before computing aua_prior/aua_change -- e.g. filter gains to complete dates first, then compute the per-account shift over only complete snapshots -- so a mid-series $0 day cannot inject phantom deltas; alternatively prevent B_00 from ever persisting an all-$0 partition.

## Finding 3 -- [low/empty-null-handling/full]
- **Location:** `C_03.account_performance.py:246-256 (served_max selection in load_account_performance_from_snapshot)`
- **Mechanism:** served_max is initialized to _dates[-1] (the newest date). The loop only reassigns served_max when it finds a date with _nz_frac >= floor. If NO date meets the floor, the loop exhausts without a break, served_max remains _dates[-1], and the subsequent `if served_max != _dates[-1]` is False -> no filtering is applied -> the incomplete newest date IS served. The guard fails OPEN in the all-incomplete case, defeating its own purpose.
- **Failure scenario:** A systemic B_00 pricing outage where every persisted snapshot date has non-zero-MV fraction < 0.5 (total price-population failure). The completeness guard logs each date as INCOMPLETE but then serves the trailing $0 date anyway, so header/served AUA collapses toward ~$0 -- the precise served-AUA=$0 failure the guard was built to prevent, silently reintroduced when all dates are incomplete.
- **Proposed fix:** When the backward scan finds no complete date, fail LOUD (log ERROR and return None so C_03 no-ops rather than overwriting served with a $0 artifact) instead of falling through to serve _dates[-1].
