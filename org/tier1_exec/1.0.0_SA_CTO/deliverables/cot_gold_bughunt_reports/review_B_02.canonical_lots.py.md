## Finding 1 -- [critical/unguarded-read/full]
- **Location:** `B_02.canonical_lots.py:83-84 (S3_UNREALIZED_KEY / S3_REALIZED_KEY constants) consumed at :652 and :674 via unguarded _read_s3`
- **Mechanism:** B_02 reads the legacy rolling BD compact keys silver/unrealized/unrealized_gain_loss.parquet (line 652) and silver/realized/bd_realized_compact.parquet (line 674) with unguarded _read_s3 (no try/except, unlike build_cusip_bridge which wraps the SAME realized read at :164-179). No process in the current COT codebase writes either key: cot_silver_merge.py writes per-day silver/{unrealized,realized}/{date}.parquet (line ~432) and compacts to silver/cot_unrealized.parquet / silver/cot_realized.parquet (line ~600) -- never to unrealized_gain_loss.parquet or bd_realized_compact.parquet. Sibling script B_01._resolve_unrealized_key (:460-482) explicitly documents that unrealized_gain_loss.parquet 'froze on 2026-03-29' and was migrated to nearest-on-or-before per-day silver/unrealized/{d}.parquet; B_02 was never migrated. gold_freshness_config.yaml (:49-58, :84-92) monitors the silver/unrealized/ and silver/realized/ PREFIXES by max date-partition-key, so the fresh per-day partitions keep the freshness gate GREEN while B_02's specific compact object stays frozen -- the staleness is invisible to the gate.
- **Failure scenario:** SILENT: on a nightly full run, bd_unrealized = the 2026-03-29 frozen snapshot. Every BD-only (non-Schwab) account's lots_unrealized is built from March lot populations stamped with today's date; any position opened after the freeze is entirely absent and cost_basis/holding_type/days_held are stale. Realized lots for BD-only accounts likewise come from the frozen bd_realized_compact. CRASH: if the frozen leftover is ever lifecycle-expired/deleted, _read_s3 raises NoSuchKey -> main() try/except -> sys.exit(1); because the chain runner runs gold compute with NO timeout and hard-fails on any non-zero exit, B_02 aborts the whole chain (C/D never run).
- **Proposed fix:** Read the same source B_01 uses: resolve silver/unrealized/{date}.parquet (nearest on-or-before within N days) instead of unrealized_gain_loss.parquet, and use silver/cot_realized.parquet (or per-day silver/realized/{date}.parquet) for realized. Wrap both reads so an absent partition is a logged skip, not a chain-abort.

## Finding 2 -- [medium/other/full]
- **Location:** `B_02.canonical_lots.py:769 (bd_snapshot_date=pd.Timestamp('today').normalize()) feeding the bd_lots_valid gate at :296-301`
- **Mechanism:** bd_snapshot_date is hardcoded to today (the run date), not derived from the BD unrealized data's actual as-of date. build_unrealized_lots trusts it to decide bd_lots_valid: BD-only lots are emitted only when abs(date - snapshot) <= 7 days. Because the source is a snapshot/frozen file (Finding 1) or at best the prior business day, 'snapshot = today' is wrong, and the 7-day window is anchored to the wrong reference.
- **Failure scenario:** A backfill run (python B_02 --upload --start-date 2026-01-01) processes every date Jan..today with snapshot=today; for all dates older than 7 days, bd_lots_valid=False so build_unrealized_lots emits ZERO BD-only lots (:363-366) -> every BD-only account's lots_unrealized on all historical dates contains only Schwab lots, a silent under-count of served unrealized coverage. On the daily path it stamps frozen/lagging BD lots as valid-for-today.
- **Proposed fix:** Derive bd_snapshot_date from the data (a data_as_of column or max(open_date) on the unrealized file, or the resolved per-day partition date), not from Timestamp('today').

## Finding 3 -- [medium/type-issue/full]
- **Location:** `B_02.canonical_lots.py:666 (accts_full['account_is_open'] == False) building closure_map at :665-670, consumed at :449-450/:467/:497`
- **Mechanism:** account_is_open arrives as a STRING, not a bool: cot_silver_merge.py casts every object column to str via apply(lambda x: str(x) ...) when building silver/transactions (line ~398-400), so booleans become 'True'/'False'; A_00.accounts_dimension carries the column through (TXN_ACCOUNT_COLS) and save_dimension re-casts object->pandas 'string' (:626-629). Comparing a string Series to the Python bool False is element-wise always False, so `closed` is empty and closure_map is always {} -- the realized closure gate (realized_excluded) is a silent no-op for every COT account.
- **Failure scenario:** An account closed before a given closing_date is never added to realized_excluded, so its rows are never dropped from lots_realized. Any post-closure/backfilled closing row in the (frozen) bd_realized or Schwab RLD for such an account is served instead of excluded. No crash; the intended date-aware closure gate simply never fires.
- **Proposed fix:** Compare against the real dtype, e.g. closed = accts_full[accts_full['account_is_open'].astype(str).str.strip().str.lower().isin({'false','0','no','n'})], or coerce account_is_open to a genuine bool upstream in A_00.

## Finding 4 -- [medium/merge-dedup/full]
- **Location:** `B_02.canonical_lots.py:305 (alive-account gate isin) and :361 (Schwab-overlap exclusion); asymmetric vs the Schwab path at :333 and :463 which do .astype(str).str.strip()`
- **Mechanism:** bd_unrealized['account_id'] is used RAW everywhere (never string-normalized), whereas the Schwab path normalizes account_id to str and alive_accounts come from silver/allocations account_id which cot_silver_merge stringifies. If the frozen unrealized file stores account_id as int/float, the join-key dtypes mismatch: `bd['account_id'].isin(alive_accounts)` (str set) matches nothing and `bd_lots[~account_id.isin(schwab_accounts)]` (str set) excludes nothing.
- **Failure scenario:** Frozen unrealized file with numeric account_id + string alive set -> line 305 drops ALL BD-sourced lots (lots_unrealized silently loses the entire BD leg -> served under-count); simultaneously line 361 fails to exclude BD lots for Schwab-custodied accounts -> those accounts get both Schwab and BD lots (double-count). Dtype-dependent and raises no error.
- **Proposed fix:** Normalize on read, symmetric with the Schwab path: bd['account_id'] = bd['account_id'].astype(str).str.strip() before any isin/gate; likewise normalize the alive/closure sets.

## Finding 5 -- [low/schema-column/full]
- **Location:** `B_02.canonical_lots.py:313 (bd[['account_id','asset_name','cusip','ticker','open_date','unit_cost','lot_index']])`
- **Mechanism:** build_unrealized_lots hard-indexes bd_unrealized for cusip, ticker, unit_cost, open_date. build_cusip_bridge (:151) defensively probes for a cusip column case-insensitively and tolerates its absence -- showing the author knew cusip may be absent/renamed -- but the lots builder does not guard it. The unrealized silver dedup contract (cot_silver_merge dedup_cols: account_id/asset_name/open_date/unit_cost) does NOT guarantee cusip or ticker.
- **Failure scenario:** If the frozen/rebuilt unrealized file lacks 'cusip' or 'ticker' (or uses a different casing than lowercase), line 313 raises KeyError -> main() -> sys.exit(1) -> the no-timeout chain hard-aborts at B_02.
- **Proposed fix:** Select defensively (reindex/.get with NaN default) or validate required columns up front with an explicit error, mirroring the bridge's case-insensitive cusip probe.
