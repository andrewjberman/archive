## Finding 1 -- [high/other/full]
- **Location:** `build_canonical_prices_v2.py:584 (build_canonical, Step 5b share-class denomination check)`
- **Mechanism:** The Step 5b invariant guard filters `t1_rows = canonical[canonical['source'] == 't1_transaction_observed']`, but resolve_prices_for_asset never emits that label. The only source values ever written are 'yahoo_finance', 'transaction_observed', 'transaction_observed_capped', 'linear_interpolation', 'carry_forward', and None (lines 414/419/420/425/426/437/444/450). Because 't1_transaction_observed' matches zero rows, `t1_rows` is ALWAYS empty, so `if not t1_rows.empty:` (line 585) is always False and the whole ratio/FATAL block (lines 586-609) is unreachable dead code. The safety net that is explicitly documented (lines 578-582) to 'detect ticker_lookup misassignments where canonical_price is on a different share-class denomination' and to raise RuntimeError on a >10x/<0.1x mismatch NEVER runs.
- **Failure scenario:** A YF_OVERRIDES/TICKER_CORRECTIONS entry maps a mutual-fund share class to the wrong-denomination ETF ticker (exactly the bug class the corrections table already fixed, e.g. VANGUARD TOTAL BOND ...INDEX I bought at ~$9.50 NAV but mapped to BND ETF at ~$73). T2 (yahoo) becomes primary and canonical price jumps ~7.7x vs the transaction-observed ~$9.50. The guard was designed to catch this and abort the run with FATAL; instead it silently passes, canonical_prices.parquet ships the ~$73 price, and A_03.positions_cube prices those holdings ~7.7x too high -> materially inflated served holdings value / AUA with no error.
- **Proposed fix:** Change line 584 to filter the actual labels: `t1_rows = canonical[canonical['source'].isin(['transaction_observed','transaction_observed_capped'])]`. Then re-verify the ratio thresholds behave against real T1 medians on a scheduled nightly artifact.

## Finding 2 -- [medium/unguarded-read/full]
- **Location:** `build_canonical_prices_v2.py:283 (load_historical_prices) and :298 (load_ticker_lookup)`
- **Mechanism:** Both loaders call `s3.get_object(...)` with no try/except (silver/historical_prices.parquet at line 283; config/ticker_lookup.json at line 298). A missing key raises botocore NoSuchKey, which propagates to main() (line 647) -> prints FATAL, returns 1. S_00 (silver-prep) runs as the FIRST step of the nightly `full` chain, BEFORE the freshness gate, invoked via run_chain under `set -e` (gold_dispatch.sh lines 1070-1083). A non-zero S_00 exit therefore aborts the ENTIRE nightly before any A/B/C/D gold script runs.
- **Failure scenario:** First run against a freshly-provisioned opal-data-cot bucket (cot was cloned from bd) where config/ticker_lookup.json was not yet seeded, or a day when the upstream Yahoo/T2 silver builder has not yet produced silver/historical_prices.parquet. get_object raises NoSuchKey -> S_00 FATAL rc=1 -> `set -e` aborts the full chain at the silver-prep pre-gate; the whole gold layer is skipped for the night with only a FATAL in the silver-prep log.
- **Proposed fix:** Wrap each get_object in try/except ClientError; on NoSuchKey treat T2 as an empty frame (T1-only pricing) and ticker_lookup as an empty dict overlaid by YF_OVERRIDES/TICKER_CORRECTIONS, logging WARN instead of aborting the chain.

## Finding 3 -- [medium/merge-dedup/full]
- **Location:** `build_canonical_prices_v2.py:514-517 (T2 yahoo merge) and :566 (no dedup before write)`
- **Mechanism:** `yahoo_join = yahoo[['ticker','date','close']]` is merged onto the spine with `how='left'` on (ticker, date) with no prior drop_duplicates. If silver/historical_prices.parquet contains more than one row for the same (ticker, date), each spine date fans out to N rows. Those duplicate dates survive resolve_prices_for_asset (set_index('date') yields a duplicated DatetimeIndex; interpolate/ffill/boolean-assign still return one row per input index entry), and the final canonical is only sort_values'd (line 566), never de-duplicated on (date, asset_name), before writing to S3.
- **Failure scenario:** historical_prices has 2 rows for (DIVZ, 2026-07-06) (e.g. an un-deduped append or a duplicated vendor pull). Every asset mapping to DIVZ gets 2 canonical rows per date. Downstream A_03.positions_cube joins holdings to canonical_prices on (date, asset_name); the duplicate price rows fan out the position rows, double-counting that holding's market value into served AUA.
- **Proposed fix:** Add `yahoo_join = yahoo_join.drop_duplicates(['ticker','date'], keep='last')` before the merge (line 517) and/or `canonical = canonical.drop_duplicates(['date','asset_name'], keep='last')` before sort_values/write (line 566).

## Finding 4 -- [low/other/full]
- **Location:** `build_canonical_prices_v2.py:428-437 then 446-450 (resolve_prices_for_asset, T1 staleness cap vs T4 carry_forward)`
- **Mechanism:** The T1 staleness cap sets `price[stale_mask] = np.nan` and `source[stale_mask] = None` for dates more than T1_STALENESS_DAYS (365) after the last T1 observation (line 436-437), intending (docstring lines 401-404) to stop 'decade-old purchase prices from dominating'. But T3 interpolate cannot fill trailing NaNs (no bracketing future point) and T4 `price.ffill()` (line 447) immediately re-carries the last valid (stale) T1 price forward across those same dates, relabeled 'carry_forward'. The demotion changes only the source label, not the value.
- **Failure scenario:** A no-Yahoo asset last transacted 3 years ago at $40. Spine extends to today. Dates beyond last_t1+365 are set NaN by the staleness cap, then ffill re-fills them all with $40 labeled carry_forward. The stated goal (demote/stop the stale price) is not achieved; the $40 still prices every subsequent day. No numeric corruption beyond the pre-existing carry-forward behavior, but the guard is effectively inert.
- **Proposed fix:** If true demotion is intended, exclude stale-demoted dates from the T4 ffill (e.g. cap ffill with a limit, or leave stale trailing dates unpriced so downstream treats them as no-price) rather than relying on a source relabel; otherwise remove the dead staleness block to avoid implying a control that does not exist.
