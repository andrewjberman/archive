## Finding 1 -- [critical/type-issue/full]
- **Location:** `data/cot/scripts/gold/B_01.holdings_lots.py:2685 (build_holdings_lots_snapshot, phantom-reconciliation Rule 3; comparison set built at L2645)`
- **Mechanism:** Gate-3 builds `_unrl_accts_with_positions = set(_unrl_gate3['account_id'].astype(str).str.strip().unique())` (a set of STRINGS). The reconciliation loop iterates `acct_id` from `lot_mv_by_acct = df[open_mask].groupby('account_id')...` whose index is df['account_id'] in its RAW silver dtype -- and it is NOT normalized before the membership test `acct_id not in _unrl_accts_with_positions` (L2685). COT's silver producer only stringifies OBJECT columns: cot_silver_merge.py L398-400 does `if df[col].dtype == 'object': df[col] = str(x)` -- a numeric BD account_id column (int64/float64) is left numeric. Sibling A_00 L480 defensively `.astype(str)` account_id at its own set sites, corroborating that raw silver account_id is not guaranteed str. When account_id is numeric, a numeric `acct_id` is never `in` a set of strings, so `silver_absent` evaluates True for EVERY account; `if bd_zeroed or bd_diminished or silver_absent:` then force-closes ALL open lots (is_open=False; current_units/market_value/cost_basis/accrued_gain zeroed).
- **Failure scenario:** silver/transactions account_id arrives as int64/float64 (BD DataMining xlsx account_id cells are numeric, so cot_silver_merge L398-400 leaves them numeric) and the Gate-3 silver/unrealized read succeeds (so `_unrl_accts_with_positions is not None`). Every account -- including accounts genuinely open in silver/unrealized -- is flagged silver_absent and force-closed. Served gold/timeseries/holdings_lots/{date}.parquet ends with ~0 open lots and the downstream C_*/D_* chain serves ~$0 AUA / empty holdings. Silent (no crash, chain still exits 0). Could not verify the LIVE silver account_id dtype from here (no S3); grounded on producer code (cot_silver_merge L398-400) that permits a numeric account_id and on the sibling defensive `.astype(str)` pattern.
- **Proposed fix:** Normalize both sides identically. Cast df['account_id'] to `.astype(str).str.strip()` once at ingest in load_transactions (so the lot frame, lot_mv_by_acct index, and all downstream keys are str), OR compute `acct_id_norm = str(acct_id).strip()` inside the loop and test membership on that. Same normalization must be applied wherever the reconciliation/gate sets are compared.

## Finding 2 -- [high/type-issue/full]
- **Location:** `data/cot/scripts/gold/B_01.holdings_lots.py:2404 (_apply_silver_noncash_cap apply step; scale_by_acct keys built at L2370-2389)`
- **Mechanism:** The confidence-tiered cap builds `scale_by_acct` keyed by RAW account_id (`acct = row.account_id` from cls_mv, which derives from df['account_id'] -- numeric when silver account_id is numeric). It then APPLIES the scale via `acct_s = df['account_id'].astype(str).str.strip(); scale_series = acct_s.map(scale_by_acct).fillna(1.0)` (L2403-2404). str keys never match numeric dict keys, so `.map` yields all-NaN -> fillna(1.0) -> scale 1.0 -> zero compression. Note the COMPUTE step works (silver_nc_map from allocations is numeric-keyed and matches the numeric acct), so n_fired>0 is reported in the log while nothing is actually scaled.
- **Failure scenario:** account_id numeric: the cap logs `accounts-fired=N` (>0) but the B/C phantom-FIFO lots are never scaled down to the silver noncash ceiling -> served market_value over-counts phantom positions. Today this is masked by Finding #1 (Rule 3 has already force-closed all open lots, so open_mask is empty and the cap returns early at L2303) -- but it becomes the live over-count the instant Finding #1 is fixed without also fixing this apply-side key mismatch.
- **Proposed fix:** Key scale_by_acct with the SAME normalization used at apply time -- store `scale_by_acct[str(acct).strip()] = scale` -- or normalize df['account_id'] to str once globally so compute-side and apply-side keys are identical.

## Finding 3 -- [medium/merge-dedup/full]
- **Location:** `data/cot/scripts/gold/B_01.holdings_lots.py:199 (_enrich_tickers merge)`
- **Mechanism:** The lot frame is left-merged to gold/dimensions/ticker_resolution.parquet on `_asset_name_norm == asset_name_normalized` (L199-204) WITHOUT deduplicating the resolution table on the join key. resolution is read with only ['asset_name_normalized','resolved_ticker'] and never `.drop_duplicates`. If ticker_resolution carries >1 row per asset_name_normalized (a name resolving to multiple candidate tickers / multiple vintages), every lot row of that asset fans out to N rows. Contrast load_latest_prices (L356-357), which explicitly dedups its join key.
- **Failure scenario:** gold/dimensions/ticker_resolution.parquet has 2 rows for one normalized asset_name -> each lot of that asset is duplicated post-merge -> current_units/market_value/cost_basis are double-counted in every downstream aggregate (inflated served AUA, duplicate lot_ids in gold/timeseries/holdings_lots). Fires on every full run whenever the resolution table has a duplicate normalized key; independent of the account_id dtype question.
- **Proposed fix:** Deduplicate before merging: `resolution = resolution.drop_duplicates('asset_name_normalized', keep='last')` (matching the intent of the COALESCE), and/or assert 1:1 on the join key.

## Finding 4 -- [low/numeric-sign-units/full]
- **Location:** `data/cot/scripts/gold/B_01.holdings_lots.py:2217 (_apply_rps_price_override bond_mask / adjusted_price at L2217-2221)`
- **Mechanism:** Bond (percent-of-par) detection is keyed purely on `cost_per_unit <= 2.0` (L2217), then `adjusted_price[bond_mask] = new_price[bond_mask] / 100.0` (L2221) and market_value is recomputed. A `non_unitized` lot has cost_per_unit forced to exactly 1.0 at L2603 (BD dollar-as-units convention, price should stay $1), and genuine low-priced equities/funds ($1-2 NAV) also satisfy cost_per_unit<=2.0. Any such lot whose (account_id, cusip) is present in the RPS closing_price lookup is mis-classified as a bond and repriced closing_price/100, corrupting the deliberately-set $1 non_unitized price (and mis-scaling low-priced equities by 100x).
- **Failure scenario:** A non_unitized lot (current_units == dollar value, price $1) whose cusip has an RPS closing_price of e.g. $50 -> bond_mask fires -> current_price 0.50 -> market_value = 0.5*current_units instead of 1.0*current_units (~50% undercount of that position's served MV). Double-gated: requires COT to actually have a schwab/silver/rps partition (else _build_rps_context raises, rps_context is None, and _apply_rps_price_override returns at L2192 -- likely a no-op if Cottonwood has no Schwab custodial feed) AND a low-cost lot with RPS cusip coverage.
- **Proposed fix:** Exclude price_quality=='non_unitized' (and the $1-forced mask) from bond reclassification, and drive bond detection from an explicit instrument-type / asset-class flag rather than a cost_per_unit price threshold.
