## Finding 1 -- [high/schema-column/both]
- **Location:** `data/cot/scripts/gold/E_24.rebuild_fee_scorecard.py:54 (_build_window, latest_by_advisor groupby.agg)`
- **Mechanism:** E_24 aggregates current-snapshot AUA via `aua=('managed_aua','sum')` UNCONDITIONALLY (line 54), and again references managed_aua at lines 63-77 (agg_cols, fee_bps_weighted, advisor_effective_bps, effective_split_pct). The producer of advisor_fee_detail, C_08.advisor_fee_efficiency.py, writes col_order = ['date','advisor','role','account_count','total_aua','implied_daily_fee','implied_annual_fee','nna_daily','inflow_daily','outflow_daily','growth_daily','nna_yield_ann'] (C_08 line 810-814) -- there is NO managed_aua column (grep confirms managed_aua exists only in D_04 and E_24, never in the fee-detail producer). pandas named aggregation with a non-existent source column raises KeyError. E_24 is a bd-clone artifact carrying bd's sleeve managed_aua/total_aua split, which cot's C_08 never produces.
- **Failure scenario:** Run E_24 (--upload or --dry-run) against any NON-EMPTY advisor_fee_detail (e.g. after cot silver gains role columns, or if run against bd data): the first window's latest_day.groupby('advisor').agg(aua=('managed_aua','sum'), ...) at line 54 raises `KeyError: "Column(s) ['managed_aua'] do not exist"`, which propagates out of main() -> sys.exit(non-zero). The whole rebuild fails. On cot TODAY the advisor layer is empty so the list is empty and E_24 returns 1 at line 190-192 BEFORE reaching line 54 -- masking the bug entirely; the moment any advisor_fee_detail partition lands, E_24 hard-crashes. (E_24 is not in gold_dispatch.sh, so this crash does not abort the nightly chain -- blast radius is the ad-hoc rebuild only.)
- **Proposed fix:** Rename the source column to the one C_08 actually emits: line 54 -> aua=('total_aua','sum'). The managed_aua/total_aua sleeve branch (lines 62-84) is a bd-only concept -- for cot, derive fee_bps_weighted from total_aua (as C_08 does at line 254-256) and drop the advisor_effective_bps/effective_split_pct managed-vs-total split, OR guard every managed_aua reference behind `if 'managed_aua' in latest_day.columns` with a total_aua fallback.

## Finding 2 -- [medium/other/both]
- **Location:** `data/cot/scripts/gold/E_24.rebuild_fee_scorecard.py:98-108 (efficiency_pctile) and 68-77 (fee_bps_weighted) vs C_08 lines 276-320 / 248-257`
- **Mechanism:** E_24 writes the SAME served artifact as the nightly C_08 (gold/artifacts/advisor_fee_efficiency.json, ADVISOR_FEE_EFFICIENCY) but computes two key served numbers with a DIFFERENT algorithm. (a) efficiency_pctile: E_24 is single-tier -- only advisors with nna>0 are ranked via (1 - rank(ascending=True,pct=True))*100 clipped to 1..100, and every zero/negative-NNA advisor gets 0 (line 98-108). C_08 is TWO-tier: negative/zero-NNA advisors get a differentiated pctile in [0, pct_tier2*100] and positive-NNA advisors in [pct_tier2*100, 100] (C_08 line 288-320). (b) fee_bps_weighted: E_24 = annual_fee/managed_aua*1e4 (line 68-70); C_08 = annual_fee/total_aua*1e4 (line 254-256). Running E_24 --upload therefore replaces the served scorecard with materially different pctile and fee numbers than the pipeline's own C_08 regeneration.
- **Failure scenario:** An operator reaches for E_24 ('Rebuild Fee Efficiency Scorecard ... No gold pipeline needed') to refresh the served fee scorecard and runs it with --upload. It overwrites advisor_fee_efficiency.json with single-tier efficiency_pctile (all non-positive-NNA advisors flattened to 0) and managed_aua-based fee_bps -- silently disagreeing with the portal's expectation and with the next nightly C_08 run, which flips the numbers back (flapping served values). This is gated behind finding #1 on cot today (E_24 crashes before writing), so it only materializes once the managed_aua schema bug is 'fixed' without also reconciling the algorithm -- a classic fix-one-bug-expose-the-next trap.
- **Proposed fix:** Do not ship a schema-only fix for E_24 in isolation. Either retire E_24 for cot (it is not chain-registered and is fully superseded by C_08.build_scorecard), or port C_08's two-tier efficiency_pctile and total_aua-based fee_bps into E_24 verbatim before it is ever allowed to run with --upload, so a rebuild is byte-comparable to the nightly output.

## Finding 3 -- [low/empty-null-handling/both]
- **Location:** `data/cot/scripts/gold/E_24.rebuild_fee_scorecard.py:200-212 (dfs assembly + pd.concat)`
- **Mechanism:** Line 206 appends only non-empty frames (`if not df.empty: dfs.append(df)`). The only emptiness guard is `if not keys: return 1` at line 190 (covers zero listed partitions). There is NO guard for the case where keys are listed but every loaded parquet is an empty DataFrame -- then dfs == [] and line 212 pd.concat(dfs, ignore_index=True) raises ValueError: 'No objects to concatenate'.
- **Failure scenario:** advisor_fee_detail/ contains one or more present-but-empty parquet objects (e.g. a hand-placed placeholder, or a future producer that writes an empty partition): keys is non-empty so the line-190 guard passes, dfs stays empty, and pd.concat([]) at line 212 raises ValueError -> non-zero exit. Low likelihood because the current C_08 only writes non-empty date groups (never emits an empty partition), so this is a defensive gap rather than a live trigger.
- **Proposed fix:** Add `if not dfs: log('ERROR: all fee-detail partitions empty'); return 1` immediately before the pd.concat at line 212.
