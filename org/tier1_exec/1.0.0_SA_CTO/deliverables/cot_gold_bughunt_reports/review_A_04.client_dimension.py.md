## Finding 1 -- [medium/empty-null-handling/full]
- **Location:** `data/cot/scripts/gold/A_04.client_dimension.py:129 (load_transactions_summary, concat of the per-partition frames)`
- **Mechanism:** keys is built by listing s3://opal-data-cot/silver/transactions/*.parquet (lines 99-103). dfs = [None]*len(keys) then df = pd.concat(dfs, ignore_index=True). When the prefix returns ZERO parquet objects, keys=[] -> dfs=[] -> pd.concat([]) raises ValueError('No objects to concatenate'), which is uncaught and aborts the whole gold chain (gold/silver compute steps run with no timeout and hard-fail on any non-zero exit).
- **Failure scenario:** First cot gold run before any silver/transactions partition exists, or the prefix is empty/renamed/mis-scoped (e.g. a silver rebuild wiped partitions). load_transactions_summary() throws ValueError before returning -> A_04 sys.exit != 0 -> CHAIN_FULL aborts at PHASE_A2. Note the code AT lines 262, 275 and 282-283 explicitly guards `len(txn_summary) == 0` (active_accts = set()) -- proving the author intended an empty-transactions run to be tolerated -- but that guard is DEAD because the empty case crashes in the loader first and can never reach build_client_dimension.
- **Proposed fix:** Guard the empty-keys case in load_transactions_summary before concat: `if not keys: return pd.DataFrame(columns=TARGET_COLS + ['trade_date'])` (or `dfs = [d for d in dfs if d is not None]; if not dfs: return empty-with-trade_date`), letting the existing len==0 guards downstream take over.

## Finding 2 -- [medium/type-issue/full]
- **Location:** `data/cot/scripts/gold/A_04.client_dimension.py:280-285 (active_accts derivation + accts['is_active'] = accts['account_id'].isin(active_accts))`
- **Mechanism:** active_accts = txn_summary['account_id'].unique() is typed by the RAW silver/transactions account_id dtype (A_04 reads that parquet with only a column subset, no cast). accts['account_id'] is typed by whatever A_00 wrote into accounts_dimension_latest.parquet. pandas .isin() compares by (dtype-sensitive) value equality: if one side is int64 and the other is object/str, .isin() silently returns ALL-FALSE with no error or warning. A_04 is the ONLY consumer in the cot gold tree that compares account_id across two independently-loaded artifacts WITHOUT the estate-wide normalize-to-str convention (`account_id = account_id.astype(str).str.strip()`) used in A_03/A_05/B_00/B_01/B_02/C_06/D_00/D_00c/D_01/D_02/D_04) -- i.e. the codebase already treats account_id dtype as unreliable everywhere except here.
- **Failure scenario:** Cottonwood account numbers are numeric in some silver/transactions partitions (read as int64) but A_00 upcasts account_id to object when it appends snapshot-only accounts (A_00 does account_id.astype(str) at lines 480-481 precisely because the snapshot source types account_id as str), so accounts_dimension.account_id is object while A_04's txn_summary.account_id is int64 (or vice-versa) -> `accts['account_id'].isin(active_accts)` is all-False -> is_active all-False -> active_accounts sums to 0 for EVERY household. The served client_dimension then reports active_accounts=0 firm-wide (and any downstream 'active households' portal number reads 0), silently, with the chain exiting rc=0.
- **Proposed fix:** Normalize both sides before the membership test, matching the rest of the tree: `active_accts = set(txn_summary[mask]['account_id'].astype(str).str.strip())` and `accts['is_active'] = accts['account_id'].astype(str).str.strip().isin(active_accts)`.

## Finding 3 -- [medium/schema-column/full]
- **Location:** `data/cot/scripts/gold/A_04.client_dimension.py:375 (dim.merge(tl[['relationship_id','first_seen_date','relationship_name','client_name']], ...))`
- **Mechanism:** tl is assembled conditionally (lines 240-259): first_seen_date is added only if accounts has relationship_first_seen_date; relationship_name only if accounts has relationship_name OR relationship_display_name; client_name only if accounts has account_owner. But line 375 HARD-selects all four columns from tl with no presence guard. A_00 emits account_owner/relationship_name/relationship_first_seen_date through an OPTIONAL filter (`available = [c for c in output_cols if c in accts.columns]`, A_00 line 588) and sources them from the BD transaction export (TXN_ACCOUNT_COLS), so any of them can be absent from accounts_dimension. Producer treats these columns as optional; consumer treats them as mandatory -> KeyError('[...] not in index') on the select, uncaught, aborting the chain.
- **Failure scenario:** A Cottonwood Black Diamond export drops or renames the account_owner column (or relationship_name) for a period -> cot_silver_merge/A_00 omit it from accounts_dimension via the `available` filter -> A_04 reaches line 375, tl has no 'client_name' (or 'relationship_name') column -> `tl[[...,'client_name']]` raises KeyError -> A_04 exits non-zero -> CHAIN_FULL aborts at PHASE_A2. (The txn-fallback at 262 only rebuilds tl when first_seen_date is absent, so it does not cover the relationship_name/account_owner-absent case when relationship_first_seen_date IS present.)
- **Proposed fix:** Select only the columns actually present: `cols = [c for c in ['relationship_id','first_seen_date','relationship_name','client_name'] if c in tl.columns]; dim = dim.merge(tl[cols], on='relationship_id', how='left')`, then default-fill any missing target columns (client_name/relationship_name -> '', first_seen_date -> pd.NaT) after the merge.
