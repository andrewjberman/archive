## Finding 1 -- [critical/numeric-sign-units/full]
- **Location:** `data/cot/scripts/gold/D_01.partner_analytics.py:1703 (build_cla_view; corrupt period_nna feeds _build_cla_segments/_lifecycle_bucket/_build_cla_totals at :1750-1847)`
- **Mechanism:** `nna` in the derived relationship frame is a DAILY net-flow value, not cumulative. `_derive_relationship_perf` (:347) sets g['nna']=g['aua_residual'] where C_03 documents/derives aua_residual = daily NNA = daily_inflow-daily_outflow (C_03.account_performance.py:32-33,338-344), summed only across accounts within one date (no temporal cumsum). cum_inflows/cum_outflows ARE cumulative-since-inception (C_03 cumsum at :164-165,332-333). build_cla_view then computes period_nna = merged['nna'] - merged['nna_start'] -- a cumulative-difference formula applied to a DAILY column -- while computing period_inflows/period_outflows CORRECTLY as cumulative diffs on the two adjacent lines. So period_nna = (net flow on end date) - (net flow on start date), which is not a period NNA at all. Unlike the NNA donut views (build_nna_geo/adv_view), CLA never uses canonical NNA, so this is unconditional on every run.
- **Failure scenario:** Current quarterly period: end=ref_date, start=last quarter-end. True quarter NNA (shown by the NNA-by-State donut, which uses canonical windowed sums) might be +$5M, but views.cla.current.geo.totals.nna sums only two single days' net flows -> e.g. -$40K. Every served CLA number is wrong and internally inconsistent (bucket.nna != bucket.inflows - bucket.outflows because inflows/outflows are cumulative-correct while nna is daily-noise): totals.{nna,nmnc_nna,nmec_nna} and per-segment nna_total in all three JSONs (header_metrics_{quarterly,monthly,annual}.json). nna_total also drives segment ranking (sort_values by abs) and the top-8 cut at :1778-1782, so which states/architects even appear is corrupted. No crash -- silent.
- **Proposed fix:** Compute period NNA from the cumulative flow diffs already present: `merged['period_nna'] = merged['period_inflows'] - merged['period_outflows']`, OR source per-relationship period NNA from canonical_nna via _period_nna_by_relationship() exactly as the NNA donut views do. Never diff the DAILY `nna` column with a cumulative-difference formula.

## Finding 2 -- [high/empty-null-handling/full]
- **Location:** `data/cot/scripts/gold/D_01.partner_analytics.py:1688-1701 (build_cla_view cp_start on raw start_ts); same missing-fallback pattern in build_nna_geo_view :1361-1375 and build_nna_adv_view :1548-1562`
- **Mechanism:** cp_start = client_perf[client_perf['date']==start_ts] filters on the RAW period-boundary start_ts with no nearest-prior-trading-day fallback -- even though generate_header_metrics builds exactly such a fallback (_cp_date_fallback) for cp_end/cp_day but never applies it to start_ts. When start_ts is a non-trading day, cp_start is empty; the how='left' merge then leaves inflows_start/outflows_start NaN -> fillna(0) -> period_inflows/period_outflows = the full cumulative-since-inception totals, massively overstated. Month-ends land on weekends very frequently (2025-08-31 Sun, 2025-11-30 Sun, 2026-05-31 Sun ...), and for cot's short history (data starts 2026-04-22) any start_ts before that date is also absent.
- **Failure scenario:** Monthly granularity, current period: start=m1=last completed month-end. If that month-end is a weekend/holiday (recurs most months), cp_start is empty -> every relationship's current-period CLA inflows/outflows become its entire inception-to-date cumulative flow, inflating header_metrics_monthly.json current-period CLA (and the NNA-view fallback distributions when canonical is absent) by up to ~100x. cp_end for the current period is ref_date (a real trading day) so the period is NOT skipped -- it silently serves the inflated numbers.
- **Proposed fix:** Resolve start_ts through the same nearest-prior-trading-day map (_cp_date_fallback / a client_perf-date lookup) before selecting cp_start, and pass the resolved start date into build_cla_view / the NNA fallbacks. Explicitly guard the pre-history case (start_ts < min(available dates)) instead of letting the baseline default to 0.

## Finding 3 -- [medium/empty-null-handling/full]
- **Location:** `data/cot/scripts/gold/D_01.partner_analytics.py:2369 (ref_date = client_perf['date'].max()) -> get_periods -> _get_periods_quarterly :172-179 (ref_date.month / pd.Timestamp(dt.year,...))`
- **Mechanism:** client_perf is DERIVED from account_performance via _derive_relationship_perf, which returns an empty frame if account_performance is empty or has zero relationship-mapped rows (the notna/!= ['','None','nan','NaN'] filter at :325 drops all rows). client_perf['date'].max() on an empty frame is NaT; _get_periods_* then evaluates NaT.month (nan) and pd.Timestamp(NaT.year, 9, 30) where NaT.year is nan -> Timestamp(nan,...) raises ValueError. Uncaught -> non-zero exit -> the no-timeout gold chain HARD-ABORTS (taking down remaining D_02/D_03/D_04).
- **Failure scenario:** A full-chain run where C_03 emits an empty/all-unmapped account_performance (e.g. an upstream snapshot no-op, or all accounts lacking relationship_id during a new-account recording lag) -> D_01 crashes with a Timestamp(nan) ValueError deep in get_periods instead of degrading gracefully, aborting the downstream chain.
- **Proposed fix:** After deriving client_perf, guard: `if client_perf.empty or pd.isna(ref_date): print('WARN: no relationship-mapped performance'); write empty/prior payload and sys.exit(0)` before calling get_periods.

## Finding 4 -- [medium/numeric-sign-units/full]
- **Location:** `data/cot/scripts/gold/D_01.partner_analytics.py:754-760 (_compute_rel_period_nna fallback branch)`
- **Mechanism:** Latent variant of Finding 1: when canonical_nna is empty/absent, the fallback computes period_nna = merged['nna'] - merged['nna_start'] using the same DAILY-vs-cumulative error, corrupting the per-relationship NNA distribution histograms (distribution.total + distribution.by_segment) in build_nna_geo_view and build_nna_adv_view. cot normally produces canonical NNA (C_01.canonical_nna.py runs in CHAIN_CANONICAL) so the donut totals use the correct windowed path, but the distribution fallback silently activates whenever gold/canonical/nna/ has no partitions.
- **Failure scenario:** A run where gold/canonical/nna/ is empty (C_01 not yet run / first run / prefix empty) -> _load_canonical_nna returns an empty frame -> every NNA distribution's percentiles + histogram are computed from two-day net-flow noise instead of true period flows. Silent (no crash).
- **Proposed fix:** Derive the fallback period_nna from cum_inflows/cum_outflows diffs (period_inflows - period_outflows) rather than diffing the daily `nna` column, matching the correct cumulative fields.

## Finding 5 -- [low/unguarded-read/full]
- **Location:** `data/cot/scripts/gold/D_01.partner_analytics.py:364-390 (load_data _read for acct_perf, acct_dim, client_dim, geo_ts, adv_ts via ThreadPoolExecutor)`
- **Mechanism:** The five core S3 reads have NO try/except, unlike REL_ARCHITECT_LOOKUP (:399-405), ACCOUNT_TEAM (:410-414), and canonical NNA (:472-484) which all fall back gracefully on absence. A missing key raises boto3 NoSuchKey, which the ThreadPool future.result() re-raises through load_data -> generate_header_metrics -> main uncaught -> non-zero exit -> no-timeout chain hard-fails with an opaque error.
- **Failure scenario:** gold/views/nna_aua_by_advisor.parquet or nna_aua_by_geography.parquet (produced by D_00, an in-chain predecessor) is missing -- e.g. D_00 failed/was skipped, or an operator runs `--from D_01` / `--group D` without D_00 first -> D_01 aborts with NoSuchKey instead of a graceful skip. Lower probability in a normal chain:full run since D_00 precedes D_01, but partial/group runs or a D_00 failure strand it.
- **Proposed fix:** Wrap the five core _read calls with explicit existence checks / graceful degradation (or a clear pre-flight assertion listing the missing key), matching the optional-table fallback pattern already used elsewhere in load_data.
