## Finding 1 -- [medium/merge-dedup/both]
- **Location:** `data/cot/scripts/gold/E_01.account_quality_tiers.py:215 (acct = gold_acct.merge(silver_acct, on='account_id', how='inner'))`
- **Mechanism:** The final join is INNER on account_id between gold_acct (accounts present in positions_cube) and silver_acct (accounts present in silver allocations). positions_cube (A_03) contains only rows with units>0 and A_03 explicitly excludes BD-zeroed / BKF-capped / liability-only accounts, so its account set is a strict SUBSET of silver's. Any account that exists in silver allocations but has no units>0 position in the cube is silently dropped from the tier output entirely -- it never appears, not even as tier F ('Unresolved'), which is the exact tier meant to flag accounts gold cannot resolve. The careful outer-join coverage computation (pos_compare, n_missing) is undone for fully-missing accounts because their coverage row is discarded by this inner join.
- **Failure scenario:** Account X has account_market_value=$250k across 4 positions in silver/allocations/{date}.parquet, but BD zeroed it (or all its positions have units<=0), so A_03 wrote no cube row for X. gold_acct lacks X -> inner join drops X. The JSON summary's total_accounts, per-tier counts, and the 'Position-trustworthy (A+B)' / 'AUA-trustworthy (A-C2)' percentages (lines 282-289) are all computed over a denominator that already excludes the worst accounts, overstating data quality, and X's $250k silver AUA is omitted from every tier bucket -- a silent, materially-misleading quality report whenever the script is run.
- **Proposed fix:** Use a how='outer' (or how='right' on silver_acct as source-of-truth) join, fill gold_mv=0 / n_cube_positions=0 / pct_covered=0 for silver-only accounts, and let them fall through assign_tier to 'F' so entirely-missing accounts are counted as unresolved rather than dropped.

## Finding 2 -- [medium/empty-null-handling/both]
- **Location:** `data/cot/scripts/gold/E_01.account_quality_tiers.py:283 and :287 (len(trustworthy)/total*100 and len(usable)/total*100)`
- **Mechanism:** total = len(acct) is the row count AFTER the inner join at line 215. The per-tier pct_of_total at line 272 is guarded (only reached when n>0, which implies total>0), but the two summary lines divide by total with no zero guard. When the inner join yields zero rows (total==0), both lines raise ZeroDivisionError, which propagates to the top-level except (lines 353-357), prints 'ERROR: 05f failed: division by zero', and sys.exit(1). total==0 whenever gold_acct and silver_acct share no account_id -- an empty positions_cube for the date, a date whose cube population does not intersect that day's silver, or an account_id merge-key dtype mismatch (cube int64 vs silver object yields 0 pandas matches silently).
- **Failure scenario:** Operator runs `python E_01.account_quality_tiers.py --date 2026-07-04` (a market holiday) where gold/timeseries/positions_cube/2026-07-04.parquet exists but is empty (no units>0 that day). cube read succeeds, gold_acct is empty, inner merge is empty, total=0, and line 283 computes len(trustworthy)/0*100 -> ZeroDivisionError -> traceback -> exit(1). The diagnostic aborts instead of reporting 'no overlapping accounts'.
- **Proposed fix:** Guard the summary block: `if total == 0: log('WARN: no accounts in gold-vs-silver intersection'); pct = 0.0` else compute the ratios; or compute pct via a helper that returns 0.0 when total==0.

## Finding 3 -- [low/incremental-full-break/incremental]
- **Location:** `data/cot/scripts/gold/E_01.account_quality_tiers.py:121 (target_date = find_latest_date('silver/allocations/')) -> :128-134 (read positions_cube_key(target_date))`
- **Mechanism:** With no --date, target_date is the latest silver allocations date, then the script reads gold/timeseries/positions_cube/{target_date}.parquet. positions_cube is produced by A_03, which is a full-chain-only dimension script (NOT in INCREMENTAL_CAPABLE, and the whole E_01 is absent from every dispatch chain). After a `--chain full --incremental` night, A_03 does not advance the cube to the newest silver date, so the cube for target_date can be absent/stale while silver has advanced -- the canonical 'incremental serves fresh silver against stale/missing upstream gold dim' interaction. E_01 reads latest silver but the matching cube is missing.
- **Failure scenario:** After an incremental night leaves silver at 2026-07-06 but positions_cube only through 2026-07-05, an operator runs E_01 ad-hoc with no --date -> target_date=2026-07-06 -> positions_cube read raises NoSuchKey -> caught at line 132 -> logs 'ERROR: positions_cube not found for 2026-07-06' -> sys.exit(1). This is a guarded, clean abort (not a traceback or corruption), so severity is low, but the diagnostic cannot run against the newest silver date without a manual --date pointing at the last full-chain cube.
- **Proposed fix:** Default target_date to the latest date that has BOTH a silver allocations file AND a positions_cube file (intersect find_latest_date over both prefixes), or fall back to the newest available cube date with a WARN, rather than assuming the cube tracks silver.

## Finding 4 -- [low/numeric-sign-units/both]
- **Location:** `data/cot/scripts/gold/E_01.account_quality_tiers.py:222-227 (gap_pct = np.where(silver_mv>0, gap/silver_mv, np.where(gold_mv>0, 1.0, 0.0)); abs_gap_pct = gap_pct.abs())`
- **Mechanism:** The relative-gap denominator is guarded on silver_mv>0. For accounts whose silver_mv is zero or negative -- cot has liability account types (C_04 references LIABILITY_TYPES: margin/loan) and A_03's units>0 filter drops negative-unit loan positions from the cube -- gap_pct is forced to a flat 0.0 or 1.0 instead of the true relative gap computed against |silver_mv|. This mis-tiers negative/zero-MV accounts: the real dollar gap is ignored and the tier is decided on coverage alone (or forced to F), independent of whether gold's MV actually tracks silver's.
- **Failure scenario:** A margin/loan account has silver_mv=-$40k (net liability) and gold_mv=$0 (its only holding is the negative-units loan, excluded by A_03's units>0 filter). gap = 0 - (-40000) = +40000, but silver_mv>0 is False and gold_mv>0 is False, so gap_pct=0.0 -> abs_gap_pct=0 -> the account is tiered purely on coverage and can be labeled 'A'/'B' (high-quality) despite gold carrying none of its -$40k position.
- **Proposed fix:** Use abs(silver_mv) in the denominator when silver_mv != 0 (gap_pct = gap/abs(silver_mv)), and handle the silver_mv==0 case explicitly; do not treat all non-positive-silver accounts with a flat 0/1 gap.

## Finding 5 -- [low/unguarded-read/both]
- **Location:** `data/cot/scripts/gold/E_01.account_quality_tiers.py:139 (read_parquet('silver/prices/canonical_prices.parquet')), :170 and :180 (read_parquet(f'silver/allocations/{target_date}.parquet'))`
- **Mechanism:** Only the positions_cube read (lines 130-134) is wrapped in try/except. The canonical_prices read and both silver allocations reads are unguarded, so a missing/renamed object raises NoSuchKey/FileNotFoundError that propagates to the top-level except and exits 1 with a raw traceback. The allocations path is low-risk because target_date is derived from listing that same prefix (line 121), but an operator-supplied --date with no allocations file, or a failed/absent canonical_prices (e.g., S_00 silver-prep did not run), aborts the script.
- **Failure scenario:** S_00 (build_canonical_prices_v2) failed on a given night so silver/prices/canonical_prices.parquet is absent or was renamed; an operator runs E_01 ad-hoc -> line 139 read_parquet raises NoSuchKey -> uncaught within main -> top-level except prints a traceback and sys.exit(1). Similarly, `--date 2026-01-01` with no silver/allocations/2026-01-01.parquet crashes at line 170.
- **Proposed fix:** Wrap these reads with the same try/except -> clear 'ERROR: <artifact> not found for {date}' + sys.exit(1) pattern used for the cube, so the failure is a legible message rather than a raw traceback (and, for canonical_prices, so the operator knows silver-prep is the missing dependency).
