## Finding 1 -- [medium/schema-column/full]
- **Location:** `data/cot/scripts/gold/A_03.positions_cube.py:1354 (_compute_account_end_dates) + :177 (_load_allocation_signals)`
- **Mechanism:** Both forward-fill liveness signals inherited from bd/49F are dead for cot, so EVERY account is treated as backfill-only and capped at its last-transaction date. (1) Line 1354 classifies daily-export vs backfill via transactions['_source_file'].str.contains('TXN_DAILY'), but cot's daily files are named TRANSACTIONS_DAILY_*.xlsx (silver TABLE_CONFIG file_prefix='TRANSACTIONS_DAILY_'; ground-truthed _source_file sample = 'TRANSACTIONS_DAILY_2026-07-07.xlsx'). 'TRANSACTIONS_DAILY' does NOT contain the substring 'TXN_DAILY', so accounts_with_daily is ALWAYS empty -> all accounts are backfill-only. (2) The rescue path uses open_account_ids from _load_allocation_signals, which is gated on an 'account_is_open' column (line 177) that is ABSENT from cot allocations (ground-truthed: allocation columns have no account_is_open / open / status field) -> open_account_ids is ALWAYS empty. With both empty, _compute_account_end_dates sets account_end_dates[acct]=last_txn for every account, and expand_pairs_to_daily caps every account's forward-fill at its last transaction date instead of global_end_date. Note the script already computes alive_account_ids (allocation presence, AUA>=100) but only wires it into the phantom-exclusion filter, NOT into the end-date liveness decision.
- **Failure scenario:** A cot account that still holds positions but goes dormant (no transaction after date X) has its cube coverage truncated at X: for every partition after X the account contributes zero rows -> its AUA is understated (drops to 0) for all recent dates. Confirmed the mechanism is live (account_is_open absent, _source_file=TRANSACTIONS_DAILY). Impact is largely MASKED today because cot's transaction feed is dense (served cube 2026-06-18 = 677 of 683 allocation accounts), so most accounts have a near-current last_txn; but the safety net is entirely gone and impact is unbounded in any low-activity window or for genuinely buy-and-hold-dormant accounts.
- **Proposed fix:** Feed the already-computed alive_account_ids (accounts present in the latest allocation with account_market_value>0) into _compute_account_end_dates as the open/liveness signal (cot's allocation presence is the system-of-record liveness signal, replacing the absent account_is_open). Independently, make the daily-export filename token configurable / match 'TRANSACTIONS_DAILY' so accounts_with_daily is populated. Either fix restores active accounts to global_end_date; both together fully restore intended behavior.

## Finding 2 -- [medium/empty-null-handling/full]
- **Location:** `data/cot/scripts/gold/A_03.positions_cube.py:1503-1507 (build_full _alloc_date) and :185-191 (_load_allocation_signals); filter applied at :1255-1256 (_prepare_partition)`
- **Mechanism:** _alloc_date = unit_events['trade_date'].max() picks the most recent trade date and _load_allocation_signals reads silver/allocations/{that_date}.parquet without checking it is non-empty. Ground-truthed that recent allocation partitions can be 0-row (2026-07-05/06/07 all have rows=0, a holiday weekend) while transactions for those dates are populated. Reading a 0-row allocation yields alloc_agg empty -> alive_account_ids = empty set. The alive-set phantom-exclusion filter in _prepare_partition (line 1255 'if alive_account_ids:') is then SKIPPED for the ENTIRE run, and because it is applied to ALL date partitions (historical included) using the single latest alive set, whether it runs at all flips the account membership of every served partition.
- **Failure scenario:** A nightly (or re-)run whose max trade_date lands on an empty allocation partition (e.g. first run after the 07-04..07-06 holiday, transactions present but allocations 0-row) computes alive_account_ids=empty -> the phantom/BD-zeroed exclusion is silently disabled and every historical positions_cube partition is rewritten WITH accounts that a weekday run would drop. The served cube's account set (and thus historical AUA totals) is non-deterministic between a populated-allocation run and an empty-allocation run of the same code.
- **Proposed fix:** Select the latest NON-EMPTY allocation partition (scan backward past 0-row/absent partitions) for both _alloc_date and the alive/open signals, or explicitly bail out of applying/suppressing the phantom filter only when a genuine populated allocation snapshot was found (log which snapshot date was used).

## Finding 3 -- [low/other/full]
- **Location:** `data/cot/scripts/gold/A_03.positions_cube.py:74 (_MATURITY_YEAR_RE) and :1241-1249 (_prepare_partition._is_matured)`
- **Mechanism:** The matured-bond/CD filter drops any position whose asset_name ends in a 4-digit year (19xx/20xx) strictly less than the partition year. Two precision issues: (a) year granularity only -- a bond/CD that matured mid-year is kept at par through Dec 31 of its maturity year (int(year) < partition_year is False when year==partition_year), so a matured position lingers at $1.00*units for up to ~1 year (phantom par over-count); (b) the bare-year branch (no MM/DD/ prefix) matches any name ending in a plain year, so a non-maturity holding whose display name ends in a bare year (e.g. an index/ETF like 'RUSSELL 2000') would be wrongly dropped.
- **Failure scenario:** Grounded against cot's actual names (txn 2026-06-18, 377 distinct): all 77 year-ending names are genuine bonds/CDs ('...X% MM/DD/YYYY' or brokered CD '...X% YYYY') and 0 have a past maturity year on that partition, so 0 false drops occur today. Residual real effects: a cot muni/CD maturing e.g. 2026-03 stays in every 2026 partition at par (bounded over-count); and the bare-year branch is a latent false-drop for any future non-bond holding whose name ends in a year.
- **Proposed fix:** Parse the full maturity date (MM/DD/YYYY) when present and compare against the partition DATE, not just the year; restrict the bare-year branch to names carrying a bond/CD signal (coupon % or an instrument-type token) so equities/funds/indices ending in a number are not caught.
