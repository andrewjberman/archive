## Finding 1 -- [medium/merge-dedup/full]
- **Location:** `data/cot/scripts/gold/D_00c.portal_leaderboard.py:406-407 (latest_aua total_aua/account_count sum), :415-417 (start_aua sum); served at :581, :668-670, :674`
- **Mechanism:** C_08 writes advisor_fee_detail at (advisor, role, date) grain where total_aua=('aua_current','sum') and account_count=('account_id','nunique') are UNWEIGHTED per-role aggregates (C_08.advisor_fee_efficiency.py:793-801). D_00c's _employee_entries_for_window then sums these ACROSS roles per advisor: latest_aua=latest_day.groupby('advisor').agg(total_aua=('total_aua','sum'), account_count=('account_count','sum')) and start_aua=...groupby('advisor')['total_aua'].sum(). For an advisor holding two roles on the SAME account, that account's AUA and account count are counted once per role, so the sum double-counts. The parallel account_team path deliberately equal-splits (melted['_weighted_aua']=total_aua*_split_weight, _split_weight=1/n_roles at :954/:947) precisely to avoid this; the detail path applies no such dedup. Revenue (implied_daily_fee) IS split-weighted so its sum is correct, but total_aua/account_count are not.
- **Failure scenario:** Advisor Travis is both architect and consultant on the same $10M account. C_08 emits an architect row (total_aua $10M, account_count 1) and a consultant row (total_aua $10M, account_count 1). D_00c serves fee_breakdown.fee_paying.aua = $20M (fee_aua=round(row.total_aua) at :581, served at :667) and fee_paying.account_count = 2 (:668) for that one $10M account; period_start_aua is likewise inflated. no_fee.account_count = max(0, tagged_accts - fee_accounts) is correspondingly deflated/floored to 0 (:639). Because tagged_aua (account_team, deduped) stays correct while fee_aua is inflated, fee_aua can exceed tagged_aua, tripping the documented no_fee_aua<0 clip at :631-638 (partly the STAUDT residual set) and zeroing no_fee.aua.
- **Proposed fix:** Before the cross-role sums, collapse detail to (advisor, account) or apply the same 1/n_roles equal-split used on the account_team path so an account's AUA/count is attributed once per advisor regardless of how many roles they fill; or source fee_paying.aua/account_count/period_start_aua from the deduped account_team melt (advisor_account_pairs / tagged_* counts) rather than summing C_08 per-role totals.

## Finding 2 -- [medium/other/full]
- **Location:** `data/cot/scripts/gold/D_00c.portal_leaderboard.py:782-785 (build_employee_leaderboard early-return), whole 49F-role machinery`
- **Mechanism:** D_00c is entirely built on the 49F advisor-role model (AVAILABLE_ROLES architect/consultant/implementor/additional_advisor/local_ops, split-weighted role_breakdown, fee_paying/no_fee buckets). Cottonwood silver produces none of these role columns, so its upstream C_08 hits `if not role_dfs: return` (C_08.advisor_fee_efficiency.py:775-777) and writes ZERO gold/canonical/advisor_fee_detail/ partitions. Consequently _load_advisor_fee_detail() finds no keys and returns None (:84-85), build_employee_leaderboard returns None (:783-785), and main() takes the else branch writing NOTHING (:1269-1273). The run does not crash (graceful skip), but employee_leaderboard.json is never (re)generated for cot.
- **Failure scenario:** Every nightly full chain for cot runs D_00c to completion with 'SKIP: no advisor_fee_detail data' and produces no artifact. If gold/artifacts/employee_leaderboard.json was ever written once (e.g. transient/test role data), D_00c never overwrites it, so a STALE leaderboard is served indefinitely; otherwise the portal leaderboard 404s/empties for cot. Matches the known empty-advisor-layer state (opal-data-cot advisors/ empty).
- **Proposed fix:** Design decision, not a code patch: either remove D_00c from the cot CHAIN_FULL/CHAIN_DOWNSTREAM catalog (it is a no-op for a firm with no role data), or have it emit an explicit empty/typed employee_leaderboard.json so the served artifact cannot silently go stale. Track under the dead-for-cot 49F-view cleanup.

## Finding 3 -- [low/unguarded-read/full]
- **Location:** `data/cot/scripts/gold/D_00c.portal_leaderboard.py:185-190 (_load_canonical_role_aua_latest), consumed via load_for_leaderboard :1216/:1224`
- **Mechanism:** Unlike every other input (which flows through the column-tolerant lib.gold_utils._load_parquet: NoSuchKey -> empty typed frame, missing requested columns added as null), this loader does resp=s3.get_object(...); df=pd.read_parquet(BytesIO(...), columns=['date','advisor','role','aua']) with a HARD column filter and NO try/except. pyarrow raises if the latest role_aua partition lacks any of those four columns. The exception propagates through fut_ra.result() -> load_for_leaderboard -> main (uncaught) -> non-zero exit. Under the dispatcher, gold/silver compute steps run with NO timeout and HARD-FAIL the chain (gold_dispatch.sh wait_phase :359 -> 'FATAL ... aborting chain; exit 1'), so a single malformed role_aua partition aborts the entire nightly at PHASE_D1. Critically, the loaded role_aua is DEAD: its only consumer is gated by `if False and role_aua is not None` (:1050), so this is a wasted load whose sole effect is crash-risk. The sibling loader in C_08 (_load_canonical_role_aua_latest_c08, C_08:172-202) wraps the same read in try/except with per-column WARN + empty fallback; D_00c's does not.
- **Failure scenario:** gold/canonical/role_aua/{date}.parquet exists (written by C_01b/C_01c/D_02) but a shadow/variant or an empty cot partition is written without the 'aua' (or 'advisor') column. D_00c's read_parquet(columns=['date','advisor','role','aua']) raises -> D_00c exits non-zero -> the no-timeout DAG FATALs and aborts the whole full chain, even though role_aua is never used by D_00c. Standard partitions carry all four cols (C_01b _ROLE_AUA_COLS) so this is drift-triggered, not steady-state.
- **Proposed fix:** Wrap the load in try/except returning the empty typed frame (matching _load_parquet / the C_08 sibling), or drop the columns= filter and select tolerantly; better, delete the dead load entirely since the consumer is `if False`.

## Finding 4 -- [low/numeric-sign-units/full]
- **Location:** `data/cot/scripts/gold/D_00c.portal_leaderboard.py:623 (rd['no_fee']['aua'] = round(rd['aua'] - new_fp_aua, 2))`
- **Mechanism:** The advisor-level no_fee_aua is explicitly clipped to 0 with a WARN when negative (:631-638). The PER-ROLE no_fee.aua computed as residual (role.aua - scaled fee_paying.aua) is NOT clipped. After the fp scaling (fp_scale = fee_aua / raw_fp_sum, :617) — where fee_aua is itself the cross-role-inflated value from finding 1 — a role's scaled fee_paying.aua can exceed that role's total rd['aua'], driving the served no_fee.aua negative. The invariant role.aua == fee_paying.aua + no_fee.aua holds by construction, but no_fee.aua is permitted to be a negative AUA.
- **Failure scenario:** An advisor whose fee_aua (C_08 billing total) exceeds their account_team-weighted role AUA gets fp_scale > 1; for a role where raw fee_paying.aua was already near the role total, new_fp_aua > rd['aua'] and role_breakdown[role].no_fee.aua is served as a negative dollar AUA to the frontend, while the advisor-level no_fee.aua for the same advisor is clipped to 0 (inconsistent).
- **Proposed fix:** Apply the same non-negative clip used at the advisor level (:631-638) to the per-role residual, or floor rd['no_fee']['aua'] at 0.0 and log the delta, keeping the parent/child aua identity via a documented reconciliation.
