## Finding 1 -- [medium/empty-null-handling/full]
- **Location:** `main() lines 434-443 (fallback trigger) -> load_latest_canonical_lots() docstring lines 87-97`
- **Mechanism:** The primary loader load_latest_holdings_lots() reads B_01 holdings_lots, then main() guards with `if 'market_value' not in lots.columns or lots['market_value'].fillna(0).abs().sum() == 0: fall back to load_latest_canonical_lots()`. But the fallback target (gold/canonical/lots_unrealized) is DOCUMENTED IN THIS SAME FILE (lines 87-93) as having all-NaN money columns because Schwab ULN was never ingested for cot -- that is the exact PROFAU.006 '$0 everywhere' bug the primary path was added to fix. When the guard trips, C_05 silently degrades to the known-bad source instead of failing loud: canonical rows exist and get is_open=True (line 192), so open_lots is non-empty, build_tax_liability_view does NOT crash, and it aggregates NaN money to total_cost_basis/total_market_value/total_accrued_gain = 0. The served Cost Basis & Tax Liability panel shows $0 everywhere with no error.
- **Failure scenario:** On a day where cot canonical_prices is stale/absent for all securities (a price outage), B_01 writes market_value=0/NaN for every lot -> abs().sum()==0 -> C_05 falls back to canonical/lots_unrealized -> all money columns NaN -> served client_tax_liability.parquet has every total_cost_basis/total_market_value/total_accrued_gain = 0 while num_open_lots stays populated. rc=0, no alarm, portal tax panel silently reads $0.
- **Proposed fix:** Do not fall back to a source known to have NaN money. If holdings_lots money sums to 0, treat it as an ERROR (raise, so the chain fails loud) or emit a validation flag rather than silently serving zeros; alternatively drop the canonical fallback entirely (B_01 is the sanctioned source per the 2026-04-14 diagnosis) and hard-fail if holdings_lots money is empty.

## Finding 2 -- [medium/empty-null-handling/full]
- **Location:** `build_tax_liability_view() lines 243-244`
- **Mechanism:** `if open_lots.empty: raise RuntimeError('No open lots found -- run 03_build_holdings_lots.py first.')`. This is an uncaught exception in build_tax_liability_view (main() does not wrap it), so it propagates out of main() -> non-zero exit. In the parallel DAG C_05 runs in PHASE_B5 (B_03 || C_05), which is BEFORE all of C_00..C_08 and every D_* portal publisher; wait_phase sees ec!=0 and does `FATAL: PHASE_B5 failed -- aborting chain; exit 1`, so a C_05 abort strands the ENTIRE remaining C+D chain and served portal artifacts go stale for the day. The error message also references `03_build_holdings_lots.py`, a bd/49F legacy script name that does not exist in the cot tree, misleading cot ops.
- **Failure scenario:** A degenerate data day where B_01 emits zero OPEN lots (all positions closed / zeroed), or the ghost-account exclusion list expands to cover every account with open lots -> open_lots becomes empty after line 239 -> RuntimeError -> C_05 rc!=0 -> PHASE_B5 FATAL -> C_00/C_01/C_02/C_03/C_06/C_07/C_08 and all D_00..D_04 publishers never run; portal serves yesterday's data with no explicit alarm on the tax view itself.
- **Proposed fix:** On empty open_lots, write an empty/typed view and return rc=0 (a firm legitimately can have zero taxable open lots) OR at minimum keep the raise but fix the message to the correct cot script (B_01.holdings_lots.py) and consider isolating C_05 so its failure does not abort unrelated downstream publishers.

## Finding 3 -- [low/schema-column/full]
- **Location:** `load_latest_canonical_lots() lines 168-171 + build_tax_liability_view() line 298`
- **Mechanism:** In the canonical fallback loader, the `term` column is created ONLY inside `if 'holding_type' in lots.columns: ... elif 'days_held' in lots.columns: ...`. If a canonical lots_unrealized partition has NEITHER holding_type NOR days_held, `term` is never created. build_tax_liability_view then does `open_lots[open_lots['term'] == 'short_term']` at line 298 (and line 309) which raises KeyError: 'term' -> uncaught -> chain abort. The primary path is safe (B_01 always writes term), so this only bites when the fallback is taken against a malformed canonical partition.
- **Failure scenario:** Fallback path is triggered (see finding 1) AND the canonical lots_unrealized schema for that date lacks both holding_type and days_held (e.g., an early/partial 07_canonical_lots write) -> term column absent -> KeyError at line 298 -> C_05 crashes -> PHASE_B5 FATAL aborts the chain.
- **Proposed fix:** After the holding_type/days_held branch in load_latest_canonical_lots(), unconditionally default any missing term: `if 'term' not in lots.columns: lots['term'] = 'long_term'` (or derive from days_held with a guaranteed fallback), so the aggregation can never KeyError.

## Finding 4 -- [low/type-issue/full]
- **Location:** `load_latest_canonical_lots() line 177 vs load_latest_holdings_lots() passthrough of B_01 purchase_year (B_01.holdings_lots.py line 2716)`
- **Mechanism:** purchase_year is written to the served view with a dtype that varies by which loader ran. Primary path passes B_01's purchase_year through untouched, which B_01 produces as pandas nullable `Int64` (B_01 line 2716: `df['acquisition_date'].dt.year.astype('Int64')`). The canonical fallback path coerces it to plain `int` via `.fillna(0).astype(int)` (line 177). So the served client_tax_liability.parquet purchase_year column is Int64 (nullable, can hold <NA>) on the normal path but int64 on the fallback path -- an unstable dtype for a documented-`int` served column and a group/merge key.
- **Failure scenario:** A downstream consumer or a comparison across two runs (one normal, one fallback) sees purchase_year as Int64 with <NA> on one day and int64 on another; a consumer that does strict-dtype validation, a hash/parquet-schema diff, or integer arithmetic assuming non-nullable int can behave differently between the two runs.
- **Proposed fix:** Pin purchase_year to a single deterministic dtype in build_tax_liability_view before write (e.g. `open_lots['purchase_year'] = open_lots['purchase_year'].fillna(0).astype('int64')`) so both loader paths produce the same served dtype matching the documented schema.
