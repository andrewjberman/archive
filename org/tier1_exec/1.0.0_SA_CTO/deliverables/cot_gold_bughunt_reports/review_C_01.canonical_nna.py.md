## Finding 1 -- [medium/merge-dedup/full]
- **Location:** `_worker_04b lines 320-345 (Schwab impute: bd_absent & schwab_present -> source_system=schwab_imputed, daily_inflow/outflow = schwab totals)`
- **Mechanism:** The Schwab overlay imputes on a per-DATE bd_absent test ((daily_inflow==0)&(daily_outflow==0)) rather than an account-level 'BD never carries this account' test. BD transactions (silver/transactions) and Schwab TRN_NNA are two feeds for the same custodial activity; when the same deposit posts on different dates in the two feeds (settle-vs-trade lag), BD counts it on day D and Schwab imputes the SAME dollars again on day D+k where BD happens to be zero. The in-code comments (schwab_flows.py lines 228-232) explicitly defer 'bd_lagged/bd_delayed' de-dup to Phase 6b 'requires event-level matching', confirming 6a cannot time-match, so lagged duplicates are counted twice in cumulative NNA.
- **Failure scenario:** Account A has a $250k Cash Deposit in silver/transactions dated 2026-05-04 (counted as daily_inflow on 05-04, source_system=bd). The same deposit appears in schwab/silver/trn_nna dated 2026-05-06; BD has no flow for A on 05-06 so bd_absent is True and schwab_present is True -> impute sets daily_inflow(05-06)=$250k, source_system=schwab_imputed. The served single-source-of-truth NNA (sum of nna_txn) now reports +$500k of inflow for one real $250k deposit. Live only when schwab/silver/trn_nna/ is populated for cot; degrades to BD-only (no double-count) when the Schwab overlay is empty.
- **Proposed fix:** Gate impute on account-level Schwab-history / event-key matching (Phase 6b) before summing, or restrict schwab_imputed to accounts with NO BD flow anywhere in the window; at minimum add a diagnostic that reconciles cumulative schwab_imputed dollars against per-account BD totals to surface suspected lag-duplicates.

## Finding 2 -- [medium/unguarded-read/full]
- **Location:** `main() line 953 load_flows_from_transactions() (unwrapped) vs lines 969-978 Schwab loader (try/except degrade)`
- **Mechanism:** The BD flow load is called with no try/except, while the structurally-parallel Schwab load right below it IS wrapped and degrades to {} on failure. load_flows_from_transactions raises RuntimeError('No transaction data found in silver layer') on an empty silver/transactions/ prefix, and any transient S3 error inside its 128-thread parallel read (future.result() at nna_flows.py line 121) propagates uncaught. Any such exception escapes main(), C_01 exits non-zero, and because the dispatcher runs all gold compute steps with NO timeout and HARD-FAILs the chain on non-zero exit (wait_phase 'FATAL ... aborting chain'), the entire cot downstream (C_02, C_03, C_04, all D_*) aborts.
- **Failure scenario:** On a night where the upstream silver/transactions publish failed (prefix empty) or S3 throttles one of the 128 concurrent GETs, C_01 raises instead of producing zero-flow NNA; the whole cot gold downstream aborts at PHASE_C1 rather than degrading like the Schwab path does. A single transient GET failure takes down the served refresh with no retry.
- **Proposed fix:** Wrap the load_flows_from_transactions() call the same way as the Schwab loader (log WARN + proceed with empty flows -> zero-flow NNA) for the transient/empty case, or add a bounded retry around the parallel partition reads so a transient S3 error does not abort the no-timeout chain.

## Finding 3 -- [medium/other/full]
- **Location:** `_worker_04b lines 513-516 (bare 'except Exception -> return None') combined with main() lines 1006-1014 and 1039 (all_stats collects only non-None; rc stays 0)`
- **Mechanism:** Each per-date worker swallows every exception and returns None; main() appends only non-None results to all_stats and never asserts len(all_stats)==total. A systematic per-date failure (an unexpected column/dtype condition, or a transient error in the worker's own boto3 get/put at lines 267/413) silently drops the gold/canonical/nna/{date}.parquet write for those dates. main() still returns success and only logs 'Dates processed: X / N', so the chain proceeds and downstream reads a partial/stale canonical NNA prefix with no alarm.
- **Failure scenario:** An intermittent S3 read fault (or an edge dtype case) makes _worker_04b throw for a subset of dates; those partitions are never (re)written, the log shows e.g. 'Dates processed: 300 / 412', rc=0, PHASE_C1 passes, and C_02/D_* publish NNA that is silently missing 112 recent partitions. Because C_01 is the declared single source of truth for NNA, the served number is silently understated with no failure signal.
- **Proposed fix:** After the executor loop, fail loud (non-zero exit or an explicit alarm) when len(all_stats) < total, or track and re-raise/report a per-date failure list instead of only counting successes; distinguish a legitimately-empty date from a swallowed error.

## Finding 4 -- [low/other/full]
- **Location:** `main() lines 936-948 (COT completeness cap: _served_max init to _sorted_ds[-1], reverse scan, and the '_served_max != _sorted_ds[-1]' guard)`
- **Mechanism:** _served_max is initialized to the max snapshot date and only reassigned when the reverse scan finds a date at/above COMPLETENESS_NONZERO_FLOOR. If EVERY snapshot in gains_cache is below the floor, the loop exhausts with no break, _served_max stays equal to _sorted_ds[-1], and the cap condition (_served_max != _sorted_ds[-1]) is False, so no capping happens and the incomplete latest date is kept on the nna date-axis — the exact 'incomplete-today prices unpopulated' case the P0 guard was added to exclude.
- **Failure scenario:** A morning run where the trailing canonical_holdings snapshot(s) all have <50% of accounts at non-zero MV (prices not yet populated firm-wide) leaves the guard a no-op: the nna date-axis extends to the incomplete date instead of capping to the last complete snapshot, so the nna surface can show an incomplete-today inconsistently vs the served account_performance the guard was meant to stay aligned with. Value stays transaction-derived, so impact is limited to the date-axis surface.
- **Proposed fix:** When no date meets the floor, set _served_max to the last date that does (or drop the trailing incomplete dates unconditionally) rather than defaulting back to the max; make the all-incomplete case cap to the newest complete snapshot or emit an explicit WARN/no-serve.
