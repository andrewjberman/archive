## Finding 1 -- [high/schema-column/full]
- **Location:** `data/cot/scripts/gold/A_02.fee_rate_history.py:261-266 (build_fee_rate_history); guard asymmetry at load_fee_files:161-178`
- **Mechanism:** fee_cols = ['account_id','trade_date','fee_bps','fee_schedule'] and the column selection `fees = fees_df[fee_cols + present_meta].copy()` hardcode fee_bps and fee_schedule as required. But load_fee_files() only enforces account_id (line 161) and trade_date (line 165) via ERROR-return guards; fee_bps is explicitly treated as OPTIONAL (`if 'fee_bps' in df.columns`, line 172) and fee_schedule is never checked or normalized anywhere in the loader. resolve_columns maps by a fixed candidate list (COLUMN_CANDIDATES), so a BD fee-report that renames/omits the Basis Points or Account Fee Schedule column simply yields no resolved column. Because pandas concat unions columns, this only bites when NO partition carries the candidate, but then the selection raises KeyError: "['fee_schedule'] not in index" (verified pandas 2.3.3). The script has no try/except, so it exits non-zero; the gold chain runs every gold/silver step with NO timeout and HARD-FAILS on any non-zero exit, so A_02 aborts the entire nightly chain.
- **Failure scenario:** cot silver/fees/ is built (so load_fee_files returns a non-None df and passes its account_id+trade_date checks) but the fee report variant does not include an 'Account Fee Schedule'/'account_fee_schedule'/'AccountFeeSchedule' column in ANY partition -- plausible for a firm whose fee export omits the schedule field, and this is a freshly-cloned cot pipeline whose silver need not match bd's schema. build_fee_rate_history executes fees_df[['account_id','trade_date','fee_bps','fee_schedule']] -> KeyError -> A_02 rc!=0 -> chain FATAL, killing every downstream A/B/C/D script for the night. The same crash occurs if the Basis Points column drifts out of the candidate list.
- **Proposed fix:** Before selecting, defensively ensure the two state columns exist with typed defaults, e.g. in build_fee_rate_history: `for c in ('fee_bps','fee_schedule'):\n    if c not in fees_df.columns: fees_df[c] = 0.0 if c=='fee_bps' else ''`; or add explicit fee_bps/fee_schedule presence guards in load_fee_files that return None (clean exit) with a clear WARN, matching the existing account_id/trade_date guard pattern.

## Finding 2 -- [high/merge-dedup/full]
- **Location:** `data/cot/scripts/gold/A_02.fee_rate_history.py:362 (cross_validate_allocations merge); invoked unguarded at main:440-441, BEFORE save_history at main:444-445`
- **Mechanism:** cross_validate_allocations does `comparison = current.merge(alloc_fees, on='account_id', how='inner')`. current.account_id descends from silver/fees; alloc_fees.account_id descends from silver/allocations -- two different silver reports read raw via pd.read_parquet with no dtype coercion on account_id. If their account_id dtypes differ (object vs int64), pandas raises ValueError: 'You are trying to merge on object and int64 columns for key account_id' (verified pandas 2.3.3) rather than returning a silent empty frame. cross_validate_allocations is a best-effort LOGGING step but is called with no try/except from main() and runs BEFORE save_history(); its exception propagates out of main -> sys.exit(non-zero) -> no-timeout chain hard-fails. Net effect: a validation-only step both aborts the whole chain AND prevents the already-correctly-computed fee_rate_history.parquet from ever being written.
- **Failure scenario:** silver/fees account_id resolves to object (e.g. 'COT00123' or zero-padded strings) while silver/allocations account_id resolves to int64 (or vice versa) -- a realistic divergence since the two silver tables are produced by different converters. main() computes a valid history, then cross_validate_allocations hits the merge -> ValueError -> chain FATAL and fee_rate_history is NOT saved, so the served dimension silently goes stale even though A_02 'ran'.
- **Proposed fix:** Normalize both keys to str immediately before the merge (current['account_id']=current['account_id'].astype(str); alloc_fees likewise), AND isolate the validation: wrap the cross_validate_allocations(history) call in try/except that logs a WARN, or move save_history BEFORE cross-validation so validation can never block the output write.

## Finding 3 -- [low/merge-dedup/full]
- **Location:** `data/cot/scripts/gold/A_02.fee_rate_history.py:145-148 (as_completed append) + 269-270 (sort_values + drop_duplicates keep='last')`
- **Mechanism:** Loaded partition DataFrames are appended in ThreadPoolExecutor as_completed order (completion order, non-deterministic run-to-run), then pd.concat'd. build_fee_rate_history does sort_values(['account_id','trade_date']) (a STABLE sort) then drop_duplicates(subset=['account_id','trade_date'], keep='last'). Rows tying on (account_id, trade_date) retain their non-deterministic concat order, so 'keep last' selects a non-deterministic winner. When a single (account, date) has >1 row with DIFFERING fee_bps/fee_schedule, the chosen state for that day -- and therefore which SCD period boundaries appear in the served fee_rate_history -- can flip between otherwise-identical runs, silently changing served fee periods and the current-fee stats.
- **Failure scenario:** An account has two rows for the same trade_date with different Basis Points (a corrected/duplicate fee line, or the same date present in two partition files). Run 1 keeps 50bps, run 2 (different as_completed order) keeps 60bps for that date, producing different effective_date/end_date boundaries and a different is_current fee_bps for that account across reruns of the same input. Low probability given the daily one-row-per-account grain, but real and non-deterministic when it occurs.
- **Proposed fix:** Make ordering deterministic before dedup: either sort dfs deterministically (e.g. append with the submit key and sort keys pre-submit) or add a stable tiebreaker to the sort (e.g. include a source-key/ingest column) so drop_duplicates(keep='last') resolves same-day duplicates deterministically; optionally log a data-quality WARN when same-(account,date) rows disagree on fee state.
