## Finding 1 -- [high/numeric-sign-units/both]
- **Location:** `_compute_gains lines 496-500 and 552-553 (realized_gl aggregation + COMP_REALIZED bit); root grounded in B_02.canonical_lots.py:517`
- **Mechanism:** realized_gl = rlz.groupby('account_id')['gain_loss_dollars'].sum() after pd.to_numeric(...).fillna(0). B_02 sets BD-only (non-Schwab) realized lots' gain_loss_dollars = np.nan (B_02:517); only Schwab-RLD-sourced lots carry a real dollar gain. B_03 coerces those NaNs to 0, so realized_gl becomes 0 for every BD-sourced closed lot. growth = price_return + realized_gl + income then omits the realized component, and aua_residual = aua_change - growth (the SERVED NNA, consumed by C_01.canonical_nna.py:269/421) silently absorbs the entire realized gain/loss. Worse, the components bitmask still ORs in COMP_REALIZED whenever the lots_realized partition merely exists with the column (line 552-553), regardless of the values being all-NaN->0, so downstream 'nna_clean' (C_01:81) marks this residual as clean/fully-decomposed when realized is in fact absent.
- **Failure scenario:** Cottonwood is a separate firm cloned from the bd/49F tree; the Schwab RLD custody feed (49-schwab, account 08242234) is a bd/49F artifact and cot likely has NO schwab/silver/rld partitions, so every cot realized lot is BD-sourced with gain_loss_dollars=NaN. A cot account sells a lot on date t for a $10k realized gain -> B_02 emits the closed lot with gain_loss_dollars=NaN -> B_03 realized_gl=0 -> growth understated by $10k -> served NNA (aua_residual) overstated by $10k, i.e. a real realized gain is reported as $10k of net-new-assets, and components still flags realized as present so it reads as a clean decomposition.
- **Proposed fix:** Distinguish 'no realized lots' from 'realized lots present but dollar-gain unknown'. Only set COMP_REALIZED when gain_loss_dollars is actually populated (non-null) for the date, and either (a) keep realized_gl as NaN (not 0) when the source column is all-null so it does not silently zero-attribute into growth/NNA, or (b) emit a coverage flag so C_01 does not mark the residual nna_clean. Confirm against served whether cot has any Schwab RLD; if not, realized_gl is structurally ~0 firm-wide and the growth-vs-NNA split is misattributed.

## Finding 2 -- [medium/merge-dedup/both]
- **Location:** `_compute_gains lines 540-547 (income path); mirrored in dead process_date lines 339-361`
- **Mechanism:** Income is summed from silver/transactions rows whose type is in {Dividend, Interest}. Dedup only fires inside `if 'transaction_id' in income_rows.columns:` (line 543). If that column is absent, NO dedup occurs and duplicated income events are summed as-is. The process_date twin's own comment (lines 347-349) states 'Dedup by transaction_id first, then fall back to composite key' and that BD exports duplicate the same income event '5x+ on some dates' -- but NEITHER code path implements the promised composite-key fallback; the comment overpromises what the code does. income feeds growth, and aua_residual = aua_change - growth is the served NNA (C_01.canonical_nna.py), so inflated income inflates growth and understates served NNA.
- **Failure scenario:** cot_silver_merge.py produces silver/transactions for cot (confirmed live). On a date whose transactions file resolves its amount via the 'action'/'amount' columns but does NOT include a 'transaction_id' column (or where the dup key is a different id), and where a dividend event is recorded 5x (the exact duplication the comment warns of), income for that account/date is counted 5x -> growth 5x-inflated on the income component -> served NNA (aua_residual) correspondingly understated.
- **Proposed fix:** Implement the composite-key fallback the comment promises: when transaction_id is missing, drop_duplicates on a composite key (e.g. account_id + type_col + mv_col + date/settle) before summing. At minimum log a WARN when income is summed without any dedup key available so a silent 5x is visible.

## Finding 3 -- [medium/empty-null-handling/both]
- **Location:** `_compute_gains lines 611-615 (per-date try/except returning None); main lines 770-778 (no failure on X<total)`
- **Mechanism:** The entire per-date computation in the live worker _compute_gains is wrapped in `except Exception: ... return None`. Any KeyError/dtype error for a single date (missing column, unexpected dtype breaking a groupby) is swallowed: the worker returns None, that date's gold/canonical/account_gains/{date}.parquet is NOT written (a stale prior partition remains, or a gap appears), and the chain proceeds rc=0. main() logs 'Dates processed: X / total' but never fails or alarms when X < total. This converts a hard data/schema error into a silent served-data gap -- exactly the 'never trust rc=0' failure mode -- for an output consumed by C_01 (served NNA) and C_03 (account performance).
- **Failure scenario:** One date's canonical holdings (B_00) is written without a 'market_value' column, or with account_id coerced to a dtype that breaks groupby, for a single partition. _compute_gains raises inside the try, returns None, and that date's account_gains is silently absent/stale while every other date succeeds; the nightly chain reports success, and served NNA/performance for that date is missing or frozen with no operator signal.
- **Proposed fix:** Track per-date failures explicitly: collect the count of None/errored dates and either exit non-zero (or emit a loud WARN/alarm + a failed-dates manifest) when errored > 0, rather than silently dropping the partition. Re-raise on schema-invariant violations (missing required columns) instead of swallowing them.

## Finding 4 -- [low/other/both]
- **Location:** `process_date lines 190-441 (defined, never called); live path is _compute_gains, submitted at main line 768`
- **Mechanism:** process_date() is a full second implementation of the decomposition that is never invoked -- main() submits _compute_gains to the pool. The two functions have diverged in subtle ways (e.g. process_date's income comment promises a composite-key dedup fallback that neither implements; process_date logs a checksum-drift WARN while _compute_gains does not). A future fixer editing process_date (the more readable, better-commented function) would produce a no-op change that never runs in production, and reviewers may reason about the wrong code path.
- **Failure scenario:** A maintainer fixes the income-dedup or realized-NaN issue in process_date (the documented function), commits, and the nightly gold run is unchanged because only _compute_gains executes -- the served numbers stay wrong while the ticket reads fixed.
- **Proposed fix:** Delete process_date (and its helper wiring) or collapse the two into a single shared function that both the serial and pooled paths call, so the executed code and the documented code are the same.
