## Finding 1 -- [medium/empty-null-handling/both]
- **Location:** `build_clients_tab lines 618-630 + load_all._load_fee_history lines 294-302 + lib/gold_utils._load_parquet lines 39-44`
- **Mechanism:** _load_fee_history is written to return None when fee_rate_history is 'not available' (its except branch), and build_clients_tab omits all fee-split fields when billable_account_ids is None. But _load_parquet swallows NoSuchKey and returns an EMPTY object-typed frame instead of raising, so on a genuinely-absent FEE_RATE_HISTORY the except branch never fires: `cur = df[df['is_current']==True]` on the empty frame yields an empty set (NOT None). Since empty-set is not None, build_clients_tab takes the fee-split path with fee_mask = acct_snap.account_id.isin(set()) = all-False.
- **Failure scenario:** gold/dimensions/fee_rate_history.parquet missing (first run, or A_02 produced nothing). D_00 publishes clients_tab.headline with fee_earning_aua=0.0, non_fee_earning_aua=<entire firm AUA>, fee_earning_client_count=0, fee_earning_account_count=0 -- a portal that asserts 100% of AUA is non-fee-earning, instead of omitting the fee cards (the intended 'null fee splits' behavior). Verified locally: empty fee frame -> set() (not None).
- **Proposed fix:** Detect true absence: have _load_fee_history return None when the frame is empty/missing (e.g. `if df.empty: return None`), or gate the fee-split block on `billable_account_ids` being a non-empty set AND fee_rate_history actually present. Do not let an absent input masquerade as 'zero billable accounts'.

## Finding 2 -- [medium/unguarded-read/both]
- **Location:** `load_all._load_perf lines 255-292 (raise at 289-292) + lib/gold_utils._load_parquet lines 39-44`
- **Mechanism:** _load_perf's try/except is designed to FAIL LOUD (RuntimeError, 'no silent stale serving') if account_performance is unavailable. But the only read is `_load_parquet(ACCOUNT_PERFORMANCE, ...)`, which catches NoSuchKey internally and returns an EMPTY columns-typed frame rather than raising. An empty frame flows through pd.to_datetime + groupby.agg without exception (verified locally: empty named groupby.agg -> 0 rows, no raise; date.max() -> NaT), so the RuntimeError guard is never reached.
- **Failure scenario:** gold/timeseries/account_performance.parquet absent/NoSuchKey (first-ever run, or a manual `--single D_00`, or an upstream C_03 that failed but left the object missing). Instead of aborting loudly, D_00 publishes clients_tab/header_metrics/snapshots with total_aua=0.0, account_count=0, client_count=0, all NNA=0 -- a silent full-zeroing of every served portal number, exactly the freeze-bug class the raise was meant to prevent. (In the nightly full chain C_03 runs first and hard-fails, so this is a latent robustness gap, not a live nightly failure.)
- **Proposed fix:** Distinguish 'absent' from 'empty': after loading, assert `not ap.empty` (or check object existence via head_object) in _load_perf before aggregating and raise the RuntimeError on absence; alternatively give _load_parquet a `required=True` mode that re-raises NoSuchKey for mandatory inputs.

## Finding 3 -- [low/numeric-sign-units/both]
- **Location:** `build_snapshots lines 834-840`
- **Mechanism:** state_total = float(state_agg.sum()) is computed over the top-49 states INCLUDING the 'Unknown'/'' state bucket, but state_rows then EXCLUDES those buckets (`if str(state).lower() not in ('unknown','','nan','none')`). Each state's aua_pct = aua/state_total therefore uses a denominator inflated by the hidden Unknown AUA, so displayed percentages are understated and do not sum to 100%. It also differs from the architect snapshot, which percents against the firm total_aua.
- **Failure scenario:** COT single-custodian with sparse client_state -> _compute_rel_geo defaults many relationships to state='Unknown', producing a large Unknown-state AUA bucket. aua_by_state.json then shows every real state's aua_pct materially depressed (e.g. a state that is 40% of US AUA renders as ~25% because Unknown is in the denominator but not shown), and the visible rows sum well short of 100%.
- **Proposed fix:** Compute state_total AFTER dropping the excluded ('unknown'/''/'nan'/'none') buckets, or filter geo_us to known states before the groupby, so the percentage denominator matches the set of rows actually emitted.

## Finding 4 -- [low/schema-column/both]
- **Location:** `build_clients_tab line 641 (compute_capital_gains_ttm_by_account(perf, today)) + _build_tax_section lines 570-575 + lib/gold_utils lines 187-190`
- **Mechanism:** compute_capital_gains_ttm_by_account requires per-account columns 'growth' and 'account_id' (its docstring: 'full account_performance.parquet load'). D_00 passes `perf` = the (date, relationship_id)-grain aggregate from _load_perf, where growth was renamed to 'market_growth' and account_id was dropped. The function's guards (`if 'growth' not in perf.columns ... return {}`; `if 'account_id' not in perf.columns: return {}`) therefore ALWAYS return {} (verified locally). cap_gains_ttm_by_account is thus always empty, so _build_tax_section's capital_gains_ttm always takes the `else round(nq_unrealized, 2)` fallback (inception-cumulative unrealized), never the intended trailing-365d window sum.
- **Failure scenario:** For a firm WITH tax lots, clients_tab.tax.capital_gains_ttm would silently be inception-cumulative gain instead of TTM -- a materially different served number. For COT specifically there is ZERO served impact: tax is empty, so _build_tax_section returns early at line 493-509 with capital_gains_ttm hardcoded 0.0, and the dead computation is never consumed. Reported as a real latent defect with nil COT impact.
- **Proposed fix:** Pass the raw account-grain account_performance frame (with account_id + growth) into compute_capital_gains_ttm_by_account -- e.g. return the pre-aggregation `ap` from _load_perf, or load account_performance separately for the TTM pass -- rather than the relationship-grain agg.
