# REVIEW -- A_00.accounts_dimension.py

- script: `data/cot/scripts/gold/A_00.accounts_dimension.py`
- verdict: **issues-found**
- runs_in_incremental: True
- findings: 5

## Finding 1 -- [critical/incremental-full-break/incremental]
- **Location:** `build_accounts_dimension snapshot union L474-487 (load_snapshot_accounts L349-367) reused by _run_incremental L680; merge_incremental overwrite L414-417`
- **Mechanism:** In incremental mode _run_incremental (L674) loads ONLY the new-window transactions into new_txn_accounts, then calls build_accounts_dimension (L680), which unconditionally unions in the holdings snapshot: _extra = every snapshot account NOT in the new-window txn set (L478-486). Because the new window is one day, that _extra set is essentially the ENTIRE COT book, injected as rows with null/default metadata (account_name=None, account_display_name=None, tax_status='taxable' via the L504 fillna default, qualified_flag=False, client_city/state/zip='', relationship_name=None, account_is_open=None, closed_date=None, account_owner=None, etc.). merge_incremental then puts each of these already-existing accounts into updated_ids (existing & new, L390) and overwrites every non-preserved column via the null-guardless loop `result_upd[col] = upd_new[col]` (L414-417). The snapshot union was designed for FULL builds (where 'not in transactions' means genuinely txn-less pre-onboard transfers, a tiny set); reusing build_accounts_dimension on a one-day txn window makes 'not in transactions' mean 'almost the whole firm'.
- **Failure scenario:** Nightly full chain runs A_00 with --incremental (CATALOG default). Established COT account X (account_name='Smith Roth IRA', tax_status='tax_exempt', qualified_flag=True, client_state='CA') holds positions (so it is in silver/holdings) but has no transaction on run date 2026-07-07. new_txn_accounts excludes X; the snapshot union injects X with account_name=None, tax_status='taxable', qualified_flag=False, client_state=''. merge_incremental sees X in updated_ids and overwrites: served accounts_dimension now has X with null name, tax_status flipped taxable, qualified_flag flipped False, blank state. This happens simultaneously for every account in the book that did not transact that day, silently corrupting the served dimension and every downstream (D_00 header, tax/state snapshots, client/portal summaries). The corruption is persistent (next incremental overwrites null-with-null) until a manual --full rebuild.
- **Proposed fix:** Do not run the holdings-snapshot union inside the incremental new_batch build (pass a flag to build_accounts_dimension to skip load_snapshot_accounts when building an incremental delta), OR make merge_incremental's overwrite null-aware: only assign `result_upd.loc[mask, col] = upd_new.loc[mask, col]` where upd_new[col] is a real non-null value (mirroring the advisor carry-forward at L419-425). Additionally, exclude snapshot-only injected rows (those with no real txn metadata) from the merge entirely so they only ADD brand-new accounts, never overwrite existing ones.

## Finding 2 -- [high/merge-dedup/incremental]
- **Location:** `merge_incremental L414-417`
- **Mechanism:** The updated-account refresh loop overwrites every non-preserved column unconditionally with the new-batch value regardless of whether that value is null/blank: `for col in upd_new.columns: if col in preserve_cols or ...: continue; result_upd[col] = upd_new[col]`. preserve_cols shields the advisor and date columns but NOT account-level descriptive fields (account_name, tax_status, qualified_flag, account_owner, closed_date, account_is_open, relationship_name, client_*). This is the same root mechanism as finding 1 but also fires for genuinely-transacting accounts whose latest new-window row nulls a non-advisor field.
- **Failure scenario:** Account Y transacts in the new window but its most recent row (e.g. a cash-sweep/fee/dividend entry) carries a null closed_date / null account_owner / null tax_status_1 while an earlier real trade had them populated. merge picks the latest row's null and overwrites Y's previously-correct value with null on served. Advisor fields are protected by the L419-425 carry-forward, but no other field is.
- **Proposed fix:** Add a null-guard to the L414-417 loop so existing values are only overwritten when the incoming value is non-null/non-blank, matching the advisor carry-forward pattern already present at L419-425.

## Finding 3 -- [medium/incremental-full-break/incremental]
- **Location:** `_list_txn_keys L149-153 (filter `if after_date and file_date <= after_date`); watermark set L697 / L726`
- **Mechanism:** The watermark is the max transaction FILE DATE and incremental selects files with strict file_date > watermark. Any transaction file whose date is <= the stored watermark is never reprocessed. If a silver/transactions/YYYY-MM-DD.parquet for a date at-or-before the watermark is re-uploaded/restated after the dimension advanced, its changes are permanently invisible to incremental runs (no LastModified/content fingerprint). The dispatcher itself documents this as the GLDINC restatement caveat (gold_dispatch.sh L898-901).
- **Failure scenario:** A back-dated correction re-writes silver/transactions/2026-06-30.parquet (e.g. an account's tax_status or relationship corrected) after the watermark has already advanced to 2026-07-06. Every subsequent incremental A_00 run skips that file (2026-06-30 <= 2026-07-06), so the served accounts_dimension keeps the stale pre-correction metadata for those accounts until a manual --full/--force rebuild.
- **Proposed fix:** This is a documented limitation; if same-date restatement is possible for COT, gate incremental on a per-file LastModified/etag fingerprint (GLDINC-P1) rather than filename date, or schedule a periodic full rebuild. At minimum, keep it on the runbook that back-dated corrections require --full.

## Finding 4 -- [low/empty-null-handling/both]
- **Location:** `build_accounts_dimension L548-549`
- **Mechanism:** `print(... matched/len(accts)*100 ...)` divides by len(accts) with no zero-guard. accts is empty only if both the transaction batch and the holdings snapshot are empty.
- **Failure scenario:** If silver/holdings is empty (e.g. before the COT holdings table is populated, or the 49F-empty case) AND the new-window transaction files contain zero rows, accts is an empty DataFrame and the alloc-enrichment branch raises ZeroDivisionError, aborting the no-timeout gold step and hard-failing the chain.
- **Proposed fix:** Guard the percentage print: `pct = matched/len(accts)*100 if len(accts) else 0.0`, or early-return/skip enrichment stats when accts is empty.

## Finding 5 -- [low/schema-column/both]
- **Location:** `build_accounts_dimension L495-498 vs output_cols L574-578; keep_cols filter L239`
- **Mechanism:** When the silver transaction schema lacks the 49F role columns (COT's cot_silver_merge produces none of architect/implementor/consultant/local_ops/additional_advisor), keep_cols (L239) drops them and only 'architect' is explicitly defaulted (L495 via accts.get(...).fillna('Unassigned')). implementor/consultant/local_ops/additional_advisor are never created, so the `available = [c for c in output_cols if c in accts.columns]` filter (L588) silently omits those four columns from the served dimension, producing an asymmetric schema (has architect='Unassigned', missing the other four).
- **Failure scenario:** A downstream consumer that reads the dimension expecting the full 49F advisor schema (e.g. A_01.advisor_assignments or D_02/D_04 doing df['implementor']) hits a KeyError on the COT dimension, or silently produces an all-Unassigned/empty advisor layer. This is the known dead-advisor-layer condition; the asymmetry (architect present, others absent) is the concrete drift.
- **Proposed fix:** Default all five advisor columns uniformly (create implementor/consultant/local_ops/additional_advisor as 'Unassigned' when absent, same as architect) so the output schema is stable across firms, or explicitly document/enforce that COT omits the role columns and make consumers use .get with defaults.
