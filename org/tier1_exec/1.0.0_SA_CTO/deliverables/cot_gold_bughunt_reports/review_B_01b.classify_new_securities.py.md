## Finding 1 -- [critical/incremental-full-break/full]
- **Location:** `B_01b.classify_new_securities.py:88-103 (_list_holdings_keys + _parse_date) driving watermark at :224-233 and :346`
- **Mechanism:** _list_holdings_keys() lists every .parquet under HOLDINGS_LOTS_PREFIX ('gold/timeseries/holdings_lots/'). That prefix ALSO contains backfill_{date}.parquet files, which B_01.holdings_lots.py writes via holdings_lots_backfill_key() whenever it is run with --full (save_lots(full=True), B_01 line 2981). _parse_date() blindly does key.rsplit('/',1)[-1].replace('.parquet','') and so returns the literal string 'backfill_YYYY-MM-DD' for those files. Because 'b'(0x62) > '2'(0x32), sorted(keys)[-1] is always a backfill file when any exists, so latest_date = _parse_date(keys[-1]) = 'backfill_...' is written into the watermark (line 346/353). The partition-selection filter is a raw string comparison: keys = [k for k in all_keys if _parse_date(k) > watermark] (line 229). Once watermark == 'backfill_...', every real partition '2026-..' compares as '2' < 'b' => FALSE, so NO partition is ever selected again.
- **Failure scenario:** B_01 is run once with --full (a routine backfill), depositing e.g. gold/timeseries/holdings_lots/backfill_2026-01-10.parquet alongside the daily 2026-04-15.parquet files. On B_01b's next run keys[-1] is the backfill file, so the watermark is written as 'backfill_2026-01-10' (verified: sorted()[-1] parses to 'backfill_2026-01-10', and '2026-04-16' > 'backfill_2026-01-10' evaluates False). From then on every nightly B_01b hits 'No new partitions. Nothing to classify.' and returns. New tickers first appearing after that date are NEVER inserted into bd-securities, so downstream C_*/D_* read them with no asset_class/sub_asset_class -> served firm-mix and allocation numbers silently drop or misclassify those holdings, indefinitely, with no error.
- **Proposed fix:** Restrict partition discovery to pure-date filenames. In _list_holdings_keys, keep only keys whose basename matches ^\d{4}-\d{2}-\d{2}\.parquet$ (excludes backfill_, shadow, and any future non-date sibling); alternatively have _parse_date validate via datetime.strptime and skip non-conforming names, and never let latest_date/watermark be anything but a real YYYY-MM-DD. This also removes the wasteful every-run re-scan of backfill partitions.

## Finding 2 -- [high/type-issue/full]
- **Location:** `B_01b.classify_new_securities.py:312 (confidence coercion) and :316 (r_name[:40]); result loop 307-343 is not wrapped in try/except`
- **Mechanism:** The per-result loop body is unguarded (the only try/except, lines 300-305, wraps just call_openai). confidence = float(result.get('confidence', 0.0)) coerces raw LLM output: get(...,0.0) returns None if the model emits "confidence": null (default is only used for a MISSING key, not a present-but-null one) -> float(None) -> TypeError; or the model emits "confidence": "high"/"n/a" -> float(...) -> ValueError. Similarly at line 316, r_name = result.get('asset_name','') is None when the model echoes "asset_name": null, and the invalid-asset_class branch does r_name[:40] -> TypeError. Any of these is uncaught, so main() propagates the exception, B_01b exits non-zero, and (per the no-timeout hard-fail chain) B_02, B_03, C_*, D_* never run.
- **Failure scenario:** In an UPLOAD run, gpt-5.4-mini returns one result object in a batch with "confidence": null (or a non-numeric string). float() raises inside the un-try'd loop -> B_01b aborts with non-zero exit -> the entire cot gold chain hard-fails for the night -> served platinum for the whole firm goes stale, from a single malformed LLM field.
- **Proposed fix:** Coerce defensively and isolate per-result failures: wrap the loop body (or at least the numeric/string coercions) in try/except that logs+increments total_errors and continues, e.g. `try: confidence = float(result.get('confidence') or 0.0) except (TypeError, ValueError): confidence = 0.0` and `r_name = str(result.get('asset_name') or '')`, `r_ticker = str(result.get('ticker') or '')`. One bad item must never abort the chain.

## Finding 3 -- [medium/incremental-full-break/full]
- **Location:** `B_01b.classify_new_securities.py:345-353 (unconditional watermark advance after the batch loop)`
- **Mechanism:** The watermark is advanced to _parse_date(keys[-1]) regardless of how many securities actually classified. total_errors is recorded in stats but does not gate the advance. A batch that fails permanently (call_openai raises after retries) does total_errors += len(batch); continue (line 302-305), and per-result SKIPs also increment total_errors, yet the watermark still moves past every partition in the window. Because the watermark is partition-grained, a single success advances it past ALL partitions scanned this run, so the un-classified securities from those partitions are not re-scanned.
- **Failure scenario:** A transient OpenAI outage during the nightly run makes all batches fail: total_classified=0, total_errors=len(new_pairs), but the watermark is still saved at the latest partition date. Those securities are only retried if they re-appear (is_open=True) in a FUTURE partition; a position that is closed before the next successful run stays permanently unclassified in bd-securities, silently under-populating downstream classification for that security.
- **Proposed fix:** Only advance the watermark when the window was fully processed (e.g. if total_errors == 0, else hold at the previous watermark / advance only to the last error-free partition) so failed windows are retried on the next run rather than skipped.
