## Finding 1 -- [medium/other/both]
- **Location:** `data/cot/scripts/gold/validate_platinum_consistency.py:1-26 (docstring, esp. line 6) vs data/cot/scripts/gold/gold_dispatch.sh CATALOG lines 77-105 + chain strings lines 120-153`
- **Mechanism:** The docstring states 'Designed to run immediately after D_04 deploys', but the script has NO entry in the gold_dispatch.sh CATALOG and appears in NO chain string (full/canonical/downstream/dimensions/groups). A repo-wide grep for 'validate_platinum_consistency' matches only the file itself -- no dispatcher step-ID, no post-D_04 hook, no wrapper in data/cot invokes it. It writes nothing to S3, so it is a pure read-only validator that is never automatically run.
- **Failure scenario:** Nightly cot CHAIN_FULL (or the incremental chain) completes; D_04 republishes platinum/. Because the validator is not wired into gold_dispatch.sh, none of its cross-surface number checks ever execute. A real firm-vs-advisor-vs-client-vs-account AUA drift introduced by a D_00/D_04 change ships to served with zero automated cross-surface validation. The script's stated protective purpose is not delivered for the cot pipeline.
- **Proposed fix:** Either (a) remove/deprecate the script from data/cot to eliminate local-vs-deployed drift, or (b) if the intent is to run it, add it as an explicit post-chain validation step in gold_dispatch.sh (like the WP-10b recon at lines 1265-1275) gated on chain_exit==0 -- but only AFTER fixing Finding 2, since as-is it would always exit 1 for cot.

## Finding 2 -- [medium/empty-null-handling/both]
- **Location:** `data/cot/scripts/gold/validate_platinum_consistency.py:210-217 (tier1 advisor gate) and 392-406 (tier2 client discovery)`
- **Mechanism:** All substantive client/account/timeseries checks are routed through the advisor layer. tier1 lists platinum/advisors/*/summary.json (line 210-211); if none exist it records a FAIL and returns WITHOUT adv_data (line 216-217). tier2 requires adv_data (returns {} at line 396-397 when empty) and discovers clients ONLY from adv_client_lists (all_client_ids built at lines 400-402, client_keys at line 405). tier3 and tier4 both early-return on empty client_data (lines 484-486, 583-584). For cot the advisor layer is empty (platinum/advisors/ empty -- 49F-inherited advisor model, cot silver produces no role columns), so adv_client_lists is empty, so client_data is empty, so the client-AUA-vs-account-AUA reconciliation (T3i), account-existence (T3j), and timeseries (T4k/T4l) checks NEVER run -- even though platinum/clients/ and platinum/accounts/ ARE populated for cot.
- **Failure scenario:** Run `python validate_platinum_consistency.py --bucket opal-data-cot` against a healthy cot platinum tree (firm+clients+accounts populated, advisors empty). Output: T1 records 'advisor summaries found = 0' FAIL, T2/T3/T4 each record '<tier> data available = FALSE' and skip; the script exits 1 having performed ZERO real number reconciliation on the client/account surfaces that exist. It simultaneously (a) can never PASS for cot and (b) validates none of the numbers that are actually served -- false/zero assurance in both directions.
- **Proposed fix:** Decouple client discovery from advisors for firms with no advisor layer: enumerate clients directly via _list_prefix(s3, bucket, 'platinum/clients/') (filter '/summary.json') as the primary source for tier2/3/4, using adv_client_lists only for the advisor->client reconciliation (T2f/T2g). Guard the advisor-tier checks (T1a, T1d*, T2f/g) behind 'if adv_summary_keys' so they SKIP (not FAIL) when a firm legitimately has no advisor breakdown.

## Finding 3 -- [low/type-issue/both]
- **Location:** `data/cot/scripts/gold/validate_platinum_consistency.py:206,229-230,243`
- **Mechanism:** Values pulled from JSON are used in arithmetic/comparison assuming numeric dtype. firm_aua = headline.get('total_aua', 0) (line 206) returns None if the key is present with a JSON null (the default 0 is used only when the key is ABSENT). Line 243 then does `if firm_aua > 0:` -> None > 0 raises TypeError (not '>' between NoneType and int), which is uncaught and crashes the validator. Same class at lines 229-230 (adv_aua_sum += book.get('total_aua', 0); adv_nna_ytd_sum += book.get('nna_ytd', 0)) -> None or str -> TypeError on +=.
- **Failure scenario:** A degraded/first-run platinum/firm/dashboard.json (or clients_tab.json) emits headline.total_aua as JSON null (key present, value null). headline is a non-empty dict so line 200 'if not headline' passes; firm_aua = None; line 243 'if firm_aua > 0' raises TypeError and the script aborts mid-run instead of reporting a clean FAIL. (Only the standalone validator crashes -- it is not in the chain and writes nothing, so no served/chain impact.)
- **Proposed fix:** Coerce numerics defensively, e.g. `firm_aua = float(headline.get('total_aua') or 0)` and wrap the advisor-sum accumulations with `float(x or 0)`; or normalize at read time. Treat a null/non-numeric headline total as a recorded FAIL rather than an exception.
