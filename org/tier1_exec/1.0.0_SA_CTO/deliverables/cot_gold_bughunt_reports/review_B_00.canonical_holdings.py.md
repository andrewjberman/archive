## Finding 1 -- [high/schema-column/full]
- **Location:** `_build_canonical_from_snapshot, lines 131 + 139 (units read + price divide); also snap['account_id']/snap['asset_name'] direct-index at 137-138`
- **Mechanism:** COT's served canonical holdings are produced ONLY by _build_canonical_from_snapshot (main() returns early at 1046-1051 because silver/holdings is populated). units = pd.to_numeric(snap.get('units'), errors='coerce'): when the 'units' column is absent, snap.get('units') returns None and pd.to_numeric(None, errors='coerce') returns a SCALAR np.float64(nan) (verified), not a Series. Line 139 then evaluates mv / units.replace(0, np.nan) -> 'numpy.float64' object has no attribute 'replace' -> AttributeError. This line is OUTSIDE the per-date try/except (which wraps only _read_s3 at 127-130), so it propagates to main() -> __main__ handler -> sys.exit(1) -> aborts the whole no-timeout gold chain (all downstream gold scripts skipped). account_id/asset_name use bare [] indexing so a rename there is a KeyError with the same chain-abort. silver/holdings column NAMES are just the qt1 vendor XLSX headers run through to_snake_case in cot_silver_merge.py with only a min_col_count:12 count guard (no name validation), so a vendor header rename or a short/malformed HOLDINGS_DAILY export changes/drops the name.
- **Failure scenario:** qt1 renames the 'Units' export header to 'Quantity' (or a malformed HOLDINGS export drops the column while still meeting the 12-col count). silver/holdings/{date}.parquet lands with no 'units' column. B_00 snapshot path: units becomes scalar NaN, units.replace(...) raises AttributeError uncaught -> sys.exit(1) -> the nightly cot gold CHAIN_FULL aborts at B_00 and every downstream script (B_01/B_02/B_03/C_*/D_* served platinum) never runs; served COT holdings/AUA freeze at the prior day with no fresh output.
- **Proposed fix:** Read the dtype-critical columns via a guarded helper that always yields a Series of len(snap) (e.g. u = pd.to_numeric(snap['units'], errors='coerce') if 'units' in snap.columns else pd.Series(np.nan, index=snap.index)); validate the required column set {account_id,asset_name,units,market_value} up front and log+skip the date if any are missing; and widen the try/except to cover the whole per-date body so one bad date logs+continues instead of aborting the chain.

## Finding 2 -- [high/schema-column/full]
- **Location:** `_build_canonical_from_snapshot, line 132 (mv = pd.to_numeric(snap.get('market_value'), errors='coerce')), consumed at 142/145`
- **Mechanism:** Same unguarded .get() idiom as units, but market_value fails SILENTLY instead of crashing. If 'market_value' is absent, snap.get('market_value') is None and pd.to_numeric(None, errors='coerce') is a scalar NaN. In the DataFrame construction the scalar NaN BROADCASTS to every row: market_value=NaN for all rows, and price = mv/units = NaN/Series = all-NaN. No exception is raised (rc=0), the chain continues, and the log line ch['market_value'].sum()/1e6 prints '$0.0M' (NaN-skipping sum of an all-NaN column). Served gold/canonical/holdings/{date}.parquet for that date carries market_value=NaN for every position.
- **Failure scenario:** qt1 renames 'Market Value' to 'Market Val' (or 'Value'). silver/holdings lands with no 'market_value' column. B_00 writes canonical holdings with market_value=NaN on every row; downstream B_01 books / platinum advisor+account summaries sum NaN -> served COT AUA collapses to 0/NaN for that date with NO chain failure and NO alarm (only a '$0.0M' line buried in B_00 stdout). A materially-wrong served number ships silently.
- **Proposed fix:** Same guarded read as units, plus an explicit required-column assertion that FAILS LOUD (or skips the date with an ERROR log) when market_value is missing rather than broadcasting a scalar NaN; optionally assert the written market_value sum is > 0 before put_object so an all-NaN date cannot be sealed/served.

## Finding 3 -- [medium/other/full]
- **Location:** `_build_canonical_from_snapshot, lines 126-150 (per-date loop; try/except only at 127-130)`
- **Mechanism:** The per-date try/except ... continue wraps ONLY the _read_s3 call. All of the transform (units/mv/price/DataFrame build), to_parquet, and put_object run OUTSIDE the try. Any exception in that body on ANY single date (a dtype anomaly, a to_parquet/pyarrow error, an S3 put error) is uncaught, propagates through main() to the __main__ handler, and sys.exit(1) aborts the ENTIRE multi-date loop and the whole gold chain -- rather than logging that one date and continuing. This is the amplifier that turns findings 1/2/4 and any one-off data glitch into a full-chain abort.
- **Failure scenario:** One historical date's silver/holdings has a malformed row (e.g. a non-encodable value that makes pyarrow raise during to_parquet). Because the write is outside the try, that single bad date crashes the loop; every date after it in the sorted list is never written, and the downstream gold chain aborts -- even though 200 other dates were perfectly fine.
- **Proposed fix:** Wrap the entire per-date body (read + transform + write) in the try/except, log the failing date, and continue; accumulate a failed-date list and exit non-zero only if the failure count/ratio exceeds a threshold, so a single bad partition degrades gracefully instead of aborting the chain.

## Finding 4 -- [medium/other/full]
- **Location:** `_build_canonical_from_snapshot, line 149 (s3.put_object without ServerSideEncryption)`
- **Mechanism:** The snapshot write omits ServerSideEncryption='AES256', while every other S3 write in this file sets it (process_date L853, _worker_02b L996/L1002, forward-fill L1348, save_watermarks L199). If opal-data-cot enforces AES256 SSE via a bucket policy Deny on PutObject lacking the header (exactly the pattern documented for opal-data-schwab), this put_object returns AccessDenied. Because it is outside the try/except, that AccessDenied propagates -> sys.exit(1) -> chain abort on the first date. If the bucket does not currently enforce SSE, the objects are still written without the encryption header the rest of the pipeline standardizes on.
- **Failure scenario:** A bucket policy requiring s3:x-amz-server-side-encryption=AES256 is added to (or already exists on) opal-data-cot. The very first snapshot put_object fails AccessDenied, uncaught -> sys.exit(1) -> the nightly COT gold chain aborts at B_00 and produces no canonical holdings, while the reconciliation-path writes elsewhere in the same file would have succeeded.
- **Proposed fix:** Add ServerSideEncryption='AES256' to the snapshot put_object at line 149 to match the rest of the file.

## Finding 5 -- [medium/other/full]
- **Location:** `main, lines 1046-1051 (early snapshot branch) vs the watermark/date-arg handling at 1081-1137 that it bypasses`
- **Mechanism:** For COT the snapshot branch runs and returns BEFORE any date-range or watermark logic. _cot_snapshot_dates() returns EVERY date present in silver/holdings (regex-matched, unbounded), ignoring --date, --start-date, --end-date, the sealed-date watermark, and --force-recent-days, and _build_canonical_from_snapshot never calls save_watermarks. Consequences: (a) an operator running `--date 2026-04-02 --upload` for a targeted single-date reprocess silently rewrites the ENTIRE history; (b) sealed-day immutability is not honored -- a restated historical silver/holdings row overwrites a previously-sealed canonical day with no --force; (c) the canonical-holdings watermark is never advanced for COT; (d) the loop is single-threaded and reprocesses+rewrites all dates every nightly (perf).
- **Failure scenario:** An upstream silver/holdings correction restates a position for a long-sealed historical date. On the next nightly, B_00's snapshot path (which never checks the watermark) silently overwrites that sealed canonical-holdings partition -- the sealed-immutability contract the reconciliation path enforces is bypassed -- and any operator expecting `--date`-scoped reprocessing instead triggers a full-history rewrite.
- **Proposed fix:** Have _cot_snapshot_dates()/_build_canonical_from_snapshot honor the CLI date range (--date/--start-date/--end-date) and the sealed-date watermark (skip sealed unless --force / within --force-recent-days), and call save_watermarks() for the dates it writes, so COT gets the same immutability + targeted-reprocess semantics as the reconciliation path.
