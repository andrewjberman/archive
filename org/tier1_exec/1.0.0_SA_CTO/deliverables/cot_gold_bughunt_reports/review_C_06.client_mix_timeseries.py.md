## Finding 1 -- [high/merge-dedup/incremental]
- **Location:** `build(), lines 815-829 (advisor branch of the mix_daily_summary merge)`
- **Mechanism:** In incremental mode the firm section is correctly merged from the full existing summary (`existing.get('firm',{}).update(firm_daily_new); firm_daily = existing['firm']`), but the advisor section is NOT. `advisor_daily_new` (line 579) is initialized empty and populated ONLY for advisors that had valid new-date data this run (lines 613-622). The merge loop (821-824) only iterates `advisor_daily_new.items()`, merging each touched advisor's history in; it never re-adds untouched existing advisors. `_write_mix_summary(firm_daily, advisor_daily_new, ...)` then OVERWRITES gold/views/mix_daily_summary.json with an advisors dict containing only this-run's advisors. C_06 runs `--incremental` unconditionally in every chain run (dispatch CATALOG line 95, INCREMENTAL_CAPABLE line 903), so this executes nightly.
- **Failure scenario:** Full build seeds mix_daily_summary with advisors {Alice, Bob}, dates d1..d10 each. Nightly incremental adds date d11; Bob's only relationship has all-ghost accounts (or its partition produced no result) on d11, so `advisor_daily_new` = {Alice: {d11:...}}. The merge preserves Alice (existing d1..d10 + d11) but never touches Bob. `_write_mix_summary` writes advisors={Alice}, silently dropping Bob's entire historical series. D_03 consumes this summary and republishes advisor mix -> Bob's served advisor mix (platinum/advisors) goes blank. Every incremental run rebuilds the advisors section to only advisors active on the newest date, so any churned/idle advisor vanishes.
- **Proposed fix:** Mirror the firm handling: seed from existing advisors and update in place, then write that. e.g. `existing_advisors = existing.get('advisors', {}); for adv_name, adv_data in advisor_daily_new.items(): existing_advisors.setdefault(adv_name, {}).update(adv_data); advisor_daily_out = existing_advisors` and pass `advisor_daily_out` to `_write_mix_summary`. (Also make the firm line symmetric/safe: `firm_daily = existing.get('firm', {}); firm_daily.update(firm_daily_new)` to avoid a latent KeyError if a hand-written summary lacks the 'firm' key.)

## Finding 2 -- [high/unguarded-read/both]
- **Location:** `load_static_tables(), lines 382-390 (read of CLIENT_PERFORMANCE = gold/timeseries/client_performance.parquet); returned/unpacked at line 527, never used`
- **Mechanism:** load_static_tables does `cp = _read_parquet(CLIENT_PERFORMANCE)` (line 383). `_read_parquet` (220-222) calls `s3.get_object(...)` with NO try/except, then `cp['date'] = pd.to_datetime(cp['date'])` and `cp.groupby('date')['total_aua'].sum()`. Any of these raising propagates out of load_static_tables -> build() -> nonzero exit, which HARD-FAILS the no-timeout gold chain and aborts every downstream D-script. Crucially the result `cp_daily_total` is DEAD: it is returned (390), unpacked (527), and never referenced again -- `compute_period_views` is called at 671/777 WITHOUT the `cp_daily_total` arg. So this read buys nothing but adds a crash surface and a hard schema coupling to C_02's output. C_02 (client_performance producer) is skipped in the incremental chain (and per pipeline notes is absent from the local tree), so client_performance is only a persisted prior-full-run artifact.
- **Failure scenario:** (a) First-ever incremental run, or client_performance.parquet deleted/aged-out/not-yet-produced: `s3.get_object` -> NoSuchKey -> uncaught -> whole gold chain aborts before any client timeseries or downstream D-artifact is written. (b) C_02 renames/drops the `total_aua` (or `date`) column: `cp.groupby('date')['total_aua']` -> KeyError -> chain aborts -- all for a value that is then discarded.
- **Proposed fix:** Remove the dead read entirely (delete the client_performance load block and the `cp_daily_total` return/unpack), OR, if it is intended to feed `compute_period_views`, wrap it in try/except returning None and actually pass it through. Either way it must not be able to abort the chain for an unused computation.

## Finding 3 -- [medium/incremental-full-break/both]
- **Location:** `build(), lines 805-809 (`watermark_date = _parse_date(all_keys[-1])`)`
- **Mechanism:** After processing, if any partition succeeded (`max_date_processed` set), the watermark is written as `_parse_date(all_keys[-1])` -- the newest partition in the FULL sorted list -- regardless of whether that newest partition actually processed successfully. A partition that raised inside `process_date` is counted in `n_err` and does NOT set `max_date_processed`, but the watermark still jumps to `all_keys[-1]`. The comment justifies this as 'don't re-process files that had no usable data', but it conflates empty-result (correctly skippable) with errored (should be retried).
- **Failure scenario:** Incremental run over new partitions [d11(ok), d12(transient S3/parse error -> err)]. `max_date_processed` = d11, `n_err` = 1, but watermark is written as d12 (= all_keys[-1]). Next incremental run filters `_parse_date(k) > 'd12'`, so d12 is never retried -- that date's holdings are permanently absent from client mix/concentration and the firm/advisor daily summary, a silent 1-day data gap from a merely transient failure.
- **Proposed fix:** Base the watermark on the max date actually processed without error (e.g. track the max successfully-processed key, or advance to `all_keys[-1]` only when `n_err == 0`; otherwise cap the watermark at the newest contiguous non-errored partition). Do not advance past a partition that raised.

## Finding 4 -- [low/empty-null-handling/incremental]
- **Location:** `_merge_and_write() period-views rebuild, lines 663-669`
- **Mechanism:** The incremental views rebuild iterates the merged `mix_list` and drops any entry whose `entry.get('total_mv', 0)` is falsy: `tmv = entry.get('total_mv', 0); if tmv and tmv > 0: ...`. Entries written by the current code always carry total_mv, but existing per-relationship JSON entries authored by an OLDER code revision (before total_mv was stamped into mix rows) default to 0 and are silently excluded from `daily_dict`, so those historical dates disappear from the recomputed quarterly/monthly/annual period views on the first incremental touch.
- **Failure scenario:** A relationship JSON on S3 has mix entries d1..d30 from a prior code version lacking `total_mv`, plus a new incremental date d31. `_merge_and_write` rebuilds views but only d31 has a positive total_mv, so `daily_dict` = {d31}; the _views.json for that relationship collapses to a single period, dropping ~all history from the served period-view chart until a full rebuild runs.
- **Proposed fix:** Guard the historical case: if any merged mix entry lacks total_mv, fall back to recomputing that date's dollar amounts another way or skip the incremental views rebuild for that relationship (leaving prior views intact) rather than emitting a truncated views file; long-term, backfill total_mv on read.
