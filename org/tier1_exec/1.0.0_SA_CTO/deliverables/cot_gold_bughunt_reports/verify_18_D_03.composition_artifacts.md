## Reasoning
The code asymmetry the reviewer identified is REAL: in C_06 build() lines 815-829, the incremental merge treats firm and advisor sections differently. Firm (819-820) does `existing.get('firm',{}).update(firm_daily_new); firm_daily = existing['firm']` — it starts from the FULL existing dict, so every historical date survives. The advisor branch (821-824) instead iterates only `advisor_daily_new.items()` (advisors TOUCHED this run), merges each one's existing history in, then `_write_mix_summary(firm_daily, advisor_daily_new, ...)` (829) writes advisors=advisor_daily_new. An advisor present in the existing summary but NOT in this run's touched set is never re-added, so it is dropped. C_06 does run --incremental unconditionally every chain (dispatch CATALOG line 95; INCREMENTAL_CAPABLE line 903), and D_03.composition_artifacts.py (486-493, 546) consumes summary['advisors'] and republishes per-advisor mix to served — so a dropped advisor would reach served.

HOWEVER the flag's concrete failure scenario cannot fire for the cot pipeline, because cot has exactly ONE advisor by construction. A_01.advisor_assignments.py:85 defines SYNTHETIC_FIRM_ADVISOR = 'Cottonwood Capital Advisors'; lines 502-514 inject that single value into the architect role UNIFORMLY across every account/SCD record whenever the real role dimension is all-Unassigned (the documented cot state — cot silver carries none of the 49F role columns). Consequently C_06's rel_advisor_dict has exactly one distinct advisor, and advisor_daily_new can only ever hold the single key 'Cottonwood Capital Advisors'.

The flag requires ≥2 advisors, one touched (Alice) and one untouched/churned (Bob) that gets dropped. cot has no 'Bob' — a single advisor that is touched on every run producing any data (all relationships map to it), whose history is correctly merged at 821-824. The only path to losing even that single advisor would need new_data non-empty (else the function returns early at 629-631, leaving the existing summary untouched) while ZERO new-data relationships map to a valid advisor — structurally impossible under the uniform injection. So no concrete triggering input exists for cot; per the default-to-refuted rule, this is refuted for the current pipeline.

Severity corrected high -> low: the asymmetry is a genuine latent correctness bug that WOULD fire the moment cot's TO-3 evolution lands real multi-advisor data (at which point the fix is to mirror the firm handling — seed advisor_daily from existing['advisors'] then update). It is worth flagging for that future, but it produces no current served-data corruption for the single-synthesized-advisor cot firm.
