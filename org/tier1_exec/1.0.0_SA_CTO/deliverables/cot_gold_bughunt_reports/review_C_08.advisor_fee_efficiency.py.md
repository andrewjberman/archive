## Finding 1 -- [medium/numeric-sign-units/full]
- **Location:** `data/cot/scripts/gold/C_08.advisor_fee_efficiency.py:302-308 (_build_window, Tier-2 efficiency_pctile block)`
- **Mechanism:** Tier-2 (zero/negative-NNA advisors) is ranked with `t2['_abs_nna'].rank(ascending=True, pct=True)` and the pct value is used DIRECTLY as the tier-2 efficiency band position: `efficiency_pctile = _t2_rank * pct_tier2 * 100`. The stated intent (comments L297/L302) is 'smallest |nna| (closest to 0 = less bad) gets the HIGHEST pctile within Tier 2'. But `rank(ascending=True, pct=True)` gives the SMALLEST |nna| the SMALLEST pct (1/n) and the LARGEST |nna| pct=1.0. So the mapping is inverted relative to the comment: the author conflated 'rank #1 = best' with the pct magnitude. To realize the documented intent the rank must be `ascending=False`.
- **Failure scenario:** Two asset-losing advisors: A with NNA=-1,000 (nearly flat), B with NNA=-5,000,000 (massive outflows). Intended: A ranks higher (less bad) within the tier-2 band. Actual served efficiency_pctile: B (worst) gets ~pct_tier2*100 (top of tier-2 band, just below Tier 1) and A (least bad) gets ~0. The 'who is least bad among under-performers' ordering is served inverted. (For cot the advisor layer is empty, so no cot rows are emitted today; bug is latent/inherited and would corrupt served rankings the moment cot has real advisor-role data, and is live in the parent 49F/bd pipeline.)
- **Proposed fix:** Change L303 to `t2['_t2_rank'] = t2['_abs_nna'].rank(ascending=False, pct=True)` so the smallest |nna| receives the highest within-tier pct, matching the documented 'closer to 0 = higher pctile' intent. Add a unit assertion that a -1 advisor outranks a -1e6 advisor within tier 2.

## Finding 2 -- [low/schema-column/full]
- **Location:** `data/cot/scripts/gold/C_08.advisor_fee_efficiency.py:383 (_build_window, role_latest_cols['accounts_as_primary'])`
- **Mechanism:** `accounts_as_primary` is defined as `('account_id','nunique') if 'account_id' in latest_day.columns else ('total_aua','count')`. `latest_day` is a slice of `agg` (the frame passed to build_scorecard at L926), and `agg` is aggregated to (date,advisor,role) grain (L793-814) with NO `account_id` column — account_id was collapsed into `account_count` via nunique. So the `'account_id' in latest_day.columns` test is ALWAYS False and the fallback `('total_aua','count')` is always used. Since agg is unique per (advisor,role) at a single date, each groupby group has exactly one row, so the count is always 1. The documented narrow-basis 'nunique accounts where advisor held this role at latest_date' is never computed.
- **Failure scenario:** An advisor holding the 'architect' role on 40 accounts at latest_date is served role_breakdown['architect'].accounts_as_primary = 1 (not 40). Every role_breakdown entry reports accounts_as_primary == 1 regardless of true account count, breaking the B8b 'exact-for-account_count' reconciliation the field exists to satisfy. (cot: empty layer, no cot rows today; latent/inherited defect also live in 49F/bd.)
- **Proposed fix:** Compute accounts_as_primary from the pre-aggregation `detail` frame (which carries account_id) at latest_date via `detail[detail.date==latest_date].groupby(['advisor','role'])['account_id'].nunique()`, passed into _build_window as a dict (mirroring accounts_touched / small_account dicts), rather than trying to nunique the account_id-less agg frame.

## Finding 3 -- [low/other/full]
- **Location:** `data/cot/scripts/gold/C_08.advisor_fee_efficiency.py:249-264 & :474 (_build_window, effective_split_pct)`
- **Mechanism:** `effective_split_pct` is set to 0.0 ONLY in the no-fee-rates else branch (L264). In the has-fee-rates if branch (L249-260) the column is never created on latest_by_advisor, so it is absent from `merged`; L474 reads it with `row.get('effective_split_pct', 0)` which returns the default 0. The field is never computed from actual split percentages on either path, so it is served as a constant 0.0 in every advisor record.
- **Failure scenario:** Any advisor with real fee splits (e.g. 60% architect share) is served effective_split_pct=0.0. A portal consumer displaying/using 'effective split %' shows 0 for all advisors. No crash (row.get shields the missing column). Vestigial/dead served field. (cot: empty layer today; latent.)
- **Proposed fix:** Either compute effective_split_pct from the split-weighted AUA in the detail aggregation and populate it on both branches, or remove the field from the served schema and its data_contract if it is genuinely unused.
