## §0 — Convergence reading

The evidence does not support treating this as primarily a compiler-design failure
yet. H1 is real but narrow: the keyword selector only tokenizes node id /
canonical_path / kind and never indexes edge attributes, so source_file='core.py'
on an edge is in fact invisible to keyword selection, exactly as hypothesized in
the report (comp/bench/selectors/keyword.py:21-23, comp/bench/selectors/
keyword.py:61-64, comp/bench/selectors/keyword.py:79-82). But H1 cannot explain why
centrality and random are also flat, and iter-5 already frames the broader plateau
correctly: all three selectors are at lift=0.0 while structural F1 remains 0.6545
and token reduction remains ~0.958-0.961, so the family is structurally improving
without generating downstream answerability (comp/dev-bundles/dev-click-001/iter-5/
result.json:8-19, comp/dev-bundles/dev-click-001/iter-5/result.json:31-32). That
makes H3 the highest-priority unresolved question because the current benchmark
design has never measured the one thing that determines whether any further
mutation on this pool can matter: full-source judge accuracy. Given program
purpose, AB lift exists to answer whether structured assistance changes frontier-
model performance on real systems tasks, while synthetic targets are explicitly
allowed as runtime shakedown only (docs/architecture/
COMP_LEARNS_PROGRAM_PURPOSE.md:11-14, docs/architecture/
COMP_LEARNS_PROGRAM_PURPOSE.md:33-40, docs/architecture/
COMP_LEARNS_PROGRAM_PURPOSE.md:51-54). If click is already saturated from full
source, the correct move is not to contort the metric until click "passes"; it is
to classify click correctly in the program.

## §1 — Recommendations by driver

### For CTO (1.1.0_SA_CTO)

[P0] R-CTO-1 — Treat H3 as the gating diagnosis, and bifurcate target role if
confirmed

The architectural choice is not among your three options as mutually exclusive. The
right response is a fourth option: keep click as a Phase-1 shakedown target for
structural fidelity and compression-retention, but stop treating it as a credible
lift-signal target if the full-source baseline comes back saturated. That is
consistent with the stated program purpose: synthetic targets are acceptable for
runtime hardening, but the downstream causal question is about real systems-
programming tasks, not about forcing lift out of a small known library (docs/
architecture/COMP_LEARNS_PROGRAM_PURPOSE.md:11-14, docs/architecture/
COMP_LEARNS_PROGRAM_PURPOSE.md:33-40, docs/architecture/
COMP_LEARNS_PROGRAM_PURPOSE.md:51-54). So:

- Option (b) is directionally right.
- Option (c) is valid only as a secondary shakedown metric on a target like click,
  not as a replacement for AB lift in the overall program.
- Option (a) is appropriate only if you want click to remain a lift-signal target,
  which requires proving there exist click questions the judge misses from full
  source.

[P0] R-CTO-2 — Do not interpret H1 as a general selector-architecture indictment

H1 is confirmed for keyword, but it is not evidence that the whole selector layer
is wrongly designed. The implementation is explicitly node-token Jaccard over
node.id, node.canonical_path, and node.kind; edge properties are out of scope by
construction, not omitted accidentally (comp/bench/selectors/keyword.py:1-5, comp/
bench/selectors/keyword.py:21-23, comp/bench/selectors/keyword.py:61-64). Because
iter-5 is flat on centrality and random too, adding edge-attribute indexing now
risks overfitting one weak baseline selector to a target whose benchmark
opportunity may itself be zero (comp/dev-bundles/dev-click-001/iter-5/
result.json:16-19, comp/dev-bundles/dev-click-001/iter-5/result.json:31-32). Treat
edge-attribute indexing as a local extension only if H3 is falsified and you still
need keyword to participate honestly on this family.

[P1] R-CTO-3 — Reclassify the click question pool into two different measurement
surfaces

The current 11 ratchet questions mix at least two distinct aims: import/class
hierarchy facts (q01-q04) and body-level implementation facts (q05-q08), plus
adversarial import-form probes (q09-q11) (comp/targets/click/gold/
ab_questions.yaml:14-67). That is acceptable for a target-level pool, but it is not
acceptable for judging one mutation family. Import/class-inherits mutations can at
best speak to q01-q04 and parts of q09-q11; they have no credible path to
resolve_command, _param_memo, or __click_params__ body facts (comp/targets/click/
gold/ab_questions.yaml:34-52). Amend the PRD/target doctrine so future dev-loops
must declare which question IDs are in-family before interpreting zero lift as
"compiler failure."

### For COO (2.1.0_SA_COO)

[P0] R-COO-1 — Run H3 baseline first; H1 code inspection can run in parallel; do
not dispatch new mutation iters until baseline lands

Operational order matters. The cheapest discriminant is H3, and it dominates the
value of every further mutation on this pool. If full-source accuracy is already at
or near ceiling, every additional compiler iteration here is measuring the wrong
thing. By contrast, H1 is already mostly answered by static code inspection:
keyword selection is node-only (comp/bench/selectors/keyword.py:21-23, comp/bench/
selectors/keyword.py:61-64). So the right sequence is:

1. SC runs the one-time H3 baseline.
2. CTO/COO classify click based on that result.
3. Only then decide whether to continue click as a lift target, retain it as a
   retention target, or pivot to another target / mutation family.

Do not pivot immediately to body-node mutations before H3. Those may be the right
family for q05-q08, but they are still wasted work if the full-source baseline is
already saturated across the pool.

[P1] R-COO-2 — Separate "family plateau" from "target plateau" in dispatch language

Iter-5 supports the claim that the import/class-inherits family plateaued on this
pool; it does not yet support the claim that click itself plateaued as a target,
because the full-source ceiling was never measured (comp/dev-bundles/dev-click-001/
iter-5/result.json:31-32). Future COO stop-rules should distinguish:

- "family exhausted for declared question surface"
- "target unsuitable for lift measurement"
- "benchmark saturated from full source"

Those are different closures and route to different next actions.

### For SC (2.1.0_SC_CompLearns)

[P0] R-SC-1 — Run a one-off full-source baseline, not a ratchet iteration

The current harness does not have a first-class "no compression / full source"
mode. ab.py builds the user prompt from SelectedContext strings emitted by
selectors, and the selector protocol is graph-oriented (comp/bench/ab.py:46-94,
comp/bench/ab.py:110-143, comp/bench/ab.py:181-189, comp/bench/selectors/
base.py:21-37, comp/bench/selectors/base.py:39-61). That means the minimal H3 test
is a one-off script using the judge backend directly, not another ratchet
iteration. Use the same 11 ratchet_critical questions, deterministic
ratchet_critical_call, and a single prompt shape containing the full click source
relevant to the target (comp/bench/judges/base.py:33-65, comp/targets/click/gold/
ab_questions.yaml:14-67).

[P0] R-SC-2 — Expected baseline cost is 11 judge calls; wall-clock should be low
single-digit minutes at most

This is an inference, not a directly logged benchmark: 11 ratchet-critical
questions means 11 deterministic calls if you do one full-source pass per question.
The current warm-up regime calls once per (selector, question) pair; your baseline
removes selector multiplicity, so it is materially cheaper than a full selector run
(comp/bench/ab.py:46-94). Iter-5 logged 33 fresh LLM calls in 1:55, so an 11-call
baseline should be roughly one-third of that call volume, though prompts will be
larger because they contain full source; call it low single-digit minutes, not
another dev-loop session (comp/dev-bundles/dev-click-001/iter-5/result.json:32).
Treat that timing estimate as an inference from existing run density, not measured
fact.

[P1] R-SC-3 — Your cache can identify the winning question, but not fully explain
it by itself

The report premise is slightly overstated here. Cache entries store question_text,
hashes, token count, and response_text, but they do not store the selected node/
edge subset itself (comp/bench/cache.py:63-79, comp/bench/cache.py:80-96). So:

- Yes, SC can likely recover which question the iter-2/random win came from by
  replaying grading against cached responses.
- No, cache alone does not preserve the actual selected context string that made
  the win happen.
  To explain the win mechanistically, SC will need the old graph plus selector
  regeneration, then map back via selector_hash / token count (comp/bench/
  selectors/base.py:64-76, comp/bench/cache.py:45-60).

### For DS (1.1.0-1.4.0_DS_CompLearns)

[P1] R-DS-1 — If H3 is falsified, stop spending mutations on imports and move to
body-semantic surfaces

The likely uncertainty region in this pool is not q01-q04; those are canonical
code-reading facts on a small library and are exactly the sort of questions a
frontier model may already answer from full source. The more plausible miss region
is q05-q08, because those require method-definition locality, lexical call
inspection, and attribute-write tracing (comp/targets/click/gold/
ab_questions.yaml:34-52). If H3 comes back below ceiling, the next mutation family
should therefore expose:

- class/method nodes for Group.resolve_command
- method-origin / override surfaces for Command vs Group
- function-body lexical call edges for _param_memo
- attribute-write surfaces for __click_params__

That is a different intervention family, not "better import edges."

[P2] R-DS-2 — Treat q09-q11 as adversarial sanity probes, not the next mainline
mutation target

q09-q11 are explicitly adversarial and target import-form / dynamic-import /
TYPE_CHECKING failure modes (comp/targets/click/gold/ab_questions.yaml:54-67). They
matter for benchmark honesty, but they are not the best first rescue path for this
plateau. If H3 is false and you need a lift recovery path, body-semantic questions
are the higher-value place to spend mutation budget first.

## §2 — Deferrals

- Deferred: recommending immediate edge-attribute indexing for keyword — Reason: H1
  is confirmed but local, and does not explain centrality/random flatness. Fixing
  keyword now risks optimizing the weakest selector before proving the benchmark
  opportunity exists.
- Deferred: recommending click question-pool replacement right now — Reason: the
  report has not yet measured the full-source baseline. Replacing the pool before
  that measurement would collapse a clean diagnostic into a redesign guess.
- Deferred: endorsing "accuracy retention at compression" as a replacement program
  metric — Reason: it is a useful secondary diagnostic for shakedown targets, but
  the canonical program question is still aided-vs-unaided capability change on
  real systems tasks, not lossless compression alone (docs/architecture/
  COMP_LEARNS_PROGRAM_PURPOSE.md:11-14, docs/architecture/
  COMP_LEARNS_PROGRAM_PURPOSE.md:22-28).

## §3 — Malformed questions or premise errors

Q-SC-2 is partly malformed in one detail: the cache does not contain the full
"question-context pair" in the way the prompt implies. It contains question text
and response payload, but not the selected context itself (comp/bench/cache.py:63-
79). That means cache forensics can identify the winning question more easily than
they can explain the winning context.

## §4 — Unknown-unknowns (MANDATORY)

What you should have asked but didn't: whether your current A/B regime is measuring
"compression beats full source" or merely "non-empty selected context can answer
the question." The warm-up/scoring path always asks the judge against selector-
emitted context only; there is no canonical unaided/full-source comparator in the
same apparatus (comp/bench/ab.py:46-94, comp/bench/ab.py:110-143, comp/bench/
ab.py:181-189). That means H3 is not just a missing one-off measurement. It exposes
a deeper design gap: the benchmark currently has strong machinery for comparing
selectors against each other, but not for comparing compiler assistance against the
full-source condition that the program-purpose document says ultimately matters. I
would fix that instrumentation gap before over-interpreting any more target-local
plateaus.

## §5 — Cross-cutting observations

This plateau is still a useful result. It demonstrates that Phase-1 runtime
hardening is now strong enough to surface a category error cleanly: "the
intervention family got structurally better, but the benchmark gave no downstream
signal." That is exactly the kind of negative result a trustworthy measurement
substrate is supposed to reveal, not hide.
