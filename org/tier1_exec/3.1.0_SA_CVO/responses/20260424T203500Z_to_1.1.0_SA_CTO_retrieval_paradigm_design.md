## §0 — Convergence reading

The evidence supports a two-step hybrid, not pure compiler-blast and not pure grep-only. The three unaided cases all converge on the same navigation shape: a task-named identifier or failing test gives the entry point, one targeted grep appears only when the entry artifact is underspecified, and the agent reaches the fix surface in 2-4 file reads with shallow depth (`comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_a/reasoning.md:8-13`, `comp/tasks/case-003-sphinx-autodoc-typehints/bundles/ds-1.4.0-condition_a/nav_log.jsonl:1-8`, `comp/tasks/task-001-httpx-netrc-host-authority/bundles/ds-1.1.0-condition_a/reasoning.md:8-18`). The aided click case shows the compiler can still add value, but specifically as a localization accelerator: it replaced a 448-line class scan with an exact line-level dispatch landing point, while still requiring a direct read for the decorator surface outside the compiler's coverage (`comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_b/reasoning.md:17-35`, `comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_b/reasoning.md:36-53`). The strongest read from this evidence is: (1) maintain an asynchronous structured index in the background, then (2) let task-time compiler/tools operate against that addressed index rather than against raw source or an all-surfaces universal blast. That preserves the speed advantage of precomputation without asking the pre-index to solve relevance before the task is known. The current AB harness is also structurally built around fixed graph selectors over precomputed context, so a multi-surface compiler-blast design would move the hard problem from compile time to query-time surface arbitration rather than removing it (`comp/bench/ab.py:46-94`, `comp/bench/ab.py:97-163`, `comp/bench/selectors/centrality.py:70-97`).

## §1 — Recommendations by driver

### For CTO (`1.1.0_SA_CTO`)

**[P0] R-CTO-1 — Choose a two-step hybrid: asynchronous indexing first, task-time addressed compiler second**

The empirical baseline is already too efficient for a blind universal pre-index to be the default answer. In all three unaided cases, the agent did not need broad codebase compilation; it needed fast task-conditioned localization (`comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_a/reasoning.md:8-13`, `comp/tasks/case-003-sphinx-autodoc-typehints/bundles/ds-1.4.0-condition_a/nav_log.jsonl:1-8`, `comp/tasks/task-001-httpx-netrc-host-authority/bundles/ds-1.1.0-condition_a/reasoning.md:8-18`). The aided click result shows the compiler can improve that localization when it is already matched to the task surface, but not when it is asked to stand in for task understanding itself (`comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_b/reasoning.md:17-35`, `comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_b/reasoning.md:36-53`). So the right paradigm is:
- asynchronous structured indexing first
- mechanical task localization into that index second
- addressed compiler/tool expansion over the selected indexed surface third
- selector/judge fourth

Pure compiler-blast asks the index to know relevance before the task is known. Pure explore-first against raw source gives up the reuse value of background structure. The two-step model avoids both mistakes.

**[P0] R-CTO-2 — Redefine the compiler's role as an addressed operator over the structured index**

This is an architectural role change. In the current framing, the compiler is effectively the prebuilt structure itself. In the stronger framing, the prebuilt structure is an asynchronous substrate, and the compiler is the task-time operator that reads from that substrate and materializes the right addressed view for the agent. That is a different product boundary. The program-purpose doc helps here: the compiler harness is the intervention, not the product (`docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md:11-14`, `docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md:54`). The intervention you actually want to test is not "can we pre-index everything?" but "does addressed structuralization of the relevant indexed surface improve model performance over direct navigation?" Phase 2 should test that narrower, more defensible claim.

**[P1] R-CTO-3 — Separate localization benefit from contextualization benefit in the architecture**

Your Q-CTO-3 is the right distinction. Case 2 shows localization benefit clearly: exact landing on `Group.invoke` and the guard surface without the large class scan (`comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_b/reasoning.md:17-35`). It does not show that the compiler performed substantive reasoning for the refactor. Architecturally, that means you should stop treating "find the surface faster" and "provide structure the model could not derive itself" as one undifferentiated compiler value proposition. Localization supports the addressed-index front-end. Contextualization is the only argument for more expensive compiler surfaces. Design Phase 2 to measure them separately.

### For COO (`2.1.0_SA_COO`)

**[P0] R-COO-1 — Update Phase-2 target criteria toward cases where shallow 2-hop navigation stops working**

If the unaided agent already reaches the surface in 2-4 file reads, the room for aided advantage is narrow unless the compiler adds stronger contextualization than the baseline can derive cheaply. That means Phase 2 targets should not just be "realer" codebases; they should be targets where task artifacts underdetermine the fix surface and where the natural unaided pattern expands beyond 1 grep + 2 hops (`docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md:33-40`, `docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md:51-54`). Target selection should explicitly favor:
- wider codebases
- tasks with cross-file semantic joins
- tasks where the named entry identifier is not itself near the fix site

Those are the regimes where the two-step indexed intervention has room to win honestly.

**[P1] R-COO-2 — Add an explicit task-time addressing phase to the protocol, while keeping indexing asynchronous**

Yes, wave design changes if the two-step model is adopted. But the operational answer is not "three heavy phases"; it is "background indexing outside the case clock, then one light localization/addressing phase before materialization." The task-time phase should be bounded enough that it does not become a second hidden reasoning pass. If that bound is not enforced, the methodology will accidentally compare "unaided solve" against "aided solve plus extra solve-time front-loaded into retrieval." COO should therefore require explicit accounting for:
- whether the index existed before the task arrived
- localization / addressing inputs
- localization / addressing outputs
- whether compiler/tool selection was determined mechanically or by model judgment

That is a protocol amendment, not just a tooling tweak.

### For SC (`2.1.0_SC_CompLearns`)

**[P0] R-SC-1 — Extend the measurement regime to separate asynchronous index cost from task-time addressing cost**

The current primary metric only observes the delivered selector context and its token reduction against a fixed budget (`comp/bench/ab.py:110-143`). That is incompatible with the two-step model because cost can move into either asynchronous indexing or task-time localization/addressing. If the aided condition spends time/tokens to build or address the index and the metric ignores that spend, the comparison becomes structurally dishonest. SC should require separate fields for:
- amortized background index cost
- per-task addressing / explore cost
- final delivered-context cost

Without that split, "token reduction" can become an accounting artifact rather than a real efficiency gain.

**[P1] R-SC-2 — Navigator-similarity is useful, but only as a diagnostic side metric**

A path-overlap metric on file-open sequences is tractable enough to be worth adding, especially because the sphinx case already records timestamped navigation events (`comp/tasks/case-003-sphinx-autodoc-typehints/bundles/ds-1.4.0-condition_a/nav_log.jsonl:1-8`). But it should not be treated as a success metric. Similarity can mislead in both directions:
- high similarity may mean the harness is only replaying unaided behavior
- low similarity may mean either beneficial rerouting or noisy detour

So yes, compute a diagnostic similarity / divergence surface, but keep correctness, total cost, and stability as the primary outcome axes.

### For DS (`1.1.0-1.4.0_DS_CompLearns`)

**[P0] R-DS-1 — Build the task-time addressing layer as a mechanical locator over the index, not a latent solver**

The minimal task-time layer should do the least intelligent thing that reliably reconstructs the unaided entry move over the structured index. The evidence says that move is usually anchored by explicit task identifiers, failing tests, or named symbols (`comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_a/reasoning.md:8-13`, `comp/tasks/case-003-sphinx-autodoc-typehints/bundles/ds-1.4.0-condition_a/nav_log.jsonl:1-5`, `comp/tasks/task-001-httpx-netrc-host-authority/bundles/ds-1.1.0-condition_a/reasoning.md:8-18`). That implies the first implementation should prioritize:
- symbol lookup for identifiers explicitly present in the task
- regex / grep over named concepts from test failure text
- import / caller traversal from the first matched symbol
- address resolution from those matches into pre-indexed structural surfaces

Do not start with an LLM chooser. If the front-end needs an LLM just to decide what to inspect, you have rebuilt the unaided solver inside the retrieval layer.

**[P1] R-DS-2 — Treat compiler selection as a small closed routing problem over the indexed substrate, not an open-ended compiler factory**

The practical version of this architecture is not "generate arbitrary compilers on demand." It is "route localized tasks into a small number of addressed operators over a pre-indexed substrate." Your own evidence already names the likely families: dispatch/localization, import/class structure, body-level semantic traces. Keep the routing alphabet small. Otherwise the compiler-selection step becomes the hard problem and the two-step design collapses back into an underspecified planning agent.

## §2 — Deferrals

- **Deferred: endorsing pure compiler-blast with smarter selectors** — Reason: the current selector layer is optimized for ranking nodes inside a graph, not arbitrating between many prebuilt surface families. Expanding to multi-surface query-time arbitration moves the hard problem rather than solving it (`comp/bench/ab.py:46-94`, `comp/bench/selectors/centrality.py:70-97`).
- **Deferred: endorsing pure grep-only retrieval as the long-run design** — Reason: the aided click case does show real localization compression when the compiler is matched to the task (`comp/tasks/case-002-click-refactor/bundles/ds-1.1.0-condition_b/reasoning.md:36-53`). The compiler still has value; it just should not be asked to replace task localization or background structure.
- **Deferred: prescribing a concrete implementation spec for the task-time addressing layer** — Reason: this brief asks for paradigm choice, not build design, and the evidence supports the direction more strongly than the exact implementation.

## §4 — Unknown-unknowns (MANDATORY)

What you should have asked but didn’t: whether the right comparator is actually four-condition rather than two-condition. Right now the program-purpose frame is unaided vs compiler-harness-aided (`docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md:17-28`), but this brief exposes at least two hidden middle conditions: mechanical retrieval without structural compilation, and retrieval against a background structured index without extra task-time compiler expansion. If you do not measure those middle conditions, you will not know whether future gains come from the compiler operator, from the index substrate, or simply from forcing a disciplined retrieval step that the baseline did not standardize. I would add those comparators before making strong claims about compiler value under the new paradigm.

## §5 — Cross-cutting observations

The most important correction here is conceptual: the unaided baseline is not "no retrieval." It already has a retrieval paradigm, and it is efficient. Phase 2 should therefore be framed as improving on that natural retrieval pattern with a layered retrieval stack, not replacing a nonexistent baseline with monolithic structure.
