## §1 — Disagreement rate correction explained

The committed `prescreen_summary.yaml` reports `disagreement_rate=0.875` (14/16 questions show exact-match-fail + semantic-aware-correct divergence). The 2 questions NOT showing disagreement are q013 + q015.

But q013 + q015's "no disagreement" reading is itself a bug artifact:
- Their committed semantic labels are `semantic-wrong-unparseable` in BOTH regimes
- Per the V1.2 disagreement formula (`disagreement = exact_pass != semantic_grade_correct`): both `exact_pass=False` and `semantic_grade_correct=False` → no disagreement flag
- BUT SC verified by inspecting the actual FS response text that both questions are semantically correct in prose. The committed `semantic-wrong-unparseable` label is grader-extraction failure, not truth.

Under correct labels (q013/q015 FS = `semantic-correct-but-unparseable`):
- `exact_pass=False`, `semantic_grade_correct=True` → disagreement=True for both
- Disagreement count: 14 → 16
- **Corrected disagreement_rate: ~1.0** (16/16)

Every single question on griffe shows the judge-correct + exact-match-fail divergence pattern. This is the V1.2 governance split's surface working at maximum sensitivity.

## §3 — Grader bug context

For CVO awareness — the grader has two distinct bug classes documented this session:

**Bug 1: Numeric regex extraction**
- Symptom: `_NUMBER_RE` extracts FIRST number found in response text
- Affects: q013 (numbered-list response — extracts "1" from "1. DocstringSectionText...") + q015 (self-correction response — extracts "21" from initial estimate before correction to "17")
- Both responses are semantically correct; grader misextracts
- Fix: smarter extraction (e.g., last numeric token, or number-near-conclusion heuristic, or tolerance for self-correction phrases)

**Bug 2: Enumerable len>1 missing guard**
- Symptom: enumerable branch uses ANY-value check (correct for single-value, wrong for multi-value enumerables)
- Affects: q006 (Parser enum, 4 members) + q008 (on_class methods, 4 members) — would false-positive as SENTINEL without manual wrapper
- SC's `run_prescreen.py` wrapper applies set_membership-style ALL-values check when len(values) > 1
- Fix: one-condition branch in `grade_semantic()` enumerable: `if len(values) == 1: existing ANY-value; else: ALL-values` (same logic as set_membership)

DS fix TO routing to 1.3.0_DS via COO. Required to land BEFORE next pre-screen (Wave 2 .087/.088 etc.) so production-path runs without the wrapper. NO re-run of griffe pre-screen — SC's manual interventions captured the truth empirically; re-running burns LLM tokens without changing the signal.
