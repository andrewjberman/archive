## §1 — The two artifact levels

### Level A — Per-wave PRD

A wave PRD instantiates INTAKE_WAVE.md for a specific wave. It identifies:
- Wave number + provenance (e.g., what triggered this wave)
- N candidates surveyed → K selected → M dispatchable (with rationale per drop)
- Any wave-specific criteria adjustments (e.g., Wave 2 might tighten Family A ceiling if Wave 1 produced a partial-correct dominance pattern)
- Predecessor wave outcomes (what informed this wave's selection)
- Success criteria (what does "Wave N completes" mean?)
- Gates: which G1/G2/G3 thresholds are wave-specific vs. inherited from INTAKE_WAVE

Path B sub-PRD has most of these implicitly. It is structured as Wave 1 even though that framing was retroactive.

### Level B — Per-iter PRD

An iter PRD (or iter spec) describes a single primary-case iteration within a target's inner loop. It would identify:
- Iter number, target, predecessor iter result (KEEP / DISCARD / Pattern C / etc.)
- Mutation hypothesis (what compiler change is being tested?)
- Family this iter belongs to (set_membership / enumerable / etc.)
- Expected mechanism (why might this work?)
- Success criteria (ab_lift threshold, KEEP/DISCARD/Pattern C decision tree)
- Predecessor learnings that informed the choice

Click iters 2-7 had all of these in some form but never in a single artifact — the COO TO captured the dispatch instruction, the SC scorecard captured the result, and the failure-mode diagnosis came in CTO session logs. There is no canonical "click iter-3 PRD" or "click iter-3 spec."

**My current view:** Level A (per-wave) needs formalization NOW because Wave 2 will trigger soon (either if griffe FAILS pre-screen → fallback awkward-array, or if griffe PASSES → Wave 2 starts). Level B (per-iter) probably does NOT need formalization — keeping iters TO-driven preserves cycle speed and the existing TO + commit-message + session-log triangulation captures everything an iter PRD would, with less ceremony.

## §3 — CTO lean per artifact level

### Level A (per-wave PRD): formalize now as a template

Author a `docs/architecture/COMP_LEARNS_WAVE_PRD_TEMPLATE.md` that COO instantiates per wave. Sections:

1. Wave number + trigger (what caused this wave to start? prior wave outcome, fallback chain activation, calendar cadence, etc.)
2. Predecessor wave summary (one-paragraph): what did the prior wave teach us?
3. Candidate survey reference (link to `comp/results/wave_<N>_candidates/candidate_survey.md`)
4. Selected K targets with rationale per (REQUIRED 1-5 + PREFERRED 6-8 grading per candidate, OUT-OF-BOUNDS exclusions cited)
5. Wave-specific criteria adjustments (if any) — e.g., "Wave 2 tightens Family A ceiling to ≤4 of 12 because Wave 1 surfaced partial-correct dominance"
6. Per-target dispatch sequence (per INTAKE_WAVE Step 3, each target's vendor + author + pre-screen plan)
7. Wave success criteria + off-ramp expectations
8. Open questions for CTO/CVO ruling (per workflow doctrine)
9. Wave change log

Wave 1 (Path B sub-PRD) has most of these implicitly. The template would let COO instantiate Wave 2 in 30 minutes from candidate survey + selected K + brief wave-trigger paragraph, instead of authoring from scratch.

### Level B (per-iter PRD): do NOT formalize

Iters are tactical, fast-cycling, hypothesis-test units. Adding a per-iter PRD layer would slow inner-loop cadence without proportional epistemic gain. Click iters 2-7 already had:
- COO TO with mutation spec + DS implementation directive
- DS commit message + session log with what was actually built
- SC scorecard with result + per-selector breakdown
- CTO session log with KEEP/DISCARD/Pattern C diagnosis + n+1 ruling
- Iteration_close brief to CVO at every iter close (workflow doctrine)

Together these capture everything an iter PRD would. Adding a 6th artifact would be process bloat.

**Possible exception:** if a future iter requires a substantial mechanism shift (not just a mutation tweak — e.g., introducing a new compiler subsystem like position-based context injection per CVO's previous deferral), that "iter" should escalate to a sub-PRD authoring cycle (like Path B's mid-Stage-3 emergence). This is captured by existing workflow doctrine — closeout briefs surface architectural shifts; CVO rules; CTO authors PRD. Don't pre-formalize this as an iter-PRD path; let the existing escalation discipline handle it.

### Q2 — Per-iter PRD: yes or no? (P0)
Should iters get formal per-iter PRDs (Level B), or stay TO + commit + session log + iteration_close brief? My lean: NO formal per-iter PRD; existing artifacts triangulate sufficiently and adding ceremony would slow inner-loop cadence. CVO has a view on whether the click iter-2-7 evidence captured enough or whether a per-iter PRD would have changed how the loop ran?

### Q3 — Wave PRD CVO review cadence (P1)
If we formalize the per-wave PRD template, when does CVO review a specific wave PRD?
- Option A: pre-authoring (CVO sees the wave PRD draft before COO ships)
- Option B: post-authoring + CTO ACK (CVO sees only what CTO ACKs)
- Option C: at off-ramp gate (CVO reviews wave outcome, not authoring)

My lean: Option B — CVO sees CTO-ACKed wave PRDs at G1 (survey → select gate). Path B sub-PRD followed this pattern. Path B was visible to CVO via the CTO ACK MCP, but CVO didn't review the sub-PRD draft pre-authoring.

### Q4 — Per-wave success criteria template (P1)
What constitutes "Wave N COMPLETE"? Three candidate definitions:
- (a) All K targets through G3 off-ramp ruling (PASS or FALLBACK), regardless of inner-loop outcome
- (b) ≥1 target through clean primary-case run
- (c) Wave-aggregate signal (e.g., "Wave 1 = griffe + sphinx fallback both characterized")

My lean: (a). Wave completion is about intake-pipeline traversal, not inner-loop outcomes. Inner-loop is target-local per V1.3 + INTAKE_WAVE; wave aggregation is Stage 4 territory. CVO view?

### Q5 — Iter-close vs wave-close brief separation (P1)
Workflow doctrine has `iteration_close` brief type at every iter close. Should there also be a `wave_close` brief type for when a wave completes (per Q4 ruling)? Or does the existing iteration_close cover both? My lean: yes, add `wave_close` as a distinct brief type — the audience and decision surface differ. Iter-close is per-iter compiler hypothesis review; wave-close is intake-pipeline performance + Stage 4 trigger evaluation.

### Q6 — Unknown-unknown
What am I not asking about wave/iter PRD shape that I should be? My blind spots: (a) whether wave PRDs should describe mutation hypotheses across iters (or stay agnostic about iters), (b) whether the per-wave success criteria should encode wave-vs-target outcome separation more explicitly, (c) whether there's a level-C (per-iter-family PRD) that I'm missing between wave PRD and iter TO.
