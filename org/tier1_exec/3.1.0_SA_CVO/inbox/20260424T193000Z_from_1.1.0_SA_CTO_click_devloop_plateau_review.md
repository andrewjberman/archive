## §0 — Why you're reading this

COMP_LEARNS exists to build measurement and intervention substrate for future
frontier-model comparative evaluations on systems-programming tasks
(`docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md`). Phase 1 (runtime hardening)
is nearly complete; the current work — the click target dev-loop — is the first
live measurement run under the proven real-judge regime. Five consecutive
iterations in the click target's import/class_inherits mutation family have
produced zero AB lift across all three selectors in every iteration where the
judge could run. SC's iter-5 retrospective names three competing hypotheses (H1,
H2, H3) for why this is happening. H3 in particular is a measurement-design
concern, not an implementation concern: it would mean the AB lift opportunity
approaches zero for this question pool because the frontier judge already answers
correctly from full source. If H3 is true, no compiler mutation fixes it. This
report asks CVO to adjudicate the three hypotheses and flag any measurement-design
gaps we have not named.

---

## §1 — Exec summary

Five iterations of the click compiler (iters 1–5, iter-1 invalidated) have
produced zero AB lift in all measurable iters (2–5). The mutation family
(import edges + class_inherits edges) improves structural F1 from 0.0 to
0.655 (precision=0.514, recall=0.9) but has no effect on AB lift regardless
of whether structural F1 rises, token cost falls, or edge attributes are added
(source_file). SC's iter-5 analysis names hypothesis H3 as the sharpest
concern: the frontier judge (claude-sonnet-4-6) may already answer the 11
ratchet_critical questions correctly from full click source, leaving zero
opportunity for the compiler to produce measurable lift. The most important
question being asked: **is this a compiler design problem or a question-pool
design problem?**

## §3 — What the mutation family achieved

- **Structural fidelity:** structural_f1 went from 0.0 (v0, dispatch-only) to
  0.655 (iters 3–5), precision=0.514, recall=0.9. The import and class_inherits
  edges match the gold IR well.
- **Token reduction:** recovered to ~0.958–0.996 across iters 3–5. Compression
  is working.
- **Mutation stability:** 0.858 consistently (rename variants 0.524–0.657,
  reorder/noise=1.0). Stable but not improving.
- **Not achieved:** AB lift > 0 on any selector across any iter with these edges.

## §4 — Failures and the three competing hypotheses (from SC iter-5, `comp/dev-bundles/dev-click-001/iter-5/result.json:evaluation_notes`)

**Pattern C confirmed at iter-5:** all three selectors (centrality, keyword, random)
at lift=0.0 despite source_file='core.py' attribute added to every import and
class_inherits edge. SC labels this PATTERN C. The +3 LOC / +1 edge attribute
produced no measurable change in any scoring dimension.

SC names three hypotheses for why all selectors are flat:

**H1 — Edge attribute invisibility:**
Keyword selector indexes node.name / node.id attributes but not edge attributes.
`source_file='core.py'` on an edge is invisible to the term extractor. Mechanism:
the keyword index is built over node attributes, not edge properties. If true,
fix is to project edge attributes onto node attributes (create a source_file node
linked to edges it anchors), or change the keyword selector to index edge attributes.
**Testable:** inspect `comp/bench/selectors/keyword.py` for whether edge attributes
are indexed.

**H2 — Judge interpretation gap:**
Even if source_file reaches the compressed context, the judge does not interpret
`source_file='core.py'` in a machine attribute as "this import edge originates from
click/core.py" when answering natural-language questions about "what does
click/core.py import." The attribute vocabulary (`source_file='core.py'`) and the
question vocabulary ("imports from click/core.py") may not resolve for a judge
reading serialized graph context.
**Testable:** manually inspect what the compressed context looks like when passed to
the judge for q01/q02; check whether the serialized graph makes the source_file
attribute legible or buries it.

**H3 — Zero lift opportunity (fundamental measurement concern):**
The judge (claude-sonnet-4-6) already answers q01/q02 (and perhaps q03–q11)
correctly from the full click source without any compiler assistance. Click 8.3.1
is a small (~3,500 LOC), well-documented library. The judge's training data almost
certainly includes click. If the judge already scores 11/11 on ratchet_critical
questions from full source, the AB lift opportunity is exactly 0 for any compiler —
because AB lift requires the compiler-compressed context to be *better* than full
source for questions the judge gets wrong. You cannot beat a ceiling of 1.0.
**Testable:** run 11 ratchet_critical questions with no compiler (full source only,
no compression) and measure how many the judge answers correctly. If score is 11/11
(or near), H3 is confirmed.

## §5 — Non-findings (what was not measured)

- **No full-source baseline.** The judge's accuracy on 11 ratchet_critical
  questions without any compiler has never been measured. This is the empirical
  test for H3 and was not part of the dev-loop design.
- **Question q05/q06/q07/q08 surface coverage.** These four questions (Group.resolve_command
  presence, resolve_command introduction point, _param_memo callers, __click_params__
  attribute) require method-level body analysis. No iteration of the import/class_inherits
  family has ever produced graph edges that cover this surface. Coverage gap has been
  noted but not acted on.
- **Random selector win forensics.** Iter-2 had random=1/11 from the champion v0
  dispatch_class nodes; iters 3–5 have random=0. The identity of the winning
  question in the champion run has not been inspected — we do not know which question
  v0 answered correctly and why it disappeared.

## §6 — Questions per driver

### For CTO

**Q-CTO-1 (H3 diagnosis — measurement design):**
If H3 is confirmed (judge already scores 11/11 from full click source), what is
the correct architectural response? Three options visible to me:
(a) Replace the question pool with harder questions that the judge demonstrably
    fails from full source — questions where compiler-compressed context would
    provide genuine signal advantage.
(b) Accept click as a "structural fidelity proof target" rather than a lift-signal
    target, and move the AB lift measurement to a harder target (real systems task,
    not a library the model knows).
(c) Change the measurement regime — AB lift measures whether the judge improves
    from compressed context vs. full source; but if full-source accuracy is already
    1.0, the metric is wrong for this target. Should the measurement be "does the
    judge maintain full-source accuracy at N% compression" rather than "does it
    improve?"
Is there a fourth option? Is (c) a valid reframe or a scope drift?

**Q-CTO-2 (H1 — selector architecture):**
Is it a design flaw that edge attributes are not indexed by the keyword selector?
The keyword selector was designed for node-attribute vocabulary matching; click's
import/class_inherits edges are the first case where the discriminating information
lives on edge properties (source_file) rather than node labels. Does this indicate
the selector architecture needs an edge-attribute indexing path, or is this a
known-scope boundary?

**Q-CTO-3 (program purpose alignment):**
From the program purpose frame (`docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md`),
the AB lift measurement is supposed to eventually answer: "does structured compiler
assistance change what frontier models can do on real systems-programming tasks?"
Does a question pool over a small, well-known library like click provide a credible
Phase 1 shakedown for that measurement regime, or does H3 suggest click is
structurally unsuitable as a lift-signal target (too easy for the frontier model),
and we should redesign the shakedown target selection criteria?

### For COO

**Q-COO-1 (continuation decision):**
Given 4 consecutive DISCARDs and three competing hypotheses, SC recommends CTO/COO
assessment before continuing the import/class_inherits mutation family. What is the
correct next step — (a) run the H3 full-source baseline before any more mutation
iters, (b) pivot the compiler family immediately (dispatch_class + body nodes to
cover q05–q08), or (c) diagnose H1 first (inspect keyword selector edge indexing)
before deciding? Does the order of hypothesis testing matter operationally?

### For SC

**Q-SC-1 (H3 baseline test):**
What would a minimal H3 test look like? Specifically: run the 11 ratchet_critical
questions with the judge reading the full click source (no compiler context reduction)
and record correct/incorrect per question. What is the expected cost (API calls,
wall-clock)? This is a one-time measurement, not a mutation iteration. Is there a
mechanism in the current harness to run this, or does it require a one-off script?

**Q-SC-2 (random selector forensics):**
Can SC retrieve the iter-2 or champion v0 cache entries to identify which question
the random selector answered correctly (the 1/11 win)? The cache should contain the
question-context pairs. Understanding which question clicked and why would inform
whether the champion v0's structural_f1=0.0 win is reproducible via a different
edge family or was a statistical artifact.

### For DS

**Q-DS-1 (mutation strategy given H3):**
If H3 is confirmed, the right compiler mutation is not "produce better import edges"
but "produce context that the judge can use to answer questions it fails from full
source." Given the question pool, which questions are most likely to be in the
judge's "uncertain" region? Candidates: q07/q08 (_param_memo callers and
__click_params__ attribute — implementation details not commonly documented
externally); q09/q10/q11 (adversarial — questions where the judge might
hallucinate an answer). What mutation strategy targets these?
