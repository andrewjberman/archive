## §0 — Why you're reading this

COMP_LEARNS exists to measure whether structured compiler assistance changes what
frontier models can do on systems-programming tasks
(`docs/architecture/COMP_LEARNS_PROGRAM_PURPOSE.md:11-14`). The question being
asked here is upstream of any individual target or wave: **what is the right
retrieval paradigm for the aided condition?** The current design pre-compiles a
static DAG and uses selectors to extract relevant subgraphs at query time. That
design has now produced five consecutive DISCARDs on the click target, with the
concurrent CVO review (25848cb1) identifying that the static compiler may be
mismatched to the tasks because it does not know the task at compile time. Andrew
has raised a broader architectural question: should the compiler come before or
after an initial explore/grep step, and does the generalized answer differ from
what we've been building? We now have empirical navigation data from three unaided
pilot runs to ground this analysis.

---

## §1 — Exec summary

The unaided agents in our Wave 2 pilot do not do broad exploration. They do
**targeted grep + shallow file-hop navigation** (2–4 file reads per task), driven
by identifiers named in the task description. This is fast and precise. The current
COMP_LEARNS compiler is the opposite: it does exhaustive pre-compilation of a fixed
surface, producing a static DAG that may or may not cover the task's relevant
surface. Two alternative paradigms exist: (A) explore-first — run a task-driven
grep before compiling, let the task guide compiler selection and generate targeted
tools on the spot; (B) compiler-blast-first — pre-compile a multi-surface index
exhaustively, use a smarter selector at query time. The central question: which
paradigm produces the most reliable aided advantage across a generalized task set,
and does the empirical unaided navigation pattern tell us something about which
paradigm the aided condition should emulate?

## §3 — Synthesized unaided navigation model

Across all three cases, the unaided navigation pattern is:

1. **Entry point from task artifacts** — the failing test, the named function, or
   the error description provides a precise starting identifier. The agent does not
   broadly explore; it reads the task carefully and extracts the relevant name(s).
2. **At most one grep** — used when the task artifact names a concept (e.g. "typehints
   on class") but not the exact file/line. The grep is for that concept, not a
   broad sweep.
3. **1–3 file reads** — following the call/import chain from the entry point. Reads
   are selective and short: agents read specific sections, not whole files when
   possible.
4. **Shallow depth** — no case required more than 2 hops to reach the fix surface.
5. **No upfront indexing** — the agents did not build an index or compile the
   codebase before starting. The "exploration" is task-driven and terminates as
   soon as the fix surface is found.

Token budget at first correct hypothesis: ~4,400 tokens (sphinx case, most complex).
The simpler cases (httpx, click) were fewer. This is the empirical baseline.

## §4 — The two paradigms and the current design

### Current COMP_LEARNS design: Static pre-compiled DAG

The compiler is run once against the full target (e.g., all of click's source).
It produces one DAG with one surface type (e.g., import/class_inherits edges).
At query time, a selector extracts a subgraph and compresses it for the judge.

**Gap relative to unaided model:** The compiler does not know the task. It produces
a fixed surface that may or may not cover the task's relevant code. For case-2
(Group.invoke refactor), the dispatch_class compiler was perfectly matched because
"dispatch surface" was the right compiler to run. For our AB lift tests on the 11
ratchet_critical questions, the import/class_inherits compiler was partially matched
(q01-q04) and completely unmatched (q05-q08).

**When this design works:** When the compiler surface matches the task's information
need. When the target's relevant surface can be defined before knowing the task.

**When this design fails:** When the task requires information not on the
pre-compiled surface. Or when the full-source judge can already answer correctly
without any compression (the H3 case).

---

### Paradigm A: Explore-first (task-driven compiler generation)

Step 1: Task/question arrives.
Step 2: Run a structured grep/scan — extract the key identifiers from the task
        description. This replicates the unaided agent's first move.
Step 3: Based on what the grep surfaces, determine which compiler surface(s) are
        needed (dispatch? imports? body analysis?).
Step 4: Run the targeted compiler(s) against just the relevant files/modules.
Step 5: Produce a small, task-specific DAG.
Step 6: Deliver to the judge.

**Advantage:** Compiler surface is always matched to the task. The judge receives
exactly the structure it needs. No wasted surface.

**Disadvantage:** Compile step is per-task (latency + cost). Requires a "compiler
selector" layer that can read the task and choose compiler tools. The compiler
generation step may itself require significant engineering (generalized compiler
factory vs. pre-built compilers).

**Structural question:** Does the compiler come after the grep — i.e., is the
explore step used to understand what AST surfaces to build, then compile just
those, then deliver the DAG? Or does the explore step itself produce the deliverable
directly (in which case the compiler is the explore, not a post-step)?

---

### Paradigm B: Compiler-blast-first (multi-surface pre-index)

Step 1: Target arrives (before any tasks are known).
Step 2: Run a battery of compilers against the full target: imports, class
        hierarchies, call graphs, dispatch chains, body analysis, decorator
        accumulation, attribute writes — every surface that could plausibly be
        task-relevant.
Step 3: Store a rich multi-surface index.
Step 4: Task/question arrives.
Step 5: Use the task text to SELECT from the pre-built index surfaces.
Step 6: Deliver the selected sub-index to the judge.

**Advantage:** Fast at query time (index is pre-built). No per-task compilation
latency. If the index covers all likely surfaces, every task has relevant context
available.

**Disadvantage:** Expensive to build the full index upfront. May miss surfaces we
didn't anticipate. The "surface selection" step at query time is itself a hard
problem — it requires understanding which index surfaces are relevant to the task,
which may require as much intelligence as the task itself.

## §5 — Tensions and open questions

**T1 — The chicken-and-egg problem in Paradigm A:**
To know which compiler to run, you need to understand the task. To understand the
task, you need to read the codebase. But the whole point of the compiler is to
avoid reading the raw codebase. In practice, the unaided agent's "grep" is the
exploration step — it reads just enough to identify the relevant surface. Can a
structured grep (regex over file names + identifier matching) substitute for the
intelligence in that first step without requiring an LLM call?

**T2 — Is the selector the right abstraction for Paradigm B?**
The current COMP_LEARNS selectors (centrality, keyword, random) operate on a
pre-built graph. They are essentially query-time filters. But they are not designed
to choose between surface types (imports vs. body analysis) — they choose nodes
within a single surface. For Paradigm B to work, the selector layer needs to
operate across surface types, not just within one. That is a different and harder
design problem.

**T3 — The unaided baseline is competitive.**
The empirical data shows the unaided agent reaches correct fix hypotheses in ~4,400
tokens and 3–4 file reads. For the aided condition to provide measurable advantage,
it must either: (a) reach the same result in fewer tokens/reads, (b) reach a higher-
quality result, or (c) be more stable/repeatable. The current COMP_LEARNS design
has demonstrated (a) in principle (case-2 dispatch graph eliminated a 448-line scan)
but not yet in the AB lift measurement (because H3 — the full-source ceiling — has
not been ruled out).

**T4 — Explore-first may require a smarter front-end than we have.**
Andrew's intuition — "modify the grep at the front end" — implies the explore step
is fast and cheap (a structured regex/AST scan, not an LLM call). If the explore
step itself requires intelligence (an LLM to read the task and decide what to grep
for), the cost comparison shifts. The unaided agent's "grep" is LLM-driven. A
purely mechanical explore step may miss what the agent's grep catches.

## §6 — Questions per driver

### For CTO (1.1.0_SA_CTO)

**Q-CTO-1 (paradigm selection):**
Given the empirical unaided navigation model (task-identifier → 1-grep → 2-hop
file-read → correct hypothesis), which paradigm — explore-first, compiler-blast,
or hybrid — is most likely to produce measurable aided advantage over that baseline?
Specifically: does the baseline's efficiency (~4,400 tokens, 3–4 files) leave room
for a compiler-assisted approach to be measurably better, or is the unaided
strategy already near-optimal for this task class?

**Q-CTO-2 (compiler role redefinition):**
In explore-first, the compiler is run after the explore step and is task-specific.
This changes the compiler's role from "pre-built structural index" to "task-driven
surface extraction." Is that a different thing architecturally — i.e., are we
describing two different products (a pre-compiler vs. an on-demand compiler), and
does COMP_LEARNS need both, one, or neither at Phase 2?

**Q-CTO-3 (what is the compiler for, precisely):**
Case-2 condition_b shows the dispatch_class compiler provided real navigation
benefit: it eliminated a 448-line class scan and gave the agent exact line numbers.
But this is a localization benefit, not a reasoning benefit — the agent still had to
do the refactor analysis itself. Is the compiler's primary value localization (find
the surface faster) or contextualization (provide structure the agent couldn't derive
itself)? The answer matters for paradigm choice: localization favors explore-first
(grep already does localization), while contextualization favors compiler-first
(structure the raw grep can't produce).

### For COO (2.1.0_SA_COO)

**Q-COO-1 (Phase 2 target selection criteria update):**
If explore-first is the better paradigm, does Phase 2 target selection need to
favor codebases where the unaided agent's natural grep/exploration is LESS efficient
— i.e., larger, more complex codebases where the 2-hop navigation model breaks down?
The unaided agent succeeded on httpx and click in 2–4 file reads. For a 500-file
codebase, the same strategy might require 20+ file reads. That is the regime where
a compiler-assisted approach would show the largest advantage.

**Q-COO-2 (wave design implications):**
If we adopt explore-first, the wave execution protocol changes: each case execution
now has a "explore phase" (structured grep) + "compile phase" (run targeted compiler)
+ "judge phase." That is 3 phases per case instead of 2 (compile + judge). Does this
change the pilot wave design in PARALLELIZATION_V1?

### For SC (2.1.0_SC_CompLearns)

**Q-SC-1 (measuring the explore step):**
If the aided condition includes an explore step (structured grep), that step itself
consumes tokens and time. How should the measurement framework account for the
explore-step cost? The current primary_metric formula includes token_reduction_pct
but measures the compression of the final delivered context only. The explore step
would be a pre-cost that the formula currently doesn't capture.

**Q-SC-2 (navigator similarity metric):**
Is there a tractable metric for "how similar is the aided agent's navigation path
to the unaided agent's navigation path"? The nav_log.jsonl format records
(timestamp, event, path, note) per file open. Could we compute a Jaccard similarity
between the aided and unaided file-open sequences? This would tell us whether the
compiler helps the agent navigate differently or just faster.

### For DS (1.1.0-1.4.0_DS_CompLearns)

**Q-DS-1 (mechanical explore layer design):**
What would a minimal mechanical explore layer look like — one that does NOT require
an LLM call? Candidates: (a) regex grep for identifiers named in the task
description, (b) AST-level symbol lookup for named identifiers, (c) import-graph
traversal starting from a named module. Which of these is fast enough to run before
compilation and specific enough to guide compiler surface selection?
