Executive summary
The problem
Anatomy already contains substantive observation, identity, qualification, structural-compilation and publication mechanisms. The immediate problem is not an absence of foundations. It is that these mechanisms do not yet implement one integrated, explicitly versioned path from newly encountered substrate to an evolving C/D world, and from that world to lawful operations and useful analysis. The September 9 report places the program in Phase 3, with a bounded observed-compiler PASS, a separate H nucleus AMEND, and unimplemented observed C3 boundary derivation. [S01, §§1–5]
The discussion developed a stronger target: D1 as explicit state, D2 as an evidenced state transformation, D3 as structurally evidenced composition of transformations, and C2/C3 as Minimal Sufficient Compositions. It also identified deterministic substrate discovery, a kernel shared by compilation and use, persistent identity across change, two distinct evolution loops, and a Bronze/Silver/Gold workspace model. These are design requirements, not descriptions of completed code. They must be reconciled with the existing contracts rather than layered on through informal renaming.
Without that reconciliation, a dependency role can be mistaken for an executed transformation, a shared identifier for a material handoff, a query cohort for a compiled system, or a successful action request for an observed change in reality. The same ambiguity would make adapter behavior substrate-specific in uncontrolled ways and make higher-order identity unstable when observations or constituents change.
The proposed solution
Implement six coordinated workstreams under a shared, versioned contract set. Part 1 defines structural laws and the expanded C/D semantics. Part 2 discovers, parses, binds and qualifies substrate deterministically. Part 3 provides executable structural primitives and the H authority/transition boundary. Part 4 extends existing identity machinery to the newly compiled higher-order structures. Part 5 publishes world evolution and separately evolves useful lenses. Part 6 provides an evidence-bound workspace for analytics, hypotheses and proposed actions.
The intended operating cycle is: acquire evidence; normalize without losing source distinctions; resolve scoped identity; derive state, transformations and compositions; validate; publish a pinned world basis; operate or analyze against that basis; and observe any external effects before recompiling them. AI may propose adapters, plans and analyses, but it cannot substitute its output for source evidence or exempt a candidate from deterministic checks.
What the user receives
A customer installs Anatomy in its own environment and grants bounded access. Anatomy inventories the accessible substrate, uses admitted readers and bindings, exposes what is unsupported or unresolved, and constructs a reproducible structural representation. A human or agent can then trace evidence, traverse relationships, compare states, decompose compositions and explore changes through the same operation contracts. External action remains separately authorized and its outcome separately observed.
The benefit is reusable implementation infrastructure: a new adapter should bind native structures into common primitives rather than implement a new world model; a new lens should compose existing operations rather than invent a private graph; and an agent should propose work through stable contracts rather than independently define identity, authority or completion.

Part 1 — C/D semantics and substrate-invariant compilation laws
1.1 Objective and existing foundation
Make the meaning of each structural level, each D representation and each permitted composition explicit enough to implement and independently test. The governing principle is structural derivation from evidence, not intent-driven grouping, recurrence thresholds, subjective importance or a user's desired system boundary.
The current foundation names c0_fact, c1_interaction, c2_motif, c3_structure and c4_routing_segment; its process rails are d1_value_grain, d2_path_flow and d3_obligation. It also carries a C3 partition distinguishing discovered structure from declared semantic verticals. The new target is therefore a contract revision, not merely a clearer description of unchanged enums. [S05]
The observed compiler currently emits graph-property D1 carriers, D2 dependency bindings, C2 observed arrangements, scoped condition applications and role-qualified joins. It explicitly emits no C3. Existing useful output must survive the migration with its original evidentiary scope intact. [S03; S01, §3]

C and D are not interchangeable axes. C describes referents and structural composition. D describes state, transformation and composition of transformations. The displayed sequence C0 → D1 → C1 → D2 → C2 → D3 → C3 is a dependency-oriented explanation, not a requirement that all extraction occur in that order or that each D rail may attach to only one C layer.
1.3 Minimal Sufficient Composition: the compilation law
Retain the agreed name Principle of Minimal Sufficient Composition (MSC). A higher-order structural object is admissible only as a losslessly decomposable composition sufficient for its evidenced D phenomenon, with no unnecessary structural support under the applicable contract.
Proposed formalization: for a pinned evidence basis E, versioned contract K, evidenced phenomenon d and candidate support set S, define Supports(E, K, S, d). Then MSC(S, d) holds when support is established and no proper subset of S also supports the same d under the same E and K. Every term in that test must be inspectable and reproducible.
“Minimal” means inclusion-minimal, not automatically the fewest nodes among all candidates. Several distinct minimal supports may exist. Deterministic serialization can order them, but an ordering must not be misrepresented as proof that one is the uniquely real system. Equivalent representations may be normalized only under an admitted equivalence contract.
The earlier conversational removal test is a useful starting point, not a complete implementation proof. Single-item deletion establishes full subset minimality only where the support predicate has the necessary monotonicity properties. The implementation must either prove those properties for its restricted grammar or check the relevant proper subsets. Search exhaustion and budget exhaustion are different outcomes.
Minimality applies to constitutive support, not to retention of evidence. Redundant receipts, repeated deliveries and alternative witnesses remain preserved in provenance even when they are not all needed in a minimal structural support set.
The remaining boundary question
MSC minimizes support for a specified D phenomenon; it does not itself decide which end-to-end phenomenon should define a unique system. That choice cannot be supplied invisibly by a query, an arbitrary traversal limit or the compiler author's preferred chain length.
The proposed first implementation derives D2 targets from bounded source-supported operation/effect records and derives D3 candidates from evidenced interface compositions. Where source records establish a complete execution, transaction or equivalent closure, that evidence can bound the target. Where no unique closure exists, emit the justified composition candidates and their boundaries as explicit results; do not claim a unique system partition. C3 publication must distinguish a compiled composition instance from an unresolved durable system designation.
A gate before declaring the C3 algorithm complete is therefore mandatory: demonstrate non-circular target generation, exact support, minimality, treatment of overlapping candidates, and behavior under incomplete evidence. The direction is agreed; that algorithmic closure remains work to perform.
1.4 Scoped resolution and grain preservation
Retain scoped resolution as the companion law: a fact or transformation is valid at the grain and scope established by its evidence. Crossing grains or identity spaces requires an explicit, evidence-bound bridge with declared direction and permitted operation. A bridge does not automatically license every inference involving its endpoints.
Multiple grains may coexist. In the Lambda example, a function, a logical S3 object, a table and an independently keyed row can each be C0 referents under different grain contracts. File version, row state and function code revision are D1 coordinates or associated records; they are not automatically new C0 identities. A row occurrence without a stable key may be identifiable only within a particular captured file version. That is a narrower identity, not a failed attempt to invent a permanent row.
The source already checks bridge endpoint grain, direction, lineage and evidence. Its admission authority in the inspected bridge path is explicitly conformance-fixture-only. Extend this mechanism through a governed production-admission contract; do not remove the fixture restriction as a shortcut. [S04, check_bridge_population]
A proposed grain bridge carries source/target identity spaces and grains, endpoint references, cardinality, validity coordinates, evidence references, mapping version and the operations it supports. For example, a file-to-row membership bridge may support enumeration and containment. It does not by itself prove that every row was logically modified by the last writer of the file. Whole-file replacement, row mutation and business-entity change remain distinct effects.
Aggregation must retain its denominator, multiplicity and membership support. A displayed sum is not invertible merely because the underlying composition is losslessly decomposable. To recover contributors, the result must retain or reference them. Missing members must not be presented as an exact zero or complete total.
1.5 D1 implementation: explicit state observations
Introduce a proposed StateObservation contract linked to the existing identity-state-observation machinery rather than creating a competing identity system. Its minimum information is: subject identity; identity space and grain; source locator; source state/version token where available; state payload or retained payload reference; effective/source time and observation time; presence/availability status; normalization version; and evidence references.
Separate immutable observation identity from referent identity and from state-content digest. Repeated delivery of the same observation, two observations of the same state and two different states of the same referent are different situations. A content digest can verify bytes; it must not independently decide referent continuity.
Use explicit states for observed present, observed absent, unavailable and unresolved. Preserve present-null separately from missing field. Record field-level support when only part of a state is visible. Unknown state is not an empty object or a manufactured before-state.
The user-facing rule is simple: the Lambda may cease to exist while its historical identity remains referable. A source table may also update or delete rows. Anatomy preserves its observations append-only under retention rules; it does not require the external source itself to be append-only.
1.6 D2 implementation: evidenced state transformation
Preserve the existing dependency bindings as structural evidence. Add a distinct proposed StateTransformation form containing operation/occurrence reference, actor when evidenced, affected subjects, read-state references, before-state references, after-state references, effect granularity, native relation references, support evidence and a completeness classification.
A D2 is not the Parquet row or metadata attached to it. It is the typed relation between supported states and an operation/effect. The row's values can be part of D1. An execution ID, write receipt or manifest supplies evidence binding the operation to the state transition; it is not the transformation by itself.
Require enough evidence for the exact transition asserted. Seeing a new version without an observed earlier absence does not prove creation from absence. A successful invocation without readback does not establish the resulting artifact state. A dependency declaration without runtime evidence remains a dependency or an encoded transformation contract, not an observed execution.
Transitions may involve several inputs and outputs. They need not be arithmetic subtraction. A no-op can retain equal before/after states when execution is evidenced; a read can establish consumption without inventing an output-state change. Failed or partially observed operations retain their observations and explicit incompleteness rather than being forced into a completed D2.
1.7 C2 implementation: minimal support around D2
For each admitted D2, construct candidate structural support from its bound actor, subjects, native relations, state interfaces and other contract-required participants. Evaluate sufficiency against that exact D2, then compute minimal supports under MSC. Store a support certificate, factor references, retained-evidence references, contract version, completeness and decomposition recipe.
The minimal closure is relative to the bounded effect being represented. A write-effect motif is not a declaration that all internal computations, upstream inputs or possible causes of that Lambda have been observed. Any unobserved external inputs remain open interfaces or explicit unknowns. This prevents a small motif from overstating causal completeness.
The previous one-eligible-edge/one-arrangement output cannot silently become a proven transition motif. Preserve it under its original representation version and migrate only records whose evidence satisfies the new C2 contract. Reject content-addressed C2 identifiers that do not rederive from their specified support; the prior review identified a missing check here. [S02, §2]
1.8 D3 implementation: structurally composed transformations
A proposed TransitionComposition references its constituent D2s, exact interface joins, ordering or partial-order evidence, exposed input/output states, internal material states, scoped source conditions and retained intermediate transitions. It expresses composition, not an externally imposed purpose.
For material continuity, match the produced state reference of one transformation to the consumed state reference of another, or use an admitted state-equivalence bridge whose scope supports that comparison. Sharing a filename, bucket key, timestamp or actor is insufficient to establish exact material continuity. If one step consumes V19 while the other produced V18, the asserted V18 handoff fails; neither underlying observation is erased.
Separate material lineage from activation/control lineage. A notification and a scheduled activation may both lead to consumption of the same material state. D3 can preserve that common material composition while also recording their different control structures. They need not be the same complete C3 identity. Whether a control participant is constitutive depends on the evidenced phenomenon and contract, not on a blanket rule that triggers always matter or never matter.
Conditions are preserved as source structures with their original scope. Do not invent freshness limits, relevance weights, required validation states or environmental rules. An opaque condition stays uninterpreted. An executable source condition may be evaluated only through an admitted evaluator with explicit input bindings; its result remains scoped to that application. Normative authorization rules belong to governance and do not rewrite what was observed.
Retain the full composed path even when the net before/after values are equal. Equal net state does not erase intermediate transformations. Joint-input, fan-out, fan-in and feedback cases need explicit composition rules; pairwise adjacency is not enough to establish conjunction or complete process closure.
1.9 C3 implementation and migration of historical constructs
Compute C3 candidates from admitted D3 targets and their C2 support, using the same MSC sufficiency/minimality contract. Record alternatives, overlap and unresolved interfaces. A selected query cut is an acquisition boundary, not proof of a system boundary. A resource budget may bound work but cannot become a structural fact.
Existing declared semantic verticals and source-authored groups must not be erased or quietly reclassified. Preserve them under their existing versioned contracts and record declarations as declarations. Under the proposed model, a user-selected analytic cohort belongs in Gold; the fact that someone declared a grouping can still be recorded from Bronze into Silver as a declaration. It does not thereby become an MSC-derived C3.
The supplied historical C3 reconciliation also discusses recurrence and union-find. The new observed lane explicitly does not impose a frequency requirement. The migration must identify which historical discovery rules are superseded for the new profile, retain their historical results and publish no blanket statement that all prior C3 constructs were already MSC objects. [S03, S05, S14]
1.10 Deliverables and acceptance gate
Deliver a versioned semantics package, a compatibility/migration matrix, D1/D2/D3 and C2/C3 schemas, grain/bridge operation contracts, proof/decomposition formats and a cross-substrate conformance suite. Implement independent validators rather than trusting producer flags.
The gate must cover unknown-versus-absent states; create/update/delete/no-op; missing before-state; forged or mismatched execution evidence; exact-version and wrong-version handoffs; event versus scheduled activation; fan-in with a missing input; opaque conditions; unsupported row-level promotion; cycles; multiple minimal supports; forged derived IDs; and query-selected boundaries. Neither deterministic output nor passing examples alone establishes the full MSC law.
Part 2 — Deterministic substrate bootstrap
2.1 Objective and existing foundation
Make onboarding largely autonomous without allowing an AI or adapter to decide what exists by plausibility. The bootstrap must expose what source surfaces are accessible, what is parseable, what bindings are established and what remains unresolved. Its output is qualified evidence and bindings, not an assertion that every possible substrate can be understood automatically.
The Phase 2 adapter currently provides repository and synthetic population acquisition, raw acquisition ledgers, qualification and explicit admission. Observation intake separately preserves source availability and knowledge-status distinctions without minting identity. Reuse these boundaries while expanding reader and binding coverage. [S07]
2A.1 Enumerate a finite, pinned acquisition frame
Begin with granted source roots, API scopes, database snapshots or other explicit acquisition frames. Record credentials by reference, source identity, enumeration method, pagination/completeness evidence, acquisition time and source vintage. No background expansion into ungranted environments is implied by discovery.
A pinned capture is finite, but the universe of all possible file formats and source semantics is not established by that fact. The implementation therefore uses a versioned supported-reader registry. Unknown, encrypted, corrupt, inaccessible or unsupported material is retained or referenced as opaque evidence with an explicit status. It is not silently dropped, decoded by guessing or treated as empty.
Different captures may have different temporal consistency. A database snapshot, a paginated API scan and a directory read are not assumed to represent one instantaneous source state. Preserve acquisition intervals and consistency qualifications, then restrict downstream comparisons accordingly.
2A.2 Parse native structure before proposing identity
Readers inspect format signatures and explicit schema where available, then produce a typed intermediate observation envelope. Proposed initial families are delimited records, JSON-like structured data, columnar/table captures, database catalog and row exports, resource/API records, event/log records and admitted code/configuration parsers. This is a rollout list, not an assertion that all readers exist today.
Each envelope retains raw evidence references, parser version, native locator, type information, structural boundaries, native keys, available constraints, time/version fields and parse diagnostics. Preserve ordering and duplicates where the format makes them observable. The normalizer may canonicalize representation only under a versioned, reversible-or-source-retaining rule.
Typed normalization must not collapse integers, floating-point values and Booleans, or overwrite native fields with adapter-added metadata. Carry forward the observed v2 repair controls. [S03; S01, Engineering C]
2A.3 Generate substrate bindings deterministically
Use a restricted binding grammar rather than arbitrary generated code. A binding declares a source selector, identity space, grain, key candidate, scope, lifetime/version coordinates, relation selectors, state extraction and evidence pointers. Generate candidates first from explicit source identifiers and constraints, then from structural combinations permitted by the grammar.
The “least identifiable atom” is not the shortest string and not necessarily a single column. Find inclusion-minimal distinguishing keys within a declared population and scope, but distinguish observed uniqueness from source-declared uniqueness and from evidenced continuity over time. A column unique in one file is only demonstrated unique in that file until stronger evidence is available.
Maintain separate candidate bindings for entity identity, state identity and occurrence identity. A timestamp may distinguish log occurrences without identifying the resource they describe. A content hash may identify a state without identifying the continuing object. A row number may identify a captured occurrence but fail as a cross-version entity key.
2B.1 The deterministic adversarial loop
The proposed loop is: enumerate candidates; canonicalize and deduplicate equivalent candidates; execute a fixed battery; retain counterexamples; minimize surviving bindings; issue a scoped qualification result; and seek explicit admission under the applicable authority contract. The battery invokes the Part 3 structural primitives rather than implementing a second algebra.
Its inputs must include the evidence-frame digest, binding-grammar version, reader versions, deterministic enumeration order, test specification and resource budget. Its outputs include the candidate, witness coverage, failed tests, unresolved obligations, minimality status and a replayable receipt. No ambient clock, mutable default or unrecorded external fetch may alter the result of a replay.
Return outcomes such as qualified for a stated scope, rejected by a counterexample, unresolved because evidence is insufficient, unsupported representation, or incomplete because the budget was exhausted. These labels are proposed output states, not replacements for current enums without migration.

A battery provides bounded conformance evidence and counterexample search. It does not prove that an empirical key will remain unique forever or that missing source information can be reconstructed. Proof obligations must state their quantification: checked over this captured population, guaranteed by this source contract, or unresolved beyond this evidence.
2B.3 Upward recursion without hand-drawn domain rules
After an identity binding is admitted, the same process may propose relation bindings, state interfaces and transformation bindings. After those are admitted, the structural compiler applies the shared C/D contracts. AWS-specific names belong in a customer-local or source-family adapter profile; the C2/D3 minimality and composition operators should not contain if AWS or if peptide branches.
Universality belongs to the grammar and validation laws, not to an assumption that every source reveals the same structures. A clinical table may establish a measured response and its collection coordinates without proving a drug caused that response. That evidence can support observations and recorded relationships; it must not be forced into a causal D2 merely to populate every level. This is an architectural test case, not a clinical assertion.
2C. AI participation after deterministic search
Attempt the admitted deterministic candidate space first. Escalation is justified by a recorded unresolved binding, unsupported representation or configured search limit. Do not require literal exhaustion of every conceivable program before using AI; require an explicit account of what bounded deterministic search actually covered.
AI may propose a selector, key combination, parser extension, evidence location or mapping expressed in the restricted grammar. It may also propose code, but such code remains untrusted development input and requires isolated review and reader admission before access to a live source. AI cannot mark its own proposal proven, change the battery, invent a bridge, broaden access or supply missing observations as facts.
An admitted adapter executes deterministically under a pinned version even when AI helped author it. A failed candidate and its counterexample may be cached to avoid repeated search. That cache improves discovery efficiency; it is not an alternative source of structural truth.
2.2 Integration, deliverables and acceptance
Extend the existing adapter SPI and qualification records; add reader and binding registries through their governed manifests; connect evidence envelopes to identity/state contracts; and route tests through the shared operation ABI. The proposed logical homes remain platform/os/adapters for acquisition and platform/substrate for structural normalization/contracts, with exact new paths admitted before implementation. [S07, S12]
Deliver a finite-frame reader manifest, binding IR, deterministic enumerator, counterexample store, qualification receipt, AI-proposal boundary and replay harness. Acceptance requires at least two structurally different fixture families, including an unsupported case that remains opaque, a false key that is rejected, a valid key qualified only within its supported scope, and an AI candidate subjected to the same tests as a deterministic candidate.
Part 3 — The deterministic operations kernel
3.1 Objective: one operation contract, distinct implementation responsibilities
The kernel is the stable executable boundary through which structural laws are applied and operations are governed. It is not an SDK, a natural-language model, a universal scheduler or an assertion that H already contains a graph query engine. SDK, CLI, web and MCP clients should invoke the same versioned operations and receive equivalent typed outcomes.
Use two cooperating layers. The structural core implements identity/state interfaces, typed relations, composition, decomposition, comparison and proof validation under B/K/J contracts. The H governance/runtime layer resolves caller authority, target context, legal operational transitions, receipts and consequential-action admission. One public operation contract can route through both without forcing every parser or compiler into one Go binary.
This preserves H's existing Fabric Runtime and Governance distinction while implementing the proposed shared path for batteries and later callers. Any expansion of H's public scope, schema inventory or package layout requires an explicit decision and successor acceptance basis. The existing H boundary specifically warns against extending the lens declarative-IR decision to H without a separate decision. [S09]
3.2 Current H capability and repair priority
The committed H nucleus contains canonical objects, required coordinates, state axes and canonical state serialization. The supplied working tree adds transition definitions and a Fabric evaluator for heartbeat/readiness, message delivery/acknowledgment, execution start/completion, evidence recording, context rehydration and HQ-disconnection observation. This evaluator is uncommitted in the supplied snapshot and is not a completed governance implementation. [S08; S02, §§3–4]
The report's three nucleus findings concern invalid Unicode, ambiguous JSON members and a caller-mutable admitted-kind list. The earlier local review also reports cross-target lifecycle leakage, idempotency-key/request mismatch and noncanonical transition ordering. These findings must be reproduced against a pinned successor and closed before expanding trusted operational use. [S01, Engineering E; S02, §4]
A proposed first repair increment must reject invalid text before canonicalization, enforce exact unique JSON keys at every level, make kind admission immutable, scope lifecycle axes to the relevant target/aggregate, bind idempotency keys to canonical request fingerprints and normalize unordered transition components. Preserve event ordering where ordering is part of the contract.

Such a result does not prove material handoff or admit a new C3. The structural operator applies the stronger evidence/compatibility contract when composition is being established.
3.4 Proposed operation envelope and result contract
An operation envelope contains operation ID/version, caller principal, tenant/environment, resolved or unresolved target references, world-basis digest, law/contract versions, typed arguments, effect class, authority references, request fingerprint and declared limits. Consequential operations also carry an idempotency key and target-specific preconditions.
A result contains status, typed value or transition, exact basis used, coverage/denominator, supporting evidence and derivation references, exclusions/unknowns, effect classification and receipt. Refusal leaves the protected prior state unchanged. Budget-limited results must never be indistinguishable from complete results.
Do not accept authority eligibility merely because the caller supplied eligible. Resolve grants, delegation, tenant scope, expiry, review separation and the applicable action/target from admitted authority records. The current evaluator consumes provided authority/dependency facts, so a trusted resolution boundary remains an integration obligation. [S08; S02, §3]
Time can be an input to evaluating an explicit authority expiry. That is different from the structural compiler inventing an age limit for a state interface. The implementation must preserve this separation between source structure and operational governance.
3.5 Cross-language execution and shared semantics
Retain working Python acquisition/compilation code while the Go kernel is hardened. Define a language-neutral operation IR and canonical result contract, then implement a reference evaluator and independent conformance vectors. Route callers through the admitted boundary; do not begin with a wholesale rewrite that obscures previously tested behavior.
Where Python and Go both validate a record, pin a common canonicalization contract. Explicitly test numeric typing, key uniqueness, Unicode, collection ordering, unsupported values and digest domain separation. Existing Python and Go serialization routines are not assumed equivalent because both use JSON.
The operation ABI should distinguish pure structural computation from trusted state mutation and external side effects. A scheduler may call it, and a transport may deliver its commands, but neither owns the structural laws. Customer-local and HQ distributions may share portable contracts without sharing customer data or private bindings. [S09, S12]
3.6 Internal versus external state transitions
The kernel may authoritatively append its own receipts and change its own target-bound operational state. It cannot commit an AWS resource change merely by updating a world-model record. An external request has separate stages: proposed, authorized, submitted, externally reported outcome, observed outcome and recompiled world effect.
A retry after an ambiguous external result must reconcile with the provider or retained evidence before issuing another potentially non-idempotent action. Kernel receipt idempotency alone is not a promise of exactly-once external execution. Tests must include partial success, lost response, delayed observation and state changed by another actor.
3.7 Deliverables and acceptance
Deliver the operation catalog, typed ABI, canonicalization profile, target-state model, authority-resolution contract, effect classification, refusal taxonomy, cross-language vectors and H repair evidence. Preserve the original H negative obligations: duplicate delivery, stale authority, self-approval, missing readiness dependency, context loss, message race, verifier absence, break-glass expiry and HQ disconnection. [S09, §6]
Acceptance additionally requires cross-target message/run isolation, conflicting idempotency reuse, forged facts, cross-tenant targets, noncanonical input, stale world basis, empty-versus-unavailable queries, incomplete traversal, and an external action whose reported success does not yet establish observed completion. H acceptance remains the prerequisite for tools admitted against its digest. [S01, §2]
Part 4 — Recursive identity continuity across composition change
4.1 Objective and verified prior work
Determine when independently compiled higher-order objects represent successive states of the same referent, and when they represent replacement, split, merge or a new occurrence. Reuse the established identity model before inventing a new one.
The source already separates opaque entity serials, native bindings and state observations. Tests cover rename versus substitution, persistence over a declared series and portability sensitive to changed content. The relation vocabulary includes candidate equivalence, canonicalization, merge, split, successor, replacement, instance and retirement. These are real prior mechanisms, though their existing fixture coverage does not establish MSC-based C2/C3 continuity automatically. [S04]
4.2 Four identifiers that must remain distinct
Keep a persistent referent identity separate from its native binding, a composition-instance/content identifier and a compilation-generation identifier. A name can change while the referent persists. The same name can be reused for a replacement. A member-set digest changes when membership changes even if an admitted higher-order continuity contract preserves the referent.
Likewise, a D2 execution occurrence is not a reusable operation definition. Two runs may instantiate the same structural motif family while remaining different transformation occurrences. A C3 compiled for one evidenced D3 instance does not automatically become the durable identity of every later run with a similar shape.
4.3 Proposed continuity contract
For each admitted class/grain, declare the identity scope, native anchors, continuity witnesses, state-change rules, replacement/incarnation evidence, allowed bridge types and unresolved behavior. The contract must say what evidence supports continuity rather than allowing a similarity score to create it.
For C2/C3, reference the existing opaque serial machinery and evidence-bound identity relations. Store a separate support-instance digest for each compilation, together with a continuity decision linking it to the referent when justified. Constituent changes must be visible in the state/version record even when identity is retained.
Start by applying existing contracts recursively to controlled rename, constituent substitution, split/merge and recreation cases. Where those contracts cannot decide a higher-order case, return unresolved continuity and retain both instances. Do not equate an unresolved case with either automatic identity preservation or automatic identity destruction.
4.4 Membership changes, overlap and trigger variation
MSC proves minimal support for an instance; it does not answer persistence by itself. A change to the activation mechanism may leave a material-composition view unchanged while altering the full control/material structure. Compare the precise object/profile being identified, not the visual resemblance of two diagrams.
A C3 split should preserve its predecessor history and link successor objects through the applicable relation rather than repurpose one serial for multiple referents. A merge should retain both origins. Overlapping C3 candidates may share C2 factors without requiring those factors to belong exclusively to one system.
Grain changes are also not renames. Replacing a file-level observation with row-level observations requires an admitted bridge and coverage evidence; it cannot silently change the grain of the same identity record.
4.5 Integration, deliverables and acceptance
Extend identity_contracts.py, its schemas and the existing continuity tests; connect identity decisions to C2/C3 support certificates and world publication. Retain source and normalization versions in continuity evidence. Schema names and serial formats should remain compatible unless a separately approved migration changes them. [S04]
Deliver a continuity decision matrix, higher-order identity profile, ambiguous-case carrier and history/decomposition tests. Acceptance must include rename, identical-name replacement, constituent change, delete/recreate, observed absence, missing observations, split, merge, alternative minimal support, cross-grain mapping and event-to-schedule variation. The result must identify which existing rules lifted successfully and which residual cases required new contracts.
Part 5 — Evolution: the world loop and the lens loop
5A.1 World evolution is evidence evolution
The world loop ingests new evidence, recompiles affected structures, validates a successor and publishes a new world basis. It does not train a model to decide reality. The kernel supplies deterministic operations and controlled publication; source change and newly available evidence provide the new inputs.
Call a published basis Wn. It is a pinned, provenance-bearing compilation under explicit contracts, not a claim of complete or infallible knowledge about reality. A successor Wn+1 may contain new observations, revised support, unresolved conflicts, retired bindings or narrower knowledge. More data does not necessarily mean every previous derivation remains current.
5A.2 Reuse the current publication machinery
The cognitive compiler already constructs generation artifacts and validates publication candidates. Its publisher retains immutable receipt/index/transaction artifacts, uses an active journal and can roll forward or roll back after interrupted publication. Generalize and integrate this path rather than adding an unrelated publisher for observed C/D output. [S06]
The proposed world manifest binds parent basis, evidence-frame digests, adapter and binding versions, semantics profile, compiler version, kernel ABI, identity decisions, materialized projection digests, support/decomposition indexes, completeness and publication receipt. Source evidence, compilation outputs and the active serving pointer have different lifecycle rules and must remain distinguishable.
The current file-based recovery mechanism does not itself establish multi-writer or distributed publication guarantees. Begin with an enforced single-writer or equivalent admitted publication boundary. Add concurrency semantics only with explicit predecessor checks, conflict handling and recovery tests; do not infer them from atomic file replacement.
5A.3 Proposed successor pipeline
First acquire and retain the new evidence frame. Next normalize and compare it with the relevant prior frame, preserving late observations and conflicting source reports. Then resolve identities and states, determine affected support dependencies, recompile and validate the candidate. Finally publish its immutable evidence and switch the active basis only through the admitted publication transition.
Use support references to identify affected higher-order objects. For each, re-establish support or explicitly mark why it no longer has current standing. Do not silently carry a C3 forward after a constituent or its evidence bridge changes.
Incremental computation is an optimization, not a different semantics. On the same evidence and contracts, incremental publication must agree with a full replay. Test that equivalence before relying on selective recompilation. A late observation may refine a historical source-time view while being recorded in a later knowledge/publication generation; preserve both coordinates.
5A.4 Corrections and retention
Keep prior evidence and derivations available under the applicable retention contract. Correct an erroneous source observation by recording its correction/supersession and recomputing dependent support, not by pretending the earlier capture never existed. Observed absence requires scoped evidence; loss of access must produce unavailable or unresolved states.
Logical append-only history does not override deletion obligations or customer retention controls. Where bytes must be purged, preserve only permitted audit metadata and an explicit unavailable-evidence state; do not claim the old result remains fully replayable. Keep this policy boundary explicit rather than promising permanent retention of every source byte.
5A.5 Acceptance
Deliver an observed-to-publication adapter, world manifest, impact/dependency index, successor compiler, recovery harness and complete replay capsule. Test duplicate delivery, no-change evidence, concurrent candidates, stale predecessor, partial publication, crash recovery, source correction, late arrival, lost access, retirement and incremental/full equivalence.
Reconcile the exact published product cut with formal certification. A bounded compiler PASS or unchanged old identity suite does not establish the current aggregate Phase 3 exit. [S01, §4]
5B.1 Lens algebra: useful projections, not new structural authority
A lens is a versioned composition of kernel operations that returns a projection, analysis or explanation. It can select, traverse, join, aggregate, compare and expose supporting evidence. It cannot create an MSC-derived C3 merely by selecting a group or improve a record's structural standing because the result is popular.
The supplied lens manifests already express derived-result authority, declared denominators, interface parity and a prohibition on writing structural truth. The individual product registry contains candidates, but no admitted members or executable entrypoints in this supplied snapshot. The discussed BM25/CatBoost and other earlier prototypes are therefore inputs to inventory, not implementations this proposal can certify from these files. [S10]
5B.2 Declarative plans and kernel execution
Build on the recorded decision that the lens/capability IR is canonical and execution is generated. A proposed lens definition includes ID/version, input types and grains, required authority, operation plan, basis policy, denominator construction, result schema, evidence/decomposition rules, exclusions, determinism and resource limits. Generated execution is derived from that definition, not an independent source of semantics. [S10, DEC-0024]
The lens planner may optimize execution while preserving plan meaning and declared result coverage. Ranking and retrieval can determine which authorized candidates are presented first, but a top-k result is not a complete population. Approximate retrieval, stochastic ranking and exhaustive structural traversal must have distinguishable result types.
Retain result lineage through every aggregation. A user must be able to distinguish a direct observation, an exact deterministic derived value, an estimate, a ranked suggestion and a hypothesis. These classifications should reference existing knowledge-engine contracts where applicable rather than introduce private lens-specific categories. [S13]
5B.3 Lens evolution through use
Capture user-authorized usage evidence: selected operations, traversal paths, successful task outcomes, explicit feedback and failures. Keep that telemetry customer-local by default and separate it from the evidence that establishes the modeled substrate.
A deterministic optimizer or an AI/ranking model may propose better lens compositions, indexes or presentation ordering. Replay the candidate against fixed tasks and admitted worlds; check answer fidelity, coverage, latency/resource use, permission boundaries and decomposition. Publish a new lens version only after these checks and the appropriate product approval.
MSC may inspire simpler plans, but structural MSC is not automatically the correct optimization objective for every lens. Removing a context record might shorten a result while making an analysis less useful. The proposal therefore requires a separate declared projection-preservation test before minimizing lens plans, rather than silently treating lens usefulness as a structural law.
5B.4 Two loops, one non-contamination boundary
World loop: new source evidence → deterministic compilation → validated successor world. Lens loop: usage/feedback → candidate projection or ranking improvement → validation → successor lens. Usage may suggest where to acquire more evidence, but the acquired material must re-enter the normal observation path. Repeated user belief does not become structural evidence by repetition.
Deliver the lens grammar, plan executor, result lineage, prototype inventory, usage schema and candidate-evaluation harness. Acceptance requires a lens change that improves a declared use metric without changing the underlying Silver world, a denied-input case, an incomplete-result case and a failed candidate that cannot alter canonical structure.
Part 6 — Bronze, Silver and Gold: evidence-bound workspaces
6.1 Objective and layer definitions
Provide the maneuvering space in which users can use the compiled world to reach conclusions, investigate connections, propose changes and compare alternatives. Preserve the three-layer model agreed in the discussion. Do not add a mandatory Platinum layer; serving can expose an authorized, typed artifact from the appropriate layer.
Layer
 | Contents and authority
 | Mutation rule
 |

 | Captured source evidence, raw payloads or retained references, acquisition and provenance records

 |

Bronze means faithful evidence capture, not a guarantee that every source statement is correct. A source can contain an error, allegation or hypothesis. Silver records its supported structure and provenance without converting an assertion into an established external effect. “Raw truth” is retained as the design intuition, but the operational contract must preserve this distinction.
6.2 Workspace state and typed analysis
A proposed workspace contains workspace ID/version, owner/authorization context, pinned world basis, selected lenses and operation plans, assumptions, proposed transformations, results, source/evidence references and execution status. It may branch or compare alternatives without changing the canonical basis.
Distinguish at least five result classes: exact projection of admitted structure; deterministic analytic derivation; model-dependent estimate or simulation; hypothesis/assumption; and proposed external action. An exact analytic result may be fully supported by Silver without itself becoming a new canonical structural object.
Workspace lifecycle and external-action lifecycle are separate axes. A workspace can be edited or archived while a submitted action is still awaiting observation. An analysis can be complete without an action being authorized. A simulated outcome can be internally valid under assumptions without being realized in the substrate.
6.3 Natural-language requests are candidate plans
Natural language may produce a candidate operation plan in Gold. Resolve referenced objects against a pinned Silver basis and expose ambiguity. A request that mentions “BuildHoldings” cannot silently choose among several tenant/environment-specific functions. The user or an admitted unambiguous binding must resolve the target before consequential action.
For “What is affected if BuildHoldings is replaced?”, the plan can resolve the function, traverse evidenced structural/dependency interfaces, inspect C2/C3 support and return a coverage-qualified projection. It must distinguish observed dependencies from a prediction of future failure. Counterfactual behavior requires an explicit simulation/model contract and assumptions; structural connectivity alone is not a performance or causal prediction.
The corresponding clinical workspace might ask where two recorded entities are connected. It can return supported relations and paths. A proposed mechanism or response prediction remains a hypothesis/model result until an appropriate evidentiary process supplies new observations and justified bindings. No domain-specific biological conclusion is built into the kernel.
6.4 From hypothetical to realized
An approved Gold plan is not promoted directly into Silver. The path is: create the plan; validate its targets and preconditions; authorize the external effect; invoke the customer-local executor; record the reported result; acquire outcome evidence; compile the observed change; and link the resulting world basis back to the action and workspace.
Only observation and admitted derivation can establish the modeled external outcome. A kernel-generated receipt can establish that the kernel accepted or submitted a command, because that is its own operational fact. It cannot by itself establish that a cloud resource changed or that a scientific intervention produced a particular response.
If the user edits a source-controlled declaration or configuration, the changed declaration can re-enter Bronze as a new source observation. Silver may represent what was declared or configured. That still does not establish that the declared configuration was deployed or that the requested effect occurred.
6.5 Staleness, permissions and serving
Gold workspaces retain their original basis. A newer world publication does not silently rebase a prior analysis. Provide explicit compare/rebase operations that show changed evidence, invalid assumptions, missing targets and results needing recomputation. A stale workspace can remain a valid historical artifact while being ineligible for a current consequential action.
Apply access controls before query execution and again at effect admission. A derived result must not expose unauthorized evidence through decomposition, counts or cached rankings. Customer-local data and bindings must not flow to HQ merely because a lens is shared or a kernel release is updated. [S09, S10]
Serving returns a typed artifact with its basis, provenance, assumptions and status. A report, API response or screen must not strip those distinctions in a way that makes an estimate appear to be an observation. No additional storage tier is required to enforce this contract.
6.6 Integration, deliverables and acceptance
Use Part 3 operation contracts, Part 5B lenses and existing D/F knowledge-engine and experience-plane homes. Review the current feature-packet, local-activity-observation and friction-hypothesis schemas for reuse. The supplied files support these object contracts, not a completed Gold runtime. [S12, S13]
Deliver workspace/result schemas, request-to-plan boundary, assumption registry, branch/diff/rebase mechanics, action handoff and explanation/interface contracts. Acceptance must include ambiguous target resolution, a hypothetical relation that remains outside canonical structure, a stale plan refused for execution, an exact query returning zero, a partial result, failed/partial external action and a successful external effect confirmed only after observation/recompilation.
Integrated worked example — one substrate, several grains
A. The pinned referents and evidence
Use a synthetic customer-local fixture containing four independently identified referents: C0-A, the BuildHoldings function; C0-B, the logical holdings object; C0-C, the CalculatePerformance function; and C0-D, the logical performance object. The labels are illustrative, not universal product constants.
C1-1 records that A writes B. C1-2 records that C reads B. C1-3 records that C writes D. Each relation retains its source and scope. A configured relationship may be present even when no execution has been observed.
D1-B17 and D1-B18 are two observed states of B. D1-D10 and D1-D11 are two observed states of D. Their version labels, content references and observation coordinates are explicit. The fixture supplies read/write evidence identifying the exact states involved; real adapters may or may not be able to supply equivalent evidence.
B. D2 and C2
D2-E1 binds an observed operation by A to B17 → B18. C2-M1 is the minimal support for that scoped write effect. Its certificate explains why the actor, subject, state transition and required relation/evidence bindings are sufficient under the contract. It does not assert that every internal input to A has been modeled.
D2-E2 binds an observed operation by C that consumes B18 and changes D10 → D11. C2-M2 is its minimal structural support, including the consumed state interface and produced-state effect. A receipt ID is evidence for that binding, not a substitute for B18 or D11.
C. D3 and C3
D3-T1 composes E1 and E2 through the exact B18 state interface, retains both transformations, and exposes the supported before/after boundary and any open inputs. C3-S1 is a minimal C2 support composition for that D3 target. It is not the set of every function sharing the holdings key.
For event activation, the fixture includes a notification/control path to E2. For scheduled activation, it includes a schedule/control path instead. Both may support the same material handoff through B18. Their control structures remain distinguishable, and identity of the full C3 is evaluated under Part 4 rather than assumed.
No freshness threshold is added. If a native condition exists, it is preserved with its scope. If E2 consumed B19 instead, the asserted E1→E2 material join through B18 is not established. The individual operations and source conditions remain in the evidence record.
D. Grain extension
Add C0-R, a holdings row identified by a source-supported compound key within a table scope. A file-version membership bridge can establish that a row-state occurrence belongs to B18. To claim that E1 changed that logical row, supply the row-level before/after mapping and operation support required by the grain bridge contract.
Without that support, the system can still say E1 wrote B18 and B18 contains the observed row occurrence. It must not silently upgrade that to “E1 changed this business row.” The same discipline applies when a Lambda is replaced but the logical output table continues.
E. Gold use and world evolution
A lens projects the two motifs and their evidence. A user creates a Gold proposal to replace A. The kernel evaluates the proposed plan and, only with separate effect authority, hands an action to a customer-local executor. The next evidence capture records what actually happened; Part 5A publishes the resulting successor basis. The original workspace and original world remain referable under retention policy.
