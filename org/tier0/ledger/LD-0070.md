# LD-0070 — Telemetry-derived liveness framework (Tier-D structural fix for kill-orphans race + heartbeat discipline)

## Decision

Per Andrew architectural conversation 2026-05-26T~00:05Z-00:18Z + 5 Q-locks per MSTR recs: replace heartbeat-authoritative liveness with telemetry-derived liveness. PostToolUse hook annotates every tool call with kind tag; broker `is_live_serial` reads `agent_telemetry/{serial}.jsonl` last `kind: work` timestamp instead of `liveness.json` heartbeat. Heartbeat MCP becomes legacy-compat refresh hint, not authoritative signal.

## The architectural rationale

Current heartbeat-authoritative model has 4 known failure modes:
1. **Race-SIGTERM** — agent doing substantive work between heartbeats gets reaped at 120s STALE threshold (LD-0063 Tier-B raised to 600s as patch; this LD-0070 fixes it structurally)
2. **Cultural-discipline burden** — agents must remember to call `heartbeat()` periodically; failure modes from forgetting are silent
3. **Self-lying watcher pings** — a stuck agent with a healthy watcher process reads LIVE indefinitely (Tier-D self-heartbeat problem)
4. **STALE-signal-lies** — "STALE" today means "forgot to call heartbeat" not "agent is not working"

Telemetry-derived liveness fixes all four structurally: tool-call telemetry is naturally dense when an agent is working; the agent can't "forget" to emit telemetry because the PostToolUse hook fires on every tool call automatically.

## Tool taxonomy (PostToolUse hook annotation)

Every tool call gets a kind tag at telemetry-write time:

| kind | what counts | counts toward liveness? |
|---|---|---|
| `work` | Read, Write, Edit, Grep, Glob, Bash (non-upkeep), Skill invocations, all MCP except below, send_message (substantive), etc. | YES — authoritative for LIVE |
| `upkeep` | register_agent, heartbeat, get_agent_status (pure poll), check_inbox (pure poll, not when acting on findings) | NO — discount for LIVE; counts for SESSION_ALIVE |
| `watcher` | inbox-watch.sh, watcher-status.sh, kill-orphans, cleanup-poller | NO — discount for both LIVE and SESSION_ALIVE? OR counts for SESSION_ALIVE only? **DECISION:** counts for SESSION_ALIVE (watcher firing means session is at least alive) but NOT for LIVE (watcher doesn't mean agent is processing work) |

Discount carve-out is load-bearing — otherwise a stuck agent with a running watcher reads LIVE forever.

## Dual-signal model

| Signal | Definition | Threshold | Consumer |
|---|---|---|---|
| **LIVE** | recent `kind: work` telemetry entry | **120s** | dispatch consumers (CTO/COO/CVO MCP routing); /stimulus-scan agent-classification |
| **SESSION_ALIVE** | recent telemetry entry of ANY kind (including `upkeep` + `watcher`) | **600s** | kill-orphans (don't reap watchers whose session is at least alive) |

A given agent can be SESSION_ALIVE + NOT_LIVE (idle between turns; watcher firing periodically) — that's the honest correct answer. kill-orphans won't reap them (SESSION_ALIVE protects); dispatchers won't message-and-wait (NOT_LIVE signals don't bother).

## Bg_task tracking (edge case #1 — long-running ops)

PostToolUse hook emits:
- `bg_start: <task-id>` when a background Bash task starts
- `bg_complete: <task-id>` when it completes

LIVE signal: also TRUE if any bg_task is in-flight (regardless of last work-call timestamp).

**Max-duration cap**: bg_tasks exceeding 4h without `bg_complete` are treated as `bg_orphan` (assumed crashed silently) and discounted from liveness. Reasonable bound for any realistic long-running op (terraform apply / bun install / SSM invoke); deters silent indefinite false-LIVE.

`set_expected_quiet` MCP NOT added in V1 — escape hatch if empirical use shows bg_task insufficient for non-bash long-ops.

## Phase rollout

**Phase 1 — dual-source observe (1 week):**
- Broker `is_live_serial` returns `max(heartbeat_ts, last_work_ts)`
- Both signals tracked
- LD-0063 Tier-B 600s threshold preserved as belt-and-suspenders
- Diagnostic logging: how often telemetry-signal beats heartbeat-signal; informs Phase 2 confidence

**Phase 2 — telemetry-authoritative (1 sprint):**
- Broker uses `last_work_ts` only for LIVE (120s threshold)
- Broker uses `last_any_ts` only for SESSION_ALIVE (600s threshold)
- Heartbeat MCP still callable for legacy clients; updates `heartbeat_ts_fallback` field that's not consulted
- LD-0063 Tier-B threshold raise becomes redundant for primary race fix (but 600s SESSION_ALIVE preserves the conservative-on-session-aliveness margin)

**Phase 3 — cleanup (post-Phase-2 confidence):**
- Remove heartbeat from inbox-watch.sh-equivalent skill bodies
- Remove explicit Tier-A heartbeat-cadence discipline guidance from agent operating docs
- `liveness.json` deprecated (kept as audit artifact OR removed entirely TBD)
- Heartbeat MCP marked deprecated; no-op or removed in subsequent cleanup

## Implementation details

### PostToolUse hook annotation

Hook MUST capture **full suffixed serial** including tilde-lanes (`0.4.0_DS_ClientPlatform~E`, not `0.4.0_DS_ClientPlatform`). Verify hook current behavior; fix if it strips suffix. Discovered as concern during MSTR walkthrough.

Hook writes JSONL entry per tool call:
```json
{
  "ts": "2026-05-26T00:25:00Z",
  "agent": "0.4.0_DS_ClientPlatform~E",
  "tool": "Bash",
  "kind": "work",
  "session_id": "..."
}
```

For bg_start/bg_complete:
```json
{
  "ts": "2026-05-26T00:25:00Z",
  "agent": "0.7.0_AE_CloudOps",
  "tool": "Bash",
  "kind": "bg_start",
  "bg_task_id": "abc123",
  "session_id": "..."
}
```

### Broker changes

- New in-memory tables: `last_work_ts[serial]` + `last_any_ts[serial]` + `bg_in_flight[serial][task_id]`
- PostToolUse hook calls `broker_record_tool_call(serial, kind, [bg_task_id])` directly (broker memory is hot-path; jsonl is audit trail)
- `is_live_serial(serial)` returns appropriate signal per consumer (LIVE for dispatch; SESSION_ALIVE for kill-orphans)
- During Phase 1: keep heartbeat-driven `heartbeat_ts[serial]` and aggregate `max(heartbeat_ts, last_work_ts)`

## Operating-mode banking observations

- **Tier-A heartbeat-cadence cultural-discipline retired** — eliminates a class of subtle silent-failure modes from the fabric
- **Trustworthy STALE signal** — "STALE" actually means "agent is not working" rather than "agent forgot to call heartbeat" — informs every downstream consumer (dispatch, stimulus-scan, /spot-check, /verify-channel) more honestly
- **Kill-orphans becomes correct-by-construction** — no longer threshold-tuned-by-tradeoff; structural correctness via SESSION_ALIVE signal
- **Bg_task tracking is a generalizable primitive** — could extend later to other long-op tracking needs beyond liveness
