# LD-0256 -- ds-commit-gate.sh is the real fork-volume culprit, not CMTQUE; consolidation + rename routed to CTO (Andrew-direct)

**What.** Continuing LD-0255's investigation, Andrew asked whether commits should be batched instead of
continuously queued. Mechanical analysis (source-read) found the answer sits one layer below CMTQUE:
`.tools/ds-commit-gate.sh` runs agent-side, before CMTQUE's queue is ever touched, and forks **six
processes per `.py` file** (py_compile, ds-precommit-check.py, ruff, comp_constants_cli.py,
manifest_check_cli.py, log_open_lint.py), looped per-file -- a 10-file commit is 60 forks from this gate
alone. CMTQUE's design (serializing only `git add`/`git commit`) never touches this. At 463 commits/day
this is plausibly the dominant process-creation-event source stressing Huntress (LD-0255's live Rio leak).

**Andrew also asked why DS owns this** -- checked `.owned-paths.yaml`: `.tools/**` is an ANY-agent lane,
not DS-restricted; the tool is already "Universal, all agents" per CLAUDE.md Rule 14. The `ds-` prefix is
a naming artifact, not a real ownership boundary.

**Proposed fix (Andrew-confirmed, routed not executed).** (1) Consolidate the 5 Python-based checks into
one entry-point calling each as an imported function, not a subprocess -- 5 forks -> 1/file. (2) Batch
across all files in a commit in one call instead of per-file looping -- 10 files: 60 -> 2 forks. (3)
Rename off "ds-commit-gate.sh" to reflect its actual universal scope. Routed as an arch-gate ask to CTO
(same class of fix CTO already personally arch-gated for the sensitive-leak-gate extraction), FYI to COO
for eventual TO decomposition, sequenced to land BEFORE NFRA_CMTQUE.TO-6R's load-test so the test
measures the corrected design.

**Why routed, not MSTR-executed.** `.tools/**` is universal-lane code outside MSTR's narrow
Andrew-granted `org/mcp/**` internal-ops carve-out (LD-0246/0250) -- Article VI governs through the org.
