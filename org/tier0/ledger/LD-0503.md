# LD-0503 — ETFS_GUARDRAIL moves to D8, and CTO gets the register file and nothing beside it

## Decision

Two edits, one commit.

```
  org/missions/DIRECTIVES.yaml   D4.members.projects  -ETFS_GUARDRAIL   (6 projects remain)
                                 D8.members.projects  +ETFS_GUARDRAIL   (4 projects)
  .owned-paths.yaml              +lane TIER0_DIRECTIVES_REGISTER [0.0.0_AB_MSTR, 1.0.0_SA_CTO]
                                 +path "org/missions/DIRECTIVES.yaml" -> that lane
```

`LD-0502` cut the ETFS_GUARDRAIL row under **D4** earlier today on subject grounds. This entry moves
it. **That is not a reversal of LD-0502** — D4 was the correct read of the code, and D8 is the correct
read of the defect.

## ⛔ THE REQUESTED EDIT AND THE CORRECT EDIT WERE DIFFERENT, AND THE DIFFERENCE IS MINE TO OWN

`1.0.0_SA_CTO` asked for one line: add `ETFS_GUARDRAIL` to `D8.members.projects`, and wrote
**"Nothing else in that file needs to move."** Executing that literally would have left the project
declared under **two directives simultaneously**.

Two independent artifacts say it belongs to one:

- `org/projects/ETFS_GUARDRAIL.json` @`54e0058551` carries `"directive": "D8"` in a **SINGULAR**
  field. A register listing it under D4 as well **contradicts the committed artifact** — and the
  register, not the JSON, is the one that would be wrong.
- **D4 is SITEZ-placed; the project carries `"fabric": "laptop"`.** The double membership would have
  **re-created the placement tension CTO's own message reports as dissolved**, on the row he did not
  touch. His argument for D8 — placement and fabric agree, so the fabric key is not overriding a
  placement — only holds if D4 releases the project.

⭐ **The removal is recorded on D4's `members_note` as THIS SEAT'S ACT, not folded into the add.** A
register edit that quietly exceeds its request is indistinguishable, later, from one that was asked
for. If Andrew reads D4 as retaining a claim here, **the D4 line is the one to reverse — the D8 add
stands on his verbatim independently of it.**

## ⭐ CTO HIT THE GATE, REVERTED, AND ASKED — WHICH IS WHY THIS IS A GRANT AND NOT AN INCIDENT

`safe-commit` refused with `lane=TIER0_MSTR; agent=1.0.0_SA_CTO not in permitted_agents`. CTO then
**reverted the edit rather than leaving it uncommitted in the shared worktree**, and gave the reason
worth carrying: *the gate refused the COMMIT; nothing would have refused the SWEEP.* An uncommitted
Tier-0 edit by a seat that may not author it is the shape that gets swept into somebody else's commit
and mis-attributed.

**SoD holds:** MSTR is grantor, CTO is grantee, CTO did not self-land.

## THE GRANT IS ONE FILE, AND THE INCUMBENT IS RE-ASSERTED ON PURPOSE

**NOT a widening of `TIER0_MSTR`.** That lane also carries `org/tier0/ledger/**`, `cycles/**`,
`reviews/**`, the `org/tier0/**` catch-all **and the whole `org/missions/**` tree**. Andrew named one
file. Widening the lane would have handed the MSTR constitutional ledger over on a request for a
register row — the same reasoning `.owned-paths.yaml` already records for `ATOM_DECOMP`
(*"a one-path lane grants exactly what Andrew asked for and nothing else"*) and for
`OPAL_ANALYST_DE_RUNS`.

⛔ **A LONGEST-MATCH PATH RULE REPLACES THE BROADER LANE RATHER THAN ADDING TO IT.** A grant naming
only `1.0.0_SA_CTO` would have **SILENTLY REVOKED `0.0.0_AB_MSTR`** — the register's owner and sole
writer — **on the register's own file**, and nothing about the edit would have looked like a
revocation. `0.0.0_AB_MSTR` is listed first in the lane for that reason. This file's own rule, learned
the hard way at `OPAL_ANALYST_DE_RUNS`: **the control that catches a grant is not the one that
confirms the grantee, it is the one that confirms the INCUMBENTS.**

## Rollback

in flight. The grant's removal restores `org/missions/**` -> `TIER0_MSTR` by longest-match falling
back one rule; the move's removal restores ETFS_GUARDRAIL to D4.

## Scope

excluded deliberately: **cutting a directive to retired is a different act from editing a live row**,
and it still routes through MSTR.
