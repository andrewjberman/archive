## Two defects, both mine, both in rules written the same afternoon

**(1) `certification` was an unanchored substring.** It matched inside
`org/tier1_exec/3.0.0_SA_CVO/logs/2026-09-01/work_0935Z_d12_certification_and_four_defective_...md`
— **a session log classified as VERIFICATION.** This is the *same* defect LD-0504 fixed in
`project_census`'s project-code match (`if code in f` -> word-bounded), reintroduced by me in
`commit_census` roughly an hour later. Fixed with `(^|/)certification`, which keeps
`.../certification.json` and rejects `..._certification_...`.

**(2) Ties were broken by `git log`'s output order.** `Counter.most_common` is
insertion-ordered, so a commit touching one deliverable and one log resolved to whichever path
git happened to print first. **Same commit, different listing, different answer, and nothing in
the output would have shown it.** Ties now break on declared `KIND_RULES` order.

## ⛔ THE FIRST FIX WAS WORSE THAN THE BUG, AND ONLY MEASURING CAUGHT IT

My first attempt was to hoist the agent-home rules above the content rules so an artifact is
"typed by what it is, not what it mentions." That sentence is true and the change was still
wrong: with AUDIT tested first, **every commit that touched product code AND wrote a log about
it voted AUDIT.**

```
                AUDIT   BACKEND   DATA   TOOLING   COORDINATION
  before          69       19      11      22          43
  AUDIT hoisted   85       16      10      17          36     <- worse
  anchored fix    69       19      11      17          44
```

**A one-file regression is repaired by anchoring one regex, not by reordering the ladder** —
reordering changed the answer for every multi-file commit in the estate. The reorder *looked*
principled and would have shipped on the strength of its own justification.

## Tie-break position is a semantic decision, and it is worth 15 commits

Because ties resolve by position, **moving a rule changes the answer for multi-file commits even
when no regex changes.** AUDIT ranked first takes 84 of 293; ranked last it takes 69. Same
regexes, same population.

AUDIT sits **last** deliberately: *a session log is a BYPRODUCT of the work, not the work.* A
commit that touched product code and wrote a log about it is product work. Exercised:
log+infra -> BACKEND, log+deliverable -> DELIVERABLES, log alone -> AUDIT (no other rule matches
an agent-home log path, so its position never affects a log-only commit).

## ⛔ RETRACTION: "one line will align the two axes" was wrong

I told Andrew twice that the stream/kind AUDIT divergence was a one-line fix. It is not.
Coverage was genuinely missing on the stream side (`drive_log*` at the agent-home root) and that
IS fixed — stream AUDIT 58 -> 71. But the residual gap (stream 71, kind 69) is **structural**:
`project_census` tests its stream rules FIRST, before the project-code match, because there a log
must beat a code it happens to mention; `commit_census` tests AUDIT LAST, because there a log
must lose to the work it documents. **Both orderings are correct for their own question, and
forcing the numbers to match would break one of them.** The two axes answer different questions
and their AUDIT counts are not required to agree; the report should not imply they are.
