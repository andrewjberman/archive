# LD-0648 -- Portal pre-push: workspace root from the hook's own location

## Decision
In `.tools/portal-hooks/pre-push`, when the hook is installed under `<workspace>/.git/modules/<name>/hooks` (a gitlink portal) and
`git rev-parse --show-superproject-working-tree` prints nothing, take the workspace as four levels above the hook's directory and look
for each gate there. The earlier candidates and the superproject candidate (LD-0646) stay.

## Provenance chain (Art. XIII)
MSTR~DELL1 measured (bus 6d6d9e57, 01:46Z) that the hook run from a throwaway portal worktree (`git worktree add --detach`, as
`portal-merge-forward.sh` and the release build do) prints an empty superproject root, finds neither gate, and under LD-0647's fail-closed
rule refuses the push -> `/integrate`: an unowned path is repaired by the integrator's box -> this edit. The CTO's ruling
@38d124d991 and its addendum (msg 109028, no escape: re-running install.sh is the remedy) are why a false refusal has no in-hook way out.

## Why now
On a gitlink box a merge-forward or release push from a worktree would now be refused for an install-layout reason, with no escape.
dell1 and dell2 do not push the trunks today, so nothing was refused; the defect is latent and cheap to close before a box does.

## Assumptions
- A hook installed by `install.sh` on a gitlink box lives at `<workspace>/.git/modules/<name>/hooks` (measured on dell1 and dell2).
- A directory-layout box (the laptop, site Z) is untouched: the `case` does not match its hook path.

## Alternatives considered
- `git rev-parse --git-common-dir`, dell1's suggestion: also works; the hook's own path needs no git call and no working directory.
- An environment escape: ruled out by the CTO (msg 109028).

## Rollback plan
`git revert` of the commit that carries this entry; re-run `bash .tools/portal-hooks/install.sh` on each box.
