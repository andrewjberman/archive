## 2. THE PARTITION VIOLATION — A SCHEMA DEFECT, AND TWO INSTRUMENTS DISAGREE ABOUT IT

```
python .tools/directives-check.py   ->  malformed=0            (reads clean)
bash   .tools/comp-directives check ->  rc=2, 1 violation(s)   (PARTITION: D8 appear in BOTH views)
```

CTO reported *"malformed=0 so it is not a violation."* **That is true of the instrument they ran and
false of the register.** `comp-directives` is the partition-native checker and it fails closed. Its
own `--self-test` passes 10/10, so the instrument is sound and the finding is real. Recording both
readings because a reader who runs only the first will conclude the register is clean.

**THE MECHANISM (Rule 24, postulate (ii) — SAME GRAIN).** `comp_directives.py:250-253` computes the
partition over **ID sets** (`set(live_ids) & set(ret_ids)`), and `:205` carries an explicit guard
calling this state a *"PARTITION breach."* So the schema deliberately treats a directive id as a
**permanent unique key**: an id is live XOR retired, forever. That is MECE over ids.

**But the axis MEANS to be over directive INSTANCES, and Andrew uses the number as a SLOT.** He wrote
*"replace Directive 8 (now crossed out 'Philosophy' job)"* — he knows the prior occupant is retired
and he is re-filling the slot. After a re-mint one ID carries two instances, so the ID stops
identifying an instance and the partition breaks. **The register's key grain and the sovereign's
usage grain disagree; his usage is not the error.**

**DISPOSITION.** The ROW STANDS as he worded it. The SCHEMA moves. The retired D8 row
(`frozen_row` + `row_sha256` + emit seal) is the historical record of the cut and **must not be
deleted** — CONSERVATION would fail and the record of the Philosophy job's retirement would be gone.

**ROUTED, NOT SELF-APPLIED (`1.0.0_SA_CTO`, tooling lane):** teach `comp-directives` that an id may
appear in both views **iff** the retired entry is a closed prior instance and the live row declares
itself a re-mint — i.e. version the instances within the id slot. I am not making that change myself:
it is an engine change to a live gate, the file is sealed against hand edits by design, and the
register owner quietly amending the checker that polices the register is the shape this estate's own
rule names — *a gate whose subject can amend its scope is a suggestion with an audit log*
(`.owned-paths.yaml:894`, MSTR's own words when it declined a similar grant).

**Until it lands, `comp-directives check` returns rc=2 on a register that is otherwise correct.**
Stated plainly here so a future seat does not read that rc=2 as a new fault and does not "fix" it by
deleting the retired row.
