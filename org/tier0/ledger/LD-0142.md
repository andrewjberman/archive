# LD-0142 — COMP_LEARNS status reclassification active -> inactive + phase-narrative drift repair

## Decision
Reclassify `org/projects/COMP_LEARNS.json` `status` from `active` to `inactive`, and repair the `phase`-field narrative drift by prepending a CURRENT-STATE clause that states the true frontier (Stage 3 intake-wave paused at CTO Category-A clearance, dormant since 2026-04-28, CL fabric wound down) ahead of the preserved historical "Phase 3 CLOSED 2026-04-21" narrative. Add a `log[]` entry recording this reclassification.

## Provenance chain (Art. XIII)
Andrew D-003 (standing facilitation of the COMP_LEARNS workstream / CL fabric) + CONSTITUTION Art. XV (MSTR Tier-0 law canonical for both ajb_workspace + feature_clb; MSTR cross-fabric governance authority) -> a CL-fabric project record carrying a self-contradiction (status=active vs phase narrative "Phase 3 CLOSED") is a record-honesty defect within D-003's facilitation scope and D-001 PHASE 2 verify-channel (truth-in-records) -> independent confirmation by two ws execs (CTO + COO) who correctly declined to reclassify a CL-touching record unilaterally and deferred to MSTR -> this reclassification. Authority does not derive from the execs' request (that is corroboration, not authority); it derives from D-003 + Art. XV. Chain closed.

## Why now
Two independent session-start reads (ws CTO + ws COO) flagged the same drift and routed it to MSTR; the relay reached me this cycle via CTO ACK. A known-false record (status=active implying live dispatch-needing work, plus a leading "Phase 3 CLOSED" header that masks the real Stage-3 frontier) misleads every consumer (/drive treats it as a stalled-active project; /overview/allocation misreport it). The CL dyad that owns the project (1.1.0_SA_CTO / 2.1.0_SA_COO) is dormant and will not resume absent Andrew's re-activation call, so the record will not self-correct. Fixing the honesty now is strictly better than leaving it.

## Assumptions
- The COMP_LEARNS.json `log[]` is the authoritative recency signal; its last entry (.092, 2026-04-28T13:03Z) reflects the true last activity (corroborated by CL fabric being wound down + no COMP commits since).
- "inactive" is the correct enum (open + dormant), distinct from "complete"/"closed" (Stage 3 is incomplete) and from "active" (no work in progress). Survey of org/projects/*.json confirms "inactive" as the established value for this state.
- Resume of COMP_LEARNS is gated on Andrew's CL-division re-activation (RV-0026 F-002), not on any ws-side dispatch.

## Alternatives considered
- **Keep status=active, only rewrite the phase narrative to "Stage 3 IN EXECUTION"** (CTO option b): rejected — it would assert active execution that is not happening (dormant >5 weeks), trading one false signal for another.
- **Flip to "closed"/"complete":** rejected — Stage 3 intake-wave is materially incomplete (Category-A clearance pending, griffe packet unauthored); closing would erase real remaining scope.
- **Leave for the CL dyad to fix on resume:** rejected — the dyad is dormant indefinitely (Andrew's call); a known-false governance record should not persist waiting on an unscheduled resume.
- **Edit working-tree only, no commit:** rejected — a governance reclassification must be durable + audited, not ephemeral working-tree state.

## Rollback plan
Revert `org/projects/COMP_LEARNS.json` to `status: active`, remove the prepended CURRENT-STATE clause from `phase`, and drop the added `log[]` entry (single `git revert` of this commit, or manual re-edit). One-edit reversal; no downstream cleanup. If Andrew re-activates the CL division, the resuming CL dyad flips status back to active as its first action.
