# LD-0011 — Kill 1.3.0_DS_CompLearns + 1.4.0_DS_CompLearns per CL-fabric COO request

## Decision
2.1.0_SA_COO (CL-fabric COO) requested via Andrew-relayed chat message:
"Please kill 1.3.0_DS_CompLearns and 1.4.0_DS_CompLearns. Both are idle —
no in-flight TOs, no state to preserve. Will respawn at M2 PREREG when
cert trial runs need parallel DS capacity."

Per the LD-0007 capability adoption + Andrew's architectural ruling
("MSTR = creator and destroyer; COO = coordinator"), this is the
canonical demand-side request flow. COO names the population need; MSTR
verifies + executes + audits.

**Pre-kill verification** (Art. VIII -- truth over progress; verifier-not-
fixer discipline):
- Win32_Process scan for `OPAL_SPAWN_MARKER` windows: 4 live spawn-marker
  windows -- MSTR + AE_CloudOps~C + DE_ClientPlatform + DE_TradingOperations.
  Neither 1.3.0_DS_CompLearns nor 1.4.0_DS_CompLearns is among them.
- Workspace telemetry (`org/mcp/agent_telemetry/*.jsonl`): no file for
  either serial (they live on CL fabric, not workspace).
- CL fabric liveness (`feature_clb/org/mcp/liveness.json`): only one
  entry (3.1.0_SA_CVO); both 1.3.0 and 1.4.0 are NOT_FOUND in the LIVE
  registry.
- Git activity: no commits by either serial since 2026-05-20 (3+ days).

**Verdict:** COO's claim ("idle, no state to preserve") matches observed
state. Both agents are already not LIVE in either fabric -- the kill
is effectively a no-op at the process level. Run it anyway for:
(a) honor COO's request through the proper channel (audit-log captures
the intent + outcome);
(b) audit-log entry establishes the COO-via-MSTR demand-side flow as
working;
(c) consistent counter accounting (the 8-cap is unchanged because
they weren't counted; the audit confirms it).

## Provenance chain (Art. XIII)
COO request (Andrew-relayed) -> LD-0007 capability adoption +
Constitution Art. VI (govern-through-the-org -- COO is the demand-side
consumer requesting through MSTR's supply-side authority) + Andrew
architectural ruling 2026-05-22 -> D-003 (standing CL facilitation
mandate; population management for CL fabric is explicit IN-scope) ->
Stakes Matrix S1 (kill is reversible, internal, low-blast) -> execute
the kill primitive.

## Why now
COO has an explicit cleanup need + a forward plan (re-spawn at
M2 PREREG). The longer not-LIVE-but-formally-LIVE agents sit on the
liveness registry, the more they pollute population scans and confuse
demand-side planning. Cheap to honor.

## Assumptions
- COO's "no state to preserve" claim is correct -- a kill, even of a
  process-dead agent, doesn't destroy any in-flight artifact. The
  liveness registry entry (if one existed) is the only ephemeral state.
- M2 PREREG is the cert trial milestone in COMP_LEARNS at which
  parallel DS capacity is genuinely needed. COO will re-request spawn
  at that time; MSTR re-spawns then.
- Killing on the workspace side affects CL liveness registry if any
  cross-fabric coupling exists; per D-003 + LD-0007 the kill-agent.ps1
  cap counts across both fabrics, so process-side cleanup is fabric-
  agnostic.

## Alternatives considered
- **Refuse the kill on "they're already not LIVE so no action needed"** --
  rejected: the canonical channel (COO requests, MSTR executes, audit
  records) has value beyond the process-level effect. Refusing teaches
  COO that no-op kills aren't honored; that's the wrong cultural lesson.
  The audit-log entry is the meaningful artifact.
- **Kill only one and verify the other** -- rejected: COO requested a
  batch (sensible -- they're a pair in her workstream view); aggregating
  the LD honors the request as posed.
- **Demand COO confirm via MCP send_message directly rather than
  Andrew relay** -- rejected: the relay channel works; the audit
  captures who originated the request via the LD entry's
  `andrew_instruction_ref` field.

## Rollback plan
`.tools/spawn-agent.ps1 1.3.0_DS_CompLearns` + `.tools/spawn-agent.ps1
1.4.0_DS_CompLearns` re-creates the lanes if the kill turns out
premature. COO explicitly noted re-spawn at M2 PREREG; MSTR re-spawns
then on her demand-side signal.
