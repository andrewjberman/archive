# LD-0245 -- broker message-DB bloat fix (fabric choke): backlog saved + delivered pruned + VACUUM

**What.** The primary fabric choke was the message broker (`org/mcp/broker.py`, PID 21028) spinning CPU
over an 89MB / 36,940-row `messages` table it never prunes (broker.py prunes `agents` + `events` but
NEVER `messages`, so delivered rows -- which no broker query ever re-reads -- accumulate since 2026-03-26).
Backup-first fix, Andrew-authorized: (1) saved the full 36,940-message backlog read-only to
`org/mcp/message_archive/` (16 weekly JSONL + a verified 89MB snapshot); (2) live-pruned 36,853 delivered
rows (zero broker disruption); (3) VACUUM 89MB->0.5MB (brief broker-stop); (4) relaunched the singleton
broker healthy with the 106 pending messages preserved. Box CPU 94%->77%; broker CPU pegged-a-core -> ~0.

**Why S3 / ratified.** Data deletion + live shared-infra mutation = S3; ratified by Andrew's direct
"yes proceed" + "save the backlog first". Made recoverable by the verified backup taken before any delete.

**Follow-ups (surfaced to Andrew):** (a) wire the RECURRING weekly offload (archive_messages.py is built +
validated; needs a broker-startup catch-up + weekly guard, or a scheduled runner) so the table doesn't
re-bloat; (b) the 3 ORPHAN broker.py processes = a broker-launch-hygiene bug (failed-bind launches that
don't exit) worth fixing.
