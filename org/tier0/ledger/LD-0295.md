# LD-0295 — NFRA_SYSTEM 06_current_state usage model: timestamp-at-top + run-the-compiler, no scheduler

Andrew's ruling (verbatim in frontmatter) settles how the "never stale" property is operated:
the document is honest about being a snapshot, wears its age on its face, and names the exact
one-line procedure to refresh it. The failure mode this kills is not staleness itself but
*invisible* staleness -- a reader can no longer mistake a 5-day-old compile for current, because
the first line answers "how old is this?" and the second answers "what do I do about it?".

Implementation (same turn, exercised):
- `org/modules/graph/comp_system.py`: markdown header leads with
  `**Generated: <UTC ISO> (HEAD <short-sha>)**` + `**To update: run comp-system.**`;
  provenance section gains `generated_at (UTC)`; JSON header gains `emitted_at_utc`
  (human twin of the epoch `emitted_at`, which is kept for existing parsers).
- `infra/system/06_current_state.{md,json}` regenerated: was 5 days stale (source drift
  232 -> 240 files), now fresh at 2026-07-14T05:02:37Z; `comp-system --check` rc=0;
  compiler `--self-test` 7/7 (no-fabrication invariant intact).

Not done, deliberately: no cron/hook/alarm wiring (the ruling IS that none is needed), and the
NFRA_SYSTEM PRD Status line + P1-P4 TO status fields remain unflipped (registry says COMPLETE and
is correct; the PRD/TO surfaces still read as in-flight -- surfaced to Andrew 2026-07-14, left for
the owning lanes unless he asks).
