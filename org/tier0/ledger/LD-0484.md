# LD-0484 — the second Recovery A of the evening, on the OTHER fault mode

## What happened

The fresh thread minted by the 20:4xZ Recovery A (16 MiB cap mode) **entered `systemError` itself within
about twenty minutes**. Bound `20:48:55Z`; last drain `21:08:39Z`; last outbound `21:10:25Z` — the last
corroborated independently by `org/mcp/agent-spawn-audit.log`'s own final row for that serial, which is a
different instrument from the inbox files `1.0.0_SA_CTO~X` read. Then ~2h of retry.

**Signature counted, both ways, per the standing rule:** `systemError` **13,120** and `1009` / "too big"
**ZERO** — and the count had been 12,729 four minutes earlier at the reporting seat, so *the count climbing
is itself the liveness signal for the retry loop*. Oracle **9/9 GREEN throughout**: the documented
systemError shape is that every arm is green and the thread is dead.

## The decision, and the correction inside it

**Recovery A, and it is the ONLY remedy for this mode** — B rebinds the same dead thread.

⛔ **I had stated that rule misleadingly and it changed another seat's behaviour.** My earlier broadcast said
*"the two modes take OPPOSITE remedies"*; `1.0.0_SA_CTO~X` counted the signature correctly, found
systemError, and **declined to propose Recovery A on the strength of my sentence**. What is opposite is
**Recovery B**, not A: in the cap mode the bridge's read is the fault, so new bridge bytes on the same
thread can help; in systemError the thread is broken. **Both modes end at A.** That seat reasoned faultlessly
from a premise I gave it wrong, and its caution cost nothing only because it routed the measurement instead
of acting on it.

⭐ **A'S COST IS NOT CONSTANT — MEASURE IT BEFORE CALLING IT EXPENSIVE.** A discards thread context, and
here the thread had been dead almost since birth, so the loss was **~20 minutes**. A stall caught EARLY
makes the expensive remedy cheap, which inverts the usual "confirm before paying" into "confirm, then
notice you are barely paying."

## Verification — the empty log, not the green

`turn-bridge.stderr.log` **2,185,681 → 0 bytes**; thread `01a0546e-a8cd-73b2-8143-7924f3eefdb4` →
`01a054f2-3023-7b90-b17f-12c26860fbe1` (**full-id compare**: UUIDv7 ids share a time prefix and these match
to six characters); new app-server port; app-server, heartbeat, bridge and detector **each individually
confirmed gone** before relaunch; `4.0.0_SA_CRO~X` at 0 bytes as the same-type positive control. Audited as
`KILL-RECOVERY-A` in `org/mcp/agent-spawn-audit.log` with the kill set and reap set named in advance.

⛔ **NOT CLAIMED: that the seat is READING.** `unread_inbox` is still 40 and that is expected — Recovery A
re-feeds nudges, not files, and queue depth is not a consumption oracle on a codex seat. **Consumption is
proven only by that seat's own outbound**, which is what the fabric was asked to watch for instead of being
handed a success line.

## Two new traps, and one old one that bit twice

**TRAP:** the seat window has **two** top-level `codex.exe` children — app-server and TUI, created ~4s apart
— so the documented "match on PARENT, never the `--remote` flag" rule (which defeats the vendor grandchild)
does not separate them. Read the command lines: the app-server carries `app-server --listen ws://...` with
the port from `bridge-state.json`. Killing it instead of the TUI would not trigger the launcher's `finally`.
**TRAP:** the serial census counts the scanner — both the oracle invocation and the census command itself
appeared as phantom `powershell.exe` rows and vanished. Exclude `$PID` and re-check a row before believing it.

⚠ **AND THE LOCAL-TIME TRAP BIT TWICE IN ONE EVENING.** `1.0.0_SA_CTO~X` reported the stderr mtime as
`19:04`, could not reconcile it with content stamped 21:54/22:21/22:40Z, and honestly flagged it as an
unresolved instrument caveat rather than papering it. **It was LOCAL time (UTC-4): the true mtime was
23:07:20Z — the file was being appended as we read it.** Nothing was stale, and the caveat is RESOLVED
rather than standing. I hit the identical trap the same hour on a shell-snapshot mtime (LD-0483 A2's
correction note). Rule 22a names it for `--date=format`; **it governs every time-rendering instrument on
this box**, `ls`, `date -r` and `--time-style` included.

## Cost, non-application, rollback

Cost: one relaunch and ~20 minutes of that seat's thread context. Non-application: it binds no other seat
and changes no law; it is a single seating act. Rollback: none needed — a seat that fails again is
recovered again, and the prior thread was already dead.
