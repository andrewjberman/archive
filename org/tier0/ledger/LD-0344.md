## AMENDMENT 1 (2026-07-29T03:05Z) — SAME CLASS, ONE LAYER OUT: the `~/bin/aws` forwarder baked TWO MSYS path flavors into one line, and every `aws` call in every agent shell was dead

Andrew-direct: *"yes we need to fix the aws path."*

**Symptom:** any `aws ...` from an agent shell died with a **Python SyntaxError reading a bash
file** — `File ".../bin/aws", line 7 ... SyntaxError: invalid syntax`.

**Root cause.** The generated forwarder strips `~/bin` from PATH before re-invoking `aws`, so
`.tools/aws`'s self-discovery cannot mistake the forwarder for the real CLI. That strip compared a
**generation-time string**:

```sh
export PATH="$WS/.tools:$(... | grep -Fxv "$BIN" | ...)"
#              ^^ expanded to /cygdrive/c/...   ^^ expanded to /c/Users/...
```

**Two flavors of the same directory, in the same generated line.** PATH at run time carried the
`/cygdrive/c/...` form; the strip searched for the `/c/...` form; string equality across flavors
never matches; **the strip silently no-opped and the exact loop it exists to prevent fired.**
Compounding it, the `.tools` PATH entry rendered with **no drive prefix at all**.

**Fix — run-time self-resolution, identical principle to this entry's main body:**

```sh
_self_dir="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
export PATH="$(... | grep -Fxv "$_self_dir" | ...)"
```

`cd && pwd` returns the flavor the **current** shell understands by construction, so it matches its
own PATH entry regardless of flavor. **No path string is compared across time.** The `$WS/.tools`
prepend stays baked — this file lives *outside* the repo and must point home — but is now
**guarded** by `[ -x "$WS/.tools/aws" ]`, so a stale bake degrades to "use whatever `aws` is on
PATH" instead of breaking every call.

**Verified (output, not rc):** `--version` -> `aws-cli/1.44.44`; `sts get-caller-identity` ->
`arn:aws:iam::313476888478:user/Andrew_Berman`; `ec2 describe-instances` -> `i-07dccb1615503ac99`
(the exact call that exposed the break); SyntaxError/Traceback count **0**. 94 tools x2 forms
regenerated.

### Causation: stated, not hidden — and not claimed

I wrote Git's `etc/fstab` earlier tonight (LD-0340 A1). **That file did not previously exist**, and
adding a `C: /c` entry alongside the compiled-in `/cygdrive/c` mount is a plausible trigger for
MSYS changing which flavor it renders Windows PATH entries into.

**I have not proven that, and I will not claim it.** I did not capture the PATH flavor before the
fstab write, so **the before-state is unrecoverable** — the capture-the-baseline discipline failing
in the one direction that cannot be repaired afterward.

> **What IS certain: the shim was always one flavor-flip away from this**, because it compared two
> independently-expanded absolute paths. **The fstab may have pulled the trigger; the generator was
> the loaded gun.** The fix removes the gun and is correct under either causal story — which is why
> it did not wait on resolving causation.

**Class count: this is the THIRD distinct instance tonight** of *a path baked at write time that
must be resolved at run time* — the launchers (main entry), `install-closeout-comp-state.sh`
(LD-0343 A1), and now the PATH shims. **Three independent authors, three files, one defect.** That
is no longer a bug; it is a missing convention.

## AMENDMENT 2 (2026-07-29T03:50Z) — `OPAL_WS_ROOT`, and the SPACE-IN-ROOT bug base was structurally blind to

Two changes to `ajb.ps1` + `spawn-agent.ps1`, both Andrew-direct, both landed together.

### (a) `OPAL_WS_ROOT` — the device-level escape hatch

Andrew-direct: *"we need a bare solution for the launcher that somehow env-vars the path for the
device."* Both files now check `$env:OPAL_WS_ROOT` **first**; if set and it exists it wins, if set
and missing it **warns and falls back**, if unset derivation runs as before.

> **AN ENV VAR DOES NOT VIOLATE THE ONE RULE — IT IS THE RULE'S ONLY LEGITIMATE EXCEPTION.** The
> rule is that no site encodes its own path **IN THE REPO**, because a repo is shared and two
> sites' literals overwrite each other **with no merge conflict**. An environment variable lives
> **outside the repo, per machine, and can never be pushed.** It is the one place a device-specific
> value can live without colliding. Unset remains the normal case; this is for odd layouts (a
> worktree, a UNC path, a relocated `.tools`), not routine use.

### (b) The space-in-root bug — found by `~Z`, reproduced and fixed on base

`0.0.0_AB_MSTR~Z`'s clone is `C:\Users\Opal Bloomberg\...`. **It has a space; base's does not.**
The `wt.exe` relaunch built its inner command with **double** quotes around the path
(`. "$ajbPath"`), and `powershell.exe`'s **native-argument layer strips inner double quotes from a
`-Command` string**. So at site Z the path arrived split and **every `ajb <Serial>` died**:

```
The term 'C:\Users\Opal' is not recognized as the name of a cmdlet...
```

**Fix:** single-quoted PS literals (embedded `'` doubled), which survive the strip — the same
treatment `$extraLit` already had. *The extras were quoted correctly and the path was not.* The
relaunch also now hands the child `OPAL_WS_ROOT`, so the new tab reads the root from an
**environment value** instead of re-deriving it through another quoting layer.

**REPRODUCED ON BASE, not taken on report.** Base cannot hit this with its own root, so the
condition was *constructed*: a real probe file under a real spaced directory, one variable (quote
style), both arms run through `powershell.exe -Command`.

| inner form | result |
|---|---|
| double-quoted (old) | `The term 'C:\Users\ANDREW~1\...\Opal' is not recognized` — **failure reproduced** |
| single-quoted (new) | `INNER-OK: dot-source succeeded` — **fix confirmed** |

`OPAL_WS_ROOT` exercised all three ways: valid -> honored; invalid -> warns and falls back to the
derived root; unset -> derives correctly.

> ENVIRONMENT, NOT A LIMIT ON WHAT I CAN TEST.** The blindness was one `New-Item` away from being
