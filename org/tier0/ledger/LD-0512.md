# LD-0512 — the byte cap measured the wrong quantity

## ⛔ THE CONTROL EXISTED AND WAS COUNTING THE WRONG THING

`embed_screens()` already refused a shot over **400 KB**. `etf_ownership_aug.png` was
**1440x1000 and 217 KB** — half the cap — so it sailed through, reached a served page, and on a
390px phone rendered a desktop UI at **22% of natural size.** That is the complaint that opened
the whole investigation.

⭐ **BYTES ARE A PROXY FOR SIZE AND THEY FAIL EXACTLY WHERE IT MATTERS:** a large, flat UI
screenshot compresses well, so the more oversized the image, the less the byte cap notices.
**PIXELS are the property that governs legibility**, and they are four bytes in the PNG header.

The renderer now reads the IHDR and fails when width exceeds `SHOT_MAX_W[frame]`
(900 desktop / 420 phone — `capture_screens.py`'s own caps). The failure names the remedy:

```
  sprint[1] screens shot shots/2026-09-01/etf_ownership_aug.png is 1440px wide but
  frame=desktop caps at 900px -- it did NOT come through capture_screens.py. Re-run it:
  capture_screens.py --date <DAY> --from shots/... --name etf_ownership_aug
```

**A width check is also a provenance check, and a stronger one than a manifest:** it verifies the
PROPERTY the tool guarantees rather than a claim that the tool was used. Nothing to forge, no new
state to keep, and it cannot go stale.

Header-parsed on purpose — no PIL at render time. **A non-PNG returns None and the check is
SKIPPED, not passed:** unchecked is not the same as clean.

## Hand-typing was the other half, and the tool now emits it

`--emit-json` prints the paste-ready `shots` entry with the `file` path and the `frame`
**as captured**, beside the actual pixel dimensions. The operator previously typed both by hand
into the day's JSON, which is how a 1440px capture came to be declared `frame: "desktop"` and
nothing objected.

## Remediation, through the tool's own path

`capture_screens.py --from` on the offending file: **1440x1000 -> 900x625, 217 KB -> 155 KB.**
All three 09-01 shots now render at 322px on a 390px phone — **36% of natural, uniform**, against
17%/17%/22% before this and LD-0505 together.

## Controls

```
  the real defective file          -> FAILS with the remedy in the message
  08-28 (3 shots) / 08-29 (1 shot) -> RENDER unchanged; every referenced shot is exactly 900px,
                                      which is itself evidence they came through the tool
  09-01 after remediation          -> RENDERS; 0 `undefined`/`NaN`; scrollWidth == viewport
  --emit-json                      -> exercised on a real file, emits the correct frame + path
```

## Noted, not acted on

`shots/2026-09-01/positioning.png` (900x887, 88 KB) is **referenced by nothing** — a captured
file no card uses. Dead weight rather than a defect, and deleting an operator's capture is not
this seat's call.

## Rollback

Revert this commit. The width check is additive; `--emit-json` is opt-in and prints only.
The remediated PNG is regenerable by re-running the capture.
