# LD-0006 — Propose Directive D-002: Standing maintenance (code-cleaning, compiler development, system understanding)

## Decision
Draft and route to Andrew a proposed new Directive `D-002` defining MSTR's
idle-cycle behavior. D-001 today governs MSTR's behavior while there is active
project work to drive ("complete every active project, then validate the
product"). It is silent on what MSTR does when the queue is materially drained
-- and that silence is the failure mode Andrew named: MSTR drifting into
originating new product/UI strategy to fill cycle budget, which is sovereign
territory MSTR may never enter.

D-002 closes that silence with an explicit standing maintenance mandate:
read-only meta-analysis of the codebase (broken / dead / unreachable code,
doc-vs-code drift, tech debt), chartering improvements to the comp-* compiler
tools (the structural-understanding layer the fabric depends on), and
deepening MSTR's own system model through reading PRDs / architecture / data
flows. Read-only-then-charter -- never edit code, never originate new product
surface.

Full proposed Directive text is in this cycle's CY-0004 record §"Proposed
amendment". This entry is the ledger trail of the proposal; enactment is
Andrew's via the Directive Authoring Protocol (Andrew states to CTO in a CTO
terminal session, CTO transcribes, reads back, commits with
`GIT_COMMIT_AUTHOR_OVERRIDE=TIER0_LAW`).

## Why now
Andrew has surfaced the gap. The longer it sits unfilled, the more likely a
future MSTR /govern cycle with a quiet queue drifts into product-strategy
origination -- the precise failure Constitution Art. II's "type-or-new-goal"
rule and Art. XIII's "authority must be traceable" rule exist to prevent at
the action level, but which D-002 prevents structurally at the *cycle-budget*
level.

## Assumptions
- "Materially drained" admits an operational definition: no progressing project
  awaits MSTR-side input AND no in-flight charter has an open receipt. Andrew
  may revise this in transcription.
- D-002 standing alongside D-001 is preferable to amending D-001 -- different
  lifecycles (D-001 closes, D-002 is standing) and cleaner /mstr_review
  reporting. Andrew may choose otherwise.
- compiler-tool development (comp-*) is high-leverage within maintenance because
  every comp-* improvement compounds across every agent in the fabric.

## Alternatives considered
- **Amend D-001's scope** to add an idle-behavior clause -- rejected for the
  lifecycle reason above (D-001 will close someday). Surfaced as an option
  for Andrew.
- **Leave D-001 silent on idle behavior** -- rejected: the silence is the
  failure mode Andrew named.
- **Make the maintenance mandate informal / advisory** -- rejected: a
  Directive is the only channel that gates `/govern` ignition; informal
  rules are not enforceable through the ignition latch.
