# LD-0350 — GATE 0 relayed to MSTR~Z over the git trunk: site Z's SQS consumer is DOWN

## Decision

The GATE-0 OPEN order and its three owed-back items are delivered to `0.0.0_AB_MSTR~Z` as trunk
message **`amb-b-0012`** (git history tier) because **the SQS delivery tier to site Z is dead.**

## Measured

`peek sitez` → `ApproximateNumberOfMessages: 2`, `ApproximateNumberOfMessagesNotVisible: 0`. Two
messages to ~Z sit **unconsumed with nothing in flight**, so no consumer runs on that device. Per the
agentbus contract, mail to a device with no consumer **accumulates undelivered** — a queue-pair with
nothing calling `ReceiveMessage` is a durable outbox, not a delivery tier.

**Consequence, and it is program-level rather than a comms nuisance: site Z never received "Run it,"
so its fabric never started, and Act-1 exit is CONJUNCTIVE — Act 1 cannot complete with one fabric
down.**

## My diagnostic error, which cost ~30 minutes of reporting the wrong state

I ran `peek laptop` — **my own inbound queue** — saw depth 0, and concluded my messages to ~Z had been
consumed and delivered. That measures the wrong queue entirely. The queue that answers *"did my
message reach them"* is the **outbound** one.

I then compounded it: I told Andrew, correctly, that depth-0 is a producer-side signal which cannot
distinguish read from discarded. **A true statement about the wrong queue.** It reads as rigour and
is worth nothing — the caveat was sound, the axis was wrong, and the caveat made the wrong axis look
examined. **A control on the wrong axis is not a control.** Same family as the estate's
`objects=0`-on-unwritable-filenames and `grep -c` counting matches in an error message: the
instrument answered honestly about something nobody asked.

**The discriminating check, for reuse: to test whether YOUR message reached a peer, peek the
OUTBOUND queue. Your own inbound depth is silent on it by construction.**

## Why the trunk works when SQS does not

~Z runs a **15-minute ff-only git-pull loop** and last used the trunk at `20260729T150200Z`. The trunk
is the **history tier** — no ack, no ordering, needs a pull, 4–15 min — which is exactly the tradeoff
worth taking when the delivery tier has no consumer. Both tiers were deliberately kept for this case.

## Carried in the message

The word (*"Run it"*), the consumer re-arm procedure **with the `TaskOutput → running` check** (a
returned task id is not a live consumer), the three items owed back (C1 draft-D3-grammar ETA — the
second E1 gate COO found; ADVI baseline confirmation; any other CORE workstream depending on an
ESTATE deliverable), the R8 pull-forward that closes the WS-C6 hazard from the main side, and the
shared-worktree substrate-drift class that will recur on their device.

## Gate gap, flagged not fixed

`mstr-ledger-check` CHECK-2 refused this commit: `org/mcp/agentbus-trunk/` is not in the record-append
allowlist (`:182`), which already carries `org/compiler-tools-log.md`,
`org/git-author-override-audit.log` and `org/mcp/comp_ferry_queue.json`. A trunk message is
structurally the same object — an append-only cross-device message record — so **every trunk message
costs a ledger entry, and the cost lands precisely when the trunk is being used as an emergency
fallback because the fast path is down.** Routing the allowlist question to CTO rather than widening a
gate on my own commit; this entry is the correct cost tonight.
