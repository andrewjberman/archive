# LD-0005 — Charter CTO + COO with cross-lane crash-recovery sweep

## Decision
Delegate to CTO (`1.0.0_SA_CTO`) and COO (`2.0.0_SA_COO`) jointly a fabric-wide
recovery sweep of the workspace working tree after Andrew's report that the
computer crashed from fork-exhaustion / overexertion. CTO drives the
control-plane and `.tools/` recovery; COO drives the REGISTRY / project-JSON /
TO-side recovery. Each routes per-lane M files to their respective lane owners
for "is this finishable, or scrap?" adjudication — never bulk-cleanup. Stashes
pre-date this crash (12 pre-existing, tagged with prior incidents) and are out
of scope.

Surfaces named in the charter:
- `org/mcp/inbox-watch.sh` — mid-flight `.unread-deliveries` sentinel feature
  (+12 lines, never committed). CTO adjudicates — finish-and-commit, or revert.

- `.claude/settings.local.json` (+50 lines) — BASE_EXEC review.

  as-is once line-ending warnings sorted.
- `infra/aws/terraform/smartx-pipeline/.terraform.lock.hcl` (-19 lines) —
  AE/CTO; almost certainly do not commit (lock-file shouldn't shrink).
- `org/projects/ADVI_DEMOV1.json` + `ADVI_DEMOV1.004` TO — COO + 0.4.0_DS_ClientPlatform.
- 411 untracked files — predominantly DS pod-4 probe scripts + screenshots.
  Each pod's DS adjudicates own debris.

MSTR's own surface (out of CTO/COO scope):
- Commit `103c9410d` (LD-0004) is local-only; origin has 2 commits ahead.
  MSTR integrates and pushes its own work in a subsequent cycle once the
  recovery sweep has settled (avoids stacking push contention with the lane

  channel survives a session crash, so the message is still pending in CTO's

## Why now
Andrew explicitly surfaced the crash; the M files include at least one
mid-flight feature that another agent will likely re-attempt cold without
realizing the prior work exists (`.unread-deliveries` sentinel is referenced in
`org/XXX.md` /loop Step 0 — a real feature, not stray noise). Letting that sit
risks duplicate-work or silent-revert when an agent rebases. The execs (CTO,
COO, CVO) are all back LIVE and clean — the recovery window is now.

## Assumptions
- The 12 stashes pre-date this crash (`stash@{0}` cites DIAGFIX.002a, `{2}-{4}`
  cite autostashes, etc. — all reference closed/superseded work). They are
  pre-existing noise; ignore.
- CTO can read each M file's diff to identify which lane authored it (the
  spawn-agent.ps1 diff size suggests CTO/DT; the .unread-deliveries sentinel
  references org/XXX.md and is plausibly COO or CTO mid-stream).
- 411 untracked files are debug / probe / screenshot artifacts from pod work;
  individual DS agents own their pod's debris.

## Alternatives considered
- MSTR triages each file directly — rejected: cross-lane scope (touches DT/AE
  control-plane + DS pod debris + COO REGISTRY); Art. VI govern-through-the-org;
  D-001 non_goal "MSTR does not itself edit code".
- Bulk `git stash` everything to recover quickly — rejected: destroys
  mid-flight work that's actually completing a real feature (sentinel
  mechanism). Slow-and-careful adjudication is correct.
- Defer the sweep — rejected: the longer mid-flight edits sit, the higher the
  probability another agent rebases over them or duplicates the work.

## Rollback plan
The charter is informational + adjudication; each lane owner's own commit/revert
is reversible. If CTO/COO over-cleans, the dropped content is recoverable from
`git reflog` for ~90 days. No destructive op authorized.
