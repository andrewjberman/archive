# LD-0329 -- Fabric-wide crash recovery: full tier-1 + DS + DT respawn after the 09:54 WindowsTerminal 0xc000027b outage

## Trigger

At **09:54:18 EDT** `WindowsTerminal.exe` (the terminal *host*, not PowerShell, not our code) threw an
unhandled WinRT/XAML exception (`0xc000027b` in `Windows.UI.Xaml.dll`) and crashed, killing **every**
agent session hosted in it. The fabric was fully dark for ~6.5 min (terminal relaunched 10:00:51). Full
forensics: `docs/references/INCIDENTS_2026-07-21.md`.

MSTR launched into the fresh terminal at ~10:01 and, on Andrew's direct order, ran disaster recovery
before anything else.

## Decisions

1. **Work-loss assessment FIRST (before any respawn).** Ground truth: MDPF_REVAMP committed + pushed to
   `origin/CLOUD @399e44fc6`, `HEAD == origin/CLOUD`, 0 ahead / 0 behind; last commits `f54765b3d` (DS) +
   `399e44fc6` (CTO) landed ~09:45-46, ~8 min pre-crash; working tree held no exposed MDPF source. **No
   work lost.** This is the load-bearing finding -- it made the outage a respawn, not a recovery-of-data.

2. **Clean-kill confirmation.** Process-truth census (`Get-CimInstance Win32_Process`) found zero orphan
   `claude.exe` and zero orphan spawn-marker `powershell.exe` survivors -- so no zombie holding a serial,
   no inbox-splitting orphan, nothing to reap before respawn.

3. **Respawn roster (Andrew-directed).** Tier-1 base trio + the MDPF workers + parity-harness owner:
   - `1.0.0_SA_CTO` (main CTO -- MDPF gate authority), `2.0.0_SA_COO` (coordination, /drive OFF),
     `3.0.0_SA_CVO` (main verify) -- Andrew: "get tier 1 base fabric online 1.0.0 2.0.0 3.0.0 ... MDPF_REVAMP is P0".
   - `0.4.0_DS_ClientPlatform` (MDPF PRIMARY), `0.4.0_DS_ClientPlatform~A` (A4 non_model lane) -- the
     "midway through" workers Andrew named.
   - `0.2.0_DT_PortfolioAnalytics` (parity harness / date-joined N=3) -- Andrew: "we need DT too".
     Note: CTO had preferred a stage-time DT spawn; Andrew's direct order overrode that (DT warms now).
   - Waves: 1-3 within the 3/spawner/60s rate cap; COO + CVO via audited `FORCE_SPAWN` overflow
     (disaster-recovery mass respawn); DT after the cap window cleared. All pre-flight 1pt-clean.

4. **MDPF_REVAMP = P0** baked into every spawn hint + the tier-1 briefs; CTO re-drives to N=3 (DS
   enumerate-19 -> inflection+global serve-real -> stage all 3 -> CTO S3 re-verify + DT date-joined
   parity). Direction flows through CTO (spawn != dispatch).

## SENT != READ correction (recorded, Rule 22b)

MSTR's first brief called CTO's `135429Z` gate verdict "unread -> DS never saw it" -- inferred from a
filesystem/delivery signal (still in top-level inbox, not `read/`) at the crash instant. CTO
(`142525Z`) grounded on DS's **consumer-side ACK** (`142324Z`): DS read + digested all 3 parts on
recovery. **Corrected finding:** unread AT the crash instant, NOT lost -- the durable filesystem inbox
preserved it and DS pulled it at startup. Closed by consumer-ACK, not a resend. The near-miss is a
resilience point (inbox survives a host crash) and a discipline reminder (ground READ on the ACK, never
inbox file-location).

All 6 respawns registered LIVE (broker `get_live_agents`) and self-oriented to their lanes within
~45s. Full fabric restored: MSTR + CTO + COO + CVO + DS base + DS ~A + DT. MDPF_REVAMP re-driving as P0
under CTO gate. Incident record committed alongside this entry.
