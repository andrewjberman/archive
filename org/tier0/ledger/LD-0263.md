# LD-0263 -- Amends LD-0262: sovereign attribution, scope (a MOVE, not a deletion), and the artifact rule

## (D) NEW STANDING RULE -- an MCP ruling is not an artifact

**A sovereign ruling lands in the committed record in the same operational window it is given, or it does
not exist.**

Originated by `2.0.0_SA_COO`, ratified here as Tier-0 doctrine. Three sovereign rulings today -- the
`logs/` deletion, the PII kill, and the PII deprioritization -- lived only in MCP message bodies. Every one
of them then had a lane act *against* a stale committed record while the ruling sat undelivered in a
channel. **The fix is not more messages.** The gate is: the agent carrying a sovereign ruling amends the
governing artifact (ledger / brief / TO / project JSON) before it takes the next action the ruling implies.

Corollary, learned the expensive way: **sovereign intent with no artifact is indistinguishable from an
accident.** An 882-file cleanup that left no record consumed a Tier-0 startup, then two Tier-1 cycles, then
a Tier-2 cycle -- each agent doing the locally-correct thing against the record it was given.

4. **A risk model asserted without reading the source it modelled.** LD-0262 claimed the armed index

Four errors, all four caught by agents *below* Tier 0 -- 0.5.0 (Tier 2) on the causal claim, 0.7.0 (Tier 2)
on the stale ledger, COO (Tier 1) on the gate false-positive and the scope, CTO (Tier 1) on the risk model.
The escalation chain is working, and it is running *upward* against Tier 0, which is what it was built to do.

## The enumeration doctrine, fourth instance -- it caught the sovereign

Ratified earlier this session (CTO, from the Q3 CloudTrail finding): *"correcting the enumeration is not the
fix; removing the dependence on enumeration is."* Instances: (1) the belt enumerated bd/cot/inf, missing
schwab; (2) the sweep enumerated 3 of 17 buckets; (3) the org CloudTrail trail enumerates bd+inf, missing
schwab and 15 others. **(4) Andrew described his own cleanup as "old docs" -- and 2 of the 42 paths were
`.py` code (`aws_access.py`, `test_connection_pool.py`).** The set someone believes they acted on is not the
set they acted on. The detector this time was the universal commit-gate, which refused to lint-pass an
archived `.py`; both files were returned to `infra/aws/` untouched.

Note the doctrine's own teeth: a *managed* enumeration is still an enumeration. Bringing every resource under
Terraform does not satisfy it. Terraform coverage and grant-blast-radius detection are **orthogonal controls**
-- coverage buys drift-detection, review and audit; it says nothing about what a grant *reaches*.

## Defect filed to CTO (blocking, real)

`.tools/commit-gate.sh:43` and `.tools/comp-surface-check:16` pass **every changed path** to `python` as
argv. A 932-file commit exceeds Windows ARG_MAX and both fail with `Argument list too long`. The gate then
fails **CLOSED** -- which is correct, and `--force` correctly does not bypass a gate failure. **Net effect: a
large, legitimate, sovereign-authorized commit is currently unlandable.** Fix is to batch/xargs the python
invocation. Until then, large changes must be chunked. Do not "solve" this by widening `--force`.
