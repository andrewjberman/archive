# LD-0588 -- daily-sprint-generator: /tmp exhausted at the checkout; storage raised, and a cleanup failure can no longer mask the job's failure

**Seat:** 0.0.0_AB_MSTR
**Authority:** Andrew-direct at this terminal, VERBATIM: "Just go fix it, use override channel, do it now.,"
(preceded by: "I am having CVO run the daily sprint for today, accordingly your job will not be to run it
from the cloud in your session here, merely to check on it and understand why it did not run in the first

**Stakes:** S1 (in-place Lambda configuration update + image act on a function with one consumer).
**Change-management ledger:** daily-sprint-generator-tmp-full-20260918

## What happened

The 2026-09-18 20:10Z scheduled fire ran and failed; Lambda's two async retries failed identically
(RequestId 923faa53-3879-4482-b899-20c7a96d6f80, 78.1 s / 79.9 s / 79.0 s). Nothing was published:
s3://opal-data-portal-v2/daily-reports/2026-09-18/ listed empty.

CloudWatch showed only: `git remote set-url failed rc=128 / error: failed to write new configuration
file /tmp/sprint/.git/config.lock`, raised from `strip_credential()` in the handler's `finally`
(lambda_function.py:430 -> :245 -> :141 @ the 09-15 image, digest 7d699a0f).

## Why that line was not the cause

`_generate()` prints "OK: clone at ..." as soon as `clone_repo()` returns. That line is present in every
passing fire (09-16 14:02Z, 17:48Z, 20:10Z; 09-17 20:10Z) and ABSENT from all three of today's attempts
-- 27 log events, 9 per attempt, none of them a progress line. So the job died inside `clone_repo()`,
the `finally` then raised as well, and Lambda logs only the exception that propagates. The real failure
never reached CloudWatch.

## The cause, measured

`git ls-tree -r -l <ref>` summed over blob sizes (the working tree a checkout must materialise):

| ref | when | files | tree |
|---|---|---|---|
| e433e10518 | 09-17 20:10Z fire's clone head (PASSED) | 37,033 | 1,462.8 MiB |
| ec5a7afd2b | origin/CLOUD through most of 09-18 | 37,881 | 1,505.9 MiB |
| 62427fa34d | origin/CLOUD after this seat's ~20:0xZ push | 38,066 | 1,509.6 MiB |

The function's `ephemeral_storage` was 2,048 MiB. The checkout lazy-fetches its blobs into the pack
beside the tree (406,798 KiB measured 09-11 per the source's own note). 1,463 + pack + per-file block
slack passed under 2,048 on 09-17; +43 MiB of tree on 09-18 did not. A full disk is also exactly what
makes git report "failed to write new configuration file ...config.lock".

CLAIM GRADE: the tree sizes and the missing progress line are MEASURED. "No space left on device" itself
is INFERRED -- it is the one exception the old code could not log. The new code prints it.

## Decision

1. `infra/aws/terraform/daily-sprint-generator/main.tf`: `ephemeral_storage.size` 2048 -> 10240 (the
   Lambda ceiling). In-place update, no replace. Headroom, not a cure for growth: the tree grew ~45 MiB
   in one day. A sparse checkout is the cure if the tree approaches ~8 GiB; not built now (YAGNI rung 1).
2. `infra/aws/lambda/daily_sprint_generator/lambda_function.py`: the handler prints the job's own
   exception and the disk state BEFORE cleanup runs; a failing `strip_credential()` no longer replaces
   the job's exception, and when the strip cannot run the whole WORKDIR is deleted instead (the PAT goes
   with it; if even that fails, it raises). Disk usage is also printed after every successful clone, so
   the approach to the ceiling is visible on passing days.
   Offline arms (stubbed git/AWS, no network), 5 of 5 PASS: A job+strip both raise -> the JOB's exception
   propagates and WORKDIR is gone; B job succeeds, strip raises -> result returned, WORKDIR gone; C clean
   path strips once and keeps WORKDIR. commit-gate clean.
