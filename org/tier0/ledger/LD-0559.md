# LD-0559 - /tradeops: spawn a seat on the other fabric, and prove it came up

## Decision

Two acts on Andrew's direct word, in order.

**1. THE SPAWN, DONE.** `4.0.0_SA_CRO` is live on the TRADEOPS fabric: pid 33724, registered on
that fabric's broker (port 7801) at 2026-09-12T02:03:48Z, cwd
`C:\Users\AndrewBerman\Downloads\docs_abcdeg`, MCP channel `server:tradeops-agent-comms`, and
`--remote-control 4.0.0_SA_CRO`.

Resolved without asking, because it was measurable: "in `downloads\docs_abcdeg`" and "on the
tradeops repo" name the **same place**. `ajb3.ps1` derives its root from its own location at
`entry\windows\`, so `docs_abcdeg` IS the tradeops repo root. There was no inconsistency in the
instruction.

`ajb3` could not be used as-is: it has no Remote Control switch. Its construction was reproduced
exactly -- root, role directive, first message, env, flags -- with `--remote-control` appended, and
nothing in the tradeops repo was modified.

**2. THE SKILL.** `/tradeops <serial>`, engine `.tools/tradeops-spawn.ps1`, carrying the
`/unstick` step he named.

## The failure the skill exists for

The launch **looked** successful and was not. Every cheap signal agreed it was fine:

| signal | read | true? |
|---|---|---|
| `wt.exe` exit code | 0 | worthless |
| tab created, titled | yes | worthless |
| `claude.exe` alive, right argv | pid 32620 | worthless |
| CPU across an 8s sample | flat at 2.7s | **the tell** |
| MCP server child process | none | **the tell** |
| tradeops liveness store | absent at +5 min | **the oracle** |

⛔ **A LAUNCHED-LOOKING TAB AND A RUNNING PROCESS ARE FULLY CONSISTENT WITH A DEAD SEAT.** The
engine therefore accepts exactly one success signal -- the serial in the broker's liveness store,
which only the agent itself can cause -- and distinguishes `rc=3` (launched, never registered)
from `rc=0` so the two can never be reported as one thing.

## A defect this seat shipped and then caught

Step 3 was written as "fail closed on an unknown serial" and checked `$LASTEXITCODE`.
`launch-directive.py` returns **exit 0** for a serial it does not recognise, reporting it only as
text: `UNRECOGNIZED ('<serial>' matched no role pattern)`. So the check **could not fail**, and the
skill document asserted the opposite. `9.9.9_XX_NotAThing` passed it.

**It was found by running the negative arm, not by reading the code**, and a positive control alone
would have read green throughout. The fix keys on the marker, and both the code and the doc state
plainly that this parses the tool's prose and inherits every future edit to that string -- a worse
instrument than an exit code, used only because the tool emits nothing better.

## Scope held

One seat per invocation. TRADEOPS only -- ajb_workspace seats stay with `/mstr-spawn`, and the two
fabrics' seats cannot message each other across separate brokers (7801 / 7800). The skill writes
nothing into the tradeops repo: it reads `ajb3.ps1`, `launch-directive.py` and `liveness.json`, and
launches a process. No commit and no worktree there, consistent with the standing rule that
docs_abcdeg work stays off this workspace.
