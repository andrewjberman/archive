# LD-0327 -- PM "Export" button emits the 2026-07 Vident 13-col full-model CSV (Andrew-sovereign portal deploy)

## The bug (grounded, live)

Yang reported the "Portfolio Management" Vident output was "still old format" even after the 07-14/07-20
migration. Ground truth established this session:
- The PM page exposes **two** Vident-CSV surfaces: **"Submit"** (ExportModal -> `exportAndSubmit` ->
  `/api/private/portfolio/export-and-submit` -> `opal-portfolio-excel-generator`) and **"Export"**
  (`handleExportCsv` in `TradeTab.tsx`).
- **LD-0324 (07-20) fixed only the backend "Submit" path.** The "Export" button is a **client-side**
  in-browser CSV generator -- it never calls a lambda -- and it was never migrated off the legacy
  9-col, trades-only format (`Ticker,SEDOL,ISIN,FIGI,Current Weight,...`).
- Evidence: `opal-portfolio-excel-generator` logged **0 invocations** when Yang worked; the newest
  `opal-trade-submissions` record was 07-13 (no submission created); Yang's own words (Andrew-relayed)
  = he used "Upload Files" then "Export", not "Submit". So the old-format file came from the un-migrated
  client `handleExportCsv`.
- This is the **same twin-drift pattern** as the backend (`opal-portfolio-excel-generator` vs the
  `trade-pipeline` "byte-identical twins"), one layer up: two CSV producers, one migrated, one not.

## The fix (shipped)

`handleExportCsv` rewritten as a faithful client-side twin of the backend `generate_vident_model_csv`
(`infra/aws/lambda/portfolio_excel_generator/lambda_function.py`): 13 `VIDENT_MODEL_HEADERS`, full
portfolio, FRACTION TargetWeight, `CASHTARGET` residual, sum-to-1 / oversubscribed / partial-model (<0.5)
refusal laws, download `FUND_Model_YYYYMMDD.csv`. **Verified against Yang's live 503-security PFDE autosave:
13 columns, TargetWeights sum to exactly 1.0, full portfolio (86 held + 417 zero-weight deletions), no
spurious cash row; portal typecheck clean.**
