# LD-0065 — Input 1 (compiler-asks) collapses to inbox-injection layer; cascade renumbers Input 0 / 1 / 2

## Decision

Per Andrew architectural insight 2026-05-25T~21:30Z: Input 1 (compiler-asks) is NOT a deterministic-generation loop like Input 2 (internal scan) or Input 3 (external scan); it's a CONDITIONAL-EMIT on top of MSTR's /govern checks + ad-hoc Andrew/Opal direct asks. Without obligated dense substrate generation, Input 1 isn't a loop — it's an inbox-injection pattern. Collapse Input 1 as a separate Input source.

## Architectural simplification

### Before (LD-0062 + prior CL CTO brief)

```
Input 0 (outcome-feedback, weekly, foundational)
Input 1 (compiler-asks via MSTR/Andrew/Opal, sparse + conditional)
Input 2 (internal scan, nightly, deterministic)
Input 3 (external scan, weekly, deterministic)
```

### After (this LD)

```
Input 0 (outcome-feedback, weekly, foundational)
Input 1 (internal scan, nightly, deterministic)   ← was Input 2
Input 2 (external scan, weekly, deterministic)    ← was Input 3
   +
Inbox-injection layer (MSTR escalation + Andrew/Opal direct asks)
   ↓ handled by CL CTO /charter Step 3 inbox-classification
   ↓ same treatment as ANDREW_DIRECTION etc.
```

## What stays the same

- **MSTR CL_STALL_CHECK mechanism** (per D-003 v1.12) — preserved; emit target = CL CTO inbox (MCP)
- **Class-6 archetype-cluster detection** — preserved; surfacing target = CL CTO inbox (MCP)
- **Andrew + Opal team direct asks** — preserved; direct MCP to CL CTO inbox
- **CL CTO /charter Step 3 inbox-classification** — already handles injection-class messages; minimal additions
- **Queue mechanics (priority/SLA/snapshot per LD-0062 D2)** — applies to Input 1 (was 2) + Input 2 (was 3) queues only

## What changes

- **MSTR_INPUT_1_CHANNEL_ARCHITECTURE.md doc** — DEPRECATED OR rescoped to "MSTR escalation MCP format guidance"; ws CTO scribes deprecation note + reference
- **Decision #3 (compiler-ask brief schema)** — RESCOPED from required-queue-schema to optional MCP body format guidance (lives in CL CTO inbox-classification doc OR in MSTR_INPUT_1_CHANNEL_ARCHITECTURE.md as deprecated-but-historical reference)
- **CL CTO V1.3 PRD draft** — Input cascade section updated to Input 0 / 1 / 2 (3 inputs not 4); Input 1 (was compiler-asks) section retired/rescoped to inbox-injection layer mention
- **Cascade renumbering propagates** through V1.3 PRD + /charter SKILL.md scribes + LD-0062 §materialization-chain text

## Rationale

Deterministic-loop principle: only loops that GENERATE substrate deterministically drive progress. Input 2 + Input 3 + Input 0 all generate substrate deterministically per their cadence. Input 1 was conditional-emit — sparse + judgment-based — which doesn't fit the loop-as-driver model. Inbox-injection is the more honest architectural primitive for "MSTR escalation OR Andrew/Opal direct ask."

Avoids over-engineering: queue mechanics + brief schema + dedicated channel architecture for Input 1 are heavy infrastructure for what is structurally just an MCP from one agent to another.

Re-introduce Input 1 as separate queue+loop if empirical use shows inbox-injection insufficient for compiler-ask substrate (e.g., MSTR escalations get lost in inbox noise, or Andrew/Opal volume warrants dedicated channel). Reversible via re-amend LD.
