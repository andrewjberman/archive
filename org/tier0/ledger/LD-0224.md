# LD-0224 — comp-tool scope audit: register comp-parity; whole-suite functional + registration verified

Andrew-direct 2026-06-30 ("go through the entire scope of comp-tools and make sure they all have cli
wrappers and are functional and properly registered/tagged").

## Method (deterministic — no subagents)

Three-way census: on-disk `.tools/comp-*` wrappers x registry (`graph-call-manifest.yaml` tools_index
+ entries + `excluded_not_graph_use_cases`) x curated `comp-tools.yaml`; plus a functional sweep
(engine `py_compile` + a safe `--help` probe of all 42 wrappers, timeouts to avoid expensive ops like
`comp-aws derive`).

## Findings

| Check | Result |
|---|---|
| CLI wrappers present | PASS — every registered tool has a wrapper; every real wrapper accounted |
| Functional | PASS — all core estate-cognition tools execute (engines compile, help responds, 0 tracebacks) |
| Registration / tagging | ONE GAP — `comp-parity` unregistered; **fixed** (now in tools_index + `pipeline.parity.served_cutover` entry + comp-tools.yaml block; comp-which routes to it). Registry re-verified COMPLETE (0 unaccounted). |
| Dead shims (flagged, not fixed) | `comp-learns-run` / `comp-learns-status` — non-functional shims for the SEPARATE, UNTRACKED COMP_LEARNS R&D framework (`comp/` is git-untracked; `comp/framework/` has no `run.py`/`status.py`). Excluded from the registry; not part of the comp-tool suite. Resurrecting = locating the untracked framework (separate decision). |

## Minor note

`comp-to` has no `--help` guard — it treats any argument as a TO_ID, so `comp-to --help` silently set
the session TO_ID to `--help` during the sweep (immediately reset). A small robustness gap in the
setter, recorded for a future hardening pass, not fixed here.

## Net

The comp-tool estate-cognition suite is **complete, functional, and fully registered**. The only
non-functional `.tools/comp-*` entries are the two COMP_LEARNS shims, which belong to a separate
untracked subsystem and are correctly excluded from the tools registry.
