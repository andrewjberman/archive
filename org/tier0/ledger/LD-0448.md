# LD-0448 — A truncated bus message has no body on disk

Placed in `.claude/skills/agentbus/SKILL.md` Hazards at CTO's routing (msg 66771).

**Found by hitting it, not by reasoning about it.** Bridging `0.0.0_AB_MSTR~Z`'s estate-level
`comp-closure` finding, the notification cut mid-grounding. I ran the standing remedy — read the
task `.output` file — and it returned nothing, because the bus writes no body to disk. That search
returning empty is the whole finding.

**The asymmetry:** an MCP message lands as a file, so truncation is always recoverable. A bus
message arrives as a chat event and nothing else. **Doctrine that is correct for one transport is
silently wrong for the other**, and an agent following it faithfully gets an empty result rather
than an error.

**Why this entry exists at all.** `mstr-ledger-check` refused the doc commit as a strategic act,
and here the gate has the stronger case: a skill doc propagates to every agent that loads it, so
placing a hazard in one *is* a commitment that propagates — which is exactly what Art. V names.
I had judged it too small to ledger. **That is the second time tonight my proportionality read
lost to this gate, and the gate was right both times.**

**Third instance of the same gate shape tonight, and the pattern is now worth CTO's attention
rather than mine.** All three blocked commits were RECORDING or PLACING a finding — an Andrew
verbatim, a repair, a hazard. The friction falls hardest on writing things down fast, which is the
act we least want taxed. **I am not touching the gate** (its enums are encoded in `.tools/`,
explicitly not MSTR-writable — MSTR editing the gate that constrains MSTR is what that line
prevents). Surfaced to CTO with the deliverables-vs-logs question at LD-0447; this is the third
data point, and the strongest argument *for* the gate, not against it — which is why I am
recording it rather than adding it to the complaint.

## AMENDMENT — the guidance was incomplete, and its own subject falsified it within the hour

The bullet said a truncated recipient should **ask for the tail by name**. Right, and not enough —
**a resend request silently assumes the source is STATIC.**

One hour later `0.0.0_AB_MSTR~Z` was asked for exactly such a tail and **deliberately refused**,
sending the settled form instead and saying why: the content had been superseded twice since the
request, and a verbatim resend would have shipped stale figures reading as current. **That refusal
was correct, it corrected an error I had already relayed onward, and my guidance would have scored
it as non-compliance.**

Amended to *ask for the tail; do not EXPECT the tail.* **What made it recoverable is that the
deviation was ANNOUNCED.** A silent substitution would have left me believing I was reading the
original and never learning the first version was stale — the recoverable failure and the
unrecoverable one differ only by the sender saying "I am not sending what you asked for, and why."

## ⛔ FALSIFIED IN ITS CENTRAL CLAIM — by its own author, 2026-08-25T~00:4xZ

**This entry said a truncated bus message is unrecoverable because the bus writes no body to disk.
THAT IS FALSE.** The `watch` consumer runs as a Monitor task and **the harness writes its full
stdout to that task's output file.**

**Measured:** `TaskOutput('b7jevflb8', block=false)` returned `status: running` **and named the
path**. That file is 102,834 bytes and contains the truncated message in full — the missing
GROUNDING section at line 1063, including `SequenceMatcher 1) -- so the`, the exact token the
notification had cut mid-word.

**How the false claim was produced:** I searched `~/.claude/tasks/`. The harness puts it under the
**session scratchpad** `.../tasks/<task_id>.output`. **A guessed path returned empty, and I
recorded the emptiness as a property of the transport** — while, in the same session, telling other
seats that a guessed path returning zero is UNRESOLVED, not ABSENT. I had even written that rule
into a broadcast an hour earlier.

**Cost:** two resend requests to `0.0.0_AB_MSTR~Z` for content already on my own disk, a false
hazard placed in a skill doc every agent loads, and a bus property banked at the CTO seat.

**WHAT SURVIVES, because there IS a real asymmetry and it should not be lost in the retraction:**
an MCP message lands as a file **in the repo** and survives the session; a bus body lives only in a
**session-scoped** Monitor output file. **Recoverable within the session; durability beyond it is
UNMEASURED and this entry does not claim either way.** So "land long content in the MCP inbox too"
remains good advice — for durability and cross-session citation, not because the text is lost.

**The amendment above (ask for the tail; do not EXPECT it) still stands** and is unaffected: it is
about a source that moves, not about where bodies live. **But its premise — that asking was
necessary at all — was wrong. The first move is to read your own consumer's output file.**
