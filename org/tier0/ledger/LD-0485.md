# LD-0485 — the push gate that a background file-mover satisfies

## What happened, in order, all measured

An integration push was refused: `HALT-GATE: blocked ... re-run with HALT_ACK=1`, surfacing a message
*"(0m ago)"*. **`HALT_ACK` was never set.** An identical `git push` about **twenty seconds later passed
silently** and carried five commits to origin.

## Why — and it is worse than a bypass, because the gate believes it was satisfied

`halt_gate_unread_for()` in `.tools/halt-gate-check.sh` defines pending mail as **`*.md` DIRECTLY under
`inbox/<serial>/`, `-maxdepth 1`**. This device runs a persistent inbox Monitor that moves each arriving
message from exactly that location into `read/` within seconds.

```
  push #1   a message sits top-level        -> gate SURFACES, exit 1, BLOCKED
  (~20 s)   the Monitor moves it to read/   -> NOBODY READ ANYTHING
  push #2   scanned location now EMPTY      -> gate PASSES SILENTLY, exit 0
```

⛔ **THE GATE CANNOT DISTINGUISH "THE AGENT READ IT" FROM "A FILE WAS MOVED."** Its effective protection
window is a few seconds wide, by accident of an unrelated background process. **This is precisely the
SENT / EMITTED / READ conflation that `ack_messages` exists to retire** — and a file-move is the EMITTED
clock, which structurally precedes any model seeing anything (the same anti-correlated shape as the
orphan-watcher: the queue clears *because* nothing is reading).

**Measured at the time of writing:** top-level `*.md` = **0** (the gate would pass silently this second);
`read/` = **5,630**. And the message that blocked the push was the CVO card-7 scope correction at
23:50:09Z — **one this seat had already read and acted on**. So it blocked on a message that had been
read, then cleared on a move nobody made. **Both halves wrong, no harm on this instance — which is exactly
why it would go unnoticed indefinitely.**

⚠ **A SECOND TRAP IN THE SAME FUNCTION:** there is a directory literally named **`unread/` that the gate
never scans** (`-maxdepth 1` excludes it); it holds 6 files, newest from 2026-05-30. **Anyone reasoning
about this gate from the directory names gets it exactly backwards** — `unread/` is invisible to it and
the top level is what counts. A name that contradicts the mechanism is worse than no name.

## Scope of the claim

**ROUTINE limb only.** The STOP-class limb is a different branch (`exit 2`, hard block, `HALT_OVERRIDE`
plus an audit line) driven by a separate `[STOP]`/`[HALT]` subject-token classifier. **It was not
exercised and nothing here is a claim about it** — though it shares the same enumeration, so the
enumeration finding reaches it while the block/override behaviour does not.

## The decision: SURFACE, DO NOT REPAIR TONIGHT

The obvious repair is to re-base the condition on the **agent-side ACK clock** (`ack_messages`) rather
than on file position — a file's location is a transport fact, an ACK is the only signal an agent
produces. ⛔ **Deliberately not shipped.** That is a behavioural change on **every seat's push path**; it
needs the surface owner's word and a battery with a live baseline, and shipping it at 00:0xZ off this
seat's own same-hour diagnosis would be the identical hasty-gate-change pattern this seat spent the
evening arguing against (LD-0483). **The finding is handed over, not acted on.** Filed to the surprise
channel as class OBSERVATION, standing ARMED, msg-ids 89601–89603.

## Cost and non-application

Cost: this entry and one message. Non-application: it changes nothing today — no gate edit, no push
behaviour change, no seat obligation. It does not bear on the deploy-scope (`safe-deploy`) limb of the
same hook, which ran and reported correctly on every window tonight.
