# LD-0249 -- REVERT the premature TO-6 phase-1 landing (racy worker singleton found)

**What.** Reverted `f5487a401` (LD-0248, the `_ensure_commit_worker` wiring into `server.py`). MSTR's
verify-the-live-state discipline found a **23-process commit-worker swarm** (singleton should be 1), and
grounding the mechanism in source showed `commit-worker.sh`'s `cw_acquire_singleton` is a **non-atomic
check-then-write TOCTOU race** (RULE-16 blocks `flock`) plus an unreliable `kill -0` on Windows. My
change wired the worker-launch **ungated on every register across 11 agents** -- landing it over a racy
singleton would turn restarts into a swarm. Caught before any session activated it (they run the old
server.py; it loads from the file on restart).

**Incident response (done):** killed the 23-worker swarm (no respawn -> no active spawner); cleared the
stale `.git/index.lock` my push-timeout left (was blocking fabric commits); restored `server.py` to safe.

**TO-2 is clean** -- the landed `safe-commit` is a pure client (only *checks* `cq_worker_alive`, never
launches), so it is NOT the swarm source; CVO's TO-2 PASS stands.

**HOLD TO-6 phase-1** until ~B makes the singleton **atomic** (a `mkdir`-based lock, RULE-16-compliant --
the same pattern safe-commit's own mutex uses) + **Windows-safe liveness** + **proves it under CONCURRENT
launches** (N simultaneous -> exactly 1 survives). Then re-verify, re-land, and reconsider gated-vs-ungated.

**Lesson.** Verifying the live state before/after a land caught a change that would have amplified a latent
fabric-choke. The "never trust a producer's rc=0 / verify against live state" discipline earned its keep.
