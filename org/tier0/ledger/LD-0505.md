# LD-0505 — the 48% cap disabled the wrap that would have saved it

## Decision

`daily_reports/templates/_shared_viz.js`, `screens()`: `max-width: n===1 ? '100%' : '48%'`
becomes `max-width: 100%`. One token.

## Both of his hypotheses were tested and CLEARED before the fix was written

He asked whether it was image inclusion **or** generation variability. Answering required clearing
the page itself first, because "everything got smaller on a phone" has a classic cause — one
overflowing element makes the browser shrink-to-fit the whole document — and that cause would have
pointed at completely different code.

`Mobile_DAILY_REPORT_2026-09-01` (the complaint) vs `2026-08-31` (a night he was happy with), both
rendered headless at 390x844:

```
  <style> blocks                 88 lines each, diff CLEAN (byte-identical)
  .headline / .headsub / .sect   26px / 13px / 10.5px   -- IDENTICAL both nights
  .sitem / .sitem .cat           16px / 10px            -- IDENTICAL both nights
  document.scrollWidth           390 == viewport on BOTH -> NO zoom-out, NO overflow
  <img> count                    0 (08-31)  vs  3 (09-01)
```

**The page chrome never changed and nothing overflowed.** The only structural difference was the
photos, rendering `155x109`, `155x116` and `322x224` from `900`, `900` and `1440` px sources —
**17%, 17% and 22% of natural size.**

## The mechanism, and why it is worth stating precisely

```
  flex: 1 1 260px;   max-width: n===1 ? '100%' : '48%'
```

`flex-basis: 260px` with `flex-wrap: wrap` means *"prefer 260px each, otherwise wrap to the next
row."* The `48%` cap forces both figures **below** that basis, so they always fit on one line and
**`flex-wrap` never fires**. ⭐ **The cap did not merely shrink the photos — it disabled the one
rule that would have stacked them.** That is why the fix is a REMOVAL, not a breakpoint: the
correct behaviour was already written and was being suppressed.

`2 x 260 + 12` gap `= 532 <= 560` (the desktop wrapper) so desktop still lays out 2-up; `532 >`
a phone's ~322px content column, so it wraps to one per row, each growing to full width. No media
query, no template change, one shared grammar still serving both pages.

## Verified AFTER, three cases, both widths

```
  09-01  mobile  390px    two 900px shots  155px -> 322px  (17% -> 36%), 1 per row, no overflow
  08-28  mobile  390px    THREE shots      all 322px,                     1 per row, no overflow
  09-01  desktop 1280px   both figures still share ONE row, 274px each -- arrangement preserved
```

## ⛔ I retracted my own source comment before committing it

The first draft of the code comment claimed the desktop layout was **"bit-identical."** It is not —
the figure is now basis-grown rather than capped at 48% of its wrapper, so the width moves a few px
— and **I had measured only the AFTER**, so "identical" was a claim with no before-reading behind
it. The comment now states what was actually preserved (the 2-up ARRANGEMENT) and names the
retraction, because a false claim left in source outlives the session that wrote it.

## NOT fixed here — the other half of the same complaint

`etf_ownership_aug.png` is **1440x1000**, above `capture_screens.py`'s own
`MAX_W["desktop"] = 900`. **That file never went through the capture tool**, and nothing enforces
that a shot referenced in the JSON is one the tool produced. At 322px a 1440px desktop UI is still
22% — **a layout fix cannot make an oversized source readable.** That belongs to the single
image-ingest function he asked for ("a reliable consistent function for this with rules"), which is
sequenced next and is where the provenance assertion goes.

## Rollback

Revert this commit. Renders are regenerated from JSON on every run; nothing is served from this
file directly. Historical `daily_reports/out/` renders were re-rendered ONLY to measure the fix and
have been restored to their committed bytes — no past day's served artifact changed.
