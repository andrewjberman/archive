# LD-0487 — MDPF_HEALGAP minted under D8

## Decision

Register `MDPF_HEALGAP` as a D8 project and write its purpose-level brief
(`docs/architecture/MDPF_HEALGAP_BRIEF.md`), on Andrew's word. Register row added to
`org/missions/DIRECTIVES.yaml` D8 `members.projects` by the register owner (this seat, per the file's
own header), verified by re-parsing the YAML rather than by the edit's success.

## Why it belongs under D8 rather than beside it

D8's stance already names this class: *"every object-mtime freshness instrument reads HEALTHY and is
correct about the FILE. That blindness is the condition D8 exists to end."* There the payload was stale
inside a file rewritten daily; here **the file is simply absent while the producer reports healthy.**
**Same blindness, different surface** — so this is the directive's own thesis one layer over, not a new
one that happens to be nearby.

## The finding worth carrying out of the brief

⛔ **THE CONFIGURATION STATES A TOLERANCE IT CANNOT DELIVER.** `maximum_event_age_in_seconds = 21600`
(six hours) sits beside `maximum_retry_attempts = 2`. AWS caps async retries at 2 and they back off in
minutes; the three observed invocations spanned **165 seconds**. For a function that *raises*, the
six-hour window is **unreachable by construction, not misconfigured** — and the heal landed at 11:33Z,
**inside** that declared window, so a policy delivering what the config claims would have caught this
with ~27 minutes to spare. **An auditor reading that config concludes the opposite of the truth**, which
is the same failure mode as the incident: an instrument that is correct about the wrong thing.

## What was deliberately NOT done

- **No design chosen and no decomposition.** Stage 2 is purpose-level; the CTO holds the design ruling
  and the COO's atom-decomp is stage 3 and precedes any TO. The brief ranks four directions **with the
  objection that would sink each**, so neither seat starts from a blank page, and decides none of them.
- **No vendor egress.** The one-shot `--date 2026-08-31` re-run remains a **separate open sovereign
  call**; Andrew's 15:40Z grant was scoped to an endpoint-typo lookup and stands recorded as GRANTED,
  NOT EXERCISED, 0 vendor calls. **"We do need to fix this" was read as commissioning the project, not
  as authorizing the re-run** — a wider reading was available and I did not take it.
- **No scope claim.** 70 `.tf` files carry a `schedule_expression`; that is the CANDIDATE population,
  not the affected one, and the real enumeration is a Rule 24 authoring act left unperformed.
  **No claim is made that any 49F runner is affected, or that any date before 08-31 is holed.**
- **No placement call.** D8 is SITEZ-placed, site Z lost all 11 seats in a 17:04Z reboot, and a codex
  fabric is being stood up locally. **Whether this project runs local or at site Z is Andrew's**, and
  taking it by default would be a placement decision made by accident.

## Evidence grade, stated rather than implied

The landing counts were re-derived at this seat by `s3api` across three dates with the two adjacent days
as built-in controls. ⚠ **`0.6.2_AE_PartnerETL` measured the same way, so this is RE-DERIVATION WITH A
WIDER DENOMINATOR, NOT AN INDEPENDENT INSTRUMENT.** Nobody has yet read this hole through a different
plane, and the brief says so.

## Cost, rollback, non-application

Cost: one measurement pass, the brief, the project row and this entry. Rollback: the project is
`dep_stage: BRIEF` with nothing built — retiring it is a register edit and a status flip. Non-application:
it changes no pipeline, no schedule, no law, and binds no seat until a decomp exists.
