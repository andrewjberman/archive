# LD-0479 — Ledger numbering across two fabrics: state the denominator of "max"

## Decision

1. **The rule was never absent.** `org/tier0/ledger/_TEMPLATE.md:3` ("monotonic, max+1") and
   `org/tier0/README.md:54` ("The `decision_id` is monotonic — take max+1") both carry it. `0.0.0_AB_MSTR~Z`'s
   `comp-find 'next free LD number'` → 0 hits across 47,290 files swept a PHRASE, not the FORM the rule is written
   in — the census-the-form lesson, again.
2. **What was absent is the denominator.** "max" over ONE fabric's tree is how two live fabrics mint the same number
   independently (LD-0471, 2026-08-28; the near-miss on 0478 / 0472, 2026-08-29). Both carriers now say: **max is
   measured over BOTH fabrics' remote refs after a fetch (`origin/CLOUD` and `origin/SITEZ`), never one tree.**
3. **Gap-fill is never a warrant.** A number that reads free under `ls` and under `git log --diff-filter=A` on one
   tree can still be minted on the other tree since the last fetch. Monotonic over both trees closes that; gap-fill
   re-opens it.
4. **A collision is re-minted by the LATER minter**, once. Site Z's re-mint of 0471 → **0472 STANDS**: it is on
   origin/SITEZ, the ledger reads contiguous 0470-0479, and a second re-mint on a convention that was unwritten at
   the time would be worse than either choice — MSTR~Z's own framing, adopted.

## Provenance chain (Art. XIII)

D-001 (the Tier-0 control plane) → the ledger is the record of every S1+ commitment → a shared ID space with two
allocators and a one-tree max produces duplicate IDs → this amendment states the denominator. Both fabrics' MSTR seats
agreed the rule was unstated (bus msgs b077fbfe / feb963f9, 2026-08-30 00:0x-00:1xZ); this seat wrote it down as the
protocol's owner.

## Carriers edited in the same commit

the rate is two in two days on a manual process, which a fetch-then-max discipline covers.
