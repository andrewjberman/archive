# LD-0031 — Fabric-fungible governance above the repo: one Tier-0 law for ajb + clb

The structural intent has been operationally validated multiple times:
- **LD-0022 cross-fabric portability** — CL CVO applied LD-0022 architectural-corroborator mechanism inside CL fabric on B.2.b (CY-0069); ws-authored framework operated in CL fabric without re-derivation
- **LD-0028 cross-fabric concurrency cap** — spawn-agent.ps1 8-cap counts across both fabrics by design

LD-0031 makes this **structural** rather than emergent: the framework that has been working fabric-fungibly gets explicitly canonicalized at the location matching its scope.

## Three implementation paths (CTO chartered to design)

**Path A — Physical relocation of Tier-0 law to parent directory.**
Move `CONSTITUTION.md` + `STAKES_MATRIX.md` + `DIRECTIVES.md` (the core law docs, NOT the ledger/cycles/reviews which are MSTR session records) to a shared parent location like `~/Desktop/opal-tier0/` (above both repos). Both `ajb_workspace/` and `feature_clb/` reference via symlink or canonical-path constant.
- Pro: literal interpretation of "above the repo"
- Con: filesystem manipulation across both repos; .gitignore + path-resolution complexity

**Path B — Declarative canonicalization.**
Tier-0 law stays at `ajb_workspace/org/tier0/`; declared in DIRECTIVES.md preamble + Constitution as canonical for both fabrics. CL fabric's Tier-1 agents read ajb_workspace's tier0/ for canonical rules; CL doctrine docs cross-reference back. MSTR session continues running in ajb (singular Tier-0 actor) but governs both fabrics by declaration.
- Pro: minimal disruption; matches empirical state today
- Con: ajb_workspace "owns" the rules in repo-structure-terms even though canonically they govern both

**Path C — Extract to separate `opal-governance` repo.**
Tier-0 law + /govern SKILL.md + ledger schema extracted to a third repo `opal-governance/` checked out alongside ajb_workspace + feature_clb. Both repos reference via git submodule or sibling-path convention.
- Pro: cleanest long-term architecture; explicit governance-layer; can version + tag the rule set independently
- Con: meaningful CTO design + migration work; submodule complexity; ledger/cycles/reviews need a home (could stay in ajb or also move)

**MSTR draft recommendation: Path B → C trajectory.** Path B immediately (declarative canonicalization captures the empirical state without disruption); evolve to Path C if/when the explicit-governance-layer benefit warrants the migration cost. Path A is awkward middle-ground (filesystem move without the architectural commitment Path C provides).
