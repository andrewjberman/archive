# LD-0019 — Charter COO + DS~C to add 2/3 dollar-scaling to demo_transform

## Decision

Andrew Q1 (ADVI_DEMOV1 project JSON `blocking` field) resolved by
sovereign direction:

> "Regarding the data set, it would be nice to evolve the numbers
> a little if possible so it doesn't look explicitly like 49, i.e.,
> make sure the AUA is more like 600m, I'd say cut all numbers by
> 1/3 if possible."

**Direction:** the demo dataset's dollar values should be scaled to
~2/3 of source (cut by 1/3). Target AUA ~$600M from 49 Financial
source ~$900M. Applies to all dollar fields in the platinum tree
(AUA, account values, holding values, etc.) -- DS~C identifies the
field set during implementation.

**Open question Q2 (refresh policy) NOT addressed by Andrew this
turn**; still open in the project JSON. Demo project continues as
one-shot snapshot per current PRD until Andrew rules otherwise.

## Implementation paths (COO + DS~C decide)

**Path (a) -- abort current run, restart with scaling:**
- Pros: clean single-pass output; no double-handling; matches the
  current two-pass deterministic-pseudonymizer architecture cleanly.
- Cons: ~30% of attempt-8 transform work lost (~6,640/22,260 objects
  written); restart adds another ~13h to demo readiness.

**Path (b) -- let attempt 8 finish, apply scaling in follow-up pass:**
- Pros: preserves attempt-8 progress; faster path to first-cut demo
  dataset (even if dollar values are wrong, structure is right).
- Cons: requires a third pass design + run; complicates
  determinism guarantees; PII-leak scan (R5) timing question
  (run on identity-only scrub, then again post-scaling? once,
  after both?).

**COO + DS~C empirical call.** MSTR doesn't force either; the
charter is the scope direction + the decision authority.

## Other implementation notes (out of MSTR's lane; for DS~C
reference)

- Scaling factor: 2/3 = 0.666... ; DS~C decides whether to use
  exact fraction or rounded decimal; preference for deterministic-
  reproducible (e.g., integer arithmetic via numerator/denominator).
- Dollar field set: traverse the PII-classification map +
  identify numeric dollar fields (account value, holdings value,
  fee dollars, etc.); whitespace fields like dates / ratios / IDs
  do NOT get scaled.
- Sub-totals + identities: scaling must respect any per-row identity
  (e.g., if account value is sum of holdings, scaling each line
  preserves the identity).
- Mapping (the real->fake key per ruling R4) does NOT change --
  this is a dollar-value transform, not an identity transform.
