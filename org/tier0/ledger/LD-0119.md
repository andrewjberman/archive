## What this closes

CVO v1 lift-grading framework (banked at `[[feedback-lift-grading-framework-cvo-judgment]]`) is CVO-judgment-only: A/B/C/D/F grade based on PRD content + design coherence + expected value. It assesses pre-deployment quality, not empirical post-deployment lift.

comp-ferry closes the "tool shipped vs tool empirically proven useful" gap by adding **empirical-anchor** companion: 0.8.0_AE_CloudComp tester agent runs ONE real-task invocation per tool per ferry cycle on actual ws workload + reports lift observed. CL CVO authors `delivered_lift_grade_v2` (empirical) alongside `expected_lift` (v1 judgment); the calibration_delta_v1_v2 = framework accuracy signal feeding future judgment refinement.

## Architecture (ratified)

Mechanism flow:
```
PRD V1.0 RATIFIED on compiler-tool
  → CL CVO emits [COMP-FERRY-READY] MCP to MSTR (tool_name + case_id + prd_path/commit + agent_traversal_pain_addressed + expected_lift + ws-use-case-question)
    → MSTR appends entry at org/mcp/comp_ferry_queue.json (state=scheduled)
      → MSTR /govern dispatches via ws COO to 0.8.0_AE_CloudComp (state=in-flight; per LD-0116 no MSTR-to-T2/3 direct)
        → 0.8.0_AE_CloudComp executes ONE real-task invocation on ws workload
          → ws COO RAVC2 ferries [COMP-FERRY-RESULT] back to MSTR (state=tested-{PASS|CONCERN|FAIL})
            → MSTR routes to CL CVO
              → CL CVO authors delivered_lift_grade_v2 + calibration_delta_v1_v2
              → If tested-FAIL or tested-CONCERN with material concern: CASE-REOPEN at original case_id → CL CTO triages
```

## 0.8.0_AE_CloudComp agent spec (ws CTO set-up scope)

- **Serial:** `0.8.0_AE_CloudComp` (0.X.0 prefix = senior Tier-2 ws-fabric; AE = Application Engineer; CloudComp = Cloud Compiler scope)
- **Fabric:** ws (ajb_workspace; cwd routing default per LD-0088)
- **Authority:** ws CTO authors prompt.md + ws COO operationally dispatches ferry-test TOs from MSTR queue
- **Scope:** test CL fabric compiler tools (comp-lineage, comp-pyimp, future comp-* family) against real ws workload
- **Methodology:** light-cycle per `feedback-light-fast-local-benchmarking-until-arsenal` — ONE real task per tool per ferry cycle; manual inspection; ~10-30min wall; NO heavy benchmarking
- **Output template:** structured report with (a) tool invocation verbatim, (b) ws workload scenario + why chosen, (c) hand-grep-replaced step count (eyeball lift), (d) tool answer verbatim, (e) manual-validation comparison, (f) noise/false-positives, (g) integration friction observations, (h) 1-line lift verdict PASS/CONCERN/FAIL with rationale
- **Launcher pattern:** ws CTO can author prompt + README; MSTR adds launcher role-pattern in ajb.ps1 per LD-0118 precedent (MSTR-side mechanical edit; ws CTO not blocked on the launcher change for prompt authoring)

## Queue file ownership (MSTR scope)

- **Path:** `ajb_workspace/org/mcp/comp_ferry_queue.json`
- **Owner:** `0.0.0_AB_MSTR` (file lives in MSTR-controlled `org/mcp/` substrate)
- **State machine:** scheduled → in-flight → tested-{PASS|CONCERN|FAIL} → optionally reopened → scheduled
- **Capacity:** in_flight_cap=1 (serialized during light-cycle phase; lift post-arsenal)
- **Cycle integration:** /govern Step 3 PROCEED actions check queue for scheduled entries + dispatch up to (in_flight_cap - in_flight_count) per cycle

## 5 open design questions — dispositions (all MSTR-ratified)

| # | Question | Disposition |
|---|---|---|
| Q1 | Ferry cadence: event-driven push OR batched weekly pull? | **EVENT-DRIVEN PUSH** — CL CVO emits [COMP-FERRY-READY] on each V1.0 RATIFIED. Pull-batched rejected (adds latency without benefit). |
| Q2 | AE methodology: free-form vs templated? | **TEMPLATED** — 8-field structured report (see 0.8.0_AE_CloudComp agent spec output template above). Mechanical comparability across tests + enables aggregation. |
| Q3 | delivered_lift_grade_v2 schema: Case frontmatter vs separate artifact? | **BOTH** — frontmatter field on originating Case (the grade) + separate ferry_result artifact (the full report). Case gets grade; ferry_result gets detail. |
| Q4 | Negative-test disposition: CASE-REOPEN vs COUNTER verdict vs amendment? | **CASE-REOPEN** at original case_id. CL CTO triages PRD v0.2 amend / scope reduce / retire. Preserves audit trail + lets CL CTO judge. |
| Q5 | Capacity gating: in-flight cap? | **SERIALIZED INITIALLY** (in_flight_cap=1) during light-cycle phase. Post-arsenal threshold, lift to N>1 to parallelize. MSTR queue tracks in_flight_count vs in_flight_cap. |
