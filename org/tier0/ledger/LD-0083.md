# LD-0083 — Embed /stimulus-scan operative core into /drive Step 2b

## Decision

Per Andrew direct 2026-05-26T~03:25Z + structural-risk surface earlier in turn: pivot from fold-by-reference to inline-embed for /drive ↔ /stimulus-scan integration.

## The structural-risk Andrew identified

Earlier in this turn I proposed folding /stimulus-scan into /drive via the established "reference" pattern (e.g., /work Step 1 says "fold /watcher Steps 1-5 inline per its SKILL.md"). Andrew flagged:

> "each of these is already almost 200 lines long, agents are not reading all of that reliably i do not trust them to do that"

This is a real reliability concern. The fold-by-reference pattern assumes the agent reads both files in full. At 150-200 lines per file, under context pressure, agents skim — operative directives buried in back halves get missed. The pattern works for tight skills (<80 lines) but breaks down at scale.

## Pivot mechanism

Embed the operative steps DIRECTLY into the consuming skill body, not by reference. /drive Step 2b is now a literal mechanical checklist with the steps the COO must execute, no external read required.

### What lands in /drive (Step 2b — new)

~75 lines of embedded operative core:
- **2b.1** — read agent state (telemetry primary, broker cross-check) — includes the canonical `jq -r | tail -1` snippet
- **2b.2** — classify each agent (ACTIVE / IDLE / STALE / NOT_REGISTERED / TELEMETRY_GAP table)
- **2b.3** — classify cause for each STALE/IDLE agent (BLOCKED / STUCK_MID_CLOSEOUT / STARVED / STANDING_BY_REDIRECT table + resolving dispatch column)
- **2b.4** — fire dispatches (mandatory; one per non-ACTIVE agent; "standing by" never acceptable terminal state)
- **2b.5** — carry agent-state context forward into Step 3 project-state classification

Step 2b sits between Step 2 (hot-registry read) and Step 3 (per-project classification) so agent-state findings INFORM project-state classification — exactly the integration value Andrew was after.

### What lands in /stimulus-scan SKILL.md

Single ~5-line note at the top of the body:
> **LD-0083 update (2026-05-26):** The operative core is **EMBEDDED directly into `/drive` Step 2b** — COOs execute it inline every /drive cycle (20m) without reading this SKILL.md. 45min trigger heuristic + `.last-stimulus-scan` state-file logic applies ONLY to standalone invocations (rare; CTOs / on-demand fabric sweep). This SKILL.md remains the **doc-of-record** for full taxonomy + dispatch-quality criteria + edge cases.

No body content changes — /stimulus-scan stays standalone-invocable for CTOs + ad-hoc sweeps; doc-of-record posture preserved.

## Why embed beats reference here

| Axis | Fold-by-reference | Inline embed (this LD) |
|---|---|---|
| Reliability | depends on agent reading second file at 200+ lines | mechanical checklist present in one file |
| Body size | both files small (~80 lines each ideal) | consuming skill grows (+~75 lines) |
| Doc-of-record | reference body IS doc | reference body becomes doc; embed is execution |
| Maintenance | single source updates downstream readers | update embed AND doc if they diverge (drift risk) |
| Fit | tight self-contained primitives (e.g., /watcher checklist) | rich operative core that must be executed (e.g., /stimulus-scan) |

The maintenance drift risk is real but acceptable: /stimulus-scan body changes slowly + the operative core (the part embedded) changes even more slowly. CL CTO + ws CVO can be tasked with periodic drift-check in their /spot-check + /verify-channel cycles if it becomes a problem.

## Broader observation banked

> Skill bodies >150 lines are at-risk for missed-step reliability when the operative core is buried beneath context / rationale / edge-cases.

Future workstream (Andrew "come back to this"): per-skill audit to extract operative cores from skill bodies. Move rationale + edge-cases + history to companion `docs/architecture/<SKILL>_DESIGN.md` docs. Skill body becomes the executable checklist; companion doc becomes the design record.
