# LD-0010 — Spawn 0.3.0_DE_TradingOperations to close yang-pipeline-lineage read-side draft

## Decision
Spawn `0.3.0_DE_TradingOperations` via `.tools/spawn-agent.ps1
0.3.0_DE_TradingOperations`. The agent's lane owns the surface CTO's
RAVC-CLOSE (msg `20260523T041141Z`) explicitly named as P1 + held back
as a live-test "downstream observation surface":
`docs/reference/yang-pipeline-lineage-readside-draft.md` — 80% drafted,
§0 load-bearing route correction (`/api/general/*` vs `/api/public/*`),
read-side data-flow document for the yang-pipeline lineage. The artifact
is present in the working tree (in the untracked list at session start);
the draft's lane owner is not LIVE; finishing + committing closes a
non-trivial debt.

Spawn != dispatch (LD-0007 policy): MSTR provisions; COO authors any
formal TO for the close-out work; the spawned agent reads its task_orders/
on startup. If no formal TO exists yet, the spawned agent reads the
working-tree artifact + its own session protocol per org/XXX.md and
surfaces an ETA / scope clarification through MCP.

## Provenance chain (Art. XIII)
D-001 (active, PHASE 1) -> a load-bearing read-side data-flow document
in the working tree is in-scope of "drive every genuinely-active project
to its done-state" -> the draft has been "80% drafted" but not committed
-> the natural lane owner (0.3.0_DE_TradingOperations) is not LIVE ->
unaddressed work surface -> spawn per LD-0007 capability + Stakes Matrix

The cycle CY-0005 missed this surface because it scanned only first-order
population signals (broker summaries naming non-LIVE agents). The second-

is not LIVE) was not in CY-0005's methodology. Surfacing now is the
right correction. Noted for /mstr_review as a population-scan
methodology refinement candidate.

## Why now
The surface was held back from routing as a "downstream-test data point"
(CTO msg `20260523T041141Z`: "I held back routing the DE 0.3.0
yang-pipeline-lineage read-side draft — keeping it as a downstream-test
data point per Andrew direction"). With this cycle the test is no longer
about autonomous discovery — the surface is named in the inbox. What
remains is whether MSTR acts on the surfaced signal. Acting now is the
expected behavior.

## Assumptions
- 0.3.0_DE_TradingOperations is the right lane owner. The "yang-pipeline-
  lineage read-side" framing positions it as a portal-data-consumer's
  view of the yang outputs; trading-operations pod consumes yang data
  in trade context. If lane-wrong, kill is reversible.
- The 80% draft is in a coherent state the spawned agent can resume.
  The file at `docs/reference/yang-pipeline-lineage-readside-draft.md`
  was present in the initial git status untracked listing; the spawned
  agent reads it on startup.

## Alternatives considered
- **Charter pod-1 DE (`0.1.0_DE_MarketIntelligence`)** -- rejected:
  yang is pod-1's PRODUCER but the read-side artifact's framing maps to
  the CONSUMER (trading-ops). CTO + COO held the lane assignment as
  0.3.0_DE_TradingOperations; trust the answer-key.
- **Don't spawn; let the artifact age** -- rejected: load-bearing route
  correction sitting uncommitted in an untracked file is risk of silent
  divergence (the next agent reading the wrong route does worse work).
  Closing is cheap and high-yield.
- **Spawn 0.3.0_DE_TradingOperations~B (a lane)** -- rejected: no
  evidence a ~B sub-lane exists for this pod with relevant context;
  base-lane is the natural owner for a base-serial artifact.
