# LD-0020 — Fork-stall escalation mechanic: COO first, MSTR resolves at cycle-2 boundary

## Decision

Introduce a fabric-wide fork-stall escalation rule, anchored in D-001 and enforced through the /govern Step 1(b) population scan:

1. **First-line responsibility: COO.** When a worker (DS / DE / AE / RD) raises a fork — competing paths, ambiguous requirements, a "which way" question that blocks them — COO is responsible for resolving it. This is an existing COO duty (operational coordination) now made explicit and tracked.

2. **MSTR /govern population-scan extension.** Step 1(b) gains a new classification axis: **FORK-STALLED** = agent surfaced a fork (in MCP message, RAVC, TO blocking field, or session log) AND no resolving directive has reached them within 1 full /govern cycle of the fork surfacing.

3. **MSTR cycle-2 mechanical resolution.** When an agent is FORK-STALLED for >1 cycle (i.e. observed STALE-on-fork in CY-N, still STALE-on-fork in CY-(N+1)), MSTR resolves the fork mechanically at its discretion — Art. VI delegations still flow through Tier 1 (CTO/COO author the resolving TO), but the **directional call** comes from MSTR. Operational-mechanical = "pick the path that is reversible, cheapest, or most-information-producing"; not architectural depth.

4. **Audit trail.** Each MSTR fork-resolution gets its own LD entry referencing the original fork, the COO-cycle that didn't resolve it, and the chosen path with rationale.

## Why now

Today's session surfaced two cycle-2 fork patterns:
- ADVI_DEMOV1 Q1+Q2 (Andrew himself had to answer)
- LD-0019 path (a) vs (b) (COO RECOMMENDED but DS~C confirm cycle was the blocker)

Andrew's directive flags this as a class — forks accumulate quietly and stall throughput because no agent has explicit ownership-of-resolution authority. The new rule installs that authority: COO owns it; MSTR backstops at cycle-2.

## Assumptions

- COO has the operational context to resolve most forks (true — operational-coordination is her D-002 mandate).
- A 1-cycle delay is the right tolerance — long enough for COO to do diligence, short enough to prevent throughput drag.
- MSTR's "mechanical" resolution heuristics (reversible / cheap / information-producing) cover the cycle-2-fork class without architectural-depth misjudgment. If MSTR judges a fork architecturally deep, it escalates to Andrew, not resolves mechanically.
- D-001 v1.5's OPERATIONAL THROUGHPUT + BOTTLENECK-RESPONSE INTENSIFICATION ladder already supports this — fork-stall is a special case of STALE with a named blocker; cycle-2 intensification = MSTR-resolves.

## Alternatives considered

- **CTO as first-line instead of COO.** Rejected: forks are predominantly operational, not architectural. CTO escalates only when the fork has architectural depth (which COO surfaces upward when she identifies it).
- **MSTR resolves immediately at cycle-1.** Rejected: pre-empts COO's operational authority, generates churn, violates Art. VI delegation discipline. COO must get the first attempt.
- **No mechanical escalation; route every cycle-2 fork to Andrew.** Rejected: makes Andrew the bottleneck, contrary to D-001's autonomy posture.
