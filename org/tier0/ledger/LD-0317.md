# LD-0317 -- Broker commit-worker 12-day silent death: launcher-liveness is not worker-liveness

## Chain

0.7.0~B git_bash victim-scan (during the WSL-stub fix wave) -> found server.py commit-worker heartbeat
frozen 2026-07-07 -> COO 193641Z routed the observation to MSTR for the governance record -> MSTR banks
it as an instance of the instruments-that-lie / SENT!=READ doctrine + sets the fix's acceptance gate.

## What is banked

1. **The observation (grounded):** the opal-agent-comms commit-worker (server.py) was DEAD ~12 days
   (heartbeat frozen 2026-07-07), while its auto-relaunch reported alive. Degraded-not-lossy -- the
   safe-commit D6 mkdir-mutex fallback carried all commits, so it was invisible. Caught only as a
   side-effect of a different fix's victim-scan.
2. **The generalization (the reasoning line):** *launcher-liveness is not worker-liveness.* "The
   launcher returned True" answers "did I spawn something," never "is the worker alive" -- the same
   producer-side-blind-to-consumer-death shape as SENT!=READ (Rule 22b), the /watcher orphan (ps is not
   a roster), and the aws-shim silent hang. A relaunch that returns success-by-default when its child
   dies into DEVNULL is a launcher-liveness proxy masquerading as a worker-liveness oracle.
3. **The acceptance gate on the fix (open follow-on, CTO/0.7.0~B):** the migration to git_bash_resolver +
   verify-not-assume MUST be EXERCISED against a real worker restart -- confirm the worker COMES UP via a
   worker-side oracle (heartbeat advance / round-trip), NOT that the launcher returned True. Otherwise it
   re-certifies the class it repairs (Rule 22a).
