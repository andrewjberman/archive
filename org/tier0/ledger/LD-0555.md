# LD-0555 - The attachments were never asked for, and no permission would have fixed it

## What Andrew reported

Analysts and employees send files over Teams; agents with Graph access cannot reach them. He had just
been told by the MSP that he now owns both Graph app registrations, and the natural next thought was
whether he could grant himself whatever entitlement the agents were missing.

## ⛔ It was never an entitlement, and that is the load-bearing finding

Measured **before** touching code: `OpalGateway`'s service principal already carries **all eighteen**
declared scopes as a tenant-wide `AllPrincipals` grant — **including the two that require admin
consent** (`ChannelMessage.Read.All`, `OnlineMeetingTranscript.Read.All`). `Files.ReadWrite.All` and
`Sites.Read.All` are both live.

>> **ADDING PERMISSIONS WOULD HAVE CHANGED NOTHING, AND WOULD HAVE LOOKED LIKE PROGRESS.** The
   obvious remedy was the wrong one, and only measuring the grant before acting caught that. <<

## The cause

Both Teams readers passed a **hand-written `$select`** that omitted `attachments`. **Graph returns
only what `$select` names.** The message body still renders `<attachment id="...">` — which is a
*reference to* the attachment, not the attachment — so a file reads as **present but unreachable**,
with no name, no contentType and no URL anywhere in the response.

Reproduced on a real message (2026-08-12, two attachments, both invisible).

⭐ **AND THE TWO READERS HAD SILENTLY DRIFTED:** chat had `importance` and no `subject`; channel had
`subject` and no `importance`; **neither had `attachments`.** Two hand-maintained copies of one list
is how that happens — so the fix is **one constant consumed by both**, not two corrected lists.

## The fields, chosen by SUBTRACTION over a printed denominator

Read from Graph v1.0 `$metadata`, not from recall: `chatMessage` carries **24 properties — 22
selectable `Property`, 2 `NavigationProperty`**. Six were selected; the remaining 18 were enumerated
and triaged.

**ADDED:** `attachments`, `messageType` (separates real messages from `systemEventMessage` noise),
`deletedDateTime` (**a retracted message still returns — without this an agent processes withdrawn
content**), `mentions`, `replyToId`, `webUrl`, `eventDetail`, `subject`, `lastEditedDateTime`.

**EXCLUDED with reasons in-code** so the next reader does not re-litigate: `chatId` /
`channelIdentity` (the caller already passed them), `etag`, `locale`, `summary`, `reactions`,
`policyViolation`, `messageHistory`.

⚠ **REMAINING GAP, DISCLOSED RATHER THAN OMITTED:** `hostedContents` and `replies` are
`NavigationProperty` — unreachable by `$select`, needing their own GET. `hostedContents` is an image
**pasted inline** rather than attached. **If an analyst pastes a chart instead of attaching a file,
none of this sees it.** Stated in the new tool's docstring.

## The lane override

`infra/aws/**` is `CLOUD_OPS_OR_ETL` ("any AE agent"); this seat is not on it and **`safe-commit`
refused correctly**. Andrew, having interrupted this seat's attempt to park the fix on a carrier for
an AE seat, said **"override" / "i authorize it" / "--force"**.

Landed under **`GIT_COMMIT_AUTHOR_OVERRIDE=CLOUD_OPS_OR_ETL`** — the sanctioned audited escape per
CLAUDE.md 14a. ⚠ **`--force` would NOT have worked**: it bypasses contamination checks only, never a
lane. The distinction is noted because the word he used names a flag that does not do this job.

⛔ **THE OVERRIDE ANSWERS A ROUTING PROBLEM, NOT A COMPETENCE ONE.** `0.7.0_AE_CloudOps` is the owner
of record and has no live session; that is *why* the work had nowhere to go. This entry carries
`review_required_by: 0.7.0_AE_CloudOps`.

## ⛔ What is NOT claimed

**That the new tool works.** `py_compile` passes and definition order was verified at source
(`_office_binary_hint` :295 before :657; `_TEAMS_MSG_FIELDS` :612 before :672/:720; `_share_token`
:618 before :645). **It has NOT been run against live Graph** — the running gateway serves the old
code, and the only other token on this box is the Azure CLI's own app, which has Directory scopes and
no Chat scopes. Its 403 told me nothing about OpalGateway; **I briefly mistook that refusal for
evidence and it was the wrong instrument.** This is **compiled and reasoned, not exercised.**

**NOT DEPLOYED.** The gateway runs on EC2. "override" answered a commit refusal; it is not a deploy
authorization.

## Rollback

`git revert` this commit. The gateway is unaffected until a deploy, so reverting before deploy costs
nothing and reverting after restores the previous field lists exactly.
