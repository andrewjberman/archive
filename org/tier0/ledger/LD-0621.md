# LD-0621 -- cleanup-disk.ps1: an unregistered folder is listed, and removed only when accepted by path

## Decision
The `orphaned-worktree-dirs` pool changes from AUTO-DELETE to LIST. A new parameter `-AcceptOrphan <full path>`
(repeatable) is the only way the pool removes a folder. `-DryRun` prints how many of the listed folders are accepted.
The pool's `git worktree prune` now runs under cmd with its streams sent to nul, as LD-0620 did for the fetch.

## What happened
On 2026-10-08 at about 09:45Z a `/cleanup` run by `0.0.0_AB_MSTR`, made without a dry run while the disk read 10 GB
free, deleted six unregistered folders under `C:\tmp`: `kit-python312-carry-20261007`, `kit-python312-pack-20261007`,
`kit-python312-scratch-20261007`, `kit-python312-scratch2-20261007`, `kit-repro-20261007` and
`kit-sitez-bb18-20261007` (4.73 GB). Three of them (the two scratch folders and `kit-repro`) were folders
`1.0.0_SA_CTO` had told three seats that no seat deletes, because a recursive delete needs Andrew's word and the
question was with him unanswered. The engine's own header said of this pool "there is nothing to lose"; seats do park
folders outside git's view, so that was false.

Measured afterwards: dell1 holds the kit tar (514,160,640 bytes, sha256 3493f72a...1dd4, re-hashed there) and dell2
holds the tar and has the kit installed. Nothing was lost that another box does not hold. The delete is not recoverable.

## Provenance chain (Art. XIII)
- Ruling: `1.0.0_SA_CTO` msg 106870 ("/cleanup prints a dry run and a named list, and removes an unregistered folder
  only when the list was shown and accepted").

## Verification
Parser reports 0 errors; the file holds 0 non-ASCII characters. A probe folder planted under `C:\tmp` with a
ten-hour-old write time: run 1 without `-AcceptOrphan` printed it and "LISTED ONLY", and the folder remained; run 2
with `-AcceptOrphan` on its path printed "removed (accepted)" and the folder was gone.

## Rollback
`git revert` of the commit that carries this entry.
