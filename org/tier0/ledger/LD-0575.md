# LD-0575 - The blank cloud sprint page: a type the contract never checked, not a token budget

## His words

> "The sprint lambda didnt actually generate any fields, everything is empty and not filled in. Go look at it and
> figure out why that is. My suspicion is that the AI call ran out of tokens or wasn't properly governed or
> something. I do not want to make an overly complex ai implementation here."

## Measured (17:3xZ, every read on the SERVED object, ETag 1a392478c07d, 48221 B)

1. The embedded report JSON has 1281 leaf fields and 0 empty. Headline, five items, 15 of 15 directives in
   projects[] and process[], blocked, team activity: all written. The model's write COMPLETED. (A truncated write
   cannot reach the page at all: json.loads raises in the handler and nothing is published.)
2. Opened in a headless browser (Playwright, served over localhost), the page throws ONE JavaScript error:
   `TypeError: p.footer.map is not a function` at the flow generator, from the sprint rail's map at view time.
   After the throw: `#stages`, `#grid`, `#proc`, `#blocked` are all length 0 and the page has 0 SVGs. The date,
   headline and source line above the throw are filled. That is exactly "everything is empty".
3. The cause: the model wrote `viz.params.footer` as a STRING ("Live for authorized Opal viewers") where the
   generator iterates an array of three-field rows `[label, value, tone]`. The render-time contract
   (viz_contract.py) derives which params are REQUIRED but never their TYPE, and its row-key derivation skipped
   destructured positional rows explicitly ("flow.footer -- positional, skip"). A present scalar passed.
4. Positive control on the same local page rendered by the laptop: 10 SVGs, every section filled, 0 "undefined".
5. Same defect in the DATA in the past: the committed 2026-09-11 report (the cloud's fire 5, the last page it
   published) has a string footer on two flow items.
   ⛔ **CORRECTED 17:5xZ, same seat: the sentence that stood here, "its served page is blank the same way", was
   INFERRED from the JSON and the current renderer, not measured on the served page.** Measured afterwards on the
   served 2026-09-11 bytes (ETag e7a03e44, opened headless): 0 JavaScript errors, projects/process/blocked all
   filled, 3 SVGs. The page carries the same `p.footer.map` code and the same string footers, yet does not go
   blank; how its two flow items rendered was not investigated further. The committed JSON is still correctly
   REFUSED by the renderer at HEAD. The wrong sentence also went into the record and the commit message of
   6c4f6ac52a; this correction supersedes it there.

## The fix (repo-side, deterministic, no model change)

- `viz_contract.derive()` now emits `array_params` (every param the generator iterates, directly or through a
  `name=p.param` binding) and `positional_rows` (the destructured arity and field names, e.g. flow.footer = 3
  scalars [l, v, c]); the self-test pins both and bounds over-firing (text params must not derive as arrays).
- `render_daily_report.check_viz_params()` refuses a non-list array param and a positional row shorter than its
  arity. Refusals carry the VALIDATION FAILED header, so the cloud run's one repair pass (LD-0571 F3) hands the
  model the exact line and it rewrites the field.
- Arms: NEG (the served cloud JSON) -> VALIDATION FAILED (1): footer must be a LIST; NEG (short row) ->
  VALIDATION FAILED (1): footer[0] must be a list of 3 scalars; POS sweep 14 committed reports -> 13 CLEAN, the
  one REFUSED is 2026-09-11 with the same defect.
- The contract JSON is injected into the model's prompt verbatim, so the model now sees the types too, without an
  image rebuild.

## On the x / y / z budget design

Not needed for this failure and not built. What exists already has that shape: x = the whole prompt (schema,
derived contract, the day's subjects); y = the model's default output cap, and the write completed; z = ONE repair
pass fed the renderer's own refusal with the prior prompt and output as context. The deterministic analyzer in
that loop is the renderer, and its gap was a missing TYPE check, closed here. Explicit token knobs would be two
env vars and a rebuild; offered, not done.
