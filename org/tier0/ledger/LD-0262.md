# LD-0262 -- A 903-deletion staged index (incl. the whole tracked `logs/` tree) was left armed on the shared CLOUD worktree

**What.** Startup `git status` reconciliation found `.git/index` carrying 1087 staged changes: 903
deletions (the entire tracked top-level `logs/` tree at 882 files, plus `.smart-lint-backup/`, `goldfish/`,
`etf_netassets_watch/`) and 149 ADDs of transient junk. The files were genuinely gone from disk; HEAD still
held every one, and HEAD == origin/CLOUD. Nothing had been lost. MSTR unstaged the index back to HEAD and
restored the 905 deleted tracked files into the worktree, leaving the 38 in-flight unstaged modifications
(other lanes' real work) untouched. Post-restore the tracked tree equals HEAD, so no commit was needed.

**Why this is S2 and not housekeeping.** The workspace is one shared worktree across the whole fabric, so
`.git/index` is shared mutable state. An armed 903-deletion index is a landmine on two paths: `safe-commit.sh`
aborts on any staged file outside the caller's pathspec (a silent fabric-wide commit block -- it had been
armed ~4.5h), and a single audited `--force` bypass or bare `git commit -a` would have committed the
mass-deletion of 882 tracked files under some unrelated message. Three Tier-1 agents booted into this.

**Cause is NOT established (Rule 22).** The symptom is state-grounded; the mechanism is not. `logs/` was
purged with no commit, no ledger, no session log, and no brief authorizing it, and `.tools/kill-storage.ps1`'s
allowlist does not include repo `logs/`. Candidates -- an unscoped `git add -A` over a pre-existing on-disk
deletion, a git-worktree add/remove cycle (the only surviving on-disk copy sits in
`.claude/worktrees/agent-a8970f0ad7c4b95af/`), or `infra/linting/smart-lint.sh` + `lib/backup.sh` (which owns
`.smart-lint-backup/` and plausibly the garbage `1].[Timestamp` rename target) -- are **INFERRED and
NON-ACTIONABLE**. None is source-confirmed. This ledger must not be cited as a root cause, and no fix may
rest on these candidates until one is grounded.

**Open, for Andrew.** Was the `logs/` purge deliberate? Restoring does not foreclose it -- a deliberate purge
can still land properly as a scoped commit with a rationale. What is not acceptable is the purge arriving as
an unattributed side effect in a shared index.

**Gate candidate (routed to CTO).** Nothing in the fabric detects an armed index whose staged set nobody
declared. A cheap pre-commit / session-start lint -- "staged deletions of tracked files exceed N, or staged
paths exceed the caller's pathspec, with no owning lane" -- would have caught this at 13:36Z instead of 18:10Z.
The `1].[Timestamp` artifact also suggests a shell-quoting defect in a lint/backup path worth its own trace.

**Stakes.** S2 (blast radius: all lanes, shared index). The intervention itself is non-destructive,
reversible recovery: unstage + restore-from-HEAD. No history change, no destructive git, no deletion.
