# LD-0340 — THE HARNESS EXIT CODE WAS CORRUPTED FABRIC-WIDE FOR 3 DAYS BECAUSE THE DIAGNOSIS NAMED THE WRONG VARIABLE

## The defect

Every Bash invocation in every agent session had a harness-appended suffix:

```
&& pwd -P >| '/c/Users/ANDREW~1/AppData/Local/Temp/claude-XXXX-cwd'
```

The harness converts the Windows TEMP path using the **MSYS convention `/c/`**. This box had C: mounted
**only** at `/cygdrive/c`, with no `/c` mount at all. The redirect therefore failed, and **as the final
command in the `&&` chain its failure BECAME the reported exit code.** Successful commands read
`Exit code 1` with a trailing `claude-*-cwd: No such file or directory`.

**Reproduced deliberately before any fix** (Rule 22 — the mechanism, not the symptom): the identical
redirect against `/c/...` failed and against `/cygdrive/c/...` succeeded, in the same shell, same turn.

## THE LOAD-BEARING FINDING: the record named the wrong variable, and that is why it survived 3 days

`memory/reference_cygwin_harness_exit_codes_corrupted_capture_true_rc_in_stdout.md` (2026-07-25,
CVO~Z-root-caused, hit by 3 agents in one cycle) attributed this to a **"Cygwin-flavored shell"** and
concluded: *"The real remedy is host-level (harness/shell config — which bash Claude Code resolves to),
not estate code. Until changed, in-stdout capture is standing discipline."*

**That attribution is wrong, and the wrongness is the whole story.** Measured: this host runs
**MSYS/MinGW64 bash 5.3.15** — not Cygwin. The operative variable is the **MOUNT TABLE**, not the shell
flavor. The identical bash binary is broken or fine depending purely on whether `/c` exists.

> **A correct symptom plus a wrong variable produces a correct workaround and a permanently deferred
> fix.** Naming the variable "which bash the harness resolves to" put the remedy outside the fabric's
> reach — nobody can change that — so the estate rationally adopted a workaround and stopped looking.
> The actual variable was one unprivileged command away. **The record did not fail by being false about
> the symptom; it failed by being false about what was VARIABLE, and that is the harder error to see
> because every prediction it made was correct.**

Sibling of `[[feedback_profile_before_reporting_a_mechanism]]` — right about the property, wrong about
the path, and the wrong path was ratified because the property kept checking out.

## The fix

```
mount -f C: /c
```

**Additive by design.** It adds `/c` as a second name for C: and leaves `/cygdrive/c` untouched. This
was the binding constraint, not a nicety: **16 live processes and every watcher Monitor in the fabric
run on hardcoded `/cygdrive/c` paths.** The tempting alternative — resetting the cygdrive prefix to `/`
so that `/c` appears the MSYS-standard way — would have **removed** `/cygdrive/c` and taken the entire
comms fabric down at once. It was considered and rejected on that basis.

**Exercised behavior-grade at every step, never config-read:**

| check | result |
|---|---|
| `/c` resolves | YES |
| `/cygdrive/c` still resolves | YES (coexistence — the constraint) |
| **the exact harness redirect** | **SUCCEEDS** (file written, content = cwd) |
| same file via both paths | identical — one drive, two names, no divergence |
| fresh bash, **independent process ancestry** (PowerShell-spawned) | sees `/c`, redirect succeeds |
| this session's subsequent commands | clean `rc=0`, no trailing line |
| CVO's independent confirmation (1420Z) | pre-1355Z commands corrupted, post-1355Z clean; its `/cygdrive/c` watcher Monitor unaffected |

## ⚠ NOT DURABLE — the outstanding operator action

There is **no `/etc/fstab`** on this box and **no registry mount entry** (all four candidate keys
checked). The mount lives in the **MSYS shared-memory table**, alive only while ≥1 MSYS process is —
24 bash processes at time of writing. **A full shutdown or reboot loses it and the corruption returns.**

Durable fix requires one elevated write, which agent shells cannot perform (probed:
`UnauthorizedAccessException`, `elevated(admin): False`). **Handed to Andrew as an operator action:**

```powershell
Add-Content -Path 'C:\Program Files\Git\etc\fstab' `
  -Value 'C: /c ntfs binary,posix=0,user,noumount,auto 0 0' -Encoding ascii
```

Options mirror the existing `/cygdrive/c` entry. Staged with rationale at
`.fedobs_tmp/fstab-fix-20260728.txt` (untracked scratch — **this ledger entry is the durable carrier
of the command**, deliberately, because a staged file in a scratch dir is exactly the shape that
disappears).

## AMENDMENT (2026-07-29T02:40Z) — fstab WRITTEN. Whether MSYS APPLIES it is NOT yet proven.

`C:\Program Files\Git\etcstab` **did not exist** on base. Andrew wrote it from an elevated
shell via `.tools/fix-git-fstab.ps1` (new, committed with this amendment). Content is proven:
no BOM, LF endings, byte-identical read-back.

```
none /tmp usertemp binary,posix=0 0 0
C: /c ntfs binary,posix=0,user,noumount,auto 0 0
```

**A draft of this fix specified `C: /cygdrive/c`.** That would have been a no-op wearing the
costume of a fix: `/cygdrive/c` is a compiled-in default that is already correct, and the line
never creates `/c` — the mount the rc repair actually depends on. **The drive is not the tell;
the MOUNT POINT is.**

### The script's own behavior check passed for the wrong reason, and that is the finding

It printed `[ok] /c is mounted`. **That check could not have failed.** LD-0340's live
`mount -f C: /c` already held the mount point, an existing mount wins over fstab, and MSYS keeps
the mount table in shared memory that outlives individual processes — so a freshly-spawned bash
inherits the stale table. `/c` appears whether or not the fstab was read.

The discriminating signal is the **flags**, because the two sources produce different ones:

| source | flags |
|---|---|
| fstab line (this amendment) | `binary,posix=0,user,noumount,auto` |
| volatile `mount -f C: /c` | `binary,user` |

Measured immediately after the write: **`C: on /c type ntfs (binary,user)`** — the volatile
mount. So the durable fix is **WRITTEN AND UNTESTED**, not confirmed. Same shape as this
session's owned-paths harness: *a check the prior state already satisfies cannot fail.* Script
corrected to key on flags and to report WRITTEN-BUT-UNPROVEN rather than DONE.

### To close this ledger entry

Reboot (always clears the MSYS cache), then:

```
& "C:\Program Files\Gitinash.exe" -lc "mount | grep ' /c '"
```

`binary,posix=0,user,noumount,auto` -> **LD-0340 durably closed.**
`binary,user` or absent -> fstab is not being read; **LD-0340 stays open.**

**Site Z has no fstab either** and carries the identical latent corruption. `fix-git-fstab.ps1`

## AMENDMENT 2 (2026-07-29T14:10Z) -- `noumount` REJECTS THE LINE, and the script told the operator to expect the flags it no longer writes

**`noumount` removed.** Site Z rebooted (first genuinely fresh MSYS mount table) and every bash
emitted `fstab_read_flags: invalid fstab option - 'noumount'` with **no `/c` line at all**. A file
that is not read cannot emit a parse error naming a token inside it: the state is
**PARSED-AND-REJECTED**, a third cell the original two-cell discriminator (LIVE vs NOT-READ) did not
have -- and ABSENT mapped to the *wrong* cell. One invalid option voids the **whole** line.

> **THE TRAP: `noumount` IS PRESENT on the working `/cygdrive/c` mount.** It is valid as an
> **internal mount flag** and invalid as an **fstab-writable option**. This line was written by
> copying flags off the working mount -- the obvious move and the wrong one.
> **THE FLAGS YOU CAN READ ARE NOT THE FLAGS YOU MAY WRITE.**

**Base carries the same defect, latent:** base's `/c` reads `binary,user` (volatile), so base's line
is rejected identically -- no error surfaces only because base has not rebooted and MSYS never
re-read the file. Script now writes `binary,posix=0,user,auto`; **the file on disk still has the bad
line** and needs an elevated rewrite. **LD-0340 STAYS OPEN.**

### The second defect: a fix that left its own instructions stale

Caught while preparing the elevated command. Line 232 was **not a comment** -- it was live `Say`
output: *"Expect flags binary,posix=0,user,noumount,auto."* The script no longer writes that, so
after a reboot the operator would have seen the **correct** result and read it as a **failure**.

> **A FIX THAT LEAVES ITS OWN INSTRUCTIONS STALE MANUFACTURES A FALSE NEGATIVE AT THE MOMENT OF
> VERIFICATION** -- the one moment the operator is relying on the text. Same stale-record class as
> the rest of this session, pointed at the human rather than an agent.

**And it was nearly missed the way LD-0343 A11 documents:** grep for `noumount,auto` returned 3
hits; two were comments explaining the removal, **the third was executable output**. *A keyword
detector cannot distinguish a specification from its prohibition* -- written into the ledger that
morning, and still required checking which construct each hit sat in.

Post-reboot guidance now carries all three outcomes, matching the verdict logic.
