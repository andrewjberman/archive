# LD-0291 — WE HELD SEND-AUTHORITY FOR A DOMAIN WE DO NOT OWN, AND EVERY INSTRUMENT SAID FINE

## 1. THE FINDING

> **Opal's AWS account held a live SES DOMAIN SENDING IDENTITY for `opalcapital.com` — a domain Opal DOES NOT OWN.**
> **Plus a drafted AWS support case naming it as ours — into a review where AWS verifies exactly that.**

Deleted. Corrected. **Nothing ever shipped** — SES had already marked it `DKIM=FAILED`, because the CNAMEs were
never added.

**Andrew, verbatim:** *"We do not even own opalcapital.com, thats on me, we need to not be using that and not having
it get wrapped into this process any further."*

## 2. ⛔ THE NEAR-MISS IS NOT THE REVIEW. IT IS THE TWO WEEKS.

**Four agents. A PRD, a project JSON, a REGISTRY row, a runbook, five shell scripts, an IAM policy, an SES identity,
and a support case to AWS. ALL BUILT ON A DOMAIN NOBODY OWNED. NOT ONE WHOIS LOOKUP.**

**Every instrument was internally consistent.** The DNS resolved. The site served. The scripts passed.

> ## ***"A PREMISE THAT NO INSTRUMENT IN THE ESTATE IS POINTED AT IS NOT A WEAK CLAIM — IT IS AN INVISIBLE ONE.***
> ## ***GROUNDING TELLS YOU WHAT IS. IT CANNOT TELL YOU WHAT IS OURS."***
> — `0.7.0_AE_CloudOps`

**The only reason the send-authority never mattered is that a CNAME nobody added made it fail.**
**We were saved by a step we forgot to do. That is not a control — it is luck with good posture.**

## 3. 🔴 THE ROOT IS A RULE DEFECT, NOT A READING FAILURE

**CLAUDE.md Rule 23, today:** *"`opalcapital.com` is unverified, never use it."*

> **Four agents read "unverified" as an SES VERIFICATION STATE — a TODO you fix by verifying it — rather than as
> "THIS DOMAIN IS NOT OURS."**

And they were not careless: **two bullets earlier the same rule calls `opalinvest.com` — a domain we DO own —
"address-verified only."** *The word carries one meaning in one clause and the opposite implication in the other.*
**The rule stated the FACT and withheld the REASON, so it read as a backlog item instead of a prohibition.**

**AMBIGUITY IN A NEVER-RULE IS A DEFECT. Fix the rule, not the readers.**

**Proposed (CTO to land):**
> **`opalcapital.com` — ✋ WE DO NOT OWN THIS DOMAIN.** Never send from it, never request a cert for it, never name
> it to a vendor as ours. **It is not a verification TODO. It is someone else's property.**

## 4. GATE — ROUTED TO CTO, NOT BUILT

> **An OWNED-DOMAIN ALLOWLIST: DENY any new SES domain identity / ACM cert / DNS-bearing resource whose apex is not
> on it.**

**The estate has instruments for what is DEPLOYED, what is FRESH, what is GRANTED — and NONE for what is OURS.**
*An unasked question does not fail loudly. It produces a clean scan of everything except itself.*

## 5. THREE LIVE HAZARDS ON THE **CORRECT** DOMAIN — ALL LOUDER THAN THE LAUNCH

1. **`opalinvest.com` is NOT an empty target.** Apex + www serve a **LIVE Wix site**. The cutover **replaces Opal's
   public website.** ⚠️ **The runbook named `72.167.58.121` as the rollback host — that host is on
   `opalcapital.com`, THE DOMAIN WE DO NOT OWN.** *The documented rollback would have "recovered" onto a stranger's
   infrastructure.* **Fixed.**
2. 🔴 **`opalinvest.com` carries Opal's LIVE Microsoft 365 email** (MX, SPF, `selector1/2._domainkey`, autodiscover,
   DMARC). **Touch ONLY the apex A and www.** *A well-meaning "clean up the old Wix records" kills company mail.*
3. 🔴 **A SECOND SPF TXT IS AN RFC-7208 `permerror` — A DOMAIN WITH TWO SPF RECORDS HAS NONE — degrading M365 mail
   FIRM-WIDE.** Required to graduate the form sender to `@opalinvest.com`. **Correctly NOT bundled into the launch.**
   **One line. Company-email blast radius. Separate window, own verification, MSTR told first.**

**CRITICAL PATH IS A HUMAN, NOT AWS:** GoDaddy DNS on `opalinvest.com`. **Andrew does not hold the sign-in — CFO
AJ Graff does.** One additive A record unblocks the whole staging phase.
