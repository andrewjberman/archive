`PROPOSED` -> `RATIFIED <record> 2026-09-02 -- verbatim: 'commit macros.yaml and ratify D11'`.

**D0 and D8 stay PROPOSED.** He named one directive. Rule 24 (iv) state coherence is what makes
that expressible at all: each directive's list is ratified on its own and **ratifying one moves no
other** -- so a one-directive word does not have to be widened to be executable.

## The scope was FALSIFIED, not asserted

A ratification is a one-word edit to a string. **Nothing about editing it proves it does what the
word intended, or that it stops where the word stopped.** So the claim was tested on a scratch
estate: the SAME macro (`NFRA`) planted under BOTH directives, one tool run, one output.

```
  org/missions/D11/NFRA/NFRA_PROBEELEV   -> [INDEX-MISSING]   no R2: past the enum gate
  org/missions/D0/NFRA/NFRA_PROBEZERO    -> [R2]              refused by the enum gate
```

⭐ **The only difference between those two rows is the field I flipped.** Same macro, same grammar,
same run -- which is what makes this a discriminating control rather than a confirming one. The
residual `INDEX-MISSING` on the D11 arm is the expected next state (`derive --write`), not a defect.

Live estate after: `missions-tree-index check` -> tree=0, flat=352, **MACROS.yaml: 1 of 3
directive(s) RATIFIED**, 0 violations; `--self-test` 18/18 PASS both before and after.

## What this does NOT do

refusal `R2` for `D11/NFRA` and leaves every other gate standing -- the row, the path agreement,
and `R5` (membership in `DIRECTIVES.yaml directives.D11.members.projects`).

⛔ **PROSPECTIVE ONLY.** The 352 flat rows in `org/projects/` are untouched, and D11's two live
members (`NFRA_C3MATERIALIZE`, `NFRA_SUBSTRATECARDING`) keep working exactly as they do today.
