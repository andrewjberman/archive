# LD-0550 - Ferrying the satellite components, and the defect the file names about itself

## Decision

Commit Andrew's file verbatim into this seat's deliverables so it reaches site Z by git, and send
the bus frame as a pointer carrying the measurement rather than the payload.

## Why a committed file and not a bus message

The file is **20,286 bytes**. The bus truncates, and a truncated component table is worse than none
— a reader cannot tell which rows are missing. A committed file rides the next parity leg intact,
is citable by POSN_ASTTAX's own records, and outlives the session.

⭐ **This carrier beat the message bus twice tonight already, for two different gate reasons**
(`mstr-no-tier2-writes`, then LD-0529). For a 20 KB artifact it is not a close call.

**Verbatim is verified, not asserted:** `sha256 ff96172b8e00b543` on both the desktop original and
the committed copy. No header, no reformatting, no annotation. **My measurement is in the commit
message and the bus frame; his file is untouched.**

## The measurement

| | |
|---|---|
| component rows | 228 across 9 satellites |
| rows whose `name` lacks a `TICKER - ` prefix | **22** |
| GLD | 11 rows — `SPDR GOLD SHARES` |
| VXX | 9 rows — `IPATH SERIES B S&P 500 VIX SHORT-TERM FUTURES ETN` |
| CLIP | 2 rows — `GLOBAL X 1-3 MONTH T-BILL ETF` |

The file's own header names GLD and VXX. **It does not name CLIP, and CLIP is the worse case: it is
the ONLY ticker that appears BOTH prefixed and bare** — prefixed in most satellites, bare in 90 and
98.

⛔ **A CLASSIFIER THAT DERIVES THE TICKER FROM THE NAME DOES NOT MERELY MISS GLD AND VXX
SYSTEMATICALLY — IT MISSES CLIP INTERMITTENTLY, AND AN INTERMITTENT MISS LOOKS LIKE A WORKING
CLASSIFIER.** A systematic absence gets noticed. A per-satellite one reads as a data quirk.

⚠ **HYPOTHESIS, NOT MEASUREMENT.** I measured his file. I have **not** read `ETFClassifier`'s ticker
derivation and do not sit on the fabric that owns it. If it already reads `metadata.symbol`, this
explains nothing and the absence has another cause — which is worth knowing fast, because it moves
the search.

## Why the timing matters

POSN_ASTTAX has **no register row and no tree home** on this fabric; the only local artifact is
`2.0.0_SA_COO~Z`'s L5 decomp draft. So this arrives as **input to a project still being cut**,
which is the cheapest moment for it to land.

## Rollback

Delete one file. Nothing depends on it; the source remains on Andrew's desktop.

## AMENDMENT 1 (2026-09-11 ~06:0xZ) - MY HYPOTHESIS IS FALSIFIED, and the caveat is what made that cheap

`2.0.0_SA_COO~Z` measured it **on the served plane** — `dynamodb get-item` against
`etf-classifications`, the table `ETFClassifier` reads and Positioning serves (site-Z msg 21217,
relayed 06:0xZ):

| ticker | asset_class | sub |
|---|---|---|
| GLD | hedge | Gold |
| VXX | equity | Volatility |
| CLIP | fixed_income | Ultra Short Duration |

…and the seeding dict carries the same three values, so there is **no drift between the stores**.
**`ETFClassifier` is keyed BY TICKER, not by parsing the name.**

⛔ **SO THE NAME-PREFIX GAP IS NOT THE CAUSE OF WHAT ANDREW REPORTS.** The measurement in this entry
stands — 22 of 228 rows genuinely lack a `TICKER - ` name prefix, and CLIP genuinely appears both
ways — but it explains **nothing** about the absence, because nothing downstream reads that field
for the ticker.

⭐ **THE CAVEAT DID ITS JOB, AND THAT IS THE DURABLE PART.** I wrote *"IT IS A HYPOTHESIS ABOUT THE
CLASSIFIER, NOT A MEASUREMENT OF IT … If ETFClassifier already reads metadata.symbol, this explains
nothing and the absence has another cause — and THAT would be worth knowing quickly, because it
would move the search."* The other fabric settled it in **two calls** and said so explicitly. **A
finding shipped with its own falsifier gets killed fast; one shipped as an explanation gets built
on.** The cost of the caveat was two sentences; the cost of omitting it would have been a project
cut around a wrong cause.

⚠ **AND THE REAL QUESTION IS NOW OPEN AND SHARPER, WHICH IS THE POINT OF KILLING A HYPOTHESIS
EARLY:** if the classifications are correct at the served table, then Andrew's *"they are not
included"* is about something other than classification — surfacing, joining, scope filtering, or a
different consumer entirely. That is `POSN_ASTTAX`'s question and it is now unencumbered by my
wrong one.
