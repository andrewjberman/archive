So the drain's carrier and the content's author differ for 19 of 26 paths, and the drain's own

row gate grades rows; nothing in the drain path grades AUTHORSHIP of what the shared index holds.

## Why the existing guards do not catch it

`.tools/safe-merge.sh` already carries a foreign-staged-path guard, and it is REAL -- but it is
scoped to the `--continue` limb (`:85`, `:190`, `:246`): the conflict path records what the merge
staged so that `--continue` can tell its own paths from a foreign seat's. A CLEAN merge never
reaches that comparison. `org/git-author-override-audit.log` records three `MERGE-REFUSED` rows
on the same family, every one of them correct -- and none of them is this case.

This is Rule 14b's hazard exactly ("five seats plus their worker subagents share ONE MUTABLE
INDEX"), one step past where the rule stops: 14b tells a seat to isolate, and `safe-merge` grades
the merge, but no limb asks whether the shared index held someone ELSE's work at merge time.

## What is owed, and what is explicitly NOT

OWED (this seat, unscheduled -- nothing in this entry builds it):
1. a shared-index isolation regression: a drain with a foreign seat's path staged must either
   refuse or name what it is about to carry;
2. the same disclosure for the CLEAN path that `--continue` already has.

NOT OWED and NOT DONE:
- **no history rewrite.** The CTO did not ask for one and none is warranted: the 19 files are
  correct content, correctly authored, landed on the shared branch by the wrong carrier. Rewriting
  a pushed shared branch is NEVER#3.
- **no gate is disabled or loosened.** The row gate behaved correctly throughout.
- **no verdict on the IRPT_FNTEND round.** `3.0.0_SA_CVO~F` adopts the slug at `f7546b6aec`;
  correction `807abf252d` was pre-existing-row treatment. That is the CVO's and the CTO's lane,
  not this one's.
