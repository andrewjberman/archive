# LD-0343 — THE AGENTBUS GIT-TRANSPORT TRUNK IS OPEN IN BOTH DIRECTIONS. Its first finding is that site Z is UNGATED.

## What was decided

The cross-device MSTR<->MSTR trunk at `org/mcp/agentbus-trunk/` is **live and bidirectional**.
Site Z (`0.0.0_AB_MSTR~Z`, second device) opened it with `amb-z-0001`; base
(`0.0.0_AB_MSTR`) replies with `amb-b-0001` (ACK) and `amb-b-0002` (DIGEST). Both sites work
the same repo on branch `CLOUD`; transport is store-and-forward over git push/pull, per the
README's protocol and the canonical design in `docs/briefs/AGENTBUS_SCHEMA_SPEC_20260717.md`.

This is a **live-fire MVP of NFRA_AGENTBUS Port 2**, standing in for the designed
DynamoDB + `m365-mcp-gateway` MCP path so the two MSTR agents can collaborate today. The
brokers are device-local (`127.0.0.1:7800`) and **cannot** see each other; git is the only
medium both sites already share.

## Why this needed a grant, and why the grant is narrow

`org/mcp/**` is lane `BASE_EXEC` in `.owned-paths.yaml` — `permitted_agents` = CTO + COO + CVO.
**Neither MSTR serial was permitted there.** CTO granted `org/mcp/agentbus-trunk/**` to both
MSTR serials at `d0e7038e7a`, on Andrew's request, leaving the `org/mcp/**` catch-all intact.

I did not self-grant. LD-0342 says MSTR executes under an Andrew-direct instruction including
self-affecting gates — but Andrew routed this one to CTO himself, and a grant with an available
independent grantor should use it. **LD-0342 removes the requirement, not the preference.**

## THE FIRST CROSS-SITE FINDING — and it came from the block itself

Site Z's trunk commit landed while base's identical commit was **refused**. The asymmetry is
the finding:

> **A FRESH CLONE GETS ZERO GIT HOOKS.** Git tracks nothing under `.git/`. Site Z is running
> with **no owned-paths gate, no mstr-ledger-check, no mass-deletion-check, no
> branch-content-isolation, and no stitch-refresh** — on the same shared branch as base.

Every enforcement this fabric describes as "gated" is **per-clone**, and a second device
inherits none of it. That is a larger portability gap than any hardcoded path, and it is
**invisible to a path census** — there is nothing at Z to scan. The census I ran tonight
(72,538 files -> 571 user-rooted -> 43 operative) could never have surfaced it. It surfaced
because a gate fired on one side of a symmetric operation and not the other.

Note the direction of the danger: **the ungated site is the one that succeeds.** An agent at Z
gets no signal that it is unguarded; it simply never sees a refusal. Base learned this only
because base is the gated one.

## What this obligates

1. **An installer, not a chain-by-hand.** `.tools/git-hooks/missions-refresh-post-commit.sh`
   has **no installer at all** — base chained it into `.git/hooks/post-commit` by hand, so at
   Z it can never exist. A single install-all-hooks entry point is now the load-bearing
   deliverable, not a convenience. MSTR-owned, unstarted.
2. **`0.0.0_AB_MSTR~Z` is not enumerated in `.owned-paths.yaml` at all.** The home-folder rule
   (`owned-paths-validate.py:80-84`) lets a `~lane` write its base's home folder, so Z can
   commit `org/tier0_exec/0.0.0_AB_MSTR/**` — but Z is blocked from every lane-based MSTR path
   (`org/missions/**`, `org/tier0/**`) **the moment hooks are installed there.** Installing the
   hooks at Z without enumerating `~Z` converts a silent-success failure into a hard block.
   Sequence the two together. Gate: at CTO.
3. **ACK is the delivery oracle, here as everywhere** (Rule 22b). A git push succeeding is not
   delivery. `requires_ack: true` past `ack_deadline` escalates to Andrew — the one alarm that
   fires on ABSENCE, and the only kind the standing alert moratorium does not touch.

## Standing

The trunk is a **prototype with a real dependency on it**, not an experiment. It carries the
device-path-agnostic work split (Z proves a fix launches an agent at Z; base edits `ajb.ps1` +
`spawn-agent.ps1` and writes the installer). Both sites must `CLAIM` a file on the trunk before
editing it — same repo, same branch, no lock.
