# LD-0226 — comp-which router enrichment (LD-0224 audit remediation): route served-content-motion to comp-xray

Andrew-direct 2026-06-30. The cheap, high-leverage half of the comp-tool discovery audit (LD-0224):
wire the Mode-1 routing misses the audit found, so agents fluidly reach the tools that already exist.

## The mechanic the audit established

Discovery is **ambient, not invoked**: in the 14 days to 2026-06-30 agents typed `comp-which` 3 times
but the PreToolUse HUD fired it **639 times** (ROUTE -> rich tool). So fabric-wide fluency is a
function of the **curated routing rules**, not whether agents remember to ask. That makes a rule fix
the highest-leverage lever.

## What changed (`.tools/comp-which` RULES)

1. **New comp-xray rule** (value-MOTION / frozen-but-fresh), placed BEFORE comp-freshness so
   "is the served value frozen / stuck / not moving / re-stamped / has the value stopped" routes to the
   content-motion tool — closing the audit's #1 demand (header_metrics raw-grepped 5x; "no comp-tool
   reads served content" named 2x).
2. **comp-freshness route surfaced its `artifact <s3-prefix>` + `ddb` modes** + prefix-freshness
   vocabulary (the audit found the ad-hoc-prefix-freshness mode was unreachable via the router).

## Guardrail / verification

comp-xray uses distinctive frozen/motion vocabulary only — regression-verified that
"what breaks if I change X" still routes to comp-blast and "which lambda serves" to comp-transform,
and that ambiguous "did X change" stays on the backstop (comp-xray surfaced as a suggestion, not
force-routed). py_compile + ruff clean.

## Scope boundary

This fixes Mode-1 (tool exists, router didn't connect). The Mode-2 **genuine coverage gaps** the audit
named (portal-chart -> data-path lineage; a CLI-name-collision guard; function-level resolution in
comp-pipescript/comp-blast; EC2-instance-role IAM reconcile) are NOT fixed here — they feed the
NFRA_COMPLEARN seed worklist (LD-0225) as its first pre-computed iteration.
