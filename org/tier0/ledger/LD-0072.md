# LD-0072 — Universal Tier-2/3 worker-loop skill `/work`

## Decision

Per Andrew direct 2026-05-26T~00:48Z: institute new universal worker-loop skill `/work` for all Tier-2/3 agents. Addresses worker-tier gap in LD-0062 architecture — workers currently have no structural self-driving loop; they react to dispatches + go STALE on blockers waiting for COO /drive scan to surface the block.

## Why this exists

**Current worker-tier failure mode:**
1. Worker receives dispatch (TO from CTO/COO)
2. Worker works on task
3. Worker hits blocker
4. Worker either: (a) goes STALE silently, (b) logs blocker without surfacing, (c) MCPs senior at random discretion
5. COO /drive scans next 15-20m → maybe identifies STALE worker
6. COO routes blocker to unblocker
7. Unblocker acts
8. Worker resumes

Latency ~30-60m + relies on worker discipline to log + COO scan timing.

**With /work loop:**
1. Worker receives dispatch
2. Worker executes per /work cycle
3. On blocker: worker self-classifies + MCPs lane COO with `[BLOCKED-ASK]` immediately
4. COO routes from there (already has hierarchy-context)
5. Unblocker acts
6. Worker /work cycle re-enters; sees unblock; resumes

Latency ~5-10m + structural worker discipline (no log-or-surface judgment burden).

### Loop body skeleton

```
Step 0 — HALT-gate check (Andrew interrupt)
Step 1 — /watcher fold inline (Steps 1-5 of /watcher SKILL.md)
Step 2 — check_inbox + classify:
  - Andrew direction → execute immediately
  - Senior dispatch (TO from lane CTO/COO/CVO) → accept
  - Peer ask → respond
  - [UNBLOCK-RECEIVED] → resume previously-blocked work
Step 3 — Walk pending TO queue:
  org/tier{2,3}*/{serial}/task_orders/*.md filtered by status≠complete + ≠cancelled
  Pick next ready item by priority (your judgment + TO order)
Step 4 — Work on current task — substantive execution
Step 5 — Conditional: if blocked:
  Identify concrete blocker (what specific thing is preventing progress)
  Compose [BLOCKED-ASK] MCP to lane COO (uniform — always COO; COO routes from there)
  Body: blocker description + what unblock needed + TO ref + current state
  Mark current TO with blocker state (e.g., status=blocked-on-{description})
  Cycle returns; idle until [UNBLOCK-RECEIVED] arrives
Step 6 — If task complete:
  Commit work + write RAVC2 if applicable per existing patterns
  Update TO status (status=complete or status=ravc2-pending)
  Continue to next pending TO if cycle time permits
Step 7 — Cycle log + heartbeat
Step 8 — Cron auto-fires next tick
```

## Why route-via-COO (not direct-to-unblocker)

| Rationale | Detail |
|---|---|
| Uniform worker behavior | workers don't need hierarchy-routing knowledge; one rule — always MCP lane COO |
| COO is operational hub per LD-0056 | already does this routing in /drive; /work delegates the routing decision |
| Single point of update | if hierarchy changes, only COO routing logic updates; workers don't need refresh |
| COO has context-density | COO knows current population state + who is alive + who is blocked + who can absorb |

Tradeoff: 2 hops to unblocker instead of 1. But COO routes in seconds; worker doesn't wait on the routing.

## Coexistence with COO /drive

| Function | /drive (COO) | /work (worker) |
|---|---|---|
| Scope | exec-side observation + dispatch | worker-side execution + escalation |
| Question asked | "what work needs assigning? what projects need moving?" | "what work do I have? am I blocked? am I done?" |
| Trigger | 15-20m cron at COO | 20m cron at worker |
| Action | dispatches work TO workers | executes work + escalates blockers |

Complementary. /drive surfaces work TO workers; /work is how workers drive THEIR work forward.

## MSTR + Tier-1 don't need /work

MSTR has /mstr-review + event-triggered skills per LD-0069. Tier-1 has /ws-charter / /cl-charter / /drive / /spot-check / /verify-channel per LD-0062/LD-0066. Their loops already cover their own work-driving.

`/work` is specifically the Tier-2/3 worker-tier addition that LD-0062 didn't cover.
