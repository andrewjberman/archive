# LD-0138 — commit-storm root cause: worktree-broken commit-queue lock in safe-commit.sh

**Opened by:** Andrew-direct commit-storm flag 2026-05-29 ("I thought the entire point of the hook was to hold off commits and manage this case"). Investigation vindicated Andrew — the serializer exists; it was worktree-broken.

## §1 — The mechanism existed (Andrew was right)
safe-commit.sh §RV-0017 F-006: an mkdir-mutex commit-queue lock (flock unavailable per Rule 16), holding from staged-index capture through commit + pre-commit-hook completion, with stale-lock reclaim (kill -0 on holder PID). Purpose: serialize concurrent agents' commits so the shared-index race can't trip false lane-violation BLOCKs. This IS the "hold off commits + manage this case" mechanism.

## §2 — Why it didn't hold (the bug)
`LOCK_DIR="$REPO_ROOT/.git/commit-queue.lock"`. In the feature_clb linked worktree (all 15+ CL agents), `$REPO_ROOT/.git` is a FILE → `mkdir "$REPO_ROOT/.git/commit-queue.lock"` fails ENOTDIR → lock never acquired → 60s spin → exit 3 → agents fall back to bare/--force commits → UNSERIALIZED → storm. Same .git-is-a-file worktree bug as the hook-installer false-alarm.

## §3 — The fix
`LOCK_DIR="${SAFE_COMMIT_LOCK_DIR:-$(git rev-parse --absolute-git-dir)/commit-queue.lock}"` — per-worktree gitdir, always a real dir, correct per-index serialization. Fixed on CLOUD (this commit); COMP copy routed to CL CTO (branch-isolation blocks MSTR on COMP).

## §4 — Resume path
Once COMP safe-commit.sh carries the fix, DS resume full-blast WITH working serialization — no storm, no force-bypass, no contamination risk. This is the real "commit-storm prevention," restored.
