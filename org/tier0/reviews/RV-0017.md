2. **Commit storm — 119 concurrent bash + 18-bash spike at 17:52:39** racing `.git/index.lock` against a 30-second `owned-paths-check.sh` pre-commit hook. **NOT zombies** — these are live bash processes (Git Bash wrappers) spawned by Claude Code Bash-tool calls for `safe-commit.sh` cycles. Each agent's auto-commit launches parent bash → git → child bash (hook). With ~13 ws agents all auto-committing inside narrow windows + 30s hook latency, lock starvation produces visible UI lag + index-lock retries. Spike trace at 17:52:39 in the brief is the structural proof.

3. **Orphan `broker.py` PID 3812** (parent PID 20276 dead) hot-looping 8158 CPU-sec / 6h45m at 10.7 MB resident. **Orphan, not zombie** (zombie = exited-but-unreaped; orphan = live-but-parent-dead). Tight loop, no I/O wait, no sleep/backoff. Killed by Andrew this session; brief is forensic past-tense. Forward fix: self-watchdog (exit if parent disappears) + explicit backoff on every retry loop.

**Andrew's question — "Is that zombies from cycles/loops, or something else?"** Answer: **NEITHER zombies NOR your cycle/loop skills**. Three different leak shapes:
- **WT memory bloat** — display-engine leak in Windows Terminal itself (independent of agent behavior)
- **Bash process pile-up** — lock-starvation symptom, not a leak; bashes exit cleanly when the lock window comes available, they just pile up faster than they drain at peak concurrency × hook-latency
- **broker.py orphan hot-loop** — orchestration bug in broker.py (no parent-death detection, no backoff)

**The /watcher + /govern + /loop primary loops are NOT the cause.** They're CronCreate-driven (one wakeup pending; bounded). The cause is the *auto-commit on every action* pattern + the slow pre-commit hook. The hook is the multiplier.
