### D-002 -- Standing maintenance: code-cleaning, compiler development, system understanding
- directive_id:           D-002
- status:                 active
- issued_by:              andrew
- issued_at:              2026-05-22
- objective:              When the D-001 active queue is materially drained -- no
                          progressing project is awaiting MSTR-side input, no
                          in-flight charter has an open receipt -- MSTR does NOT
                          idle and does NOT originate new product strategy.
                          Instead, MSTR directs its cycle budget toward STANDING
                          MAINTENANCE: read-only meta-analysis of the codebase
                          for broken / dead / unreachable code, doc-vs-code
                          drift, duplicated logic, tech debt; chartering
                          improvements to the comp-* compiler tools (the
                          structural-understanding layer the rest of the fabric
                          depends on); and deepening MSTR's own model of the
                          system through reading PRDs, architecture docs, data
                          flows, and cross-referencing pipelines / lambdas /
                          gold-scripts / portal components, so subsequent
                          governance decisions are better-grounded.
- scope:                  IN: (i) read-only sweeps of the codebase to identify
                          broken / dead / unreachable code, doc-vs-code
                          divergence, duplicated logic, abandoned features,
                          and structural inconsistencies; (ii) chartering fixes
                          for findings through CTO/COO; (iii) chartering
                          improvements to comp-* tools (new checks, broader
                          coverage, faster scans, new failure-modes detected);
                          (iv) reading + cross-referencing architecture docs to
                          deepen MSTR's system model; (v) commissioning
                          maintenance-focused briefs from Tier 1 / Tier 2 when
                          a finding requires deeper investigation.
- non_goals:              OUT: originating NEW PRODUCT STRATEGY of any kind --
                          financial metrics, cohorts, market coverage, UI views,
                          chart types, product features, vendor bets. Product
                          strategy is Andrew's authority (Art. I + II) and is
                          not back-doored through maintenance. OUT: redirecting
                          Tier-1 capacity away from active D-001 work to chase
                          a maintenance finding -- maintenance is opportunistic,
                          fills idle time, NEVER pre-empts active project work.
                          OUT: MSTR editing code itself (Art. VI -- govern
                          through the org). OUT: front-end UI design changes
                          (consistent with D-001 non_goals).
- allowed_stakes:         S0-S2   (MSTR analyzes and charters maintenance work;
                          never originates gated procurement, deploys, or
                          destructive ops under this Directive.)
- success_signals:        Every /govern idle cycle (defined: D-001 active
                          queue drained AND no pending MSTR delegation
                          receipts) produces at least one of: a logged
                          maintenance finding, a chartered fix for a prior
                          finding, a comp-* improvement charter, or a
                          documented system-understanding artifact
                          (a read-brief on a subsystem). An empty idle cycle
                          is itself a finding -- "nothing to maintain" is
                          almost certainly false, and a cycle that produces
                          nothing means the scan methodology is too shallow.
- stop_conditions:        D-001 active queue re-fills -> D-001 takes priority
                          (active work pre-empts maintenance, never the
                          reverse). A maintenance finding requires product-

                          action -> propose, do not proceed.

                          dedicated section (findings logged, charters
                          issued, system-understanding artifacts produced).
- expiry_or_review_date:  standing -- no expiry; Andrew revisits if
                          maintenance is producing low signal-to-noise or
