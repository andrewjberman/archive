## Finding 1 -- [low/merge-dedup/both]
- **Location:** `data/inf/scripts/gold/INF_D_00c.portal_leaderboard.py:535 (_compute_new_clients_per_advisor) and :566 (_compute_new_client_hhs_per_advisor)`
- **Mechanism:** Both functions inner-merge account_team.account_id with accounts_dim.account_id (the accounts_v2 repoint) on 'account_id' WITHOUT normalizing dtype first: `team.merge(adim, on='account_id', how='inner')`. This is the ONLY cross-source account_id merge in the file that omits the defensive `.astype(str)` its siblings all apply (aua path 1009/1013, perf path 605/608, hh_lifecycle 908/913). It currently matches only because both producers happen to emit Int64 (INF_A_00 accounts_dimension writes account_id Int64 -> INF_C_07 line 244 `pd.to_numeric(...).astype(_orig_dtype)` restores Int64; build_accounts_v2 coerce_silver_ids -> Int64), and pandas reconciles Int64<->Int64.
- **Failure scenario:** If either producer's account_id dtype drifts to object/str -- e.g. INF_C_07's dtype-restore at line 244 hits its silent `except: pass` (leaving the line-205 astype(str) value as object), or a future accounts_v2 schema change -- the inner merge silently yields 0 rows. Every advisor's new_clients (entry['new_clients'], role_breakdown.new_clients, fee_breakdown new_clients) and the summary total_new_clients collapse to 0 across all windows with NO error and NO log warning (the try/except in each function only catches raised exceptions; a 0-row object-vs-Int64 merge that returns empty just yields {}). The served leaderboard under-reports new-client acquisition to zero.
- **Proposed fix:** Cast both sides before the merge, matching the sibling functions: `adim['account_id'] = adim['account_id'].astype(str)` and `team['account_id'] = team['account_id'].astype(str)` (both functions), so the join key is dtype-stable regardless of upstream producer dtype drift.

## Finding 2 -- [low/schema-column/both]
- **Location:** `data/inf/scripts/gold/INF_D_00c.portal_leaderboard.py:778 (_aggregate_gro_per_advisor_window) and :810 (_aggregate_gro_firm_window)`
- **Mechanism:** The nna-sum expression is `float(sub['nna_$'].fillna(0).sum()) if 'nna_$' in sub.columns else float(sub['net_nna'].fillna(0).sum())`. The `else` branch accesses `sub['net_nna']` with no guard that the column exists. The only upstream schema gate is `if 'return_pct_twr' not in client_perf.columns: return {}` (lines 739/805) plus load_client_performance validating only 'date'/'household_id' -- neither guarantees an nna column is present. A KeyError here propagates out of compute_leaderboard_entries (called at line 1400 inside main's body), through the top-level `except Exception` at 1448, to sys.exit(1). Because the dispatcher runs all gold steps with NO timeout and hard-fails the chain on any non-zero exit, this aborts the entire D-chain rather than degrading gracefully.
- **Failure scenario:** client_performance.parquet (INF_C_02 output; STALE gold in incremental mode) is emitted with `return_pct_twr` present but WITHOUT `nna_$` and WITHOUT `net_nna` (e.g. a partial/regressed INF_C_02 rebuild that ships the TWR column but not the NNA bundle). The line-739 guard passes, the code enters the aggregation, hits the `else` branch, and `sub['net_nna']` raises KeyError -> whole INF_D_00c gold run aborts. Low probability because the GRO.003 columns are normally emitted as a bundle, but this is a graceful-degrade code path that crashes instead of degrading.
- **Proposed fix:** Guard the fallback: `nna_sum = float(sub['nna_$'].fillna(0).sum()) if 'nna_$' in sub.columns else (float(sub['net_nna'].fillna(0).sum()) if 'net_nna' in sub.columns else 0.0)` in both functions, so a client_perf lacking both nna columns degrades to 0.0 rather than aborting the chain.
