## Finding 1 -- [medium/unguarded-read/full]
- **Location:** `data/inf/scripts/gold/INF_A_00.accounts_dimension.py:201-203 (build_accounts_dimension, reg_name derivation) + lib/txn_cache_reader.py:92,196-202`
- **Mechanism:** build_accounts_dimension unconditionally does txns.sort_values('transDate').groupby('accountId')['registrationName'].first(). The loader load_cached_transactions -> _load_canonical_snapshot only enforces REQUIRED_CANONICAL_COLS = {accountId, transDate}; for any OTHER requested column (registrationName) it logs 'WARN: requested columns missing' and CONTINUES, returning a frame WITHOUT that column. So the seam permits registrationName absence but the consumer assumes presence.
- **Failure scenario:** A silver/transactions canonical snapshot is written (or drifts) without a registrationName column (schema variation, or the REST silver writer emits a reduced surface). load_cached_transactions returns txns with only accountId+transDate (WARN logged, not raised). At line 202, txns.groupby('accountId', sort=False)['registrationName'] raises KeyError -> the top-level except at line 300-304 calls sys.exit(1). Because run_script runs gold steps with NO timeout and hard-fails the chain on non-zero exit, the entire CHAIN_FULL aborts at the A-stage: no B/C/D gold, no platinum/portal refresh that night.
- **Proposed fix:** Guard the registrationName column: if 'registrationName' not in txns.columns, skip the reg_name merge and add dim['registration_name'] = pd.NA (object dtype) so the output surface stays stable; alternatively add 'registrationName' to REQUIRED_CANONICAL_COLS in txn_cache_reader so absence fails loud at the loader with a clear message rather than a bare KeyError deep in the build.

## Finding 2 -- [medium/numeric-sign-units/full]
- **Location:** `data/inf/scripts/gold/lib/tax_status.py:152 (add_tax_status_column) vs :130 (classify_reg_type); invoked at INF_A_00.accounts_dimension.py:245`
- **Mechanism:** add_tax_status_column (the DataFrame path actually used) does mapped = df[reg_type_col].map(INF_REG_TYPE_TO_TAX_STATUS) with NO normalization, while the single-value classify_reg_type applies str(reg_type).strip() and the module docstring (lines 37-38) claims matching is 'case-sensitive on a str(...).strip()-normalized key'. The map is exact-match and case-sensitive. reg_type is now sourced 1:1 from accounts_v2.account_type (rename map), whose vocabulary was never empirically re-verified post-DWSPLT (the empirical frequency table lines 13-32 was measured on the OLD silver/accounts_dim, not accounts_v2). Any whitespace or case/label drift misses the map and returns NaN -> fillna('taxable').
- **Failure scenario:** accounts_v2.account_type delivers a value like 'Roth ' (trailing space), 'ROTH', or a label variant not in the 60-key map. .map() yields NaN and the row is classified taxable + qualified_flag=False instead of tax_free/tax_deferred. tax_status and qualified_flag are served on accounts_dimension_latest and consumed by INF_C_05 client_tax_liability to split qualified vs non-qualified AUA, so the served tax split is silently wrong. If the contaminated share stays under 5% the >5% WARN gate (INF_A_00 line 249) never fires, so the corruption is invisible.
- **Proposed fix:** In add_tax_status_column, normalize before mapping: mapped = df[reg_type_col].astype('string').str.strip().map(INF_REG_TYPE_TO_TAX_STATUS) so the DataFrame path matches classify_reg_type and the documented contract; and add a one-time assertion/log of the distinct unmapped account_type values against the map so accounts_v2 vocabulary drift surfaces explicitly instead of silently defaulting to taxable.
