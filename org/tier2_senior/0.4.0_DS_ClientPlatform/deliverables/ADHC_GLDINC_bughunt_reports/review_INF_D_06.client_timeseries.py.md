## Finding 1 -- [high/type-issue/full]
- **Location:** `data/inf/scripts/gold/INF_D_06.client_timeseries.py:365 (build_per_client_timeseries) with blast at :537 and :541`
- **Mechanism:** household_id is coerced with a bare `hd['household_id'] = hd['household_id'].astype(str)` (line 365). The dim comes straight from silver via `df[['account_id','household_id']].drop_duplicates(...)` (lines 196/204) with NO dtype normalization (silver rule 17 forbids fillna/dropna). If ANY account has a null household_id, pandas reads the whole column back as float64, so astype(str) yields '12345.0' for populated ids and 'nan' for nulls. The output guard at line 537 is `int(hh_id) if str(hh_id).isdigit() else hh_id` -- '12345.0' and 'nan' are both non-digit, so they pass through unchanged, and the S3 key at line 541 becomes `platinum/clients/12345.0/timeseries.json` (or `.../nan/...`).
- **Failure scenario:** silver/api_dims/household latest partition has one or more rows with a null household_id (an account not yet assigned to a household). The household_id column loads as float64. For household 12345 the artifact is written to `platinum/clients/12345.0/timeseries.json` with JSON field `household_id: "12345.0"` (a string), while the frontend/other publishers key on integer 12345 -> the client's timeseries 404s / mismatches at the expected `.../12345/...` path. Separately, every null-household account is bucketed into a phantom `platinum/clients/nan/timeseries.json` household.
- **Proposed fix:** Coerce to a clean integer-or-string id before use: e.g. `hd = hd.dropna(subset=['household_id']); hd['household_id'] = hd['household_id'].astype('int64').astype(str)` (or `pd.to_numeric(...).astype('Int64')` then format), dropping/logging null-household accounts explicitly rather than letting float64 produce '.0'/'nan' path segments. Apply the same normalization on both the api_dims and accounts_dim fallback branches.

## Finding 2 -- [high/empty-null-handling/full]
- **Location:** `data/inf/scripts/gold/INF_D_06.client_timeseries.py:456 (mv coercion) -> :511-527 (pct/total) -> :117 (_write_json_s3 json.dumps)`
- **Mechanism:** `mv = float(row.get('market_value', 0) or 0)` (line 456) intends to default missing values to 0, but `or 0` only catches falsy values -- a float NaN is truthy (`bool(float('nan'))` is True), so `nan or 0` returns nan and mv=nan. That nan is summed into hh_class_mv, so total = sum(class_mv.values()) is nan. The zero-guard at line 512 `if total <= 0: continue` does NOT catch it because `nan <= 0` is False, so the period is kept. `pct()` (line 515) computes round(nan/nan*100, 2)=nan for every class, and total_household_mv=round(nan,2)=nan. `_write_json_s3` calls `json.dumps(obj, default=str)` with the default allow_nan=True, which emits bare `NaN` tokens -- invalid JSON that JS `JSON.parse` rejects.
- **Failure scenario:** A household holds a position whose canonical_holdings market_value is null/NaN (unpriced security not covered by the INF_S_00 price-fill tiers) in the nearest holdings partition for a quarter. The household's timeseries.json for that period gets equity_pct/fixed_income_pct/cash_pct/alt_pct/total_household_mv all = NaN, and the file is serialized with literal `NaN` tokens -> the served artifact is malformed JSON -> the client timeseries page fails to parse/render. If --upload, the NaN also gets frozen into the anchor cache (lines 474-477) and re-served on later runs.
- **Proposed fix:** Guard NaN explicitly at read: `import math; v = row.get('market_value'); mv = float(v) if v is not None and not (isinstance(v,float) and math.isnan(v)) else 0.0` (or fillna(0) on the market_value column before the loop). Also make the total guard NaN-safe (`if not total or total <= 0 or math.isnan(total): continue`) and serialize with `json.dumps(obj, default=str, allow_nan=False)` so a stray NaN fails loud instead of emitting invalid JSON.
