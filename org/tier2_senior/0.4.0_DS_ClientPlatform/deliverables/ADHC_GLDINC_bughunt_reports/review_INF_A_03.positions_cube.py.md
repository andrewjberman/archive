## Finding 1 -- [medium/type-issue/both]
- **Location:** `INF_A_03.positions_cube.py compute_unit_events (lines 142-153 groupby.sum/cumsum) + _expand_one_pair (line 182 `units_arr > 1e-9`); root cause = un-coerced noUnits in the silver->gold path`
- **Mechanism:** `units` (bronze `noUnits`) is consumed by arithmetic (groupby(['account_id','ticker','trade_date'])['units'].sum() -> groupby.cumsum() -> numpy `units_arr > 1e-9`) with NO numeric coercion anywhere. The transaction silver builder (convert_transactions_to_silver.py) reads bronze via pd.read_json(..., dtype=False) and coerces ONLY id columns + transDate (CR_FLOAT_COLUMNS covers only currentAccountValue/currentCashValue); noUnits is an un-coerced passthrough. INF_A_03 itself never coerces units. If the source-selected canonical snapshot delivers noUnits as object dtype (numeric strings), groupby.sum() STRING-CONCATENATES ('10'+'5'->'105'), cumsum concatenates further, and the worker's `units_arr > 1e-9` raises TypeError (verified: numpy '>' str vs float -> TypeError). Separately, the drop_zero_units filter `df['noUnits'] != 0` silently no-ops on object strings (str != int 0 is always True, verified -> [True,True]), so zero-unit cash rows would also leak in. This is the exact object-dtype drift class that coerce_id_columns was built to defend account_id/rep_id against -- units has no equivalent guard.
- **Failure scenario:** Orion REST returns noUnits as quoted JSON strings (e.g. "12.5") on some pull; pd.read_json(dtype=False) keeps the silver noUnits column object dtype (no downstream coercion). INF_A_03 groupby('units').sum() concatenates the strings; _expand_one_pair then evaluates `units_arr > 1e-9` on an object array -> TypeError raised inside the ProcessPool worker -> re-raised by pool.map -> uncaught -> main() except -> sys.exit(1). Because INF_A_03 runs in CHAIN_COMPUTE with NO timeout and hard-fails the chain on any non-zero exit, the ENTIRE full chain aborts at INF_A_03, skipping B/C/D and the served-AUA refresh. Currently dormant (the script runs green daily, so noUnits is presently numeric), but there is zero defensive guard on the arithmetic-consumed column.
- **Proposed fix:** Coerce units to numeric immediately after the rename in load_transactions, e.g. `txns['units'] = pd.to_numeric(txns['units'], errors='coerce')` (drop resulting NaN or treat as 0), mirroring the coerce_id_columns guard already applied to account_id/rep_id; and/or add noUnits to an explicit float-coercion bucket in convert_transactions_to_silver.py so silver standardizes it (Rule-17 dtype standardization, not slimming).

## Finding 2 -- [low/incremental-full-break/full]
- **Location:** `INF_A_03.positions_cube.py build_positions_cube lines 406-408 (should_skip input_keys)`
- **Mechanism:** The per-partition skip-gate is called with input_keys=[f'silver/transactions/{d}.parquet'] (per-DATE silver partitions), but post-DWSPLT the transaction data is source-selected from a SINGLE newest canonical snapshot (txn_cache_reader._load_canonical_snapshot walks newest-first and returns ONE full-history partition), NOT from per-date partitions. So the freshness key the gate checks is not the file the data actually comes from. For a historical output date d the gate references an old silver/transactions/{d}.parquet whose mtime never changes; for weekend/holiday output dates (the cube emits a partition for every calendar day, but silver has no txn partition on non-trading days) _head_object returns None and the loop `continue`s (treated as not-newer). Either way, a change to the newest snapshot does not bump the referenced key's mtime, so should_skip returns SKIP and the stale prior positions_cube/{d}.parquet is served.
- **Failure scenario:** With INFINC_PHASE1=1 enabled, a backdated transaction correction lands in today's Orion REST snapshot and changes positions for 2024-06-01. silver/transactions/2024-06-01.parquet mtime is unchanged (or 2024-06-01 is a weekend with no such key), so should_skip('INF_A_03','2024-06-01', out_key, ['silver/transactions/2024-06-01.parquet']) returns SKIP -> gold/positions_cube/2024-06-01.parquet is never rewritten -> stale units served for that historical date. CURRENTLY INERT: orion-gold-dispatch.sh never exports INFINC_PHASE1=1 (defaults 0), so should_skip always returns False (COMPUTE) and every partition is recomputed each full run; the mismatch only bites if/when phase1 is flipped on.
- **Proposed fix:** When the skip-gate is enabled, key the freshness check on the ACTUAL data source -- the canonical-snapshot S3 key the cache reader source-selected (return it from load_cached_transactions and pass it as the single input_key for all partitions) -- instead of the per-date silver/transactions/{d}.parquet, so a snapshot update correctly invalidates all affected historical partitions.
