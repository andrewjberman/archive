## Finding 1 -- [high/incremental-full-break/both]
- **Location:** `INF_D_02b.top_holdings.py:61,88-111 (SILVER_API_ASSETS_PREFIX = 'silver/api_dims/assets/'; _latest_silver_assets_partition/load_assets) vs orion-gold-dispatch.sh CATALOG (no build_assets_dim.py entry)`
- **Mechanism:** INF_D_02b consumes silver/api_dims/assets/ (line 61) and always reads the lexicographically-latest snapshot_date= partition (lines 96-99). The ONLY writer of that prefix is data/inf/scripts/silver/build_assets_dim.py (via write_silver_api_dim_parquet, which writes silver/api_dims/{dim}/snapshot_date=YYYY-MM-DD/data.parquet). build_assets_dim.py has NO entry in orion-gold-dispatch.sh's step catalog (verified: catalog ends at CATALOG_END line 303 with no such mapping; all 54 repo hits for 'build_assets_dim' are docs/logs/TOs, none wire it into a chain or cron). The daily incremental producer INF_API_SILVER_ASSETS_V2 (convert_assets_v2_to_silver.py) writes a DIFFERENT prefix, silver/assets_v2/{date}.parquet, with a different 58-col Orion schema (no position_mv / asset_ticker / rep_id) -- it does NOT feed INF_D_02b. So neither CHAIN_INCREMENTAL nor CHAIN_FULL/CHAIN_COMPUTE ever refreshes INF_D_02b's input; it is frozen at the last manual build_assets_dim run (docstrings reference canonical_2026-04-20 / '8-day staleness acceptable for v1').
- **Failure scenario:** Nightly CHAIN_INCREMENTAL runs INF_D_02b --upload every day. Each run recomputes from the SAME frozen silver/api_dims/assets/ partition and rewrites platinum/firm/top_holdings.json (and per-advisor files) with a FRESH generated_at (line 207 = _now_str()) but an unchanged data_as_of (the stale snapshot_date) and identical numbers. The advisor-facing Top-Holdings / PartnerAnalytics / Distribution panels therefore serve holdings frozen ~months stale while the artifact's generated_at makes it look current -- a silent, freshness-monitor-evading stale served number (data_as_of would betray it, but the panel/monitor keys on regeneration).
- **Proposed fix:** Wire the assets-dim producer into the chain: either add build_assets_dim.py as a dispatched step ahead of INF_D_02b (so silver/api_dims/assets/ is rebuilt from current canonical each run), OR repoint INF_D_02b at the live silver/assets_v2/ partition (adapting the column map: current_value->position_mv, ticker->asset_ticker, etc.). Interim: add a freshness assertion in load_assets that FAILs/DEFERs when the latest silver/api_dims/assets/ partition's snapshot_date lags the pipeline as-of by > N days, so a frozen input is caught instead of silently republished.

## Finding 2 -- [medium/unguarded-read/both]
- **Location:** `INF_D_02b.top_holdings.py:104-106 (load_assets empty return) + 238-240 (main: if df.empty: return 1)`
- **Mechanism:** load_assets() returns an empty DataFrame when _latest_silver_assets_partition() finds zero matching keys (lines 96-97,104-106). main() then does `if df.empty: return 1` (line 240). The gold dispatch runs all gold/silver steps with NO timeout and HARD-FAILs the whole chain on any non-zero exit. Unlike the silver builders (convert_assets_v2_to_silver.py uses defer_guard_bronze -> DEFER/carry-forward, rc=0 on a tolerated absent input), INF_D_02b has no DEFER/carry-forward path: absent-or-empty input => rc=1 => chain abort.
- **Failure scenario:** If silver/api_dims/assets/ ever has no partitions (fresh/re-provisioned bucket, a QA scope, pruned partitions, or build_assets_dim never having run there) -- or if the latest partition parquet is present but 0-row -- INF_D_02b returns 1, and the no-timeout hard-fail chain ABORTS at step INF_D_02b, so every downstream D step queued after it (INF_D_03, INF_D_02d, INF_D_02c, INF_D_04b, INF_D_04, INF_09, INF_D_09) never runs that cycle. A single non-AUA-critical publisher's missing input takes down the rest of the D-chain.
- **Proposed fix:** Make an empty/absent assets input non-fatal for the chain: log WARN, emit an empty-but-valid firm/per-advisor envelope (or carry forward the prior served artifact) and return 0, matching the silver builders' DEFER contract -- reserve rc=1 for genuinely corrupt input, not merely-absent input, so this publisher cannot abort the downstream aggregates.

## Finding 3 -- [medium/schema-column/both]
- **Location:** `INF_D_02b.top_holdings.py:159-166 (_aggregate_top_holdings groupby: account_count=('account_id','nunique'))`
- **Mechanism:** The groupby-agg unconditionally references account_id (line 163). Every other consumed column is defensively guarded with an `if <col> in work.columns` fallback -- asset_ticker (lines 130-134), asset_name (136-138), position_mv (140-147) -- and main() even guards account_id for its log line (`df['account_id'].nunique() if 'account_id' in df.columns else 0`, line 248). But the aggregation itself is NOT guarded, so a missing/renamed account_id column raises KeyError from pandas .agg() rather than being handled. The main() guard gives false confidence that account_id absence is tolerated.
- **Failure scenario:** If a future/alternate producer of silver/api_dims/assets/ (or a schema drift in build_assets_dim) omits or renames account_id (e.g. to account or acct_id), _aggregate_top_holdings raises `KeyError: "Column(s) ['account_id'] do not exist"`. It is uncaught inside the function, propagates to the top-level except (lines 310-314), and INF_D_02b exits 1 -> the no-timeout chain hard-fails and aborts the D-chain -- even though the log line at 248 would have printed '0 accounts' as if account_id-absence were handled.
- **Proposed fix:** Guard account_id like the other columns: if 'account_id' not in work.columns, synthesize a null/placeholder column (or set account_count via a safe fallback) before the groupby, so a missing account_id degrades account_count to 0 rather than crashing the whole chain.
