## Finding 1 -- [high/empty-null-handling/both]
- **Location:** `build_model_summary lines 260 and 279 (`aum_map.get(mid) or 0.0`)`
- **Mechanism:** The `x or 0.0` idiom is meant to default a missing model AUM to 0, but it only works for a dict-miss (None -> 0.0). A model that IS present in model_composition with a NULL model_aum reads back as float64 NaN or nullable pd.NA. float NaN is truthy, so `NaN or 0.0` returns NaN (the intended default is NOT applied) and the NaN propagates into that model's model_aum_eclipse and aum_variance; worse, the firm-total row sums float(aum_map.get(m) or 0.0) across all 9 models (line 279), so a SINGLE null model_aum makes the firm-row model_aum_eclipse and aum_variance NaN. It is then written into gold/eclipse/{date}/_meta/gold_complete.json (line 373, json.dumps default allow_nan=True emits a bare `NaN` token = invalid strict JSON). If silver typed model_aum as nullable Float64, `pd.NA or 0.0` instead raises TypeError 'boolean value of NA is ambiguous'.
- **Failure scenario:** model_composition silver has model_aum null for one of the 9 Opal models (e.g. model_id 28). Served model_portfolio_summary.parquet firm row model_aum_eclipse = NaN and aum_variance = NaN (a materially-wrong served headline AUM, with no crash or signal), and gold_complete.json firm_headline.model_aum_eclipse = NaN (invalid JSON any strict JS consumer rejects). If model_aum is a nullable Float64 column, the script instead raises TypeError and the eclipse leg goes dark (Model Portfolios freeze).
- **Proposed fix:** Coerce NaN/NA safely instead of relying on truthiness: `v = aum_map.get(mid); model_aum = round(float(v), 2) if v is not None and pd.notna(v) else 0.0`, and apply the same guard inside the firm-sum generator. Optionally json.dumps(sentinel, allow_nan=False) to fail loud on any residual NaN before writing the served sentinel.

## Finding 2 -- [medium/schema-column/both]
- **Location:** `build_account_grain lines 168-208 (defensive slices at 171 & 181 vs unconditional consumers at 186, 197-203, 204, 208); join-key normalization main() lines 333-336`
- **Mechanism:** full_slice and av_slice are built defensively with `[c for c in cols if c in df.columns]`, which explicitly anticipates that input columns may be absent -- but the output-DataFrame builder then references full-derived columns UNCONDITIONALLY: total_value (197), managed_value (198), excluded_value (199), current_cash (200), num_of_associated_accounts (201), last_rebalanced_on (202), status (203); and accounts_v2-derived household_id (186 `acct['household_id'].notna()` and 204) and orion_current_value (208). If any such column is missing from the silver input, the defensive filter drops it, the left-merge never creates it, and the direct `acct['col']` raises KeyError. (account_number/account_name/portfolio_name/representative_name/advisor_firm/custodian are correctly read via acct.get(); these are not.) The main() normalization loop likewise assumes simple has model_id/id/eclipse_account_id_int, full has id, model_comp has id, accounts_v2 has account_id -- any missing -> KeyError before the builders even run.
- **Failure scenario:** The new/largely-untested Eclipse silver converter renames or omits `current_cash` in portfolios_full. build_account_grain line 200 `_round2(acct['current_cash'])` raises KeyError; because INF_E_00 runs in the best-effort eclipse block the chain is not aborted but the eclipse leg goes dark (Model Portfolios freeze), and under a manual `--chain eclipse` it hard-aborts. Same class: accounts_v2 missing household_id -> line 186 KeyError.
- **Proposed fix:** Consume these columns via acct.get('col') (as already done for the string dims) or reindex full_slice/av_slice to the full expected column set with NA fill before building `out`; and validate the required id/value columns up-front with an explicit, clear error instead of a bare KeyError.

## Finding 3 -- [medium/unguarded-read/both]
- **Location:** `_latest_eclipse_silver_date lines 79-103 (explicit-date early return) + main() lines 319, 324-328 (_read_parquet)`
- **Mechanism:** The dispatch catalog invokes INF_E_00 with `--date {date}` = today's RUN_DATE (line 302). When --date is explicit, _latest_eclipse_silver_date returns it IMMEDIATELY (line 85-86) without verifying the partition or its silver_complete.json sentinel exists -- the robust newest-with-sentinel fallback (lines 99-103) only runs when --date is omitted. The subsequent _read_parquet (lines 324-328) does an unguarded s3.get_object; a missing today's partition raises NoSuchKey (uncaught) -> crash. In the post-sentinel eclipse block, INF_ECLIPSE_PULL and INF_ECLIPSE_SILVER run just before INF_E_00 and are themselves best-effort/non-fatal, so INF_E_00 still executes even after they fail -- guaranteeing the missing-partition read.
- **Failure scenario:** On a market holiday/weekend (e.g. the July-4th dormancy noted in the repo) or when the Eclipse API returns no data, INF_ECLIPSE_SILVER writes no silver/eclipse/{today}/ partition; INF_E_00 --date=today calls _read_parquet('silver/eclipse/{today}/portfolios_simple.parquet') -> NoSuchKey -> crash. Served Model Portfolios silently freeze at the last good date (the exact 'silently-dark eclipse leg froze Model Portfolios' incident class). Under `--chain eclipse` (fatal run_chain) the run aborts.
- **Proposed fix:** When --date is explicitly given but that partition lacks a completion sentinel, fall through to the sentinel-checked latest-date resolution (or head-object the key and skip cleanly rather than crash). Alternatively, have the dispatcher pass the resolved eclipse-silver date rather than raw RUN_DATE.

## Finding 4 -- [medium/merge-dedup/both]
- **Location:** `build_account_grain line 172 (merge full on id) and line 183-184 (merge accounts_v2 on account_id)`
- **Mechanism:** Both are how='left' merges with no uniqueness guard on the right key. Silver dedups only EXACT-duplicate rows, so two accounts_v2 rows sharing account_id but differing in any column (e.g. representative_name) both survive; likewise a duplicated portfolio id in portfolios_full. A duplicate right key expands each matching opal portfolio into multiple rows, so its total_value / managed_value / orion_current_value are double-counted in the household (build_household_grain), per-model, and firm sums (build_model_summary) -> inflated served AUM with no error raised. Secondary: normalizing eclipse_account_id_int/account_id via to_numeric(errors='coerce').astype('Int64') turns any non-numeric id into <NA>, which can mis-group across the merge.
- **Failure scenario:** accounts_v2 snapshot has two rows for account_id 12345 (differing only in a non-key attribute); the opal portfolio on that account becomes 2 rows after line 183; firm total_value_eclipse and orion_current_value in the served model_portfolio_summary.parquet (and the household roll-up) are overstated by that portfolio's value -- a silently materially-high served number.
- **Proposed fix:** Enforce right-key uniqueness before merging: full_slice = full_slice.drop_duplicates('id') and av_slice = av_slice.drop_duplicates('account_id'), or pass validate='m:1' to .merge() to fail loud on a non-unique right key.
