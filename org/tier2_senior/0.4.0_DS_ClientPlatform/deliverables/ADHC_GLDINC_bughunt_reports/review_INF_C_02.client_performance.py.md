## Finding 1 -- [medium/empty-null-handling/full]
- **Location:** `data/inf/scripts/gold/INF_C_02.client_performance.py:304 (groupby household aggregation); root null-source at INF_A_00.accounts_dimension.py:238`
- **Mechanism:** The household aggregation groupby(['_date_str','date','household_id']) at line 304 uses pandas' default dropna=True, so every row whose household_id is <NA> is SILENTLY excluded from the aggregation and never appears in any row of client_performance.parquet. household_id is Int64-nullable: INF_A_00 line 238 explicitly coerces accounts_v2 household_id with pd.to_numeric(errors='coerce') BECAUSE (per its own comment) 'older accounts_v2 data may have string \'unknown\' values that need coerce-to-NaN'. Those NA household_ids flow through canonical_performance (INF_C_00 left-joins acct_dim household_id, unmatched->NA) into all_perf. The defensive household_id merge at lines 292-295 is skipped (household_id column IS present), so the NAs are never repaired. Nothing logs the dropped rows; the line-431 AUA headline sums the already-filtered total, so the drop is invisible in the script's own validation.
- **Failure scenario:** Orion account 12345 holding $2.0M has a blank/'unknown' household_id in accounts_v2 -> INF_A_00 coerces it to <NA> -> canonical_performance_{date}.parquet carries household_id=<NA> for that account -> INF_C_02's groupby drops the row -> the served household-grain total_aua (line 433 headline AND the D-chain platinum publishers INF_D_00/INF_D_02/INF_D_03/INF_D_04 that consume client_performance.parquet) is $2.0M under-counted, with no WARN emitted. Multiple unmapped accounts compound the silent AUA shortfall.
- **Proposed fix:** Before the groupby, count/log rows with household_id.isna() and their total_aua sum (observability), and either (a) assert household-grain total_aua parity against the account-grain sum, or (b) route NA household_ids to an explicit 'unassigned_household' bucket instead of silently dropping. At minimum emit a loud WARN when NA-household AUA is non-trivial.

## Finding 2 -- [low/type-issue/full]
- **Location:** `data/inf/scripts/gold/INF_C_02.client_performance.py:167 (_build_daily_factor_table)`
- **Mechanism:** Line 167 does perf['client_id'].astype('int64') (numpy non-nullable). But silver/performance client_id is Int64-nullable, NOT the clean int/str the convert_performance_to_silver docstring claims: coerce_silver_ids() (data/inf/scripts/silver/_orion_api_silver_lib.py:255-270) runs pd.to_numeric(errors='coerce').astype('Int64') over DEFAULT_SILVER_ID_COLS which INCLUDES client_id. astype('int64') on a column containing any <NA> raises TypeError ('cannot convert to int64-dtype NumPy array with missing values'). That exception is uncaught inside main(), so the top-level except at lines 484-488 fires sys.exit(1); INF_C_02 runs with NO timeout and HARD-FAILs the chain, so the whole gold chain aborts at C_02 and the entire D-chain (served platinum) never runs. In practice the puller emits only clean int client_ids so NA is currently unlikely, but the guard is trivially missing and the source dtype is genuinely nullable (and its docstring misdescribes it, which is exactly how such a null slips in).
- **Failure scenario:** A single silver/performance row with client_id=<NA> (a bronze row where Orion returned a blank/non-numeric client id, or a hand-patched/backfilled bronze partition) -> INF_C_02 raises TypeError at line 167 -> traceback + sys.exit(1) -> 'CHAIN FAILED at INF_C_02' -> D-chain skipped -> served portal artifacts go stale with a loud-but-total abort.
- **Proposed fix:** Use .astype('Int64') (keep the nullable extension dtype -- an Int64 join key still matches the Int64 household_id in the merge), or dropna(subset=['client_id']) before the cast, so one malformed client_id degrades one client's decomp instead of aborting the 40+-script chain.
