## Finding 1 -- [critical/schema-column/both]
- **Location:** `data/inf/scripts/gold/INF_D_00.portal_aggregates.py:168-177 (load_accounts_dim) -> :735-739 (_ensure_tax_status) -> :766-800 (build_firm_tax_block); regression from repoint commit cf4a05a9c (2026-06-30)`
- **Mechanism:** The ADVI_INFREF P1 LEG-1 repoint switched load_accounts_dim() off silver/accounts_dim/latest.parquet (which INF_A_00 writes WITH a tax_status column, per lib/tax_status.py) to the accounts_v2 latest partition, and now hand-builds `out` with only 4 columns: account_id, household_id, registration_name, first_trade_date. accounts_v2 silver carries NEITHER tax_status NOR reg_type (verified: convert_orion_api_to_silver.py accounts_v2 keep-map lines 432-474 has no 'Reg Type' mapping; the reg_type mapping at lines 841/924 belongs to the legacy accounts_dim handler), and load_accounts_dim would drop them anyway. build_firm_tax_block() then calls _ensure_tax_status(), which sees no 'tax_status' column and calls add_tax_status_column(dim, reg_type_col='reg_type'); with reg_type absent, tax_status.py sets tax_status='taxable' for EVERY row and returns fallback_rate=1.0. The subsequent groupby collapses all AUA into the 'taxable' bucket. The prior code returned the full accounts_dim frame including INF_A_00's tax_status, so this is a silent regression, not a pre-existing gap. The repoint commit asserted 'total_aua STRUCTURALLY UNAFFECTED... touches name/advisor/count only' but missed that the frozen accounts_dim also fed the tax block.
- **Failure scenario:** Nightly full OR incremental chain runs INF_D_00 (it is in CHAIN_COMPUTE line 335 and CHAIN_INCREMENTAL line 340). load_accounts_dim returns [account_id, household_id, registration_name, first_trade_date] with no reg_type/tax_status. build_firm_tax_block emits tax={taxable=<total AUA>, taxable_pct=100.0, tax_deferred=0.0, tax_deferred_pct=0.0, tax_free=0.0, tax_free_pct=0.0} into platinum/firm/clients_tab.json (fallback_rate=1.0 logged as a WARN only). INF_D_04.build_clients_tab_slim (lines 4082-4098) re-reads and re-serves that tax block into clients_tab_slim, so the portal TaxCostBasisPanel shows 100% taxable / 0% tax-deferred / 0% tax-free -- materially wrong, since tax_status.py's own empirical census shows ~48% of Inflection accounts are IRA/Roth/retirement (tax_deferred + tax_free). No crash and no alarm fires (only a chain-log WARN), so the corruption is silent to the portal user and has been live since 2026-06-30.
- **Proposed fix:** Restore a real registration-type source for tax bucketing. Either (a) add a dedicated tax-status load that reads reg_type/tax_status from a dim that carries it (e.g. keep sourcing tax_status from silver/accounts_dim/latest.parquet or the unified_account_dim -- registration type is registration-static so the 04-29 freeze is acceptable for tax classification, unlike names/advisor), joined to accounts_v2 account_id; or (b) add 'Reg Type'->reg_type (or a pre-classified tax_status) to the accounts_v2 keep-map in convert_orion_api_to_silver.py AND carry it through load_accounts_dim's `out`. Do NOT substitute account_type -- it is not a registration type and will not map through INF_REG_TYPE_TO_TAX_STATUS. Also consider promoting the fallback_rate==1.0 WARN to a hard guard so a fully-collapsed tax block cannot be served silently.
