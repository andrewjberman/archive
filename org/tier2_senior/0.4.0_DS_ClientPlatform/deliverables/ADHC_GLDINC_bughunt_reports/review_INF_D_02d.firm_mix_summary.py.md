## Finding 1 -- [medium/schema-column/both]
- **Location:** `data/inf/scripts/gold/INF_D_02d.firm_mix_summary.py:280 (_load_assets_v2_classification)`
- **Mechanism:** The S3 read + read_parquet is wrapped in a try/except that returns {} (feeding the documented 'classifier empty -> current-only fallback'). But the very next statement, `df.drop_duplicates(subset=['ticker'])` at line 280, is OUTSIDE that try/except. If the latest assets_v2 silver parquet is present and non-empty but its schema lacks the literal 'ticker' column, drop_duplicates raises KeyError, which is NOT caught here, NOT caught in _build_mix_periods_multi (line 423 call site), and NOT caught in main (line 495) -- it hits the top-level except (line 534) -> sys.exit(1). This escapes the graceful-degradation contract entirely. Note the historical-holdings path guards the same column (`if 'ticker' in df.columns` line 368) and INF_D_03's diagnostic guards `{'account_id','ticker','market_value'}.issubset(...)`, so the codebase knows 'ticker' can be absent -- this path just omits the guard.
- **Failure scenario:** The Orion assets_v2 field is renamed (e.g. ticker->symbol) or a partial/corrupt converter run lands a schema-drifted-but-non-empty silver/api_dims/assets_v2 parquet. Read succeeds, then `df.drop_duplicates(subset=['ticker'])` raises KeyError "['ticker'] not in index". Under the no-timeout hard-fail compute chain, INF_D_02d aborts and kills every downstream step (INF_D_02c, INF_D_04b, INF_D_04 portal summary, INF_09 partner analytics, INF_D_09) instead of falling back to current-only.
- **Proposed fix:** Guard the column before use inside the fallback boundary: `if 'ticker' not in df.columns: log(...); return {}` immediately after the read, or move the dedup/iteration inside the try/except that already returns {}.

## Finding 2 -- [medium/empty-null-handling/both]
- **Location:** `data/inf/scripts/gold/INF_D_02d.firm_mix_summary.py:473-477 (main)`
- **Mechanism:** Missing firm_composition.json is treated as a HARD error (return 1 -> sys.exit(1) -> chain abort), but its sole producer INF_D_03 GRACEFULLY no-ops (logs 'no canonical holdings partitions found -- skipping composition' / 'exiting with 0', INF_D_03.composition_artifacts.py:499-503) and does NOT write the artifact when no gold/canonical/holdings_*.parquet exists. This asymmetry converts a designed graceful-skip into a full downstream-chain abort.
- **Failure scenario:** Cold start / disaster-recovery / new-firm onboarding where no gold/canonical/holdings_*.parquet has ever been written AND no prior platinum/firm/firm_composition.json exists: INF_D_03 exits 0 (chain continues) without emitting firm_composition.json, then INF_D_02d reads None (line 473) and returns 1, aborting the entire D-chain -- INF_D_04 (client_portal_summary) and INF_09 (partner analytics) never run, turning a benign 'no data yet' into a full pipeline failure.
- **Proposed fix:** Mirror INF_D_03's graceful contract: when composition is None, log a WARN and `return 0` (skip publishing mix_summary.json) rather than `return 1`, so a missing optional upstream degrades gracefully instead of killing downstream publishers.

## Finding 3 -- [medium/other/both]
- **Location:** `data/inf/scripts/gold/INF_D_02d.firm_mix_summary.py:369-371 and 245-262 (_build_historical_point/_classify_product_category) vs 193-209 (_build_current_period_point)`
- **Mechanism:** The current-period point of mix_periods takes its equity/fixed_income/cash/alternatives split from firm_composition.json, which INF_D_03 classifies using the canonical holdings' OWN `asset_class` column (INF_D_03 line 386 groups by asset_class). The historical quarter points instead RECLASSIFY each ticker via the assets_v2 `product_category` keyword classifier and default any ticker not present in the CURRENT assets_v2 dim to `alternatives` (line 370). So the two ends of the same time-series use different classification methodologies, and historical tickers absent from today's assets_v2 are silently absorbed into alternatives.
- **Failure scenario:** A muni-bond fund classified `fixed_income` by the holdings asset_class column (current point shows it in fixed_income) whose assets_v2 product_category lacks bond/fixed/income/credit/debt keywords -- or which was liquidated and dropped from the current assets_v2 dim -- is bucketed `alternatives` in every historical point. QuarterlyMetricsBar then renders a fictitious 'fixed_income collapse / alternatives spike' between the latest completed quarter and the current quarter that reflects a classifier mismatch, not a real allocation change -- a silently wrong served time-series.
- **Proposed fix:** Classify all points with ONE methodology: either run the current period through the same assets_v2 keyword classifier used for history, or classify history from a per-snapshot asset_class column; and route unknown/absent tickers to an explicit `other`/`unclassified` bucket instead of silently folding them into alternatives.
