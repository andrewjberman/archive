## Finding 1 -- [critical/other/both]
- **Location:** `data/inf/scripts/gold/INF_run_c_chain.py:32 (run()) + :110 (run('INF_C_04.validate_aua.py'))`
- **Mechanism:** run() unconditionally builds `cmd = ['python3', f'{CODEDIR}/{script}', '--upload']`, appending --upload to EVERY script. INF_C_04.validate_aua.py is a validator whose main() uses a plain argparse.ArgumentParser that declares ONLY `--date` and calls parser.parse_args() (INF_C_04.validate_aua.py:82-85), which rejects unknown args. Running it as `INF_C_04.validate_aua.py --upload` makes argparse print 'unrecognized arguments: --upload' and sys.exit(2). run() then sees r.returncode!=0 and calls sys.exit(1), aborting the runner. This differs from the dispatch catalog, where INF_C_04 is registered with EMPTY default_flags (no --upload) precisely because it is a validator.
- **Failure scenario:** Any invocation of INF_run_c_chain.py reaches line 110, spawns `python3 /tmp/orion_c_chain/INF_C_04.validate_aua.py --upload`, argparse exits 2, run() reports 'FAIL: INF_C_04.validate_aua.py (exit 2)' and sys.exit(1). The runner aborts at INF_C_04 on EVERY run; INF_C_05 (client_tax_liability), INF_C_06 (client_mix_timeseries), and INF_C_08 (advisor_fee_efficiency) at lines 111-113 are never reached and never produced by this runner, and the process exits non-zero.
- **Proposed fix:** Do not hard-code --upload inside run(). Move --upload into the per-script flags argument and pass it only for producer scripts (validators get no flags), e.g. `cmd = ['python3', f'{CODEDIR}/{script}'] + (flags or [])` and call `run('INF_C_00...', ['--upload'])` etc., with `run('INF_C_04.validate_aua.py')` (no flags). Alternatively, change validate_aua.py to parse_known_args, but the runner is the wrong layer to force --upload on a validator.

## Finding 2 -- [high/other/both]
- **Location:** `data/inf/scripts/gold/INF_run_c_chain.py:89, :94, :99, :104 (and :76, :81)`
- **Mechanism:** The C-chain idempotent skip guards key on files that persist across runs, so after the first run they always exist and the guarded producer is permanently skipped. (a) Line 89 checks the HARDCODED key `gold/canonical/canonical_performance_2026-04-20.parquet`, but INF_C_00 writes a DATED partition `canonical_performance_{date}.parquet` (INF_C_00.canonical_performance.py:185/229). Since the 2026-04-20 file exists from months ago, `if not _dim_exists(...)` is always False -> INF_C_00 is skipped every run and today's canonical_performance_{today}.parquet is never written. (b) Lines 94/99/104 check the fixed, undated 'latest' keys gold/timeseries/client_performance.parquet (INF_C_02 overwrites this exact key each run, INF_C_02.client_performance.py:61/463), gold/timeseries/account_performance.parquet (INF_C_03), and gold/views/account_team.parquet (INF_C_07). Once written on the first run, `if not exists` is always False, so INF_C_02/C_03/C_07 are skipped forever and their served outputs are never refreshed. The runner logs the steps as intentionally skipped and reports success.
- **Failure scenario:** Runner invoked 2026-07-06. canonical_performance_2026-04-20.parquet still exists -> INF_C_00 skipped, no fresh canonical_performance produced. client_performance.parquet / account_performance.parquet / account_team.parquet exist from an earlier run -> INF_C_02/C_03/C_07 skipped. The served client-performance and account-performance timeseries stay frozen at whatever date they last held, while the runner prints 'skipping' and continues as if healthy (masking staleness). Only INF_C_01b/C_05/C_06/C_08 would ever refresh via this runner.
- **Proposed fix:** Make the guards date-aware and refresh-correct: check for the CURRENT run-date partition (e.g. `canonical_performance_{today}.parquet`) instead of the hardcoded 2026-04-20, and for the 'latest'/overwritten keys either drop the skip guard entirely (these must refresh every run) or gate on a per-run marker (e.g. gold/artifacts/<id>/<RUN_DATE>) rather than the durable output key.

## Finding 3 -- [medium/unguarded-read/both]
- **Location:** `data/inf/scripts/gold/INF_run_c_chain.py:46-49 (download()), called in the loop at :72-73`
- **Mechanism:** download() does `resp = s3.get_object(Bucket=BUCKET, Key=f'code/gold/{script}')` with no try/except for all 14 hardcoded basenames. get_object raises botocore ClientError (NoSuchKey) if any exact key is absent/renamed at code/gold/. The exception is uncaught, so the runner crashes with a traceback before running any step (unlike orion-gold-dispatch.sh sync_scripts, which is defensive).
- **Failure scenario:** If any of the 14 pinned basenames is missing or deployed under a different name at s3://opal-data-inf/code/gold/ (e.g. INF_C_01b.role_aua_backfill.py absent, or a first-run/fresh bucket), the loop at line 72-73 raises NoSuchKey and the runner aborts with a non-zero traceback before executing a single gold script.
- **Proposed fix:** Wrap the get_object in try/except and emit a clear 'ERROR: <script> not found in code/gold/' (or head_object-verify each key first), so a missing/renamed deployment fails with an actionable message rather than an opaque boto traceback.
