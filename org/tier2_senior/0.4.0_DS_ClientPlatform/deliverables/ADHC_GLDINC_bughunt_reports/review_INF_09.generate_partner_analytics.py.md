## Finding 1 -- [low/incremental-full-break/incremental]
- **Location:** `main() L324-337 (input listing) + L368/L376 (data_as_of) -> served platinum/firm/partner_analytics.json`
- **Mechanism:** INF_09 is a member of CHAIN_INCREMENTAL (orion-gold-dispatch.sh L340) and re-publishes the SERVED artifact platinum/firm/partner_analytics.json on every incremental run. Its two data inputs are both produced by scripts that are NOT in the incremental chain: canonical_nna_{date}.parquet is written by INF_C_01 (a C-gold script) and holdings_{date}.parquet by INF_B_00 (a B-gold script). CHAIN_INCREMENTAL contains only INF_API_* + INF_D_* + INF_09 -- no INF_B_* / INF_C_*. So an incremental run reads whatever canonical_nna / holdings partitions already exist (the newest being from the last FULL run) and recomputes data_as_of = max(latest_nna_date, latest_holdings_date), which is the stale full-run date, not today. The NNA values themselves are internally correct (concat of daily-delta partitions is sound; net_nna/inflows/outflows sum correctly), so this is a stale-but-correct number, NOT a crash and NOT a corrupted value. The full chain is clean because INF_B_00/INF_C_01 run earlier in the same full pass, so holdings + NNA are fresh and consistent.
- **Failure scenario:** An intraday CHAIN_INCREMENTAL run fires after the daily CHAIN_FULL. INF_D_04 (in the incremental chain) rebuilds dashboard.json / header_metrics.json from FRESH silver and stamps today's date, while INF_09 republishes partner_analytics.json with data_as_of = yesterday (last full-run canonical_nna date) and yesterday's NNA windows/series. The portal then shows inconsistent 'as of' dates across the platinum family, and if a full run is skipped or fails for several days the partner_analytics NNA/AUA freezes at the last full-run cutoff while sibling widgets keep advancing -- a silent, correct-but-stale served number.
- **Proposed fix:** Either (a) add INF_C_01 (canonical_nna) and INF_B_00 (holdings) to CHAIN_INCREMENTAL ahead of INF_09 so its inputs are refreshed on the same cadence it publishes, or (b) if partner_analytics is intentionally a full-run-only artifact, drop INF_09 from CHAIN_INCREMENTAL so incremental runs do not re-stamp a stale data_as_of; failing that, have INF_09 detect that its newest canonical_nna/holdings partition predates the run date and emit a WARN (or carry a source_as_of field distinct from run date) so the staleness is visible rather than silent.
