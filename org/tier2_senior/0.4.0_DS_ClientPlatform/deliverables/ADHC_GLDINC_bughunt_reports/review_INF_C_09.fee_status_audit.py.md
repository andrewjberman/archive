## Finding 1 -- [low/type-issue/full]
- **Location:** `_empty_audit lines 316-317 (pd.NA) vs compute_audit lines 266-271 (bool) — both write OUTPUT_KEY gold/views/fee_status_audit.parquet`
- **Mechanism:** The two code paths that produce the SAME output parquet emit different dtypes for the same columns. When billing_stack is non-empty, fee_status_at_first_known and current_fee_status are derived directly from is_fee_earning (a genuine bool in build_billing_dim) -> bool columns. When compute_audit falls through to _empty_audit (billing_stack.empty), those two columns are constructed from the scalar pd.NA (lines 316-317) -> object dtype. first_known_fee_status_date/has_state_changes/observation_days happen to agree (datetime64/bool/int64) across paths, but the two fee-status bools do not. The parquet schema at gold/views/fee_status_audit.parquet is therefore non-deterministic across daily full runs (arrow bool vs arrow null/object).
- **Failure scenario:** During an S3 incident on a full-chain day, every get_object on a billing partition in load_billing_stack raises -> all partitions counted as n_err -> frames empty -> load_billing_stack returns an empty frame -> compute_audit hits billing_stack.empty and calls _empty_audit, which writes fee_status_at_first_known/current_fee_status as object(pd.NA). The prior day's parquet wrote the same columns as bool. Any consumer with a pinned schema (Athena/Glue external table, or a pandas reader that concatenates day-over-day) sees a bool->object type flip. No crash and no wrong served number today because the artifact is empirically UNCONSUMED (PARKED per header) and real billing data since 2026-04-01 keeps billing_stack non-empty in normal operation.
- **Proposed fix:** Pin the two status columns to a stable nullable dtype in BOTH paths: in _empty_audit build them as pd.array([pd.NA]*n, dtype='boolean') (or astype('boolean')), and in compute_audit cast fee_status_at_first_known/current_fee_status to 'boolean' before writing, so the parquet schema is bool-nullable regardless of which path runs.

## Finding 2 -- [low/other/full]
- **Location:** `compute_audit lines 256-289 (audit built from billing groupby, then LEFT-merged with accounts_dim) vs _empty_audit lines 309-321 (all accounts_dim rows)`
- **Mechanism:** On the populated path the audit row-set is derived from billing_stack.groupby('account_id') and accounts_dim is only LEFT-merged in (line 289), so the output contains ONLY accounts that appear in at least one non-placeholder billing partition. On the empty fallback path _empty_audit returns ONE ROW PER accounts_dim account (superset). The docstring promises 'one row per account_id' and the backfill consumer contract is 'what was account X's fee_status at date D?', but on a normal run an account present in accounts_v2 yet never seen in billing (e.g. a brand-new account, or one outside the billing snapshots) is silently absent from the audit rather than emitted with NaT/NA. So the row grain of the served table depends on billing coverage and diverges between the two paths.
- **Failure scenario:** accounts_v2 latest partition has 861 accounts but only 732 appear in the surviving billing partitions. compute_audit emits ~732-861 rows keyed off billing accounts; the ~129 accounts with no billing observation are dropped entirely (not merely NA). A consumer querying fee_status for one of those accounts gets a missing-row/KeyError instead of the intended 'unknown/backfill from NA' answer. Muted in practice because the artifact is UNCONSUMED (PARKED).
- **Proposed fix:** Build the audit skeleton from accounts_dim (left-base) and LEFT-merge the billing-derived aggregates onto it, so every accounts_dim account gets a row (NaT/NA where unobserved), matching both the docstring 'one row per account' contract and the _empty_audit fallback grain.
