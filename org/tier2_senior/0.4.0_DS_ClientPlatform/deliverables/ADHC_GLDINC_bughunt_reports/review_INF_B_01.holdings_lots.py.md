## Finding 1 -- [high/other/full]
- **Location:** `main(), lines 169-189 (ThreadPoolExecutor as_completed loop) + return 0 on line 189`
- **Mechanism:** Every per-date task runs inside a ThreadPoolExecutor and the as_completed loop wraps fut.result() in try/except that only logs 'WARN: <key>: <e>' (lines 181-182). 'written'/'total_rows' accumulate ONLY on success; the loop never re-raises and main() unconditionally returns 0 (line 189). There is no floor check (no assert written>0, no 'did the newest/requested date succeed' check). Because B_01 is a hard-fail COMPUTE step, the chain relies on a non-zero exit to catch data problems -- but this script converts ALL per-date data errors into silent WARNs and exits 0, so the chain proceeds as 'success'.
- **Failure scenario:** On a full run, the newest positions_cube partition read, the ticker merge, or the S3 to_parquet/put_object for today's date throws a transient error (throttling, a momentary schema/parse issue, a memory spike in one of 32 threads). That single future is caught as a WARN, main() returns 0, and gold/holdings/{today}.parquet is left absent or stale from a prior run. Downstream INF_B_03.account_gains + INF_D_03/D_06/D_07/D_07a read the stale/missing latest holdings, so served composition, concentration, cash-drag and account-gains go stale/under-counted -- with NO ChainFailed alarm and no operator signal. In the extreme (canonical_prices loads but every process_one_date raises), the script writes ZERO partitions and still exits 0.
- **Proposed fix:** Collect per-date failures into a list inside the loop; after the pool, fail loud (raise / sys.exit(1)) when any REQUIRED date failed. At minimum: if pos_keys and written==0 -> raise; for --date/--start-date runs, treat any failed target date as fatal; for the full run, fail if the newest partition (max date_str) is among the failures. Preserve the WARN-and-continue only for old backfill partitions that already exist in S3.

## Finding 2 -- [medium/empty-null-handling/full]
- **Location:** `process_one_date(), lines 112-120`
- **Mechanism:** The price join is how='left' on 'ticker' (line 116-119) and market_value = units * price (line 120). Any ticker held in positions_cube but absent from canonical_prices for that date yields price=NaN -> market_value=NaN. The ONLY guard is a whole-day WARN when day_prices is empty (line 113-114); a single unpriced ticker on an otherwise-priced day produces a NaN market_value silently, with no count logged and no exclusion.
- **Failure scenario:** A newly-acquired security appears in positions_cube before INF_build_canonical_prices covers it (or a ticker Yahoo does not cover that also has no transaction-observed price and falls outside carry-forward). Its holdings row is emitted with market_value=NaN and no warning. Downstream aggregations (INF_D_07 concentration, INF_D_07a firm_concentrations, INF_B_03 gains) sum market_value with the pandas default skipna=True, so that position contributes 0 -- the account/firm AUA and concentration figures are silently under-counted rather than flagged. Separately, if canonical_prices' max date lags positions_cube's newest date (price pipeline behind positions), the whole newest day is NaN (only a WARN), so the freshest served market_value/AUA is null/under-counted.
- **Proposed fix:** After the merge, compute unpriced = holdings['price'].isna().sum() and log it explicitly (count of unpriced (account,ticker) rows, not just whole-empty days). Decide policy deliberately: either fail/loud-alarm above a coverage threshold, or carry-forward the last known price, so an unpriced holding cannot silently drop value from downstream sums.

## Finding 3 -- [low/merge-dedup/full]
- **Location:** `process_one_date(), lines 116-119`
- **Mechanism:** The left merge on 'ticker' does not dedup day_prices or assert day_prices['ticker'].is_unique. It trusts canonical_prices to be unique per (date,ticker). Today that invariant holds (INF_build_canonical_prices resolves one price+source per ticker per date on a unique spine; apply_price_overrides mutates in place, adds no rows). But there is no defensive check, so a future price-builder change that emits two rows for one (date,ticker) would fan the holdings row out.
- **Failure scenario:** If a later canonical_prices change (e.g., an override tier appended as a new row instead of overwriting, or a resolver bug) produces two rows for one (date,ticker), the left merge duplicates that account's holding row. Downstream sums of units/market_value then double-count that position, silently over-stating account/firm AUA with no error.
- **Proposed fix:** Guard the merge input: day_prices = day_prices.drop_duplicates(subset=['ticker'], keep='last') before the merge, or assert day_prices['ticker'].is_unique and fail loud if violated.

## Finding 4 -- [low/schema-column/full]
- **Location:** `process_one_date(), lines 122-128 (available filter + custodian backfill)`
- **Mechanism:** output_cols is filtered to available = [c for c in output_cols if c in holdings.columns] (line 124), which SILENTLY drops any promised output column that is missing from positions_cube instead of failing loud. Only 'custodian' has a backfill (line 127-128); account_id and units have none. The docstring promises account_id/units/custodian in the output schema.
- **Failure scenario:** If INF_A_03 positions_cube is refactored so account_id is renamed or dropped (schema drift), B_01 writes gold/holdings/{date}.parquet WITHOUT account_id and exits 0 -- no error here. Downstream INF_B_03.account_gains (which merges on account_id) then KeyErrors, or an aggregation silently collapses across accounts. The failure surfaces far from its cause rather than at B_01.
- **Proposed fix:** Before selecting, assert the required columns are present: missing = [c for c in ('date','account_id','ticker','units') if c not in holdings.columns]; if missing: raise RuntimeError(f'positions_cube {date_str} missing required columns: {missing}'). Keep custodian as the only defaulted column.
