## Finding 1 -- [high/merge-dedup/full]
- **Location:** `build_lots, loop header line 247 vs residual path lines 298-304 (residual reachable only from inside `for (acct_id, tkr), buy_group in buy_groups`)`
- **Mechanism:** The entire canonical-anchor reconciliation, including the intended 'H>0 but zero traceable lots -> emit one residual lot at canonical unit price (floor year)' recovery, executes ONLY inside the buy_groups iteration. canonical_units is never iterated independently. A canonical-held (account_id, ticker) that has zero BUY_DESCS transactions in the silver window (buy_group absent) is never visited, so NO lot -- not even a residual -- is emitted for it. The residual path only fires when a pair HAD in-window buys that FIFO-sold to ~0, not when it had no in-window buys at all.
- **Failure scenario:** A client holds 1,000 units of a fund per gold/canonical/holdings, but every acquiring transaction (the original Buy / Transfer In) predates the silver/transactions window -- the exact 'buy history predates the silver window' case the code comment (lines 279-284) names. That (account_id, ticker) has no row in buy_groups, so build_lots skips it entirely. The position appears with full units in canonical holdings but is MISSING from gold/lots/lots_latest.parquet, so the downstream INF_D cost-basis-by-year / tax-lot served numbers understate that client's cost basis by 100% of the position. Silent under-count, no error.
- **Proposed fix:** After the buy_groups loop, iterate canonical_units for any (account_id, ticker) with H>0 not already represented in lot_rows and emit a floor-year residual lot at canonical unit_price (cost == market value), mirroring the existing lines 298-304 residual so held-but-untraceable positions are still attributed.

## Finding 2 -- [medium/unguarded-read/full]
- **Location:** `load_canonical_units, line 198 (`df = _read_s3(keys[-1])`)`
- **Mechanism:** The newest gold/canonical/holdings_*.parquet is read WITHOUT a try/except, unlike load_transactions which wraps every _read_s3 and fails over to the next partition. Any read error (corrupt parquet, KMS/permission blip, or a NoSuchKey race if the just-listed key is deleted) raises out of load_canonical_units, propagates through main() to the __main__ except, and calls sys.exit(1). INF_B_02 runs with no timeout and hard-fails the chain on non-zero exit, so this aborts the whole CHAIN_COMPUTE (full) run. This directly violates the function's own docstring contract ('Empty dict if unavailable -- fail-open').
- **Failure scenario:** The nightly full chain's newest holdings partition is written but truncated/corrupt (partial upload) or its key is swept between the list_objects_v2 call and the get_object. _read_s3 raises; instead of the promised fail-open (return {} -> raw FIFO, chain proceeds), the exception hard-aborts INF_B_02 and every subsequent INF_C_*/INF_D_* step in the full chain never runs.
- **Proposed fix:** Wrap the newest-key read (and ideally iterate to the next-newest holdings partition on failure) in try/except, logging a WARN and returning {} to honor the documented fail-open, matching load_transactions' guarded read-and-fallback pattern.

## Finding 3 -- [medium/numeric-sign-units/full]
- **Location:** `build_lots, lines 293-297 (`scale = h / remaining_total; for lot in lot_list: lot['remaining'] *= scale`)`
- **Mechanism:** The clamp treats remaining_total <= 1e-9 (clean residual at canonical price) and remaining_total just ABOVE 1e-9 (scale path) asymmetrically. When residual FIFO 'dust' survives just above the 1e-9 gate, scale = h / remaining_total becomes enormous and multiplies that near-noise lot up to the full canonical position size -- attributing the entire held position to a single tiny stale lot's buy_price and purchase year. Additionally, scale is applied to ALL lots including those <=1e-9 excluded from remaining_total, so a sub-threshold lot can be pushed above 1e-9 and emitted, breaking the sum-to-H invariant.
- **Failure scenario:** An account sold a position down to 5e-9 rounding-dust units in its oldest (2019, low-price) lot, then reacquired 1,000 units whose buy transactions predate/are outside the window (or are cash-sweep buys not in BUY_DESCS). canonical holdings says H=1,000. remaining_total=5e-9 > 1e-9, so scale=2e11 inflates the 2019 dust lot to 1,000 units at the 2019 price. The served lot reports 1,000 units bucketed to purchase-year 2019 at a stale low cost basis -> materially wrong cost basis and wrong tax-year attribution, instead of the correct market-value residual the <=1e-9 branch would have produced.
- **Proposed fix:** Raise the remaining_total floor used to choose scale-vs-residual to a meaningful fraction of H (e.g., if remaining_total < H * epsilon, take the residual path), and only scale lots that are individually above the 1e-9 threshold, so trivial FIFO dust does not capture an entire reconciled position.

## Finding 4 -- [medium/merge-dedup/full]
- **Location:** `build_lots line 287 (`canonical_units.get((str(acct_id), tkr))`) vs load_canonical_units keys (`df['account_id'].astype(str)`, raw ticker) and INF_B_00 holdings ticker `.astype(str).str.strip()``
- **Mechanism:** The anchor key is (str(account_id), ticker). account_id matches safely (both sides normalize to clean int-strings: silver coerces accountId to Int64, holdings writes account_id.astype(str), build_lots str(acct_id)). But the ticker component is NOT normalized on the txns side (raw silver 'ticker'), while the holdings ticker in INF_B_00 is `.astype(str).str.strip()` and can be sourced from a different Orion endpoint (positions 'ticker' vs bronze 'Asset Ticker'). A representational difference (trailing whitespace, case, or symbology) makes the anchor lookup miss; the miss branch (`if not anchor`) DROPS ALL lots for that (account, ticker) as a phantom.
- **Failure scenario:** A held position's ticker is 'BRK.B' in transactions silver but 'BRK/B' or 'BRK.B ' (trailing space) in canonical holdings. build_lots' anchor lookup returns None, so `if not anchor or anchor[0] <= 1e-9` drops every FIFO lot for that real, canonical-confirmed position -> it vanishes from gold/lots -> downstream cost basis for that holding is silently zero/understated.
- **Proposed fix:** Normalize the ticker on both sides identically before keying (strip + consistent case, and align on a single canonical ticker field), or, safer, only drop lots when the position is genuinely ABSENT from canonical after a normalized lookup -- never on a formatting mismatch.

## Finding 5 -- [low/type-issue/full]
- **Location:** `build_lots lines 229-231 (`buys['units'].abs()`, `sells['units'].abs()`) and line 323 (`lot['remaining'] * lot['buy_price']`); upstream convert_transactions_to_silver.py build_silver coerces only ID columns`
- **Mechanism:** The silver transactions converter is an explicit Rule-17 passthrough that coerces ONLY the ID columns (id, accountId, clientId, householdId, transTypeId, assetId) to Int64 and transDate to date; navPrice and noUnits are passed through with whatever dtype the bronze JSON delivered. INF_B_02 renames these to units/nav_price and then does `.abs()`, `> 0` comparisons, and `remaining * buy_price` with no to_numeric guard. If a bronze partition delivers noUnits/navPrice as JSON strings (object dtype), `.abs()` raises TypeError: bad operand type for abs(): 'str' and float*str raises TypeError, crashing build_lots -> sys.exit(1) -> aborts the no-timeout full chain.
- **Failure scenario:** An Orion REST bronze partition returns noUnits/navPrice as quoted strings (or mixed object dtype with stray strings, the exact drift dtype_coerce.py was created to handle for IDs). buys['units'].abs() on line 229 raises TypeError, INF_B_02 exits non-zero, and CHAIN_COMPUTE aborts. Currently latent because Orion delivers these numeric, but there is no guard.
- **Proposed fix:** Coerce units and nav_price with pd.to_numeric(..., errors='coerce') immediately after the rename in load_transactions (dropping/zeroing NaN units as appropriate), so the FIFO math is never exposed to object/string dtype.
