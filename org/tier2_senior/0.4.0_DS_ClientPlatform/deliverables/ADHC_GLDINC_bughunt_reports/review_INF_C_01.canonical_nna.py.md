## Finding 1 -- [critical/merge-dedup/full]
- **Location:** `_normalize_silver_schema lines 413-416 (advisor_key/rep_bucket derivation) + classify_nna groupby line 546`
- **Mechanism:** advisor_key and rep_bucket are derived by mapping rep_id through the HARDCODED 4-entry dicts _INF_REP_ID_TO_ADVISOR_KEY / _INF_REP_ID_TO_BUCKET ({'3','6','11','12'}) with NO fillna/default. Any rep_id not in that dict, or a null/<NA> rep_id, yields NaN advisor_key AND NaN rep_bucket. Both columns are then used as GROUP KEYS in flows.groupby([...,'advisor_key','rep_bucket','custodian']) at line 546. pandas groupby defaults to dropna=True, so every row whose advisor_key/rep_bucket is NaN is SILENTLY EXCLUDED from the aggregation. The REQUIRED_COLS check (line 465) only tests column PRESENCE, not null content, so nothing catches it. No warning is logged for dropped rows.
- **Failure scenario:** Inflection onboards a new advisor whose Orion rep_id = 15 (Inflection's core business model is advisor-acquisition, explicitly noted in this file's own docstring lines 36-38). Their clients' contributions (real new money) flow through silver with rep_id=15. _INF_REP_ID_TO_ADVISOR_KEY.get('15') -> None -> advisor_key=NaN, rep_bucket=NaN. At the groupby, all of that advisor's inflow/outflow rows are silently dropped. The served canonical_nna (and every downstream INF firm-level NNA rollup) is UNDER-COUNTED by that advisor's entire flow with zero error and zero warning. A null rep_id (Int64 <NA> -> astype(str) '<NA>' -> unmapped) triggers the same silent drop.
- **Proposed fix:** After the .map() calls, either (a) log/assert on any NaN advisor_key: unmapped = rep_str[txns['advisor_key'].isna()].unique(); if len -> log a loud WARN with counts and dollar sums, and fill with an explicit catch-all bucket (e.g. advisor_key.fillna('inflection_unmapped_rep'), rep_bucket.fillna('firm')) so the flow is retained and visible rather than vanishing; and/or (b) pass dropna=False to the groupby so NaN-keyed rows aggregate into an explicit bucket instead of disappearing. Preferred: source rep->advisor mapping from a maintained dim rather than a 4-entry hardcode.

## Finding 2 -- [high/schema-column/full]
- **Location:** `load_all_transactions source-selection guard line 296 vs classify_nna REQUIRED_COLS line 443-467; _normalize_silver_schema lines 400-416`
- **Mechanism:** Source-selection accepts the first snapshot whose columns include REQUIRED_CANONICAL = {'accountId','transDate','transTypeId'} (line 296). But downstream REQUIRED_COLS (line 443) additionally needs 'type_desc', 'advisor_key', 'rep_bucket'. Those three are created CONDITIONALLY in _normalize_silver_schema: type_desc only if 'trans_type_desc' in columns (line 400), advisor_key/rep_bucket only if 'rep_id' in columns (line 413). Since the source-selection guard does NOT require trans_type_desc or rep_id, a snapshot can pass source-selection yet lack them, so those columns are never created and the REQUIRED_COLS check at line 465 raises RuntimeError.
- **Failure scenario:** The REST silver writer emits a snapshot carrying accountId/transDate/transTypeId (passes source-selection) but a schema drift drops trans_type_desc or rep_id (e.g. a renamed field or a partial write). _normalize_silver_schema skips the conditional block, type_desc / advisor_key / rep_bucket are never added, classify_nna raises 'Silver TRN missing required columns: {...}', the exception propagates to main()'s handler -> sys.exit(1). Because every INF_A/B/C/D gold step runs with NO timeout and hard-fails the chain on any non-zero exit, the ENTIRE gold chain aborts at INF_C_01 with no partial recovery.
- **Proposed fix:** Make the source-selection REQUIRED_CANONICAL set match the real downstream dependency: add 'rep_id' and 'trans_type_desc' to the required_canonical set at line 296 so a schema-incomplete snapshot is rejected at selection time (falling through to the next candidate / the loud 'REST silver writer not running' RuntimeError) instead of a confusing mid-classifier KeyError-style abort. Alternatively fail loud early in _normalize_silver_schema if rep_id/trans_type_desc are absent.

## Finding 3 -- [medium/empty-null-handling/full]
- **Location:** `_load_cashflow_taxonomy lines 141-167 (module import time); classify_nna filter lines 499-508`
- **Mechanism:** INFLOW_TYPES/OUTFLOW_TYPES are built at MODULE IMPORT (line 167), OUTSIDE main()'s try/except (which only wraps the main() call at lines 691-697). Two silent/hard failure modes: (a) if orion_cashflow_taxonomy.yaml is not synced next to the .py on the EC2 dispatcher (_resolve_taxonomy_path returns candidates[0] even when absent, line 115), open() raises FileNotFoundError at import -> uncaught -> interpreter exits non-zero -> no-timeout hard-fail chain abort. (b) if the YAML loads but has ZERO rows with bucket=='NNA' (e.g. the bucket enum drifts or the direction values change), INFLOW_TYPES and OUTFLOW_TYPES are both EMPTY frozensets -> NNA_TYPES empty -> is_nna = series.isin(empty) is all-False (line 500) -> flows empty -> classify_nna returns {} -> main logs 'No NNA partitions produced' and returns cleanly (exit 0).
- **Failure scenario:** A taxonomy edit renames the bucket value 'NNA' to something else, or the yaml v4 schema changes the nna_direction encoding, without touching this consumer. The chain runs GREEN (exit 0), mark_empty is written for dates, and served NNA silently collapses to ZERO across all accounts/dates -- a materially-wrong served number with no alarm, indistinguishable from a legitimately quiet period. (Or, in mode (a), the missing-YAML deploy gap hard-aborts the whole nightly chain at import.)
- **Proposed fix:** Assert the taxonomy is non-trivial at load: after _load_cashflow_taxonomy, raise if len(INFLOW_TYPES)+len(OUTFLOW_TYPES)==0 (fail loud rather than serve silent zero). Guard the import-time read so a missing YAML raises a clear, attributable error (or move taxonomy load inside main() so it is covered by the top-level handler and telemetry). Add a floor/sentinel check in main() that flags a suspicious all-empty NNA result when silver has transactions.

## Finding 4 -- [medium/numeric-sign-units/full]
- **Location:** `classify_nna lines 515-519 (np.where(..., flows['trans_amount'].abs(), 0.0))`
- **Mechanism:** Direction is assigned purely from type_desc membership (INFLOW_TYPES/OUTFLOW_TYPES) and the amount is taken as abs(), deliberately ignoring the sign of trans_amount (comment lines 515-517). A transaction whose type_desc is an INFLOW type but whose actual amount is NEGATIVE (a reversal/correction/clawback of a prior contribution) is counted as a POSITIVE inflow of its magnitude instead of reducing NNA. Same for a negative-signed OUTFLOW type reversal.
- **Failure scenario:** A client contribution of $500k is later reversed (money returned) and Orion books the reversal under the same 'Client Contribution' type_desc with amount = -500000. abs() turns it into a +$500k inflow, so instead of net contribution ~$0 the served NNA reports +$1.0M of inflow for that account -- an over-stated NNA. The magnitude of the error scales with how often Orion encodes corrections as same-type negative-amount rows rather than distinct 'Reversal' type_descs.
- **Proposed fix:** Confirm with the Orion taxonomy owner whether reversals reuse the base type_desc with a negative amount. If so, respect the sign: for inflow types use amount.clip(lower=0) as inflow and abs of the negative part as outflow (or net by signed amount within direction) rather than a blanket abs(); or route negative-amount inflow/outflow rows to the opposite bucket. At minimum, log a diagnostic count of sign-vs-classified-direction disagreements so silent over/under-count is observable.

## Finding 5 -- [low/other/full]
- **Location:** `main lines 653-654 (should_skip input_keys) vs load_all_transactions source-selection lines 281-311`
- **Mechanism:** The per-partition skip-gate is called with input_keys=[f'silver/transactions/{date_str}.parquet'] (line 653), i.e. a LEGACY per-date silver filename. But post-DWSPLT the actual source is a single LastModified-newest bronze-name SNAPSHOT selected in load_all_transactions, NOT per-date files. In should_skip, _head_object on the (likely non-existent) per-date key returns None and the freshness comparison is `continue`-skipped (skip_gate.py line 214-215), so output validity is never gated against the real source snapshot's mtime. This is currently INERT because INFINC_PHASE1 defaults to 0 (dispatch never exports 1), so should_skip always returns False (always compute).
- **Failure scenario:** If INFINC_PHASE1 is ever flipped to 1 to enable incremental skip semantics, a previously-written canonical_nna_{date}.parquet would be judged 'current' and SKIPPED even after the underlying silver snapshot is refreshed/corrected for that date (its true source mtime is never checked), serving STALE NNA. Latent today; a foot-gun the moment the skip-gate is enabled.
- **Proposed fix:** Pass the ACTUAL selected snapshot key (the LastModified-newest key resolved in load_all_transactions) as the input_key to should_skip, or thread that key back from load_all_transactions, so the freshness gate compares output mtime against the real source rather than a non-existent per-date filename that silently no-ops the check.
