## Finding 1 -- [high/merge-dedup/full]
- **Location:** `data/inf/scripts/gold/INF_A_04.client_dimension.py:136 (build_client_dimension, agg.merge(household_names, on='household_id'))`
- **Mechanism:** The merge join key 'household_id' is not dtype-aligned across the two frames. Left side (agg) inherits household_id from the accounts dimension, which INF_A_00 deterministically coerces to nullable Int64 (INF_A_00.accounts_dimension.py:238-239). Right side (household_names) inherits household_id straight from the aum_snapshot silver, whose producer _normalize_aum_df renames CSV column 'HH ID' -> household_id with NO dtype coercion at all (data/inf/scripts/silver/convert_orion_to_silver.py:589-606); the dtype is whatever pandas.read_csv infers. When that inferred dtype is object (any non-pure-numeric token in the CSV column), pandas.merge raises ValueError, not a silent join. Verified empirically on pandas 2.3.3: Int64-vs-int64 merges OK, Int64-vs-float64 merges OK (value match), Int64-vs-object raises 'ValueError: You are trying to merge on Int64 and object columns for key household_id'. INF_A_04 never coerces the aum-side key the way INF_A_00 does, so it is the one place the pipeline's own SILVER-ID-DTYPE-UNIFY convention is not enforced.
- **Failure scenario:** An Orion AUM CSV export in which the 'HH ID' column contains any non-numeric token (a blank-then-text cell, a placeholder like 'unknown', a thousands-separated value such as 1,234, or a quoted leading-zero id) causes pandas to infer that column as object; build_aum_silver writes the aum_snapshot silver partition with household_id dtype=object (it applies no coercion). On the next daily CHAIN_FULL run, INF_A_04 line 136 executes agg.merge(household_names, on='household_id') with agg.household_id=Int64 and household_names.household_id=object -> ValueError -> falls to the __main__ except -> sys.exit(1). Because orion-gold-dispatch.sh runs every gold step with NO timeout and hard-fails the whole chain on any non-zero exit, INF_A_04 aborts the entire INF_A/B/C/D compute chain, blocking all downstream served platinum for that night. (Note: the EMPTY-frame fallback path at lines 94/101 is safe -- an empty object-dtype key merges without error and correctly yields null household_name; only a POPULATED object-dtype aum key triggers the crash.)
- **Proposed fix:** Before the merge, coerce the join key on the aum side to match the accounts side, mirroring INF_A_00: in load_household_names (or immediately before line 136) do household_names['household_id'] = pd.to_numeric(household_names['household_id'], errors='coerce').astype('Int64'); optionally coerce agg['household_id'] defensively too. This both prevents the hard crash and ensures household_name actually joins on the numeric path.

## Finding 2 -- [low/empty-null-handling/full]
- **Location:** `data/inf/scripts/gold/INF_A_04.client_dimension.py:99-108 (load_household_names) with effect at merge line 136`
- **Mechanism:** load_household_names returns the empty fallback DataFrame (WARN only, no failure) whenever the latest aum_snapshot partition is missing the household_id OR household_name column. The aum_snapshot producer keeps only columns 'present' in the source (convert_orion_to_silver.py:605), so if an Orion AUM CSV is delivered without the 'HH Name' column, household_name is dropped from the silver partition, INF_A_04 takes the empty fallback, and every household_name in the served client_dimension becomes null. The run stays green (empty-frame left-merge is safe), so the degradation is silent apart from one WARN line.
- **Failure scenario:** Orion delivers an AUM CSV whose header lacks (or renames) 'HH Name' -> aum_snapshot silver omits household_name -> INF_A_04 emits client_dimension.parquet with household_name null for all households, no error, chain succeeds. The named-client field is silently blank estate-wide until someone reads the WARN in logs.
- **Proposed fix:** Treat a missing household_name/household_id column as a hard or gated condition (assert non-null household_name coverage above a threshold, or source names from an alternate dim) rather than degrading silently to all-null; at minimum surface it as an ERROR/validation failure instead of a single WARN.
