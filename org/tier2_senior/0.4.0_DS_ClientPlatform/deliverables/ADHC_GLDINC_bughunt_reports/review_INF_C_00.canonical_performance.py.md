## Finding 1 -- [high/other/full]
- **Location:** `data/inf/scripts/gold/INF_C_00.canonical_performance.py:239-258 (main per-date try/except + unconditional return 0)`
- **Mechanism:** main() wraps process_date in a bare `except Exception` (line 247) that only logs a WARN and continues, and after the loop always `return 0` (line 258). There is NO guard for the case where every date raised (written==0, skipped==0, len(dates)>0). The chain's hard-fail protection keys on non-zero exit, so a systematic failure emits rc=0 and the chain reports success while producing zero fresh partitions. This defeats the 'never trust rc=0 / verify against served' contract for this step.
- **Failure scenario:** INF_B_00 holdings schema drifts (e.g. the 'custodian' or 'market_value' column is renamed/dropped) -> the account-level agg `custodian=('custodian','first')` (line 128) or the market_value coerce (line 122) raises KeyError/AttributeError on EVERY date -> all dates WARN-skipped -> written stays 0 -> main returns 0 -> chain goes green -> canonical_performance_* frozen at the prior run; INF_C_02/INF_C_03 and the D-chain serve stale household/account performance and growth with no alarm.
- **Proposed fix:** After the loop, when upload is set, fail loud on total failure: `if written == 0 and skipped == 0 and dates: log('ERROR: 0 partitions written across N dates'); return 1`. Optionally count per-date exceptions and return non-zero if the error rate exceeds a small threshold, so a systematic break aborts the chain instead of silently succeeding.

## Finding 2 -- [medium/merge-dedup/full]
- **Location:** `data/inf/scripts/gold/INF_C_00.canonical_performance.py:123-149 (holdings-only account spine + NNA how='left' merge)`
- **Mechanism:** The account universe of canonical_performance is defined solely by the day's holdings snapshot (acct_aua = h.groupby('account_id'), lines 123-131). NNA is joined FROM that spine with how='left' (line 149), so any account_id present in canonical_nna but ABSENT from that date's holdings is dropped together with its daily_inflow/daily_outflow/net_nna. Because growth = aua_change - net_nna (line 161) and INF_C_02 sums net_nna and derives growth at household grain, a dropped outflow understates net_nna and overstates growth. There is no reconciliation warning when NNA account_ids are not a subset of holdings account_ids.
- **Failure scenario:** An account is fully liquidated on date D (large client withdrawal -> outflow classified as NNA in canonical_nna) and has zero position rows in holdings_D (no snapshot for a zero-balance account) -> the account is absent from acct_aua -> the left-merge drops its outflow -> its household's net_nna is too high (missing the withdrawal) and served household growth is over-stated by the withdrawal amount; INF_C_02 cum_outflows also permanently under-counts. The same mechanism silently drops ALL NNA on any date where the holdings feed has a gap (gap_manifest confirms holdings gaps occur) but transactions posted.
- **Proposed fix:** Build the per-date account spine as the UNION of holdings accounts and NNA accounts (outer merge, or reindex acct_aua to include NNA-only accounts with total_aua=0 / aua_prior carried) so liquidation-day and gap-day flows are retained; at minimum log a loud WARN with the count/sum of NNA account_ids not found in holdings so the drop is visible.

## Finding 3 -- [low/empty-null-handling/full]
- **Location:** `data/inf/scripts/gold/INF_C_00.canonical_performance.py:141-144,226 (prev_aua seed) + 213-216 (start-date scoping)`
- **Mechanism:** prev_aua is initialized to None (line 226) and the day-over-day baseline is chained purely in-loop. When invoked with --start-date (a documented backfill usage, line 26), the loop is scoped to dates >= start_date and prev_aua is never seeded from the partition immediately before start_date. The first processed date therefore gets aua_prior=NaN -> fillna(0) (line 144) -> aua_change = total_aua for every account, and growth = total_aua - net_nna.
- **Failure scenario:** Operator backfills `--upload --start-date 2026-06-01`. The 2026-06-01 canonical_performance partition is overwritten with aua_change equal to the FULL account AUA (a ~100% one-day spike) instead of the true 1-day delta, and growth is correspondingly inflated; INF_C_02 then recomputes household growth and cumulative series off the corrupted boundary date. The scheduled nightly runs with no --start-date, so day-1 of full history is genuinely prior-less and correct -- this only corrupts the supported backfill path.
- **Proposed fix:** When start_date is set, load canonical_performance (or holdings) for the trading day immediately preceding start_date and seed prev_aua from its account_id/total_aua before entering the loop; or refuse --upload together with --start-date unless a valid prior-day seed is found.
