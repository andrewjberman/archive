## Finding 1 -- [medium/incremental-full-break/incremental]
- **Location:** `data/inf/scripts/gold/INF_D_03.composition_artifacts.py:203 (_load_assets_v2_classifier via _latest_silver_partition) vs :504 (holdings latest_key)`
- **Mechanism:** The holdings source (gold/canonical/holdings_*, INF_B_00 output) is loaded at its LATEST partition, but INF_B_00 is NOT in CHAIN_INCREMENTAL, so in incremental mode holdings are frozen at the last full-run date D0. The Orion classifier, however, IS refreshed in incremental (INF_API_SILVER_ASSETS_V2) and _load_assets_v2_classifier loads its LATEST partition D1 > D0. The (account_id,ticker) classification universe (D1) is thus misaligned with the holdings universe (D0).
- **Failure scenario:** Full run lands holdings on 2026-07-02 (data_as_of=07-02). Incrementals then run 07-07 with a fresh silver/assets_v2 from 07-07. An account that held VOO on 07-02 but rotated out of it by 07-07 is absent from the 07-07 classifier -> the left-merge (line 553) yields NaN product_category -> _bucket_from_orion returns '' -> that MV is dumped into the 'unclassified' bucket instead of 'equity'. The served firm_composition.json / advisor composition.json mix pcts under-count the real asset classes and over-count unclassified, and the served composition changes between the nightly full and the next incremental with NO change in the underlying (stale) holdings. Magnitude grows with the D1-D0 gap (e.g. a multi-day full-run outage while incrementals continue, or the 07-03..07-06 holiday freeze).
- **Proposed fix:** Load the assets_v2 classifier partition aligned to data_as_of (nearest silver/assets_v2 partition with date <= data_as_of) instead of _latest_silver_partition, so stale holdings are classified with the era-matched classifier; or explicitly document/accept the drift and gate on a max staleness.

## Finding 2 -- [medium/merge-dedup/both]
- **Location:** `data/inf/scripts/gold/INF_D_03.composition_artifacts.py:214 (_load_assets_v2_classifier — no drop_duplicates) consumed at :553 (main merge) and :660 (_load_classify_date historical merge)`
- **Mechanism:** The classifier is built from silver/assets_v2, which convert_assets_v2_to_silver.py produces as a mechanical row-preserving transform at ASSET grain (one row per Orion asset id, 'no aggregation, no joins'), NOT unique per (account_id,ticker). _load_assets_v2_classifier selects/normalizes columns but never dedups the join key. It is then LEFT-merged onto holdings, which ARE unique per (account_id,ticker). Any (account_id,ticker) that appears >1x in the classifier fans the single matching holdings row into N rows, each carrying the full market_value.
- **Failure scenario:** silver/assets_v2 returns two rows for one (account_id,ticker) — e.g. account 12345 holds AAPL as two distinct asset lines/sleeves, or two unticker'd assets both normalizing to the same blank key. The merge at line 553 duplicates the (12345,AAPL) holdings row; _build_composition total_mv (line 376) and the groupby-sum (line 386) then count that market_value twice, silently inflating served total_market_value, the AAPL top-holding value, and the equity bucket pct — same fan-out corrupts the firm_mix_views timeseries via the identical un-deduped merge at line 660. NOT currently triggering: all 4 sampled real assets_v2 pulls have 0 duplicate (account,ticker) and 0 blank tickers, and INF_B_00 drops blank-ticker holdings, so the fan-out is latent — it fires the day Orion returns a duplicate/blank-ticker key.
- **Proposed fix:** In _load_assets_v2_classifier, dedup to one classification per join key before returning: out = out.drop_duplicates(subset=['account_id','ticker'], keep='first') (or aggregate deterministically, e.g. pick the largest-position row's category). A single dedup at source also protects the historical _load_classify_date path since it reuses the same classifier object.

## Finding 3 -- [low/unguarded-read/both]
- **Location:** `data/inf/scripts/gold/INF_D_03.composition_artifacts.py:214 (df[['account_id','ticker','product_category','asset_class']]) and :205 (RuntimeError on absent partition), called unconditionally at :547`
- **Mechanism:** _load_assets_v2_classifier raises RuntimeError when silver/assets_v2 has no partition, and does an unguarded column selection df[[...]] that raises KeyError if any required column is missing/renamed. Both exceptions propagate to the top-level except (line 800) -> sys.exit(1). Because every gold/silver step runs with NO timeout and hard-fails the chain under set -e, this aborts every downstream D step (D_04, D_09, ...). Contrast: load_assets_dim() immediately below degrades gracefully (returns empty) on the same class of failure.
- **Failure scenario:** A true cold-start with no prior silver/assets_v2 partition (or a schema change in convert_assets_v2_to_silver.py that renames/drops product_category or asset_class) makes _load_assets_v2_classifier raise, hard-failing the whole no-timeout chain rather than publishing composition unclassified or emitting a clear degraded signal. Steady-state is protected by the upstream INF_API_SILVER_ASSETS_V2 DEFER carry-forward, so realistic triggers are cold-start or silver schema drift.
- **Proposed fix:** Add an explicit required-column presence check with a clear error message before the selection, and decide deliberately whether a missing classifier should hard-fail (fail-loud, current behavior) or degrade to publishing holdings as unclassified — align the choice with load_assets_dim's graceful pattern if degradation is acceptable.
