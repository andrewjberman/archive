## Finding 1 -- [high/numeric-sign-units/full]
- **Location:** `process_one_date, lines 115-134 (merge at 115-119; unrealized_gain fillna at 124-126; term default at 132-134)`
- **Mechanism:** unrealized_gain = market_value.fillna(0.0) - cost_basis.fillna(0.0) subtracts two values sourced from DIFFERENT position universes with DIFFERENT unit bases. market_value comes from I_B01 holdings = positions_cube units (raw txn cumsum, I_A03) x price. cost_basis comes from I_B02 lots = current_units CLAMPED to gold/canonical/holdings (Orion positions API). I_B02's own docstring states raw-txn units diverge from the positions API (over-retains ~3.15x on the Peter Lee book), so the two operands routinely reflect different unit counts. Separately, fillna(0.0) converts a missing cost_basis (holding present in positions_cube universe but absent from the canonical-anchored lot set) into a full-market-value gain rather than NaN; symmetrically an unpriced holding (market_value NaN from I_B01's price left-join) becomes unrealized_gain = -cost_basis (phantom full loss). The left join drops no rows and raises nothing, so the corruption is silent.
- **Failure scenario:** On 2026-07-06 account 12345 holds XYZ. positions_cube/I_B01 reports 100 open units -> market_value = 100 * $50 = $5,000. I_B02 lots for (12345, XYZ) are clamped to canonical holdings at 30 units -> cost_basis = 30 * $40 = $1,200. B_03 computes unrealized_gain = 5000 - 1200 = $3,800, mixing a 100-unit MV with a 30-unit CB. If (12345, XYZ) is absent from lots entirely, cost_basis is NaN -> fillna(0) -> unrealized_gain = full $5,000 (100% phantom gain) and term defaults to short_term (NaT holding period). I_C05 then aggregates that $5,000 into household unrealized gain and taxes it at the short-term rate; I_C03 sums it into account unrealized_gain. Served tax-liability / unrealized-gain numbers are materially overstated for every account whose positions_cube units or key set diverge from the canonical lot set, with only a WARN.
- **Proposed fix:** Source market_value and cost_basis from the SAME position universe (anchor I_B01 holdings units to gold/canonical/holdings, or derive market_value from the canonical-anchored lots' current_units x price) so the subtraction uses one unit base. Do NOT fillna(0.0) the operands: leave unrealized_gain NaN when either market_value or cost_basis is missing so downstream sums exclude it instead of booking a full-MV phantom gain/loss, and only assign term when the holding period is actually known.

## Finding 2 -- [medium/other/full]
- **Location:** `main() per-date loop, except Exception at lines 202-203; unconditional return 0 at line 208`
- **Mechanism:** Every process_one_date call is wrapped in a blanket `except Exception: log('WARN', ...)` and main() always returns 0. Because the dispatcher hard-fails the chain only on a non-zero exit, B_03 can never signal a per-date OR systematic failure. A schema drift that breaks EVERY date fails silently: written stays 0 but rc=0.
- **Failure scenario:** I_B01 renames or drops `market_value` (or `units`, or `account_id`/`ticker`). Every process_one_date raises KeyError at line 125 (or the merge at 115 KeyErrors on the missing join key); the except at 202 logs a WARN for all N holdings dates, written stays 0, main() returns 0. The no-timeout dispatch reads rc=0 as success and proceeds. gold/account_gains/ is never rewritten, so I_C03/I_C05 read the now-stale partitions and serve stale unrealized_gain / tax liability with no chain alarm.
- **Proposed fix:** After the loop, if holdings_keys is non-empty and written==0 (or a failed/total ratio exceeds a small threshold), log ERROR and sys.exit(1) so the hard-fail chain surfaces the systematic failure instead of exiting 0.

## Finding 3 -- [low/type-issue/full]
- **Location:** `process_one_date, line 131 (holding_period_days = (snap_ts - oldest_buy_date).dt.days)`
- **Mechanism:** (snapshot_ts - oldest_buy_date).dt.days returns an int64 Series when no row is NaT, but a float64 Series (with NaN) when ANY row has a NaT oldest_buy_date. Per Finding 1, unmatched holdings (NaT oldest_buy_date) are routine, so the physical parquet column type for holding_period_days flips between int64 and double across date partitions. Documented schema says `int`. No current code consumer reads the column (I_C03/I_C05 ignore it; pandas concat upcasts), so this is a latent schema drift, not a live crash.
- **Failure scenario:** Partition 2026-07-05 (every holding matched a lot) writes holding_period_days as int64. Partition 2026-07-06 (one holding lacks a lot -> NaT) writes it as double. A strict-schema reader over gold/account_gains/*.parquet (Athena/Glue crawler, or pyarrow.dataset with schema unification disabled) raises an int64-vs-double column-type mismatch across the two partitions.
- **Proposed fix:** Pin the dtype deterministically: merged['holding_period_days'] = (snap_ts - merged['oldest_buy_date']).dt.days.astype('Int64') so every partition writes a nullable-integer column regardless of NaT presence.

## Finding 4 -- [low/incremental-full-break/full]
- **Location:** `main() line 192, should_skip('INF_B_03', date_str, _output_key, [hk])`
- **Mechanism:** B_03's output depends on BOTH the holdings partition AND gold/lots/lots_latest.parquet (cost basis), but the skip-gate call passes only [hk] (the holdings key) as input_keys. skip_gate.should_skip only invalidates the cached partition when a listed input's mtime exceeds the output mtime, so a refresh of lots_latest alone will not trigger recompute. Currently inert (INFINC_PHASE1 defaults to 0, so should_skip always returns False), but a latent correctness bug the moment the master gate is enabled.
- **Failure scenario:** With INFINC_PHASE1=1, I_B02 re-runs and rewrites lots_latest.parquet with corrected cost basis, while the 2026-07-06 holdings partition is unchanged. should_skip checks only the holdings key mtime (<= output mtime) and returns True (SKIP). account_gains/2026-07-06 keeps the OLD cost_basis and stale unrealized_gain; the corrected lots never propagate to the served number.
- **Proposed fix:** Include the lots artifact in the freshness inputs: should_skip('INF_B_03', date_str, _output_key, [hk, LOTS_KEY]) so a cost-basis refresh invalidates prior account_gains partitions.
