## Finding 1 -- [medium/merge-dedup/full]
- **Location:** `build_snapshot_reconciled, line 416 (bronze override) + build_snapshot lines 293-317 (no dedup of pmv_out)`
- **Mechanism:** build_snapshot produces one output row per positions_mv silver row and never dedups to (account_id, ticker) grain. build_snapshot_reconciled outer-merges pmv_out against bronze, which IS aggregated to unique (account_id, ticker) (lines 255-257). When pmv has >1 row for a key, the merge is many-to-one and line 416 `merged.loc[in_both,'market_value'] = merged.loc[in_both,'_bronze_mv']` assigns the FULL bronze MV to EACH duplicate pmv row. This fires for BOTH the reconciled (delta<1) and bronze_override (delta>=1) classes, so it is not limited to divergent rows.
- **Failure scenario:** positions_mv silver for a date holds two rows for the same (account_id, ticker) -- exactly the 'same ticker split across cash classes' case the bronze loader explicitly groups away at line 255. Suppose the two pmv rows are $50 + $50 and bronze is one $100 row. Post-override each of the two in_both rows gets market_value=$100, so their contribution to sum(market_value) is $200 instead of $100. The served firm AUA (Sigma market_value, the number D-max exists to tie to Orion's canonical Total) is over-counted by the full bronze MV of every duplicated key, silently.
- **Proposed fix:** Aggregate/dedup pmv_out to a unique (account_id, ticker) grain before the reconciliation merge (groupby sum of market_value / first of metadata), OR assert uniqueness and fail loud, OR distribute the bronze MV proportionally across duplicate pmv rows instead of assigning the full value to each.

## Finding 2 -- [medium/empty-null-handling/full]
- **Location:** `main(), lines 661-663`
- **Mechanism:** list_accounts_v2_dates() returns {} when the silver/api_dims/accounts_v2/ prefix has no data.parquet partitions. The immediately-following log f-string calls min(accounts_v2_available) and max(accounts_v2_available) on the empty dict, raising ValueError: min() arg is an empty sequence. There is no pre-guard here; the clean guard (RuntimeError 'No silver/api_dims/accounts_v2 partitions found.') lives deeper in accounts_v2_key_for_snap and is never reached because the log line crashes first.
- **Failure scenario:** Run `orion-gold-dispatch.sh --single INF_B_00` or `--chain gold-b` against a fresh/wiped bucket where accounts_v2 silver has not been built (or was written as zero partitions). positions_mv exists (passes the line 636-640 guard) but accounts_v2 is empty; line 662 raises an uncaught ValueError -> main's except -> sys.exit(1). Because every gold/silver step in the dispatcher runs with NO timeout and HARD-FAILS the chain on non-zero exit, this aborts the whole compute chain at B_00 with a raw, misleading 'min() arg is an empty sequence' instead of the intended clean 'no accounts_v2 partitions' message.
- **Proposed fix:** Add `if not accounts_v2_available: log('ERROR: no silver/api_dims/accounts_v2 partitions found.'); sys.exit(1)` before the min/max log line, or guard the f-string (e.g. only compute min/max when the dict is non-empty).

## Finding 3 -- [low/type-issue/full]
- **Location:** `_build_bronze_only, line 542 (and the DataFrame constructor at 529-542)`
- **Mechanism:** In the AC8 Cottonwood path (positions_mv absent, bronze present) the output is built with the literal `'pmv_market_value': None`, so the entire pmv_market_value column is inferred as object dtype (all Python None). On every other path -- reconciled (line 408 `merged['pmv_market_value']=merged['market_value']`, float64, with None set only per-row into a float column) and pmv-only fallback (line 386, float64) -- pmv_market_value is float64. So the written parquet column dtype VARIES by code path across per-date files.
- **Failure scenario:** A newly-onboarded firm date runs through _build_bronze_only and writes holdings_{date}.parquet with pmv_market_value as a null/object column; all neighboring dates write it as float64. A downstream consumer that reads multiple holdings partitions together (pd.concat, a directory-level pd.read_parquet, or a pyarrow dataset that unifies schemas) can raise a pyarrow schema-mismatch (null vs double) on the AC8 file or silently coerce/upcast, whereas single-file reads look fine -- an intermittent, path-dependent break.
- **Proposed fix:** Initialize pmv_market_value as an explicit float NaN column in _build_bronze_only, e.g. `pd.Series(float('nan'), index=bronze.index, dtype='float64')` (or np.nan), so every path emits float64.

## Finding 4 -- [low/incremental-full-break/full]
- **Location:** `main(), line 671 (should_skip call) with input_keys=[_silver_key]`
- **Mechanism:** The per-partition skip-gate is passed only the positions_mv silver key as its freshness input. accounts_v2 (advisor attribution source) and the bronze assets.csv (reconciliation override source) are NOT in input_keys, so a change to either does not invalidate an already-emitted holdings partition. Latent because it only activates when INFINC_PHASE1=1 (the lib no-ops should_skip otherwise), but it is a genuine staleness gap in the skip logic.
- **Failure scenario:** With INFINC_PHASE1=1, accounts_v2 silver is rebuilt with a DIAGFIX.011-style advisor re-attribution (rep remap) while positions_mv for an already-emitted date is unchanged. should_skip finds output present, schema current, and the only input_key (positions_mv) not newer -> returns True -> B_00 skips that date. holdings_{date}.parquet retains the STALE advisor_key/rep_bucket, silently mis-attributing that date's AUA to the previous advisor in every advisor-level downstream (INF_D_00c leaderboard, INF_C_07 attribution, INF_D_08 nna).
- **Proposed fix:** Include the resolved accounts_v2 key (accounts_v2_key_for_snap result) and, when the bronze path is in use, the bronze assets key in the input_keys list passed to should_skip, so any upstream attribution/reconciliation change invalidates the cached partition.
