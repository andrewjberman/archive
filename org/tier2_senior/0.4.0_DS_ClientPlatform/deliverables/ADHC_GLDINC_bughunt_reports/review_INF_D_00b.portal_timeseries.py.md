## Finding 1 -- [low/merge-dedup/both]
- **Location:** `data/inf/scripts/gold/INF_D_00b.portal_timeseries.py:408 (coercion) vs :326-339 (aua_snap groupby + merge) and :448-453 (meta cur_hh merge)`
- **Mechanism:** Asymmetric merge-key coercion. build_lifecycle_periods() coerces cp_first_seen['household_id'] with pd.to_numeric(errors='coerce') at line 408 (and acc_inc at 416), so hh_inception['household_id'] is numeric. But the SAME cp DataFrame is passed unchanged into _build_lifecycle_periods(), where aua_snap is built via cp.groupby('household_id') (line 326) and then merged against the numeric hh_inc on 'household_id' (lines 336-339); likewise the meta cur_hh = cp[...].groupby('household_id') merged with hh_inception at line 453. The groupby side inherits cp's ON-DISK household_id dtype (never re-coerced), the lookup side is forced numeric.
- **Failure scenario:** If client_performance.parquet is ever read back with household_id as object/string (e.g. an upstream schema regression: INF_C_00 joins household_id from accounts_dim, and INF_C_02 only re-derives it via acct_dim when the column is ABSENT (INF_C_02.py:292) -- a string household_id already present in canonical_performance would pass through C_02 uncoerced), then aua_snap['household_id'] is object while hh_inc['household_id'] is int64. pandas 2.3.3 raises ValueError 'You are trying to merge on object and int64 columns' at line 336 (verified empirically), the exception is uncaught, propagates through build_lifecycle_periods -> main() -> the top-level except at :628 -> sys.exit(1), and HARD-FAILS the no-timeout gold chain. Currently MASKED because INF_A_00 pins household_id to Int64 (INF_A_00.py:238) and C_00/C_02 preserve it, so production household_id is Int64 on both sides and the merges succeed -- so this is a latent robustness gap, not a live break.
- **Proposed fix:** Coerce household_id to a single canonical numeric dtype at the source: in load_client_performance() (or the top of build_lifecycle_periods before the split) do cp['household_id'] = pd.to_numeric(cp['household_id'], errors='coerce').astype('Int64'), so the aua_snap/cur_hh groupby side and the hh_inception merge side always share one dtype. Alternatively cast both merge keys explicitly immediately before each .merge().

## Finding 2 -- [low/schema-column/both]
- **Location:** `data/inf/scripts/gold/INF_D_00b.portal_timeseries.py:330 and :448-451 (unguarded cp['total_aua']) vs :488 (build_daily_firm_aua guards it)`
- **Mechanism:** Inconsistent missing-column handling for total_aua within the same script. build_daily_firm_aua() explicitly guards 'total_aua' not in cp.columns and returns an empty frame (line 488), but _build_lifecycle_periods() indexes cp.groupby('household_id')['total_aua'] with no guard (line 330), and the meta block does cp[...].groupby('household_id')['total_aua'].sum() unguarded (lines 448-451).
- **Failure scenario:** If client_performance is ever produced without a total_aua column (schema drift in INF_C_02), build_daily_firm_aua silently degrades to empty windows (no error), masking the problem, while build_lifecycle_periods raises KeyError('total_aua') at line 330 -> uncaught -> top-level except at :628 -> sys.exit(1) -> chain abort. The two code paths disagree on how to treat the same missing column. Currently MASKED: INF_C_02 always emits total_aua (INF_C_02.py:306), so total_aua is present in production; latent only.
- **Proposed fix:** Validate required columns (date, household_id, total_aua) once in load_client_performance() and fail fast with a clear log line if any are missing, or add the same 'total_aua' presence guard to _build_lifecycle_periods and the meta block so all three consumers behave consistently.
