## Finding 1 -- [critical/type-issue/full]
- **Location:** `data/inf/scripts/gold/INF_D_05.client_top_holdings.py:248 (upcast) -> manifests at :328 (S3 key) and :323 (JSON body)`
- **Mechanism:** household_dim household_id is Int64 (silver coerce_silver_ids convention). Line 248 `holdings['household_id'] = holdings['account_id'].map(hh_map_str)` upcasts the mapped column to float64 the moment ANY holdings account_id is not present in the dim (the unmapped rows introduce NaN, and pandas Series.map upcasts int->float to hold NaN). Line 249 `.notna()` filters rows but does NOT restore int dtype, so `mapped['household_id']` stays float64 and `hh_ids = mapped['household_id'].unique()` yields numpy.float64 values (e.g. 9001.0). Verified empirically on pandas 2.3.3. There is no int re-coercion anywhere before the value is used: line 328 f-string renders `clients/9001.0/top_holdings.json` and line 323 `int(hh_id) if str(hh_id).isdigit() else hh_id` leaves it a float because '9001.0'.isdigit() is False. Sibling INF_D_06 avoids this by doing `.astype(str)` on household_id first; INF_D_05 does not.
- **Failure scenario:** On any daily full run where >=1 account in gold/canonical/holdings_{date}.parquet is absent from silver/api_dims/household (near-certain: the two are produced by independent chains/filters, so a newly-opened account, a missing geo_verify row, or timing skew guarantees at least one unmapped account), mapped['household_id'] becomes float64. Every artifact is then written to platinum/clients/9001.0/top_holdings.json (dot-zero suffix) with body household_id=9001.0. The portal fetches clients/{int}/top_holdings.json (e.g. clients/9001/, the integer id it gets from clients_tab.json and that sibling artifacts detail.json/composition.json/timeseries.json use) -> 404 -> EVERY client's Top Holdings panel serves empty/stale, while the chain logs 'N files uploaded' and exits 0 (false success, no abort). Intermittent/data-dependent: when account coverage is exactly 100% the map keeps int64 and keys are clean, so it silently flips broken<->clean run to run.
- **Proposed fix:** After `mapped = holdings[holdings['household_id'].notna()].copy()` add `mapped['household_id'] = mapped['household_id'].astype('int64')` (safe: notna guarantees no NaN), OR coerce at loop top: `hh_id = int(hh_id)` and use that integer for the S3 key (line 328), the body household_id (line 323), and the cache hh_id (line 331/288). This restores the canonical clients/{int}/ path used by clients_tab and every sibling D-script.

## Finding 2 -- [medium/empty-null-handling/full]
- **Location:** `data/inf/scripts/gold/INF_D_05.client_top_holdings.py:435 (orion_normalize_as_of) fed by None from :139-142; crash inside silver/_orion_vendor_asof.py:88 (prior_trading_day)`
- **Mechanism:** _get_latest_holdings_meta (line 138-142) sets latest_date=None when the newest gold/canonical/ object matching the loose substring filter `'holdings_' in k` has a filename that does not parse via pd.Timestamp(fname). load_latest_holdings re-derives the same None. main() then calls (line 435) `orion_normalize_as_of(latest_date)` -> prior_trading_day(None) -> `None - dt.timedelta(days=1)` -> TypeError. It is unguarded; the exception propagates to the __main__ handler (line 455-459) -> sys.exit(1). Because run_script runs all gold steps with NO timeout and hard-fails the chain on any non-zero exit, this aborts the whole gold chain at INF_D_05. Before the 2026-07-02 label-fix that added the orion_normalize_as_of call, a None latest_date was tolerated (data_as_of_str='').
- **Failure scenario:** A stray or legacy object under gold/canonical/ that contains 'holdings_' but a non-date name (e.g. holdings_latest.parquet, holdings_backup.parquet, holdings_.parquet) sorts lexicographically AFTER holdings_2026-07-06.parquet (letters > digits), is picked as 'latest', its filename parses to date None, the parquet still loads non-empty (so the empty-guard at :427 passes), and line 435 then raises TypeError -> chain hard-abort at D_05 (and every downstream D step never runs).
- **Proposed fix:** Guard the normalize call: `data_as_of = orion_normalize_as_of(latest_date) if latest_date else None`; and tighten the holdings selector to a strict `holdings_\d{4}-\d{2}-\d{2}\.parquet` regex instead of `'holdings_' in k` so non-date siblings can never be selected. Optionally make prior_trading_day reject None loudly.

## Finding 3 -- [low/other/full]
- **Location:** `data/inf/scripts/gold/INF_D_05.client_top_holdings.py:406 vs :264/:435`
- **Mechanism:** The full-skip pre-check computes `data_as_of_str = str(latest_date)` from the RAW (Orion-forward-labeled) partition date at line 406, but the anchor-cache `period` field is written (line 331-336) using the Orion-NORMALIZED data_as_of (line 264, from orion_normalize_as_of at :435). When normalization shifts the date (the common pre-open/weekend/holiday case), the pre-check's `period == data_as_of_str` filter (lines 411-414) matches zero cache rows, so _cached_hh is empty and the 'CACHE FULL HIT' fast path never fires.
- **Failure scenario:** Normal daily run where the labeled partition (e.g. 2026-07-06) normalizes to the prior trading day (2026-07-02): cache rows carry period=2026-07-02 but the pre-check queries period=2026-07-06 -> no subset match -> the holdings parquet is always reloaded and recomputed. Purely a missed optimization; output is byte-identical, no wrong number. (Side note: this same mismatch currently prevents finding #1's float-poisoned cache hh_ids from ever producing a false full-skip, so it is masking, not compounding, a correctness issue.)
- **Proposed fix:** Normalize latest_date before computing the pre-check data_as_of_str (apply orion_normalize_as_of in main before line 406) so the pre-check period matches the cache's normalized period.
