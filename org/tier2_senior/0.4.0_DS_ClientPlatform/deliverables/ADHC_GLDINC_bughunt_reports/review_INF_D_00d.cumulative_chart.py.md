## Finding 1 -- [medium/schema-column/both]
- **Location:** `build_nna_geo_view lines 437-443 (triggered by _supplement_hh_dim_state lines 194-195)`
- **Mechanism:** When the household silver dim is empty/absent, _supplement_hh_dim_state hits `if hh_dim.empty or 'household_id' not in hh_dim.columns: return v2`, and v2 is built from accounts_v2 with ONLY columns ['household_id','state_code'] (line 186-192) -- it has NO 'account_id' column. build_nna_geo_view's early-return guard (line 428) only checks `'state_code' not in hh_dim.columns`; v2 HAS state_code so the guard passes, then line 438-443 does `hh_dim[valid_state].dropna(subset=['account_id'])[['account_id','state_code']]` which raises KeyError: 'account_id'. (build_geo_drill_view is safe because it guards `'city' not in hh_dim.columns`; only nna_geo omits the account_id guard.) The exception is uncaught, reaches the __main__ try/except (line 666) -> sys.exit(1); INF_D_00d is a hard-fail gold step run with no timeout, so the whole chain aborts and no cumulative_chart.json is emitted.
- **Failure scenario:** silver/api_dims/household/ has no partition or its latest partition is empty (realistic: the household silver dim is NOT produced by any orion-gold-dispatch chain step -- there is no `--dim household` entry in CHAIN_FULL/CHAIN_INCREMENTAL, so its existence depends on an out-of-band process; a fresh env, a lagging cron, or an advisor_firm-filter that yields 0 rows leaves hh_dim empty), while accounts_v2 silver has state values (v2 non-empty) and canonical_nna is non-empty. main() -> load_household_dim() returns empty -> _supplement_hh_dim_state returns v2 (household_id+state_code only) -> build_nna_geo_view(nna, v2, ...) passes the state_code guard then KeyError: 'account_id' -> chain aborts at INF_D_00d.
- **Proposed fix:** Add an account_id column-presence check to build_nna_geo_view's early-return guard, e.g. `if nna.empty or hh_dim.empty or 'state_code' not in hh_dim.columns or 'account_id' not in hh_dim.columns: return empty-view`. (Mirrors build_geo_drill_view's existing 'city' guard.) Optionally also have _supplement_hh_dim_state preserve/emit an account_id column, or never return a schema narrower than callers expect.

## Finding 2 -- [low/empty-null-handling/both]
- **Location:** `load_accounts_v2 line 170`
- **Mechanism:** `df = _read_s3(keys[-1])` can return None (the _read_s3 helper maps NoSuchKey to None, line 98-99). The very next line logs `f'accounts_v2 (latest snapshot): {len(df):,} rows'`, dereferencing df with len() BEFORE the None-guard on line 171 (`return df if df is not None else pd.DataFrame()`). If df is None this raises TypeError: object of type 'NoneType' has no len(), which the None-guard on the following line is meant to prevent but never reaches.
- **Failure scenario:** keys is non-empty (early-returned otherwise) but the latest key returned by list_objects_v2 no longer resolves on get_object (object deleted/expired between the list and the read, or S3 read eventual-consistency / a transient error surfaced as NoSuchKey). _read_s3 returns None -> `len(df)` at line 170 -> TypeError -> uncaught -> sys.exit(1) -> chain aborts. Low probability but a real ordering bug that defeats the very guard on the next line.
- **Proposed fix:** Resolve the None fallback before logging: `df = _read_s3(keys[-1]);\n    if df is None:\n        df = pd.DataFrame()\n    log(f'accounts_v2 (latest snapshot): {len(df):,} rows')\n    return df`.

## Finding 3 -- [low/merge-dedup/both]
- **Location:** `_supplement_hh_dim_state line 191 + build_geo_view line 276 vs load_client_performance lines 121-122`
- **Mechanism:** household_id join keys are normalized by two DIFFERENT rules. load_client_performance normalizes cp.household_id via `str(int(x))` -> '18'. hh_dim/accounts_v2 household_id is normalized via `.astype(str)` (line 191, 198, 276). These agree ONLY while the dim side is integer-typed: silver coerce_silver_ids delivers Int64, and Int64.astype(str) -> '18' (verified), so the geo/geo_drill left-merges match today. But if the dim-side household_id is ever float64 (e.g. an Int64 column that got upcast to float64 by a NaN-introducing operation, or a future gold-sourced hh_dim -- the gold client_performance layer demonstrably produces float household_ids, which is the entire reason cp performs `str(int(x))` normalization at line 119), `.astype(str)` yields '18.0' which does NOT equal cp's '18' (verified). The left-merge then returns NaN state -> `.fillna('Other')` -> those households collapse into 'Other', which the frontend strips from geo totals.
- **Failure scenario:** hh_dim or accounts_v2 household_id arrives as float64 (18.0) instead of Int64 -> `.astype(str)` -> '18.0' -> merge against cp's '18' misses -> state=NaN -> 'Other' -> the affected states drop out of the top-N geo view and their AUA becomes invisible in the served Continuous-GEO-AUA chart. This is exactly the '$14M invisible in Continuous-GEO-AUA' class (ADVI_INFTGT.TO-4b) that _supplement_hh_dim_state was written to fix -- the fix is silently defeated for any float-typed household_id. Currently masked by silver Int64, so latent/defensive.
- **Proposed fix:** Normalize household_id (and account_id) with ONE canonical rule at every merge boundary, e.g. a shared helper `pd.to_numeric(s, errors='coerce').astype('Int64').astype(str)` (or reuse the `str(int(x))` pattern) applied in load_client_performance, _supplement_hh_dim_state, build_geo_view and build_geo_drill_view, so the keys can never diverge between '18' and '18.0'.
