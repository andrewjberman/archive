  <context>
    orion-gold-dispatch.sh substitutes the literal {date} token into catalog rows from a single global RUN_DATE (the only two substitution sites: run_script L323, run_eclipse_step L398). --run-date D shifts RUN_DATE. But only date-CAPABLE catalog rows -- those carrying a {date} token -- honor it; date-AGNOSTIC rows (no {date} token: the PULL steps + all gold-tier steps) ignore it and pull current / full-history data. So --chain full --run-date D is a CATEGORY ERROR: the date-agnostic PULL steps write bronze keyed to today (their own internal date -u), while the date-capable SILVER steps are pinned to D and read bronze/.../D.parquet -- which does not exist -- so every silver step fails bronze-not-found; and had it somehow succeeded it would be a mixed-date artifact (today's bronze fused with D-dated gold). The failing run was an aggregator-triggered invocation: the inf-silver-aggregator's gold-trigger event carried a snapshot_date, so inf-gold-trigger (L184/L238/L242) appended --run-date to a --chain full. The daily 06:00 EventBridge cron sends {"mode":"full","source":"cron"} -- no snapshot_date, a plain --chain full -- and is clean (proven empirically: chain_full_20260515_060048 exit 0). The CTO-ratified fix is TACTICAL: a dispatcher guard + an explicit date-capability predicate + an inf-gold-trigger refusal + the aggregator-payload correction. It changes nothing about what any script consumes.
  </context>

  <objective>
    orion-gold-dispatch.sh structurally rejects an incoherent --run-date + date-agnostic-step combination; inf-gold-trigger refuses the always-invalid snapshot_date + full/incremental event before dispatch; and the inf-silver-aggregator emits a plain {mode:full} (no snapshot_date) trigger so the primary aggregator-driven gold chain runs GREEN. A windowed --run-date is then valid only for a chain composed entirely of date-capable steps (e.g. --single INF_API_SILVER_TXN --run-date D against an existing bronze pull).
  </objective>

  <scope>
    <item>E1 -- date-capability predicate (Option 1b, CTO-ruled). Add ONE documented predicate to orion-gold-dispatch.sh -- step_is_date_capable(): a step is date-capable iff its catalog default_flags contains the literal {date} token. Add a catalog comment at the catalog block: "{date}-token presence IS the date-capability contract; do not add {date} to a row whose script ignores it." NO separate date_param column (Option 1a was rejected -- it introduces a desync surface where a row could declare date-capable yet not substitute). Zero catalog-format change.</item>
    <item>E2 -- the reject-incoherent-combination guard. Add validate_rundate_coherence to orion-gold-dispatch.sh, evaluated AFTER chain resolution and BEFORE run_chain, active ONLY when RUN_DATE_OVERRIDE is non-empty: accept --run-date only if EVERY resolved step is date-capable (per E1's predicate); else REJECT -- exit non-zero, printing the offending date-agnostic step ID(s) and the section-3.3 rejection message (ASCII only, no emoji, names the steps, points at the valid --single SILVER form). This is the single dispatcher chokepoint -- it catches every caller (the inf-gold-trigger Lambda, SSM-direct dispatch, manual CLI).</item>
    <item>E3 (section-3.4) -- inf-gold-trigger Lambda defense-in-depth. In infra/aws/lambda/inf-pipeline/inf-gold-trigger/lambda_function.py: hard-refuse -- loud error, fail BEFORE dispatch (error return, non-zero) -- when an event carries snapshot_date AND mode is full OR incremental. Those two modes are STRUCTURALLY always-mixed (they always contain date-agnostic PULL steps), so no valid --run-date full/incremental run exists, ever. Do NOT extend the Lambda refusal to mode single or partial -- those can be legitimately date-capable-only and are handled by the E2 dispatcher guard. Two layers at the right altitudes: the Lambda kills the always-invalid full/incremental case at event-parse; the dispatcher guard is the catch-all chokepoint.</item>
    <item>E4 -- the layer-1 aggregator-trigger fix (the primary-path repair). The inf-silver-aggregator Lambda currently emits a gold-trigger event carrying a snapshot_date -- which, with mode=full, is exactly the always-invalid combination E3 now hard-refuses. Fix the aggregator to emit a plain {mode:full} event with NO snapshot_date (source:aggregator) -- the same clean payload shape the 06:00 cron uses. WITHOUT E4, E3 converts a silent failure into a loud one but leaves the primary aggregator-driven gold trigger dead; E4 restores it. If AE finds the aggregator's intended mode is incremental rather than full, the same no-snapshot_date rule applies (both modes are clean without it) -- ship that; surface to COO only if the mode itself is genuinely in question.</item>
    <item>SCOPE BOUNDARY -- TACTICAL only. Does NOT make any pull script date-windowed (the sub-class-A pulls -- REPS / NEW_PORTFOLIO / ASSETS_V2 / POSITIONS_DAILY -- stay full-history-as-wired; that is ADVI_TXNAMG section-7-Q5). Does NOT change any script's argparse or any bronze read/write key. Touches ONLY: orion-gold-dispatch.sh (arg-validation + the post-resolution guard + the predicate + the catalog comment), inf-gold-trigger/lambda_function.py, and the inf-silver-aggregator trigger-payload code.</item>
  </scope>
