## New approach

The park is right: only site Z can act on the runner. But two things shorten it: one read dell1 can still take, and
one escalation path not yet used.

1. A discriminator readable from dell1: the two bbg S3 run records themselves (20:00:00Z and 20:05:20Z, 0 fetch
   attempts each). HVST-bv-1 makes "a pair error keep its detail" (`cycle_runner.py` header, pin b5a7a3a4b6). Read each
   record's error or stop fields. The code at the pin (`git show b5a7a3a4b6:lib/opal_data_harvest/cycle_runner.py`,
   read 21:3xZ) narrows the four hypotheses:
   - Each cycle takes a FRESH checkpoint id (`fresh_cycle_id`, `:148-157`), so two runners do not collide on a
     checkpoint file. A state-dir lock is an unlikely cause.
   - "Stopped, then idle": `MAX_CONSECUTIVE_PAIR_ERRORS` stops a publisher (`:16`). The runner idles `IDLE_SECONDS = 300`
     after a pass with no completed cycle (`:41`). bbg is the only publisher with live sessions (wsj and barrons wait on
     Andrew's sign-in, call 9f24). If bbg stops on errors, every publisher is stopped or unsigned, and the runner loops
     idle, writing only LOCAL cycle records and no S3 run record. That is exactly the measured silence. Two
     0-attempt records followed by nothing fits a session or sign-in failure under `--no-sign-in`.
   - "Hung on a shared profile": D1-S5's second python PID 37816 on the OLD pin may still hold bbg's Chrome profile.
     A second browser on one user-data-dir refuses or hangs, and the new runner's pair job then blocks.
   If the two records' detail names a session, sign-in or browser error, the cause is one of these two, and the site-Z
   act is the same for both: end PID 37816 (and its Chrome children), confirm bbg's session, and restart the runner on
   the pin. Then the site-Z ask becomes one concrete instruction instead of an open read.
2. Escalate the silence by fabric, not by repetition. Three chases to a LIVE-but-not-acking site Z (b5703186, msgs
